# 11 · Rider Fare & Surge Engine (founder's dynamic model, specified exactly)

Two different numbers, never confused: **customer delivery fee** (what the customer pays — zone matrix, file `10`) and
**rider payout fare** (what Undal pays the rider — this file). The gap/surplus is Undal's logistics margin, visible in Admin unit-economics per order.

## 11.1 Inputs (founder schema + Undal completions)

```ts
interface FareInputs {
  base_fare_poisha: number;          // zone+vehicle setting — guaranteed minimum per completed delivery
  per_km_rate_poisha: number;        // motorbike 1400 (৳14/km), bicycle 800 (৳8/km) — founder rates
  included_km: number;               // distance covered by base fare (default 2.0)
  travel_distance_km: number;        // rider→vendor + vendor→customer routed km (OSRM; fallback haversine×1.35)
  to_vendor_km: number;              // deadhead leg (paid at 50% per-km — see §11.2)
  traffic_delay_minutes: number;     // routed-vs-freeflow + live calibration (D-19)
  active_orders_in_zone: number;     // open orders needing riders (last 10 min window)
  active_riders_in_zone: number;     // online, not-stale, with free capacity
  weather_condition: 'clear'|'rain'|'storm'|'extreme_heat';  // Open-Meteo + Admin override
  vehicle_type: 'motorbike'|'bicycle';
  batch_position: number;            // 1 = first order in batch, 2 = second… (§11.4)
  order_food_payable_poisha: number; // for the 3% bonus line (file 10 — shown separately, NOT inside fare)
  is_priority: boolean;              // priority orders pay rider priority uplift (setting, default +৳10)
}
```

## 11.2 Formula (deterministic, pure function — SQL/TS canonical, golden-tested)

```
loaded_km      = max(0, travel_distance_km − to_vendor_km)
billable_km    = max(0, loaded_km − included_km) + 0.5 × to_vendor_km
distance_pay   = per_km_rate × billable_km
subtotal       = base_fare + distance_pay
── surge (founder bands, linearly interpolated inside bands for smoothness) ──
SDR            = active_riders_in_zone / max(1, active_orders_in_zone)
  SDR ≥ 1.0            → surge = 1.00
  0.5 ≤ SDR < 1.0      → surge = 1.20 → 1.40  (linear as SDR falls 1.0→0.5)
  SDR < 0.5            → surge = 1.50 → 2.20  (linear as SDR falls 0.5→0; hard cap 2.20)
── weather premium (on subtotal×surge) ──  rain +20% · storm +40% · extreme_heat +10% (setting) · clear 0%
── traffic compensation ──  blocks = floor(traffic_delay_minutes / 5); traffic_pay = blocks × traffic_block_poisha
   (default ৳4/block ≈ protects ৳/hour; zone-tunable)
fare_before_batch = (subtotal × surge × (1+weather_pct)) + traffic_pay + priority_uplift
── batching (§11.4) ──  position 1: ×1.00 · position 2: base_fare portion ×0.60 (distance on shared legs prorated) · 3: ×0.50
rider_fare_total  = max(minimum_fare_floor, round_half_up(batch_adjusted))   // floor default ৳30 bicycle / ৳40 motorbike (settings)
```
Vehicle guardrails: bicycle offers only when each loaded leg ≤ zone bicycle radius (default 4 km, founder 3–4 km guidance);
motorbike to 12 km; beyond → order flagged long-distance (Admin may allow with per-km top-up setting).
Every computed fare persists its full input snapshot JSON on `order_offers`/`orders` — “Why this fare?” in Rider app renders
the itemisation (base, distance km × rate, surge ×1.3 “busy zone”, rain +20%, traffic +৳8, batch rule) — radical transparency.

**Worked example (golden vector F-1, machine-verified in Appendix F):** motorbike, base ৳30, to-vendor 1.2 km,
loaded 3.8 km → billable = (3.8−2)+0.6 = 2.4 km → distance ৳33.60 → subtotal ৳63.60; riders 3 / orders 8 → SDR 0.375 →
surge = 1.5 + (0.5−0.375)/0.5 × 0.7 = **×1.675** → ৳106.53; rain +20% → ৳127.84; delay 12 min → 2 blocks +৳8 →
**fare = 13,584 poisha = ৳135.84** (+ separate 3% food bonus + tip on completion). All fare examples must be generated by running
the fare function (Appendix F) — hand-arithmetic in docs is forbidden (it already caught one error during guide creation).

## 11.3 Fairness & safety rails

Surge changes apply to *new offers only* (accepted fare is locked). Fare shown **before** accept (never bait-and-switch).
Waiting-at-vendor >10 min beyond committed prep → wait compensation ৳2/min (setting, auto from timeline events — the
reference app's “15 min avoidable wait” becomes paid justice here). Cancel-after-pickup / failed delivery: fare still paid
(§10.6). Weekly earnings screen mirrors invoice lines 1:1 (rider can self-audit every poisha).

## 11.4 Batching economics (founder case: 2 orders, same vendor, similar prep)

Eligible when: same vendor (or vendors ≤300 m apart), ready-times within 8 min, drop-offs within zone batching radius
(≤1.5 km apart or en-route detour ≤6 min), combined items fit bag class, neither is Priority (Priority always direct).
Rider sees **one bundled offer** (“2 pickups · 2 drops · total ৳X”) with per-order fare lines. Customer ETAs disclose
“shared delivery” honestly. Assignment scoring for batches lives in file `12` §4.

## 11.5 Admin levers (all settings, audit-logged, zone-overridable)

base fares per vehicle, per-km rates, included km, floors, surge band bounds, weather %, traffic block value, batch factors,
priority uplift, wait compensation, long-distance top-up, weather manual override per zone, fare simulator
(Admin enters sample inputs → live itemised output using production function).
