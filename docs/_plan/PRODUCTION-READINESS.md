# Production readiness and known blockers

**Status: not production-ready. Last repository-only assessment: 2026-11-01, at the D176 code baseline.** This is an evidence-based working register, not a claim that every possible defect has been found. Repository review and automated tests cannot establish production configuration, live data correctness, security, reliability, legal approval or Foodpanda-scale performance. No live TiDB or production environment was inspected or modified in D168–D176. Reassess this register as implementation and independent testing proceed.

## Progress rating and provisional schedule

The current provisional platform-wide progress rating is **about 3/10**. This is a qualitative assessment of the scope implemented, not a test-health score or a calculated percentage. Backend foundations and passing CI are meaningful, but do not substitute for missing applications, verified deployments, or production evidence. In this checkout, there is no `web/` tree and Android contains only the shared money module; the customer, rider, partner and admin apps in the plan are not present.

From the current repository state to the **remaining full-production scope**, a rough planning range is **12–24 months for an experienced 6–10 person cross-functional team**, or **3–5+ years for one full-time developer**. This estimate is highly provisional: it is not based on measured team velocity and is not a delivery commitment or guarantee. It assumes scope broadly comparable to the plan, sustained staffing, timely provider and legal decisions, and access to isolated staging, representative devices and test integrations. Scope changes, staging findings, security remediation and external approvals may materially extend the range. Re-estimate after isolated TiDB integration/recovery testing and an up-to-date app-scope inventory. A limited pilot may be possible sooner, but would not establish full production readiness.

The original 28-day schedule in [`35 §10`](../35-execution-plan.md) is retained as the plan's historical, idealized response sequence; **it is not the current forecast**. The blockers below—including financial atomicity, audit integrity, missing apps, staging/operations evidence, and provider, legal and licensing approvals—are included in the revised planning range, not considered complete.

## Required evidence before launch

- A fresh isolated TiDB migration and upgrade from a representative snapshot; verify schema and data, rollback/recovery procedures, least-privilege accounts, TLS and concurrent failure cases. No live TiDB result is available here.
- Security review and penetration testing: authentication, session rotation, RBAC and tenant/zone isolation, sensitive media, secrets, dependency and supply-chain controls, abuse/rate limiting, privacy and retention. Document and address findings.
- Real end-to-end customer, partner, rider, finance and admin journeys with controlled external providers and non-production credentials; mobile device/OS/background-delivery testing; accessibility and Bangla/English review.
- Performance, load and failure testing with measurable targets for order placement, dispatch, notifications, location, database and third-party rate limits; graceful degradation, capacity and cost planning. A local benchmark is not a production SLO.
- Operable monitoring and on-call alerts, incident response, tested backups and restores, disaster recovery, reconciliation, audit access controls, staged rollouts and rollback plans. Verify actual production configuration, not just templates.
- Product, payment-provider, regulatory, legal, privacy and licensing approval, including PASVL/LOSDA requirements. No assumption is made about business approvals or connected services.

## Recently mitigated in code (not deployed or independently validated)

D163 keeps unsafe production cash writes blocked. D164–D166 add unused transaction, receipt and transactional-ledger foundations. D167 hardens ledger report arithmetic and removes fictitious sequence reads. D168 expands column extraction and drift detection, fixes the verifier workflow path/driver and requires a read-only verification credential, enforces verified TLS for Python database connections, makes migration ledger read failures fail closed, and disables destructive retention. D169 prevents legacy audit link checks from reporting verified integrity. D170 adds a proposed cross-language v2 format; D171 adds an independent raw-text safe-integer JSON parser and shared vectors. Neither is integrated with persistence or routes, and neither proves TiDB/driver JSON preservation. D172 upgrades workflow actions to Node 24-compatible majors and corrects the CodeQL input name; CI, money-math and android-debug passed, with no Node 20 deprecation annotations in the captured CI and money-math logs. D173 makes housekeeping install the hash-verified PyMySQL dependency, refuse privileged URL fallbacks, use only the dedicated read-only URL, and collect every diagnostic report before retaining a failing result for the intentionally incomplete audit check. D174 canonicalizes UUID and IPv4/IPv6 inputs for new legacy audit writes, so the digest uses the same identity/address form stored in binary columns; historical rows are unchanged, the delimiter/JSON format remains legacy, and tail reads are still non-serialized. D176 makes appends fail closed on absent or non-32-byte tail hashes and unsafe `BIGINT` sequence arithmetic, preventing silent chain resets and JavaScript number rounding before insert. It does not serialize appends, make business/audit writes atomic, verify persisted payloads or resolve historical rows. The core suite passes locally (876 tests: 874 passed, 2 skipped); workspace typechecks, guardrails and fixtures pass. Tests use fakes; no live TiDB or production data was accessed. The dedicated housekeeping workflow, its secret configuration, database behavior, and CodeQL, GCP-auth and release-artifact flows remain unverified. These changes are not evidence that the entire platform is safe or deployed.
