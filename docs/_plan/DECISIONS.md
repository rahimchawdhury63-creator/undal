# Decision record

[`35 §7`](../35-execution-plan.md) leaves 31 points to the building agent. The TiDB migration closed
two of them outright (the `gen_random_uuid` source, the PostGIS index parameters), leaving **29
open**; this record adds **three** that the corpus leaves implicit but the build cannot avoid
(D31–D33) and **two visible deviations** from the corpus that the operator's brief forces
(D34–D35). Every entry states the decision, what was rejected, and why — so a later reader can tell
a choice from an accident.

Format: **Decision.** *Rejected:* … *Why:* …

---

## Android (D1–D9)

**D1 — Navigation.** Navigation Compose 2.8 with **type-safe serializable routes**; each feature
module owns its `nav/` graph and the app module composes them. *Rejected:* string routes, Voyager,
Decompose, a hand-rolled navigator. *Why:* type-safe arguments make the 14 deep-link paths
compile-checked, the library is first-party, and nav graphs are testable without a UI harness.

**D2 — State model.** Plain `ViewModel` + `StateFlow` + a sealed intent type with a pure reducer;
no Molecule. *Rejected:* Molecule, MVI frameworks. *Why:* every screen's logic must be unit-testable
on the JVM without Compose; a pure reducer gives that for free, and a 283-screen app does not need a
second concurrency model.

**D3 — Room → domain mapping.** Explicit mapper functions in `core/database/mapper/`, one per
entity. *Rejected:* annotation processors, auto-mappers, mapping in the repository. *Why:* money
and nullability mistakes hide inside generated mapping code; an explicit map is greppable, diffable
and 100%-coverable.

**D4 — Icon pipeline.** `design/icons/*.svg` → a committed generator (`scripts/design/vectors.ts`,
run in CI, output diffed) → `core/designsystem/icons/*.kt` as `ImageVector`. *Rejected:* runtime SVG
parsing (a library and a frame-time cost), hand-porting 118 icons. *Why:* compile-time vectors, no
runtime dependency, and a regeneration diff in CI makes drift impossible.

**D5 — Image cache.** Coil 3 with a 250 MB / 60-day LRU on customer and partner, 120 MB on rider,
cache keys including the chosen variant, and map tiles in MapLibre's own cache so they cannot be
evicted by menu photography. *Rejected:* one shared cache, unbounded cache. *Why:* the rider's
14 MB-per-shift budget (`19 §9`) depends on tiles surviving a shift.

**D6 — Rider offline map.** MapLibre Native with pre-cached vector tiles for the rider's zone.
*Rejected:* Leaflet in a WebView (battery, gesture latency, a second rendering engine, no
`no-layout-animation` guarantee). *Why:* one engine, one style, one attribution component shared with
the admin map; turn-by-turn still hands off to Google Maps (`19 §5.1`).

**D7 — Cronet.** `com.vk.knet:okcronet`, pinned in `libs.versions.toml`; vendoring only via a Gradle
source dependency if an API is missing. *Rejected:* building Cronet from source in Actions (minutes
budget), plain OkHttp (loses HTTP/3, criterion A8). *Why:* the brief names Okronet, and a pinned
published artifact is reproducible.

**D8 — Baseline profiles.** Generated by `android-test.yml` on a controlled emulator with
`BaselineProfileRule`, committed as `src/main/baseline-prof.txt`, regenerated on every release tag.
*Rejected:* hand-written rules, generating on every PR (cost, noise). *Why:* cold start ≤ 1 400 ms
is build-failing, and profiles are the cheapest way to hold it.

**D9 — DI in tests.** Hilt in production; `core:testing` exposes hand-written fakes and
`@TestInstallIn` replacements, and unit tests construct objects directly. *Rejected:* running the
Hilt test runtime for 8 000 JVM tests. *Why:* Robolectric + JUnit5 want plain constructors; the Hilt
test graph costs seconds per class for no coverage gain.

## Workers (D10–D16)

**D10 — Middleware order.** `request-id → logging → security-headers → body-limit → auth → rbac →
step-up → idempotency → rate-limit → zone-scope → handler`, with the envelope written last on both
paths. *Rejected:* idempotency before auth, rate-limit before auth. *Why:* the idempotency key is
scoped to an actor, and rate limits must be per-actor where an actor exists, falling back to IP.

**D11 — Database connection.** `@tidbcloud/serverless` over HTTP, no pool, one lazily created client
per isolate. `DATETIME(6)` columns mean no time-zone conversion happens on write, so the invariant is
enforced three ways: every business timestamp is **app-generated UTC**, `CURRENT_TIMESTAMP(6)` is
used only as a default on audit rows, and a boot probe asserts `@@session.time_zone = '+00:00'` and
fails the isolate if it is not. *Rejected:* relying on a connection-string parameter alone,
`TIMESTAMP` columns, a pooled driver. *Why:* the corpus's UTC guarantee must not depend on a
variable a future driver version might silently change.

**D12 — Python runtime.** Pyodide on the Workers Python runtime. *Rejected:* RustPython/WASM
(incomplete stdlib, no numerics), a second JS implementation from day one. *Why:* the engines are
pure arithmetic and statistics; if cold start exceeds 400 ms the fare engine is ported to TypeScript
(R37) with the differential test guaranteeing identical results.

**D13 — Feature-store hot tier.** KV for versioned config, weights and `vendor_stats` snapshots;
Cache API only as an in-isolate memo of a feature payload for a single request. *Rejected:* Cache API
for config, D1 for features. *Why:* KV's 1 000 writes/day fits config that changes rarely, its
100 000 reads/day fits the hot path, and a per-request memo needs no durability.

**D14 — SSE keepalive.** A `: ping` comment frame every 15 s for proxy/idle keepalive, plus a real
`tick` event every 15 s carrying server time **only** on streams that compute staleness (order
tracking, admin map — `22 §4`). *Rejected:* an `event: heartbeat` on every stream. *Why:* comments
never reach an `EventSource` listener, so they cost nothing; ticks are required where staleness is
displayed and would be noise everywhere else.

**D15 — Binding errors.** Service bindings return the same envelope shape rather than throwing;
`undal-core` maps a downstream failure to `502` with `UPSTREAM_{SERVICE}_FAILED`, preserves the
request id, and writes a dead letter. *Rejected:* letting exceptions cross the boundary. *Why:* a
thrown binding error loses the error code and the correlation id, which is exactly what an incident
review needs.

**D16 — Retry budget.** One request budget (2 500 ms) threaded through hops as `budget_remaining_ms`;
each nested call receives `min(remaining / 2, its own budget)`; retries only on idempotent verbs and
`1213`/`1205`/`5xx`; at most 2 retries per hop and 4 across the chain. *Rejected:* per-hop retry
budgets. *Why:* nested retries multiply tail latency; a single budget makes the p99 provable.

## Web (D17–D22)

**D17 — Router.** React Router 7 in **data mode** (`createBrowserRouter` + loaders). *Rejected:*
framework mode, Next.js, client-only rendering. *Why:* loaders give the pre-render pipeline
data-before-render, while Vite stays in control of the build that Pages deploys.

**D18 — Pre-render.** Our own plugin in `web/storefront/prerender/` (route manifest from
`/v1/public/sitemap-data`, HTML emission, JSON-LD, thin-page failure). *Rejected:* `vite-plugin-ssg`,
a Gatsby-style framework. *Why:* `prerender-verify` requires per-route content assertions a generic
plugin cannot express, and Bengali mirrors double every route.

**D19 — Styling.** CSS Modules + custom properties generated from `design/tokens.json`.
*Rejected:* vanilla-extract, Tailwind, CSS-in-JS. *Why:* zero runtime, static CSS that survives
pre-rendering, and a critical-CSS budget of 42 KB that extraction can actually meet.

**D20 — Virtualisation.** `@tanstack/react-virtual` for admin grids and any list over 60 rows.
*Rejected:* react-window (older API), no virtualisation. *Why:* it composes with TanStack Table,
which the 60+ grids already need, and it is headless.

**D21 — Charts.** Recharts in the admin; hand-rolled SVG in the storefront and apps.
*Rejected:* Recharts everywhere. *Why:* the storefront's 160 KB bundle budget cannot carry a charting
library for three visuals; the admin's budget (420 KB) can.

**D22 — Service worker.** Hand-rolled (~150 lines) implementing the five strategies in
`20 §7` explicitly. *Rejected:* Workbox. *Why:* Workbox adds weight and its defaults are broader than
the corpus's narrow scope — "API mutations are never cached" must be a line of code, not a config
option.

## Data (D23–D26)

**D23 — UUIDv7.** One implementation per language — `packages/contracts/src/common/ids.ts`,
`workers/brain/src/lib/ids.py`, `android/core/common/Uuid.kt` — 48-bit millisecond timestamp + a
12-bit intra-millisecond counter + 62 random bits, against one shared test vector and a 10 000-call
monotonicity test per language. SQL never generates an id. *Rejected:* a SQL function (impossible
without stored functions), v4, `AUTO_INCREMENT`. *Why:* ids must sort by creation time for index
locality, and TiDB has no `gen_random_uuid()` at all.

**D24 — Item snapshots.** Full snapshot JSON on `order_items` (names en/bn, unit price, option labels
and deltas, photo URL), not a delta. *Rejected:* delta against the live menu. *Why:* an invoice must
be reproducible years later, and a delta against a mutable menu cannot be; `receipt-reproducibility`
(A76) is the test.

**D25 — Trace retention.** No partitioning for `brain_traces`; TiDB TTL by age (7 days default, 90
for dispatch and money-adjacent engines) plus the request-triggered sweep as a fallback.
*Rejected:* monthly partition tables, unlimited retention. *Why:* Starter has TTL, the 5 GiB ceiling
is the tightest constraint in the platform, and partitioning would split the single replay query.

**D26 — `vendor_stats`.** Maintained by an upsert inside the order-delivered write path, with a
nightly integrity job recomputing a sample and comparing. *Rejected:* a refresh-on-read materialised
view. *Why:* the ranking hot path must not pay an aggregate join; a bounded upsert on the write path
costs one statement.

## Process (D27–D30)

**D27 — Task graph.** Turborepo with `codegen → build → typecheck → lint → test`, explicit `inputs`
and `outputs`; remote cache off. *Rejected:* remote caching (a paid service for a 40-second cache
hit), Nx. *Why:* the free-tier rule outranks a build-speed win.

**D28 — Versioning.** No changeset tool. Versions live in four constants (`versionName` per app, a
Worker version, a contract version) bumped in the release commit, and `lockfile-drift` guards the
lockfiles. *Rejected:* Changesets, semantic-release. *Why:* nothing here is published to a registry;
a second source of truth for versions is pure overhead.

**D29 — Screenshot tolerance.** Pixel diff only for the 1 200 deliberate visual snapshots
(0.1% differing pixels, per-pixel threshold 0.1). The responsive matrix asserts **layout
invariants** — no overflow, no clipping, target sizes — rather than pixel equality.
*Rejected:* pixel-diffing 56 600 renders. *Why:* cross-platform font rasterisation makes pixel
equality of an unrendered state meaningless; the invariant is the real contract (`A151`, `A154`).

**D30 — Flaky tests.** A failing-on-rerun test moves to a `quarantine` suite that **still runs and
must still pass** but does not gate merges, with an auto-created issue and a 7-day expiry that turns
the build red when it lapses. *Rejected:* skipping, deleting, "fix later". *Why:* the corpus's zero
tolerance needs a mechanism that cannot be quietly ignored; an expiring quarantine is that mechanism.

## Implicit, and decided here (D31–D33)

**D31 — Generated Kotlin models.** `scripts/codegen/kotlin-models.ts` generates `@Serializable` data
classes for all 412 endpoints into `core:network/model/generated/`, with money as `Paisa` (a `Long`
value class) and never `Double`. *Rejected:* hand-written DTOs. *Why:* 412 hand-written mirrors of a
Zod contract drift within a week, and a generated `Double` is a money bug waiting for a fare.

**D32 — QR key rotation.** Two HMAC keys are accepted for a 24-hour overlap
(`QR_HMAC_KEY`, `QR_HMAC_KEY_PREVIOUS`), and `rotate-secret.yml` writes both. *Rejected:* a single
key (rotation invalidates in-flight pickups). *Why:* `27 §6.1` requires rotation without invalidating
in-flight orders; two keys is the only way to satisfy it.

**D33 — Error text ownership.** Every error code's English and Bengali copy lives in
`packages/contracts/src/errors/registry.ts` and is extracted into `packages/i18n`; the server returns
a code plus an optional server-rendered sentence, and clients render from the catalogue.
*Rejected:* server-only strings, client-only strings. *Why:* `i18n-completeness` must be able to
prove all 184 codes exist in both locales, and offline clients must still be able to explain a
failure they received earlier.

## Visible deviations from the corpus (D34–D35)

**D34 — One Pages project, not two.** The storefront and the admin SPA deploy as one project: `/`
serves the pre-rendered storefront, `/admin/*` serves the admin SPA with a **path-scoped** CSP in
`public/_headers` (stricter: no `img-src data:`, no inline styles), an `HttpOnly` refresh cookie
scoped to `/admin`, and a Cloudflare Access policy on `/admin/*`. [`21 §13`](../21-admin-panel.md)
specifies a separate project at `admin.{domain}`; the operator's brief specifies **one Pages
project**, and this is the closest thing to both. *Rejected:* two projects (violates the brief),
one project with one shared CSP (loses the admin's stricter policy). *Why recorded here:* the
residual risk is an origin shared by a public storefront and the admin surface — R36 in the build
plan — and it should be a decision someone can find, not a surprise.

**D35 — `minSdk 26`, not 24.** Non-negotiable 39 in [`01`](../01-mission-and-non-negotiables.md)
requires Android 8.0 and names its own test matrix (API 26/30/34/35); [`16 §3.1`](../16-android-foundation.md)
and [`18 §1`](../18-partner-app.md) say 24. The non-negotiable wins because it is explicitly ranked
above the documents and because CI can only promise what it tests. *Rejected:* 24 (untested floor, a
stated rule broken), 23 (below 16's own warning). *Why recorded here:* it excludes Android 7.x
devices — a small, shrinking share of the Bangladeshi base — and that cost should be visible rather
than discovered in a Play Console device report.

## D36 — The five platform-wide error codes keep their bare names

**Decision.** The sixteenth group file is `packages/contracts/src/errors/rows/system.ts`, but its
five codes are exactly `INTERNAL`, `SERVICE_DEGRADED`, `DEPENDENCY_TIMEOUT`, `IDEMPOTENCY_CONFLICT`
and `NOT_IMPLEMENTED` — no `SYSTEM_` prefix — and the three `OAUTH_*` codes are counted inside the
`AUTH_` group.

**Rejected.** Inventing `SYSTEM_INTERNAL` and the rest so that every prefix matches its table row.

**Why.** `08 §11` labels the row `SYSTEM_` but names the codes without it, and clients match on the
code string exactly. The registry is the contract, so the 184 strings are authoritative and the table
label is the typo. The parity test asserts `AUTH_ + OAUTH_ = 21` and `BARE = 5` so the reconciliation
lives in the test rather than in a reader's head.

## D37 — `platform_config.zone_id` uses the all-zero UUID for "global"

**Decision.** `zone_id BINARY(16) NOT NULL DEFAULT 0x00…00`, where the zero UUID means the global
default. The DDL in `29` was rewritten from CockroachDB types to `VARCHAR`/`BINARY(16)`/`JSON`/
`DATETIME(6)`.

**Rejected.** Keeping `zone_id UUID NULL` with a nullable primary-key column.

**Why.** MySQL — and therefore TiDB — will not store `NULL` in a primary-key column: the insert fails
with 1048 rather than creating the global row the design describes. The sentinel keeps the same
semantics, the same key order and the same access path, and it is visible in the type instead of in
a comment that the database ignores. `no-postgres-dialect` caught the original DDL on the first
guardrail run.

## D38 — An unknown route answers `NOT_IMPLEMENTED`, not `404`

**Decision.** `undal-core` and `undal-realtime` return HTTP 501 with code `NOT_IMPLEMENTED` and
`details: { method, path }` for any path they do not serve.

**Rejected.** Adding a `ROUTE_NOT_FOUND` code (which would break the 184-code contract) or borrowing
`CATALOG_VENDOR_NOT_FOUND` (which would lie about what was missing).

**Why.** On a versioned API an unknown path means "this build does not serve this", which is exactly
what 501 says in RFC 9110, and it is the one registered code whose meaning is true. A `404` would tell
the client the resource exists elsewhere and send it looking.

## D39 — Guardrail exemptions are named, not silent

**Decision.** Three exemptions are written into the rules themselves: markdown is exempt from the
700-line cap; test and fixture paths are exempt from the placeholder scan and the money-float scan;
`scripts/guardrails/` is exempt from the placeholder scan.

**Rejected.** Keep-whole rules with a suppression comment, or a `# guardrail-ignore` escape hatch.

**Why.** A rule that can be silenced locally stops being a rule. Each exemption below is a property of
the tree rather than of a file: the spec corpus is one document per subject and splitting
`06-data-model-tidb.md` at line 700 would separate a table from the paragraph that explains it; tests
are not shipped and a test that asserts "no TODO in the registry" must be able to spell the word; the
guardrail tooling is the code that lists the forbidden words.

## D40 — The Kotlin differential runs on its own workflow

**Decision.** `ci.yml` compares TypeScript against Python on every push; `money-math.yml` adds the
Kotlin answers from the JVM-only `:shared:money` module.

**Rejected.** Setting up a JVM in the main gate for one more language.

**Why.** Three minutes on every push for an assertion whose inputs change only when
`packages/money` or `android/shared/money` change is three minutes the maintainer spends waiting on a
tablet. The paths filter on `money-math.yml` runs it exactly when it can fail.

## D41 — Operational workflows ship before the scripts they call

**Decision.** `migrate`, `verify-schema`, `d1-migrate`, `db-query`, `housekeeping` and `brain-replay`
exist from this response as the interface a browser-only maintainer uses, while the scripts they
invoke arrive with the migration pipeline (R6) and the Brain (R17).

**Rejected.** Deferring the workflows until their scripts exist.

**Why.** Each of these is a `workflow_dispatch` button, and a button that exists, is documented and
fails loudly at a named missing script is better than a button discovered missing at 2 a.m. with a
broken deployment — the failure names its own remedy. Nothing here runs on push, so the gate that
guards every commit is unaffected, and no step in any of them pretends to have done work it did not do.

## D42 — The 109 table names are the schema; the document's total of 99 was a slip

**Decision.** `db/migrations` creates the 109 tables `06 §2` names, and the document's total row now
says 109.

**Rejected.** Implementing 99 tables and dropping ten names, or keeping 99 and hiding the gap.

**Why.** The per-group counts in that table were correct from the start — 14, 8, 12, 12, 12, 15, 12,
10, 14 — and they always summed to 109; the total was the only wrong cell. Ten tables cannot be
dropped to satisfy a typo, so the names win and `scripts/db/check_schema_parity.py` now compares the
inventory to the migrations on every push.

## D43 — `CHECK` is declared in SQL and enforced in TypeScript

**Decision.** `scripts/db/extract_constraints.py` parses every `CHECK` out of the migrations, writes
`packages/contracts/src/constraints.json`, and generates `constraints/generated.ts`: 164 validators
across 76 tables, each carrying the SQL it came from.

**Rejected.** Trusting the DDL, and trusting a hand-written validator list beside it.

**Why.** TiDB parses `CHECK` and does not enforce it, so the DDL alone would look guarded and enforce
nothing. The generator is a real parser (tokens, recursive descent, arithmetic and `NOT IN`
precedence), not a regex: every generated expression is proven to parse as JavaScript by `node
--check` at generation time, and `tsc` proves it again in CI. Anything the parser does not understand
is a hard failure, because a validator that skips a rule silently is worse than no validator.

## D44 — Foreign keys stay where the specification put them

**Decision.** Tables defined in the corpus keep their `REFERENCES` clauses; tables authored against
the inventory get them too, except the three the corpus names as deliberately unkeyed (`order_items`,
`order_state_events`, `order_offers`).

**Rejected.** Removing every foreign key to make migration order easier, and adding keys to the three
high-write tables for uniformity.

**Why.** An orphaned ledger row is a reconciliation bug nobody can fix after the fact, while an
orphaned order item is a row that outlives a cancelled order by design. The exception is documented
where it applies — in the migration that creates each of those three tables — rather than in a policy
statement a reader has to find.

## D45 — `platform_config`'s primary key is ascending

**Decision.** `PRIMARY KEY (key, zone_id, effective_at)`, with no `DESC`.

**Rejected.** The `DESC` the specification wrote, which is legal on a secondary index and not on a
primary key.

**Why.** MySQL rejects a descending column in a primary key; TiDB parses it inconsistently across
versions. "Latest value for this key" is a backward index scan on the same key, which TiDB serves
without a second index, so nothing is lost but the parse failure the SQL validator caught.

## D46 — The geospatial layer is checked three ways, every push

**Decision.** `scripts/geo/parity.py` runs 6 000 deterministic cases through the exported
TypeScript functions, an independent Python mirror, and SQL, and writes
`.artifacts/geo/parity.json`. The `geo-parity` rule fails the build on any mismatch, and in CI
(`GEO_PARITY_REQUIRED=1`) also fails when the artifact is missing.

**Rejected.** A shared constants file, a formula copied into three languages, and a check that
silently passes when no artifact exists.

**Why.** It earned its keep on the first run. SQLite's `/` on two integers truncates where MySQL's
divides into a DECIMAL, so the "same" floor expression gave a different cell for every negative
coordinate; the probe also caught that `haversineMeters` returns whole metres, which the Python
mirror was comparing at three decimals. A check that cannot disagree is not a check.

## D47 — The ledger records statements, not files

**Decision.** `scripts/db/migrate.py` writes one `schema_migrations` row per statement, with the
file's SHA-256, and refuses to continue if an applied statement's checksum changed.

**Rejected.** One row per file, and a `--force` escape hatch.

**Why.** TiDB auto-commits DDL: a file that fails at statement 7 leaves six statements applied and no
rollback. A per-file ledger would then either re-run all six (they are idempotent, but the window in
between is wrong) or mark the file applied and skip statement 7 forever. Per-statement resume plus an
immutability check is the only combination that is safe when the platform has no transactions around
DDL.

## D48 — Two session-security tables join the identity group

**Decision.** `refresh_tokens` and `security_events` are created by `013_session_security.sql`, the
inventory's identity group grows from 14 to 16 names, and the total from 109 to 111.

**Rejected.** Storing refresh families in KV, and logging token reuse to `audit_log`.

**Why.** Rotation with family reuse detection needs a row per issued token that survives a KV
eviction — a stolen token is exactly the event where losing state is unacceptable. Reuse is evidence
about an actor, not an action taken on data, so it belongs in a table security reads rather than in
the finance-facing audit chain, which is also append-only with a single writer.

## D49 — Twenty-seven rate limits, not thirty-eight

**Decision.** `ratelimit/limits.ts` implements the 27 limits the `08 §12` table actually lists, and
asserts that count at module load.

**Rejected.** Inventing eleven more buckets to reach the prose figure.

**Why.** Counted cell by cell the table has 27 filled cells; the surrounding sentence doubles the
auth pair (IP and phone) and the five SSE caps. Same failure as D42, caught the same way: the table
is data and the prose is a summary, and a fabricated bucket would be a limit nobody chose.

## D50 — The audit chain is verified by a second implementation, not by itself

**Decision.** `db/fixtures/audit_chain_vectors.json` holds three chained rows with their digests;
`workers/core/src/audit/chain.ts` and `scripts/db/housekeeping.py` must both reproduce them, and both
do in CI.

**Rejected.** Verifying the chain only in the language that wrote it.

**Why.** A chain checked by the code that wrote it proves the code is self-consistent, which is not
the property anyone needs. The fixture is the contract between the two implementations, and it
immediately earned its keep twice: `null` had to hash like an absent field, and the housekeeping job
was reading a `payload_sha256` column that does not exist.

## D51 — The tip and the small-order fee are inside the collected cash, not beside it

**Decision.** In the canonical `ORDER_DELIVERED` set the customer's whole payment — food, delivery,
tax, tip, small-order fee, less the rounding delta — is the single `RIDER_CASH` debit. The tip and
the small-order fee appear only as credits: the rider's payable grows by the tip and by the rider's
share of the fee, the platform's small-order revenue grows by the rest. A tip added *after* delivery
is its own `TIP` entry with the `+tip / −tip` pair that `24 §3` prints.

**Rejected.** Posting `RIDER_CASH +tip` inside the order set, as a literal reading of the §3 table.

**Why.** §2.1's `raw_total` already contains the tip, so a second cash debit counts the customer's
money twice — the generator caught it on case 21 of the closure property test, which is exactly the
kind of double count that leaves a ₹5 000 hole in a rider's float after a week of tips. The §3 table
describes the *pass-through* entry, not the order entry; the difference only shows up when both
exist, and now the test knows which is which.

## D52 — A balance is a sum, never a stored column

**Decision.** `domain/ledger/balance.ts` computes every balance as `SUM(amount_paisa)` over the
postings table, in one grouped query for the whole platform, with an optional `asOfSequence`.

**Rejected.** A `balance_paisa` column on `ledger_accounts`, updated on every posting.

**Why.** Two sources of truth for money is one source of truth and one source of argument. A cached
column drifts the first time a compensating delete runs, and the daily reconciliation compares these
sums against the provider's statement — so the sum has to be the definition, not a cache of it. The
`asOfSequence` variant exists because an auditor asking "what did we hold on the 3rd" needs the sum
as it stood then, which a mutated column cannot answer at all.

## D53 — The golden posting sets are generated by a second implementation, not by the code

**Decision.** `scripts/money/posting_sets.py` implements `24 §2.1` and `§3` again in Python, from the
document, and writes the thirty-four golden sets the TypeScript builders must reproduce. CI runs the
generator with `--check`, so a drifted golden file fails the build instead of quietly agreeing.

**Rejected.** Committing a table of expected numbers produced by the TypeScript builders.

**Why.** A file generated by the code under test asserts that the code still does what it did last
Tuesday, which nobody doubted. The Python side disagreed twice on first contact and both times it was
right: the pickup tax base must include the pickup fee (it is platform revenue, so invariant 2 of
`§2.3` puts it in the base), and a cancellation refund has to address the *customer*, not the order
id — the TypeScript had been crediting the order. Neither would have surfaced from a hand-typed table
without the same disagreement, and a hand-typed table would already have been wrong.

## D54 — `-0` is not zero

**Decision.** `applyRate` normalises a zero result to `+0`; the refusal test asserts it with
`Object.is`.

**Rejected.** Leaving the sign in place because `-0 === 0` is true.

**Why.** `-0` passes every equality check, survives `Object.is`, prints as `-৳0.00` through the
formatter, and keys a `Map` identically to `0` while failing a `deepStrictEqual` — a shape that only
ever appears in a diff at three in the morning. The coverage gate found it: the branch that
multiplies a negative amount by a small rate had never been executed, and the first execution printed
`-0`.

## D55 — `LEDGER_IMBALANCE` is a value the ledger produces, not a webhook it sends

**Decision.** `domain/ledger/imbalance.ts` returns the exception (`trigger`, `severity`, `slaSeconds`,
the drifting accounts largest-first, both language strings) and leaves delivery to the alarm pipeline.

**Rejected.** Posting the alarm directly from `postEntry`, or from the nightly sweep.

**Why.** The alarm pipeline arrives in R13 and owns retries, dead letters and the on-call page; the
ledger owns the arithmetic. Keeping them apart means the exception is testable without a network, the
admin panel's "verify now" button and the nightly sweep call the same function, and a caught
in-memory imbalance produces the *same* exception shape as a drifted trial balance — one alarm with
two detection paths rather than two alarms that can disagree about severity.

## D56 — The small-order fee splits three ways, and the vendor is one of the three

**Decision.** `ORDER_DELIVERED` credits the vendor's share of the order fee through the vendor's
line (`subtotal − commission − bonus + vendor_share`) and books only
`fee − rider_share − vendor_share` as `PLATFORM:REVENUE_SMALL_ORDER`.

**Rejected.** The two-way split the ledger had: platform gets `fee − rider_share`, vendor gets
nothing.

**Why.** `10 §8` and `§12.1` both print ৳25 as ৳5 rider + ৳5 vendor + ৳15 platform, and the fare
engine's vendor payout carries the vendor's ৳5. The ledger disagreed with the engine by exactly
that ৳5 — every posting set still closed, because closure only says the totals agree, not that they
agree with the *right* people. Found by writing the fare engine's constants next to the ledger's
small-order lines, which is the check that no property test performs: the two modules were each
internally consistent and mutually wrong.

## D57 — At SDR 0.50 the bridge lands on 1.475×, not the table's 1.48×

**Decision.** `surge_bps(0.50)` returns 14 750, the value the printed function computes from the
bridge between the severe and moderate bands.

**Rejected.** Forcing 14 800 to match the row the table prints.

**Why.** `10 §4.3`'s table and `10 §4.2`'s code disagree by 50 bps at exactly one point, because
the table's author rounded 1.475 to two decimals while writing it. The code is the specification
here — it is the thing that ships, it is continuous by construction, and a table row is a
human-written summary of it. The test names the point and states which side it took, so the next
reader does not have to re-derive the disagreement.

## D58 — The delivery line closes on its residual, not on `margin − weather`

**Decision.** The closure identity uses `platform_delivery_net = delivery_fee − rider_fare`, with no
separate weather term. `platform_delivery_margin = delivery_fee − ride_core` remains the *gross*
figure and remains the tax base, exactly as `10 §9` requires.

**Rejected.** The literal identity of `10 §10.1`, which subtracts the weather premium and the gross
margin.

**Why.** The printed identity is true only when the rider's fare equals the core plus the weather
premium. It is not true when a bundle moves the fare onto a marginal detour, and it is not true when
the minimum-payout floor binds — and in those cases it does not merely drift, it *fails*, which the
brain found on vector 06 with a 3 867-paisa drift on a perfectly ordinary order. The residual is the
same statement without the assumption: whatever the customer paid for the delivery minus whatever the
rider was paid for it, and every term stays named in the failure message.

## D59 — Thirty of the forty vectors are regression pins, and the file says so

**Decision.** Vector 01 is asserted by hand against `10 §12.1`'s printed table. The other 39 are
generated by `workers/brain/test/generate_fare_vectors.py`, committed, and checked for drift in CI;
each is also asserted to close over its own terms.

**Rejected.** Implying all forty were derived independently of the engine that produces them.

**Why.** The document works ten vectors in full; the other thirty exist to pin boundaries — every
surge band edge, both bridges, four weather conditions on both vehicles, both clamps, bundles,
tips, discounts. Calling a generated pin "hand-computed" would be a lie in a file whose whole
purpose is to be trusted. The distinction is written into the generator's docstring, the test's
docstring and this entry: one vector is the document's, thirty-nine are history's, and the closure
identity is what makes history worth keeping.

## D60 — A pickup reaches DELIVERED, because the document leaves it stranded

**Decision.** `PICKED_UP → DELIVERED` is a `SYSTEM` edge guarded by `pickupOnly`, `cashRecorded` and
`cashReconciles`; a pickup therefore travels `ACCEPTED → PICKED_UP → DELIVERED`.

**Rejected.** Leaving the row out because `06 §7.3` does not print it.

**Why.** For a pickup the table offers `ACCEPTED → PICKED_UP` (customer, QR scanned by the vendor)
and then no edge that fits — `PICKED_UP → ARRIVED` needs a rider who does not exist, and
`ARRIVED → DELIVERED` is unreachable from there. Taken literally, every pickup order stops in
`PICKED_UP` and its cash never settles: the one path where the money is taken *before* the order is
complete would be the one path the ledger cannot close. The added edge is a `SYSTEM` transition, not
a customer one, so it cannot be used to skip a payment, and the coverage sweep now proves that no
non-terminal state is a trap.

## D61 — Guards read an explicit context, never the database

**Decision.** Every guard is a predicate over `TransitionContext`, a sparse object the caller fills;
a missing field fails the guard rather than passing it.

**Rejected.** Guards that load the vendor or the order themselves.

**Why.** The same transition has to be evaluable by an HTTP handler, a DO alarm, a test and a
replay of last month's events. A guard that reads the world can only be run in one of those four
places, and the event log stops being something a reconciliation job can re-derive. "Absent field
means refused" is the direction that fails closed: a context built by a caller who forgot the quote
refuses the placement instead of selling the order at a price nobody computed.

## D62 — A quote is a signed snapshot, not a row

**Decision.** The quote is a canonical-JSON snapshot of the fare inputs and totals, HMAC-signed and
handed to the client; placement verifies the signature, re-prices from scratch and refuses any
difference with `QUOTE_MISMATCH` and the moved lines. No `quotes` table exists, and none is needed.

**Rejected.** Persisting quotes and comparing rows.

**Why.** A row would be written before the customer has agreed to anything, which means a table that
grows with abandoned carts — and it would still not enforce the promise, because the promise is
*re-price and compare*, not *remember*. The signature proves the platform issued the price; the
re-price is what makes it true. It also survives a Worker restart, a zone boundary and a deploy,
none of which a row would.

## D63 — The order code is derived from the order id

**Decision.** `UND-` plus eight characters folded from the id's own bytes.

**Rejected.** A sequence, a counter row, or `Math.random()` — then checking for collisions.

**Why.** A counter needs a lock, and this platform deliberately has no interactive transactions: two
Workers placing in the same millisecond would race for the same number and one would lose an order.
Deriving the code from the id makes collisions impossible by construction (distinct ids, distinct
codes at this bit width), needs no coordination, and keeps a code the customer can read down a
phone line without a homoglyph in it — the alphabet omits `0/O` and `1/I`.
## D64 — Order routes ask the state table; they never branch on state themselves

A route that decides "can this be accepted?" with an `if` chain reimplements the machine and drifts
from it the first time an edge changes. `accept`/`reject` therefore build a `TransitionContext` and
hand it to the lifecycle, which returns either the target state or a refusal code that the route
returns verbatim. The route contributes facts (who owns the order, the prep time, the reason), never
the rule.

Concurrency is the same question asked of the database rather than of memory: the move is
`UPDATE orders SET state = ? WHERE id = ? AND state = ?`, and `affectedRows !== 1` means another
writer got there first — surfaced as `applied: false` and answered with the refusal for the state the
order is actually in, not a 500. Two vendors accepting at once must produce one ACCEPTED row and one
event, and the loser must be told `ORDER_ALREADY_ACCEPTED`.
## D65 — An order line is a photograph, and the history has no gaps

`order_items` copies the name, the unit price and the quantity the customer agreed to. Nothing on a
receipt is joined live to the menu: a rename or a price rise must not edit an invoice that has
already been paid, and the only way to guarantee that is to stop reading the catalogue at render
time. Modifiers are folded into the unit price rather than stored per row, because the receipt shows
one number per line and a second number that disagrees is worse than no breakdown.

Placement refuses a cart that the rows cannot explain: an empty cart, the same menu item twice, a
quantity outside `1..20`, more than `MAX_ORDER_LINES` lines, and — the check that matters most — a
line subtotal that does not equal the quoted `subtotal_paisa`. A total is a claim; the lines are the
proof of it.

`order_state_events.seq` is dense by construction, so `firstGap` treats a hole as an incident rather
than as history. `orders.state` says where an order is; the event table is the only thing that can
say how it got there, and a deleted row is a settlement dispute waiting for a quiet week.
## D66 — Core prices money; the Brain prices the trip, and a disagreement never moves a price

`10 §4` turns rider counts into a surge multiplier, and that curve is the one float in pricing. It
lives in the Brain (`fare/surge.py`) and nowhere else: Core's deterministic engine takes the
multiplier *published for the zone* as an integer input and refuses anything that is not a whole
value in `10 000..22 000` bps. A second float implementation in TypeScript would be a second answer
to "what does this trip cost", which is exactly what a published multiplier exists to prevent.

Everything below the multiplier is integer paisa and is duplicated deliberately in
`workers/core/src/pricing/fallback.ts`, because an order must still be priced when the Brain is cold,
deploying, or merely slow. The duplication is falsifiable rather than hopeful: the same forty fare
vectors the Python engine is tested against are read from the same file and run through the
TypeScript engine in `test/pricing-fallback.test.ts`.

`resolveFare` treats the Brain as a second opinion, never as the price. If it answers within its
400 ms budget with whole paisa and agrees on all four published numbers (delivery fee, ride core,
rider payout, surge), the order is stamped `fare_source = 'BRAIN'`. If it is late, unavailable,
malformed, or disagrees by a single paisa, the deterministic breakdown stands, the order is stamped
`'FALLBACK'`, and the reason plus every disagreeing field is returned so it can be counted. A
Brain bug therefore cannot charge an unexplainable price, and a Brain outage costs nothing but a
metric.
## D67 — A quote is priced in straight lines and says so; a promotion is a warning, never a refusal

Routed distance needs OSRM, which lives behind the dispatch worker and is not bound yet. Rather than
invent a routed number, a quote uses the haversine distance between the vendor and the delivery point
and returns `distanceSource: "ESTIMATED"` beside it. `08 §4.1` already prints `distanceM` in the
explain sheet, so the provenance travels with the figure: a customer can see that the ৳62 delivery
was priced on 3.8 km as the crow flies, and the day the binding lands the field changes to `OSRM`
without a contract change.

A promotion the customer typed is always answered — an unknown or expired code becomes a `warnings`
entry and a zero `DISCOUNT` line, never a 4xx. Refusing the whole quote because a code is stale makes
the customer re-enter a basket to be told nothing about the code, and it turns a marketing typo into a
conversion bug. A code that applies less than its face value (below the minimum, over its cap) is
reported the same way.

The quote endpoint is a `POST` that writes nothing, and declares `readOnly: true` so the
audit-coverage guardrail can stay strict about every other mutating verb without filling `audit_log`
with thirty quotes a minute. Free delivery is applied *after* the fare engine, so the total and its
rounding line are re-derived from the surviving components and floored once — a cash total is always
whole taka.
## D68 — Placement takes its cart from the signed token, and a guest quote is claimable once

`POST /v1/orders` never reads a cart from the request body. The items come from the signed quote and
are re-priced against today's menu and today's rates; the request contributes only what a quote cannot
know — the delivery point and the customer's note. A client that sent its own items beside a stale
token would otherwise order a different basket at the old price, and the re-price would confirm a cart
nobody quoted.

Re-pricing runs the *same* code as quoting (`pricing/cart-service.ts`), because a comparison between
two implementations reports its own bugs. The snapshot now carries the chosen modifier ids
(`QuotedItem.modifierIds`), so the re-price prices the same choices rather than trusting a modifier
total from the token as a number.

A guest quote records no customer, and the customer who signs in to place it claims it. A quote that
already names a customer belongs to that customer alone. This is what makes it safe to issue a quote
before the customer has an account, and it is a one-way claim: nothing re-opens a claimed quote.

Refusals keep their own codes. An item that left the menu is `QUOTE_INGREDIENTS_CHANGED` — the
customer is told the item is gone, not that "the total changed" — while a price that moved is
`QUOTE_MISMATCH` with every differing line attached, and an expired token is `410 QUOTE_EXPIRED` even
when the price is unchanged, because the five-minute promise is about *when* the customer agreed.

## D69 — Distance is geography, not money, and it says which it is

`domain/order/distance.ts` owns the straight-line estimate and the degrees→E7 conversion. Both round,
and neither is money, so keeping them out of `pricing/` is what lets the money rule refuse *every*
float in a pricing path with no exceptions to audit. `RouteEstimate` carries `source`, which travels
into the quote as `distanceSource: "ESTIMATED"` and into the order row as `distance_source`.
## D70 — Dispatch is fourteen numbered filters and five waves, decided as values

The candidate filters of `11 §3` live in one array with the document's own numbers. A rider who is
not asked is told *which* filter refused them, because "you cannot take this order" and "you cannot
take this order because your notifications are off" are different products — the second is fixable by
the rider in ten seconds. The two rejection filters are separate inputs, not one boolean: a rider who
said no to *this* order is never re-offered it (12), and a rider in a vendor cooldown is not asked
about that vendor at all (13). Collapsing them is how a rider gets the same offer twice.

Waves are filled until the chance nobody accepts falls below one in ten, and the candidate that
crosses the target is *included* — stopping one short sends a wave the model has already judged
worse than the threshold. Ranking is by predicted acceptance, so a stable ranking gives a stable wave;
a wave that shuffled between retries would page one rider twice and skip another.

`decideClaim` is the Durable Object's decision written as a pure function, so the race is testable:
three taps, exactly one winner, and the losers distinguish `OFFER_CLAIMED` (a race) from
`OFFER_EXPIRED` (nobody came) and `OFFER_NOT_YOURS` (a stale card). A race must never look like a
malfunction on the losing phone.
## D71 — A snapshot is a copy with a version, and evidence is judged before it is stored

`06 §7.1` says anything on an invoice is frozen into the order at placement. The part that matters a
year later is the version: a snapshot is read by code that has moved on, so every snapshot carries
`version`, and a reader that does not recognise it refuses rather than guessing. Reading it anyway is
how a renderer drops a field it never heard of and prints an address missing its flat number.

A proof is admissible only if it could be evidence of *this* handover: a photograph needs media, a
scan needs its payload, the capture must be inside the same geofence a pickup scan satisfies, and it
must be recent — a capture from an hour ago, or one dated in the future by a device with a wrong
clock, is refused rather than stored and argued about later. The decision is a pure function on a
capture, so it is assertable with no camera, no GPS and no network.

A delivery needs *one* door-side proof — photograph, signature or handover selfie — and a scanned
pickup code does not count as one: it says the food left the kitchen, not that it reached a doorstep.
## D72 — Pre-flight answers a question; pickup answers with the scanner's facts

`POST /v1/orders/validate` returns `200` with four named checks and a `canPlace` flag, and only a
malformed body is a 4xx. A basket that cannot be placed is not an error — it is the answer to the
question the checkout screen asked, and the screen needs *all* the reasons at once so it can grey the
button and highlight the right field. The checks are produced by unpacking the refusal the pricing
service would have returned, so pre-flight and quote cannot disagree about the same cart.

`POST /v1/orders/{id}/pickup` moves an order out of `RIDER_ASSIGNED` on evidence, not on request: the
presented code is verified against the order's own rotating HMAC, the rider's position is checked
against the same 150 m geofence a handover uses, and the guards are given the *scanner's* facts
(`pickupCodeMatches`, `riderDistanceToVendorM`) rather than the request's claims. An order that is not
waiting at the counter answers `QR_ALREADY_SCANNED` whatever the code contains, and a lost race on the
state update writes no event row, so a concurrent scan leaves no phantom in the history.
## D73 — Dispatch ships the formulas, not the worked table, and normalises weights that do not sum to one

`11 §6` prints a worked dispatch for order `UND-7K2M9QX4` with a full factor table and the rank
**B, A, D, C, E**. Four of its columns do not reproduce from the formulas the same document prints in
`§5.1` and `§5.2`: `eta_fit` matches only for rider E, `fairness` only for rider B. The formulas are the
specification and the table is an illustration, so the engine implements the formulas and the test
file records the discrepancy explicitly (`DocumentDiscrepancyTests`) instead of asserting numbers that
would have to be reverse-engineered to look right. What the table does establish — the ordering, and
that nearest-rider is not the winner — is asserted as the ranking.

`11 §5` also prints "Sum: 1.000" above fourteen weights that add to **1.005**. A weighted average is
only an average if the weights sum to one, and every threshold on a score depends on that, so
`DEFAULT_WEIGHTS` is the printed set divided by its sum (tolerance ±1e-9, enforced in `Weights.__post_init__`).
The printed figures stay in the module as `PRINTED_WEIGHTS` so the next reader can see both numbers.

Dispatch also stops pretending filter 10 is implemented: `batch/feasibility.py` does not exist yet, so
a rider already carrying an order is not offered a second one. That is the conservative answer and the
honest one — a cold meal is worse than a second wave.
## D74 — Batching ships the constraints and the cost function; the worked score is 0.5812, not 0.566

`12 §6.1` prints five terms for the Vector 06 bundle — 0.417, 0.579, 0.750, 0.880, 0.393 — and a total
of **0.566**. The document's own weights (0.32, 0.26, 0.18, 0.14, 0.10, which do sum to 1.0) applied to
the document's own five terms give **0.5812**. The implementation follows the weights and the terms,
and the test asserts both numbers — the computed total *and* that it is not the printed one — so the
next reader finds a recorded discrepancy instead of a silent inequality (`D73` set the precedent for
dispatch's table).

The detour model is the document's, term for term, including the part that is easy to forget: the
second order's detour carries the *whole* of the first order's handover. A model that priced the hop
and forgot the doorstep would promise seven minutes and deliver eleven.

`C2` reports `None` when nothing in the bundle is fragile, which is deliberately different from
"passed": a constraint that does not apply must not be recorded as a constraint that was satisfied, or
the trace cannot tell a careful bundle from a lucky one. `C7` charges a fragile item one bag of
capacity, and `C10` refuses a bundle whose rider payout is below the sum of the two solo minimums —
the rider must never earn less for carrying two meals than for carrying one.

A proof is re-validated when the rider accepts (`12 §5`), and it is checked against the proof's *own*
stored detours as well as the fresh world: a stored detour already over budget means the proof was
never honest, which is a different failure from a world that moved.

## D75 — The trace emits one key per real factor, and the cascade's clock is absolute

`09 §6` prints a `DISPATCH` trace whose fourteen factor keys include `cooldown` and `zoneFit`, and
which omits area familiarity. Cooldown is filter 13 — a veto, not a factor — so a trace that listed it
would show an operator a bar that no score ever produced. The engine therefore derives its trace keys
from the factor list itself (`TRACE_FACTOR_KEYS`), keeps the document's camelCase spelling where a
factor matches (`cashRisk`, `zoneFit`, `vehicleFit`), and the test asserts exactly one key per factor
and that `cooldown` is absent. A new factor cannot be added without appearing in the trace, which is
the only version of "no field missing" (`D12`) that survives the next change.

The cascade advances a wave **immediately** when every rider in it has rejected. Waiting out the
25-second TTL for phones that have already answered is pure delay, and the brief's own rejection flow
says "advance the cascade". The rest of the schedule does not move: the ladder's clock is absolute
from T+0, so an early wave 2 leaves a gap before wave 3 rather than pushing the fallback later. Any
claim or rejection stamped at or after T+112 belongs to the ladder, not the cascade, and is not
replayed into it — a decision after the deadline is a different decision.

The pre-warm invalidates on age (60 s), on drift and at its TTL (180 s), and drift is the *symmetric
difference* over the previous rider set, not additions alone: a zone that lost five riders and gained
five different ones is not the same crowd. The threshold is strict — exactly 20% is still warm — and
the weight version is a fourth invalidation, because a cache that outlives a weights deploy would
serve yesterday's ranking with today's version stamped on it. Step 1 of the ladder widens only the
bicycle radius, the cash cap and the zone edge; a motorbike's 12 km limit is a practical bound, not a
tuning knob, and a boost is floored to taka exactly once like every other amount of money.

## D76 — The benchmark gates on the comparison, not on the printed targets, and reports nine metrics

`11 §12.1` prints eight metrics; `30 §4.1` prints nine, adding the on-time rate. The report carries all
nine and the gate checks all nine, because a dispatch that is fast and late is not a good dispatch and
dropping the ninth number would be choosing the flattering table. The baseline is deliberately strong:
it uses the same five-wave cascade, the same 90% confidence target and the same random draws, and
differs only in ranking by distance — plus the expansion ladder and same-vendor batching, which are
Undal's policy and not the baseline's. Beating a straw man would prove nothing; the gap between the two
policies is therefore the value of the fourteen factors, measured.

The absolute targets in the documents are shown in every row and are usually missed, which is recorded
rather than hidden. The synthetic city is 60 orders over eight riders on staggered six-hour shifts,
with longer trips than the calibrated city the printed numbers came from: assignment waits run in
minutes rather than the printed 41 seconds, and the batch rate is ~7% against a 15–30% target because a
bundle needs two consecutive orders at the same vendor inside eight minutes. What the gate enforces is
that Undal is better than the baseline on every metric — which it is, on 15 000 order-days — because a
relative regression is the thing that can be caused by a code change, while the distance to a target
that was calibrated elsewhere cannot.

Three smaller decisions came out of making the benchmark runnable. The world generator lives in
`bench/world.py` so no file crosses the repository's 700-line cap, and because a world that does not
know which policy will run on it cannot be quietly kinder to one. "No rider found" counts the orders
still waiting when the day closes, not orders that waited a while: a late delivery is measured by the
customer-wait and on-time metrics, and counting it twice would double-charge the same failure. And two
of the seven adversarial scenarios — GPS plausibility and promo eligibility — are rules for modules that
land later (R10 and R17); the benchmark asserts the rule now so that it cannot change quietly, and says
so in the file rather than pretending the shipping code exists.

`brain-replay` is now the harness the workflow calls: a fixture carries the whole request and the answer
it produced, three are committed, and a changed ranking fails the build. Until `brain_traces` has live
rows the fixtures are the record; the workflow's `--traces` input is reserved for the loader that lands
with the realtime worker. The old workflow pointed at `replay.py` and `replay_check.py`, neither of
which ever existed — a check that cannot run is worse than no check, because it looks green by being
absent.

## D77 — The `sql` coordinator composes the statement; only `undal-core` executes it

`05 §4.2` says the free-tier claim is one conditional `UPDATE` against `dispatch_locks`, issued by
`undal-realtime`; `05 §2.1` and `34 §3.1` say `undal-realtime` writes no TiDB row, ever, and reaches the
database only through a service binding into Core. Both are load-bearing, so the coordination layer
resolves them the only way that keeps both: `TiDBCoordinator` takes a `SqlExecutor` port and composes the
statement, and the production executor is Core's internal surface over the binding rather than a driver
in this Worker. The atomicity the claim relies on is a property of the SQL, not of the process that
sends it — one `UPDATE` whose `affected_rows` is 1 for exactly one caller — so moving the execution one
hop changes latency, not correctness.

The consequence is honest about the number R10 must not invent. The claim now includes a binding hop
(same colo, no egress, one extra isolate) on top of the statement, so the free-path p50 stays a range
until it is measured, alongside the withdrawn 31 ms figure discussed in `05 §4.2`. What the suite can
prove without a network is the semantics: `MemorySql` implements the same conditional update and the
same unique `(order_id, seq)` index, and the 50-way claim runs against the real coordinator class, so a
regression in the statement fails the build on both backends.

## D78 — Presence is a socket at `/v1/presence`, and the mode has one name

`14 §2` specifies `wss://realtime.{domain}/v1/presence?role=…`, heartbeats as `{"t":"hb","s":n}` frames,
and the close event as the primary absence signal; `05 §4.1`'s diagram lists `/rt/presence` for
heartbeats. The specific document wins: presence is the socket, because the two-second budget depends on
the runtime's close event arriving in under 200 ms, and an HTTP heartbeat route cannot observe a dropped
connection at all. A POST reconciliation path may be added later, and if it is, it will be a second
signal rather than the transport.

The variable that selects the backend is `COORDINATION_MODE` (`05 §4.2`, `14 §3.3`, `39 §4`). The code
previously read `PRESENCE_BACKEND`, a name no document mentions; it now reads the documented name,
defaults to `sql` because that is what the platform launches on, and refuses a value it does not know
instead of silently running the other backend while the operator believes otherwise. The two-second
promise is arithmetic rather than a benchmark: 200 ms of transport plus the 1 500 ms grace is 1 700 ms,
and the grace is clamped to 1 800 ms so no configuration can push detection past 2 000 ms.


## D79 — `undal-realtime` holds the public half of the signing key, and refuses without it

`29 §2.6` gives `JWT_SIGNING_KEY` to `undal-core` alone, and `05 §4.2` has realtime authorizing a socket.
Both are honoured the same way: realtime is given `JWT_PUBLIC_KEY`, a base64url JWK holding only the public
half, and verifies Ed25519 signatures with it. Verification is the only thing the key can do, so a
compromised realtime deployment cannot mint a session for a rider it wants to dispatch to.

The `kid` is derived rather than configured — base64url of the first eight bytes of SHA-256 over the JWK's
`x` — so a rotation is a deploy of two Worker secrets and no coordination between them: core signs with the
new key, realtime accepts a key whose `kid` it can compute, and an unknown `kid` is `UNKNOWN_KEY` rather
than a signature failure, because "we have never heard of this key" and "you signed with the wrong key" are
different answers to an operator.

The route refuses with `501 jwt_public_key_missing` when the secret is absent, and that is a decision rather
than an oversight. The alternative — treating an absent key as "trust the token's claims" — would make a
misconfigured deploy an open door instead of a loud refusal, and the failure mode of a missing secret is
exactly when a deploy is least likely to be inspected. `INTERNAL_TOKEN` is the same shape: absent, the
internal surface answers `403` rather than serving presence to anybody who finds the URL.
## D80 — A ring outlives the isolate, so a broadcast is a fact rather than a coincidence

`08 §9` promises a reconnecting client the events it missed. An in-isolate ring cannot keep that promise:
Cloudflare may evict the isolate between the broadcast and the reconnect, and the client would be told its
replay is complete when the events it wanted never existed in the process it asked. So a ring lives in a
`StreamRoom` Durable Object, one per channel (`stream:order:<id>`, `stream:zone:<id>`), and the fanout
awaits a `record` for every channel before it answers.

Three details are load-bearing. The snapshot carries `evictedThrough` and `highestId` as well as the
events, because restoring only the events would reset the counters and a later replay would look complete
while silently skipping the gap. `StreamRoom` prunes to the same five-minute window the in-memory ring uses,
so a room that is woken after a quiet hour does not replay an hour. And a broadcast whose rooms are not
bound is refused with `501 rings_not_durable` — the honest answer, since a ring in one isolate is
forgotten by the next request, which is worse than an error a client can see.

Order streams are the exception, deliberately: an order's event log is already the whole truth and already
durable in TiDB (`06 §4`), so replay reads the log and the ring holds zone and admin channels. Two copies of
one order's history would eventually disagree, and the log is the one that is authoritative.

## D81 — Presence is one room per zone, and the Worker hands the room an identity it has already proved

The socket route is `/v1/presence?zone=…` and it forwards into a `ZoneHub` Durable Object addressed as
`zone:<zoneId>` (`14 §2`). Two things follow, and both were choices rather than consequences.

The room never sees a token. `undal-realtime` verifies the access token with the public JWK (`29 §2.6`),
and forwards three headers — `X-Undal-Actor`, `X-Undal-Actor-Type`, `X-Undal-Device` — which the room
believes because there is no other path into it. The headers are set on a *copy* of the request, so a
client that sends its own `X-Undal-Actor` is overwritten rather than trusted. The alternative, giving the
room the public key and letting it verify, would put the same verification in two Workers and would let a
room's misconfiguration be a security difference between routes.

A room per zone rather than one room for the platform: presence is a safety signal and the ladder runs per
zone, so one failure domain for every zone's heartbeats would be one cold start from being the reason no
rider is dispatched. The zone travels in the upgrade query and is remembered in the room's storage, because
`getByName` is not on every account tier and `state.id` on an id-addressed room is opaque. A later upgrade
with no `zone` reuses the remembered one; an upgrade with neither is `422`, and a zone the token does not
carry is `403` *before* any socket is opened, so an unauthorized zone never appears in a presence count.

The room's own refusals (`426` for a request that is not an upgrade, `401` for an upgrade with no
identity) stay rather than being duplicated in the Worker: they are reachable only through the Worker, they
describe the room's precondition, and a duplicate check is a second thing that can drift.

## D82 — The order-authorization answer comes from core, and every other channel is decided locally

`08 §9` lets a client subscribe to `order:UND-7K2M9QX4`, and whether it may is a question about three
order rows: who placed the order, which vendor cooks it, and which rider was assigned. Those rows are
`undal-core`'s (`06 §3`), and realtime is not allowed to read them — so the answer arrives through a port,
`OrderViewer`, implemented by a `POST /internal/stream/watches` call to core with the internal bearer token.

*Rejected:* giving realtime a read replica of `orders`. *Why:* a second copy of the order table is a second
answer to "who owns this order", and the copy that lags is the one deciding who sees a delivery address.

The client is fail-closed in the strongest sense the shape allows: a timeout, a non-2xx, an HTML body, an
envelope with `ok:false`, or an `allowed` that is absent all read as "no". That is not defensive
programming, it is the domain — this one answer decides whether a stranger sees an order's note, its rider
and its money, so an unsettled answer has exactly one safe reading. The timeout is 900 ms, shorter than the
client's patience, because a browser held while realtime waits on a slow core reads a silent stream as a
dead connection.

The rest of the channel table is decided locally and needs no hop. `rider:`, `vendor:` and `admin:` are
identity channels: only that actor, only under the kind their actor type owns. `zone:` is the admin map's
channel and carries every order in the zone, so admins only, and only in a zone their token names. Admins
bypass the port for `order:` as well, because `getOrder` already lets an admin read any order — a hop to be
told what the API would already have said is a hop that can only fail. Everything not in the table is
refused, including a channel kind added later by someone who did not update the table.

A deployment with no `INTERNAL_TOKEN` cannot authenticate the question, so it does not ask: `order:`
channels answer `403` and everything else works. That is the same shape as D79's missing public key —
absent configuration is a refusal somebody notices, never a silent allow.

*Rejected:* answering the watch question inside realtime from the token's claims. *Why:* a token says who
you are, not which orders are yours; the second changes with every assignment.

The `sql` coordinator's executor (D77) is the *other* thing this route is the boundary for, and it stays
unbuilt: it needs the same token and a statement-level permission that has not been designed yet. Naming it
here is deliberate so the next reader does not mistake one finished port for two.

## D83 — The push payload is data-only and signed, and its access token is cached in the isolate

`15 §2.1` fixes the payload and `15 §2.2` shows a KV-backed token cache. The payload is built exactly as
specified — `v`, `type`, `severity`, the order and vendor, `issuedAt`/`expiresAt`, `itemCount`,
`totalPaisa`, `customerArea`, `alarm`, `alarmMaxMs`, `sig`, with `android.priority: "high"`, a TTL of at
most 300 s, `collapse_key`, `direct_boot_ok` — with two additions and one deviation, all recorded here.

**The signature is hex, over the sorted map, excluding `sig` itself.** `k=v` pairs joined by a newline,
HMAC-SHA256, lowercase hex — the same construction `11 §3` uses for other signed payloads. Sorting is not
cosmetic: JSON object order is not preserved across every runtime the platform touches, so a signature over
the serialised JSON would verify on the Worker and fail on a device built by a different Kotlin compiler.
Excluding `sig` lets the map be signed once and the signature inserted, which is why `signatureOf` is a
pure function of the map.

**Every data value is a string, and money is integer paisa.** FCM's client map is `Map<String, String>`;
a number that arrives as a number is an integer on one platform and a double on another, and ৳549.00 as a
double is 54900.0000000001 paisa by the time it is formatted. `totalPaisa` crosses as `"54900"` and the
client formats it.

**Attempts are numbered.** The ladder sends a second push at 10 s and a third at 25 s (`14 §4.1`), and they
replace rather than stack via `collapse_key`. Each carries `attempt: "2"` / `"3"` so the device can tell
which one it is ringing for, and the evidence block (`presence/evidence.ts`) records the message ids.

*Deviation:* the access token is cached **in the isolate**, not in KV. A token lives an hour; a KV read per
alarm would be a paid request per push for a value that changes twelve times a day per isolate, and a cold
isolate can mint a new one in a WebCrypto signature plus one HTTPS round trip. Refresh is single-flight, so
the first alarm of a busy minute mints one token rather than twenty, and a failed mint is not inherited by
the next caller. The cache object is per `createTokenSource` call, so two isolates each hold their own —
which is correct, because a token is cheap and a shared one would need a shared store.

The sender is the only module that may POST to FCM, and it addresses `https://fcm.googleapis.com/v1/…`
from a constant rather than a caller-supplied URL. Failures are classified, not retried blindly:
`UNREGISTERED`/`NOT_FOUND` means delete the token (and, if it was the device's last, raise an exception),
`SENDER_ID_MISMATCH` means a build pointing at the wrong project, `QUOTA_EXCEEDED` backs off, and
everything else gets three attempts at 250/750/2 000 ms. A deployment with only one of the two secrets is
refused at construction (`fcmFrom`), because a service account with no signing key would send payloads every
device discards while the platform recorded a successful delivery.

*Open:* the ladder that calls this module (`presence/escalation.ts` decides *what* is due) still has no
scheduler storing ladder state across isolates, and `fcm_dispatches` (`15 §8`) has no table. Both are the
next rung, not omissions of this one.

## D84 — The two-minute ladder is one Durable Object per order, and its last rung is a request

`14 §4.1` is a schedule: a probe at 8 s, unreachable and a second push at 10 s, a third at 25 s, the backup
contact at 45 s, an exception at 60 s, an early-out offer to the customer at 90 s, and cancellation at 120 s.
The schedule was already a table (`presence/escalation.ts`). What it had was nowhere to live.

It lives in `VendorAlarm`, one Durable Object per order (`VENDOR_ALARM`, migration v5), under one storage
key. That answers three questions a `setTimeout` cannot. *Does it survive the process that published it?*
Yes — an order published at 12:00:03 is still being escalated at 12:02:03 if the isolate that published it
was evicted, which is precisely the case a cold start would otherwise forgive. *What wakes it?* One alarm,
armed at the next unfired rung and re-armed after every run, so nine instants cost one alarm rather than
nine timers. *What if the alarm is late?* It fires everything it owes in table order, once, because the rungs
are marked in the record rather than inferred from the wake-up.

`begin` sends the first push and marks `PUBLISH` fired, because the ladder's 8-second probe assumes the alarm
started at publication. Each push rung carries its `attempt` (`2`, `3`), and all of them collapse onto
`order_<id>` so the third replaces the second rather than stacking on a lock screen.

The last rung is a **request, not a write**. `POST /internal/orders/auto-cancel` is answered by core, which
owns `orders.state`: the `PLACED → AUTO_CANCELLED` edge exists as a `SYSTEM` transition with the
`vendorUnreachable` guard, so a ladder that fires early is refused by the same table that refuses an illegal
customer cancel, and the `WHERE state = 'PLACED'` on the update means a vendor who accepts mid-flight wins
(`raced`). The audit row names `SYSTEM`, carries no user, and records the elapsed time — the one cancellation
nobody clicked is the one the trail has to explain. `moveState` now takes `actorUserId: Uint8Array | null`,
because `order_state_events.actor_user_id` is nullable and a `SYSTEM` actor has no user to name.

Two refusals are honest rather than fatal, and the evidence block records both. A room with no push sender
refuses `begin` (`501 push_not_configured`), because a ladder nobody can ring is worse than no ladder. A room
with no canceller still runs to 120 s and records `canceller_not_configured`, raising the operator's
exception instead of claiming a cancellation that never happened.

Two events the ladder publishes were missing from the stream's name map — `vendor.unreachable` and
`admin.exception_raised`. `StreamHub.record` gates on that map, so a component naming its own catalogue event
was having it silently dropped; they are in the map now (`08 §9.1`). The cancellation is published from the
room as `order.cancelled` in this version, because core did not yet broadcast its own transitions — D85
supersedes that line and the room no longer publishes what core writes.

*Open:* `fcm_dispatches` (`15 §8`) still has no table, so a send's message id lives in the ladder's record
rather than in the platform's evidence table.

## D85 — A transition announces itself, and the announcement can never undo the transition

Core wrote every order transition to a row and answered the caller. Nothing told the watchers, so the SSE
stream had nothing in it and the customer's screen learned about an acceptance by polling. `bindings/
announce.ts` is now called from the four places an order moves — placement, accept, reject, pickup, and the
ladder's auto-cancel — and each call is one line plus a payload.

Three rules make it safe to call from inside a transaction's aftermath.

**It never throws.** `createRealtimeClient` returns a `Result`; `announce` discards it. An order that moved is
a fact whether or not a socket heard about it, and a platform that failed a placement because its notification
path was cold would be losing money to its own broadcast. The suite asserts this against a 502, a thrown
transport and an unconfigured deployment.

**It never blocks the response.** The call is handed to `ctx.waitUntil`, which is no longer faked: `index.ts`
now passes the runtime's `ExecutionContext` through, so the promise outlives the response instead of racing
the isolate's teardown. That was a real defect in the pipeline before this change — `waitUntil` was
`() => undefined`, which silently turned "schedule this" into "start this and hope".

**It says nothing when it is not configured.** No `REALTIME_BASE` or no `INTERNAL_TOKEN` is a deployment that
has not wired the stream. That is not an error and not a warning on every order; the client degrades to a poll,
which is exactly what the platform did before.

The payload is the catalogue name, the order code, the new state and the log sequence. The sequence matters:
a stream that reconnects with `Last-Event-ID` and a stream that is live must agree on the order of frames, and
the only number both can agree on is the one the log wrote.

This removes the duplication D84 recorded. The ladder used to publish `order.cancelled` from the room, because
nothing else did; core announces its own auto-cancel now, so the room's line is gone and one transition
produces one frame.

## D86 — The push log exists, and only core writes it

`15 §8` closes the delivery loop: send → `fcm_dispatches(message_id, token, sent_at)` → the device's
`alarm_received` → the gap between them. The table did not exist, so a send's message id lived in the ladder's
Durable Object and the admin panel's "device matrix" had nothing to be built from.

`014_fcm_dispatches.sql` adds it: `order_id` and `device_id` nullable and `ON DELETE SET NULL`, `fcm_token`,
`attempt`, `outcome`, a nullable `message_id` and `received_at`, and three indexes — one order's attempts, one
token's record, and the receipt sweep. The nullable subject is the point: a dispatch outlives the order it
announced, because "was this vendor's phone reachable last week" is a question asked after the order is gone.

*Rejected:* letting realtime write the table. *Why:* `05 §2.1` forbids it TiDB writes, and the reason it does
is that the only way this Worker would write is with a database credential, which would put a second writer on
the order tables' neighbourhood to save one HTTP call.

So the room reports and core records (`POST /internal/fcm/dispatches`, internal token, a batch of at most
twenty). One call per rung rather than one per phone, because a rung rings every device at once. The route is
not in the path of any decision: nothing reads these rows to decide whether an order moves, so a lost row
cannot hold an order hostage — and the recorder on the realtime side returns `false` and is ignored rather
than throwing, because a delivery log that can fail an alarm silences the thing it is auditing.

The batch is audited **once** at `INFO`, naming the order, the attempts and the sent/failed split. Per-device
audit rows would add tens of thousands a day to a hash-linked chain the admin panel reads end to end, and the
per-device detail already exists — in `fcm_dispatches`.

An unknown order code and an unregistered token both still write a row, with `NULL` in the column that would
have named them. A send that happened is a send that happened; a log that dropped it for want of a foreign key
would be a log with a hole exactly where the interesting case is.

The receipt half of the loop is D87 — at the time this was written nothing filled `received_at`.

One finding, recorded rather than fixed. `scripts/db/expected.py` only reads backticked column names, so
twenty-eight tables parse as zero columns — `orders`, `users`, `devices`, `refresh_tokens` and now
`fcm_dispatches` among them. The generated `db/expected.json` is still the file `verify_schema.py` compares a
live database against, which means for those tables it compares nothing. The regeneration is committed here
because CI regenerates and diffs it; the generator is a change of its own, and this note exists so the gap is
a known one rather than a check that appears to pass.

## D87 — The receipt arrives on the socket, and the device is the session's, never the frame's

`15 §8` closes the delivery loop with the device's acknowledgement. There is exactly one place that can
arrive: the presence socket, because the app does not call the API to say its alarm rang — the alarm is
answered on a lock screen with no app in the foreground.

So `ZoneHub` learned a second frame. `{"t":"alarm_received","orderId":…}` is no longer `not_a_heartbeat`;
the room looks up the session that owns the socket and reports `(orderCode, deviceId, receivedAtMs)` to
`POST /internal/fcm/receipts`, which fills `received_at` on the **latest unacknowledged** dispatch for that order
and device. Anything else on the socket is still refused by name, so a client bug stays a message.

**The device comes from the session, not the frame.** A payload that could name its own device could claim a
delivery for a phone that never rang, and a delivery matrix built from self-reported identity would flatter
exactly the broken phones it exists to find. The order does come from the frame: it is a fact about what rang,
not about who is asking.

A receipt is **not presence evidence**, and there is a test for it. A device can hear an alarm a second after
its socket went quiet — that is the entire reason the alarm exists — so acknowledging a push must not move a
heartbeat deadline or cancel an absence. The two frames answer different questions on the same socket.

Two smaller decisions. The match is against the newest unacknowledged row, because an alarm rings three times
and the receipt is for the one the device heard; and `received_at IS NULL` in the update makes a repeated frame
a no-op rather than a second receipt. A receipt that matches nothing — an order deleted since, a device whose
tokens were rotated — answers `recorded: 0` and writes no audit row: the alarm already rang, and a log entry
about a row that was not there is noise.

*Open:* closed by D88, which stores the two fields the client sends beside the receipt.

## D88 — The device's own measurement is stored beside the receipt, never above it

`15 §8` draws the loop with two numbers in it. The platform can see one of them: `sent_at` from the Worker
that rang, `received_at` from the socket's clock when the `alarm_received` frame arrived, and the gap between
them is the send-to-received latency the device matrix ranks OEMs by. The device sees the other: how long its
own radio took to wake, and which path reached it first. D87 validated those two fields and dropped them,
because storing them needed a decision about what they are.

They are evidence about the device, so they are stored under names that say so — `device_latency_ms` and
`device_path` (`015`) — and the platform's own gap keeps the authority. This matters because a slow phone
often reports a *fast* number: an OEM whose push handler runs before the radio's power state settles measures
from the process waking, not from the message arriving, and a matrix built on that self-report would clear the
exact devices the alarm exists to catch. The median the panel charts is `received_at − sent_at`; the device's
number sits beside it so support can show a vendor "your phone says 400 ms and ours says 9 seconds" instead of
arguing.

Filtering happens once, in core (`receiptDetails`), and it drops rather than refuses. A latency that is not a
finite number, is negative, or exceeds ten minutes loses the number and keeps the receipt; a path outside the
closed set `FCM | SOCKET | BOTH` is not stored, so a client that invents a channel cannot enter one into the
matrix. Refusing the frame would punish the delivery record for a bug in the measurement, and the delivery
record is the half that cannot be reconstructed. Realtime forwards both fields as the device made them,
bounded only so a frame cannot carry a paragraph where a measurement belongs: the room is a pipe, and the
closed set lives at the writer.

The two columns land in the same `UPDATE` as `received_at`. A second statement would leave a window in which a
row is stamped by one caller and measured by another, and `received_at IS NULL` is what makes a repeated frame
a no-op — that guarantee only covers writes inside the statement it guards.

Both columns are null for a client that predates this decision, and the matrix treats null as "not reported"
rather than zero, because a device that says nothing and a device that says 0 ms are different facts.

## D89 — A beat is a frame; a stamp is a write

The `sql` coordinator wrote the presence row on every heartbeat. The arithmetic that makes that wrong is
short: `14 §3.1` asks for a beat every 750 ms, an eight-hour shift is 38 400 beats, and the old `heartbeat`
did a `list` to find the row and a `put` to refresh it — 76 800 store operations per device per shift, to
record a fact the process holding the socket already knows. The same arithmetic kills the store D77 named:
Workers KV's free tier is 1 000 writes, 1 000 reads and 1 000 lists a day, so one vendor's morning would
exhaust the allowance before the lunch rush. The free path's presence store is therefore the TiDB the
executor reaches, which is also what `14 §2` and `14 §3.3` have always said; D77's "key-value store behind a
lease" is corrected here.

What replaces the per-beat write is a stamp and a memo. The memo is per isolate, holds the row's key, the
session as last written and the instant it was written, and it means a beat inside the window costs nothing
at all: no read (the memo holds the value), no list (the key is known), no write. The window is 15 s, so a
shift costs one write per 15 s of beating. A *negative* memo — the device is not present — expires on the
same window rather than being remembered forever, because a beat can arrive before the `declarePresence`
that follows the upgrade, and a device must not be invisible because two frames raced.

The cost is paid in freshness, and it is paid openly. A stamped row is up to one window behind the device
it describes, so a reader that compares `lastHeartbeatMs` against the two-second deadline would call a
beating device gone. The width of "online" is therefore a property of the backend, `presenceWindowMs` —
17 s for stamped rows, 2 s for the Durable Object, which does write on every beat — and `/internal/presence`
asks the coordinator instead of hard-coding either. The two-second deadline is untouched: it is enforced by
the process that holds the socket, and the ack still returns `now + 2 000`.

Listings are not filtered. A row disappears when the escalation that watched the socket go quiet calls
`markAbsent`, never by being quietly omitted from a list, because a row that vanishes is indistinguishable
from a device that never connected and the two deserve different answers. So `listPresence` returns what the
store holds and the readers judge: `/internal/presence` answers `online` by the window and still reports
`lastSeenAt` from the row it found.

*Open:* the store itself is still the test's `MemoryStore`. `presence_sessions` as a table, and the executor
that lets core write it, are the next rung — this one fixes the write pattern so that rung has a budget to
fit inside.

## D90 — The free path's statement travels as a name, and core is the only hand on the database

D77 left the `sql` backend unbuildable: `coordinatorFrom` returned `coordinator_not_configured` because the
`SqlExecutor` port needed core's internal surface and there was none. This rung builds it, and the shape it
takes is the decision.

**A name crosses the boundary, never SQL.** `undal-realtime` composes a statement — `CLAIM_SQL`, `state_put`,
whichever a situation calls for — and the executor turns that text into a catalogue name before anything
leaves the Worker; core looks the name up and runs *that* statement. The catalogue lives in
`@undal/contracts`, so there is exactly one spelling of `claim_lock` in the platform, `statementFor` proves
the coordinator's constant is that spelling, and a statement a caller invented cannot be sent at all: it has
no name. The alternative — a route that accepts SQL text from a sibling Worker — would be a database proxy
inside the trust boundary, which is the specific thing `05 §2.1` exists to prevent.

**Thirteen statements, thirteen fixed spellings.** Locks (`open_lock`, `claim_lock`, `release_lock`,
`lock_holder`), the order log (`next_seq`, `insert_event`, `read_events`), a liveness read (`ping`), and the
coordinator's state (`state_get`, `state_put`, `state_delete`, `state_list`). No table, column, ordering or
limit is caller-chosen; parameters are strings, finite numbers and `null`, and a boolean or an object is
refused rather than coerced, because a driver that quietly turned `true` into `1` is how a lock comes back
held by nobody. Reads answer `{rows, truncated}` and writes answer `{affectedRows}` — the kind is the
catalogue's, not a sniff of the SQL.

**The executor throws.** A claim that answered `affectedRows: 0` because core was unreachable is
indistinguishable from a claim another rider won, and the coordinator would tell a rider the offer was taken
when it was never offered. Timeouts abort the request and reject: 900 ms, the same budget the other
authority calls carry.

**The state the coordinator keeps is a table, not a product.** `coordination_state` (`016`) is a key, an
opaque JSON value and an expiry. D77 named Workers KV and D89 retired it: 1 000 writes a day is one vendor's
morning. The store validates its own keys — no `%`, no `_`, at most 191 characters — because the listing is a
`LIKE` prefix and a key carrying a pattern character would turn a zone's presence into every zone's. Expiry is
an absolute instant computed on the caller's clock, so a row stops being read as present at the moment the
coordinator that wrote it said it would.

**The route is exempt from the audit rule, on the record.** It writes lock rows, order events and coordinator
state, and every one of those is the effect of a decision made in the coordinator or in core's order routes,
where the audit row already lives. An audit row per statement would be a trace of SQL rather than of
decisions, and on the claim path it would put fifty racing riders behind one hash-linked chain for a row that
exists to be contended. The exemption is a marker the rule accepts — `audit-exempt:` with a reason of at
least sixteen characters — so it is an argument a reviewer reads, and the rule still rejects a bare one.

With this, `COORDINATION_MODE=sql` builds when `CORE_BASE_URL` and `INTERNAL_TOKEN` are present, and refuses
by name when one is missing. What has *not* been measured is the number R10 gates on: presence p95 on the
`sql` backend. The binding hop is now real, so the next rung can take that measurement instead of estimating
it.

*Open:* closed by D92, which pages the listing by key instead of stopping at the first 500 rows.

## D91 — The two seconds include the database, so the largest grace is smaller than it was

The two-second promise was arithmetic with two terms: 200 ms for the transport to notice a dead socket, and
1 500 ms of reconnect grace. That was true while the absence lived in a Durable Object's memory — the room
knew, immediately, and writing it down was someone else's problem. D90 made it false: on the free path a
publication costs a row written through core and a row read back, each with a service binding in between,
and a promise whose arithmetic does not mention its own database is a promise nobody is keeping.

So the budget has three terms. `PRESENCE_STORE_OP_MS` is 50 — same colo, one indexed statement, one binding
hop — and a publication costs two of them, 100 ms in total: the marking write, and the read that proves the
device is gone from the list. The default grace stays 1 500 ms and the worst case becomes 1 800 ms, inside
the two seconds with 200 ms spare.

The consequence is in `MAX_PRESENCE_GRACE_MS`, which was 1 800 and is now 1 700, derived as
`MAX_DETECTION_MS − TRANSPORT_CLOSE_BUDGET_MS − PRESENCE_STORE_BUDGET_MS`. An operator configuring the top of
the range now gets a worst case of exactly 2 000 ms rather than one that quietly exceeds it by 100 ms. This
is the whole reason the number is a constant and not a configuration default: a range limit that admits a
grace the platform cannot afford is a range limit that documents a promise it does not keep.

Two smaller things. `50 ms` is a *budget*, not a measurement, and it is stated as one — the honest claim is
"two store operations may cost this much", not "we measured 50 ms", because the measurement needs a deployed
`sql` coordinator and a real TiDB, neither of which a test suite has. And the thousand-loss latency test now
adds the store's allowance to every measured loss, so the p95 it asserts is the one the platform promises
rather than the one its two in-memory terms happen to produce.

*Open:* the wall-clock version of this number — p95 across a thousand real losses against a deployed free
path — is a load test, not a unit test, and is still not run. What this rung fixes is that the arithmetic the
load test would be checked against now includes the thing it is measuring.

## D92 — A listing of a zone finishes, or it says it did not

D90 shipped `state_list` with a `LIMIT 500` and called the truncation open. It was worse than untidy: the
listing is how a zone's presence is read, and a zone entering a busy Friday evening would have had its
sessions listed up to five hundred and no further — a dispatch decision made on half the fleet, with nothing
in the answer to say so.

The fix is keyset pagination, and the choice between that and `OFFSET` is the whole decision. Rows are being
written and deleted while the listing runs, so an offset counts rows that may have moved: a rider who
reconnects between two pages shifts every later row by one and the listing either repeats a device or skips
one. A keyset cursor is the last key returned, `state_key > ?` is immune to that, and `ORDER BY state_key` is
already the table's primary key, so the page boundary is an index range rather than a sort.

Paging stops at `MAX_STATE_PAGES = 20`, ten thousand rows. What happens there is the second decision: it
throws. A caller that asked for a zone's sessions and got a partial list would act on half a fleet without
knowing; a caller that gets a `RangeError` knows exactly what it has. Ten thousand sessions in one zone is
far past anything this platform is designed for, so the ceiling is a bug detector rather than a capacity
limit — and if a zone ever legitimately reaches it, the answer is a per-zone count or a role-filtered listing,
not a longer read.

`state_list`'s parameters therefore changed to `(prefix, after, now, limit)`; the `after` term is `''` on the
first page, which sorts before every key this platform writes because no key starts with a control character.
Nothing else about the store changed, which is the point of having kept the port.

## D93 — The ladder was complete and unreachable, so placement now starts it

D84 built the vendor ladder and D87 closed its delivery loop. Nothing called it. `VendorAlarm` could walk
three rungs, ring every device, receive its own receipt and cancel at 120 s, and a placed order never touched
it — so the sequence existed and the first sentence did not. A placement now ends by ringing the vendor.

**Three facts, three tables, one module.** The ring needs the vendor's owner (`vendors.owner_user_id`), the
live tokens that owner's devices registered (`device_tokens` joined `devices`, `valid = 1`, newest first,
capped at five) and the area to show (`addresses.area`, reached through `orders.delivery_address_id`). They
live together in `repositories/recipients.ts` because they answer one question — whose phone should ring, and
what should it say — and a caller assembling a notification from three repositories would eventually assemble
it slightly differently from the next caller. Staff do not exist yet; when they do, this is the one place that
learns about them.

**The order does not wait for the ring, and the ring does not stay quiet.** Placement is a money event: it
writes rows and answers `201`, so the ring is handed to `waitUntil` and a cold room adds nothing to the
customer's receipt. But D85's rule for announcements — a failure is a degraded poll, so say nothing — does not
transfer. A missed broadcast means a screen refetches; a missed ring means the vendor never learns, the ladder
never starts, and the customer waits two minutes for a cancellation nobody chose. So a ring that could not
happen is an audit row at `WARNING`, `ladder.unrung`, with the reason it did not: `no_device` when the vendor
has no registered phone, `begin_refused` when realtime would not start the ladder. Both are the platform
failing to reach somebody, and neither is allowed to be silent.

**What the push says is what the order knows.** `CRITICAL`, `alarm: loop`, twenty seconds per ring so the
second attempt is audible over the first, and an expiry equal to the ladder's own 120 s — a push that outlives
the ladder would ring a phone for an order the platform already cancelled. The total crosses as paisa because
the client formats it, the short code is the part a person reads out (`UND-7K2M9QX4` → `7K2M9QX4`), and
`attempt` is absent because each rung numbers its own. `customerArea` is the address's area, trimmed, or the
empty string when the customer pinned a map point and typed nothing: the field is always present so a client
never has to handle absence, and an empty one is honest in a way a guess is not.

*Open:* closed by D94, which places a real order through the real route with a stream configured and asserts
that the ring happened — and that it fails when the call site is deleted.

## D94 — The call site has a test that fails when it is deleted

D93 wired the ring into placement and recorded the one thing it could not claim honestly: the call was a
single line, everything around it was tested, and no test would fail if someone removed that line. A mitigation
was named — the `ladder.unrung` audit row — but a mitigation is not coverage. This rung is the coverage.

The test places an order the way a client does: it asks the real quote endpoint for a token, places against it
through the real placement route, with `REALTIME_BASE` and `INTERNAL_TOKEN` configured and a fetch stub in
place of the network. The route hands its background work to `waitUntil`; the harness now collects those
promises instead of discarding them, so the test waits for the ring the route actually started rather than for
a sleep that hopes it did. It then asserts the begin went to `/internal/ladder/begin` with the order's code,
the vendor's two registered tokens, `CRITICAL`, the customer's area from `addresses.area`, and an expiry
exactly 120 s after the issue — the ladder's own window.

Two more cases, both about the failure being visible rather than quiet. A vendor whose owner has registered no
device produces **no** begin and an audit row containing `ladder.unrung` and `no_device`. A deployment with no
stream configured places the order, hands nothing to `waitUntil`, and calls no transport at all — the same
"unconfigured is not broken" rule the announcement follows, asserted rather than assumed.

The harness needed one change to make any of this possible: the placement tests now answer the three reads the
ring performs — `vendors.owner_user_id`, the owner's live `device_tokens`, and the order's
`delivery_address_id` — which is what "teach the harness the recipient queries" turned out to mean. They are
matched before the generic vendor handler, so the order's own vendor lookup still sees the vendor row it
expects.

And the claim was checked the only way that makes it a claim: commenting out the `ringVendor` call fails two
of the three tests, re-enabling it passes all ten. A test that would not notice the feature's absence is a test
that documents a hope.

## D95 — A position is a claim by a phone, and the gate says which claims it believes

R11 starts where `07 §4.5` left a table and no code: the rules that decide whether a fix may land in D1 at
all. `workers/realtime/src/d1/ingest.ts` now implements them, and the decisions that are not in the table are
the ones worth recording.

**A mock flag is a batch decision, not a fix decision.** One fix carrying the OS's mock flag rejects the whole
upload and sets `suspendShift`. The tempting alternative — store the nine honest fixes, drop the spoofed one —
produces a device that is *partly* trustworthy, and the platform has no way to say which part. A rider whose
phone is mocking its location is either testing the platform or defeating it, and both deserve a human before
the next order.

**Refusals are named, because the names are different stories.** `poor_accuracy` is a phone under a bridge and
costs nothing. `implausible_speed` is a tower fix, a tunnel exit, a spoof or a teleport; it increments
`teleports` so the caller can add it to the rider's `teleport_count`, which is what puts a rider in front a
reviewer. `outside_zone` sets `raiseException`, because a position twenty kilometres outside its bounding box
is not a data-quality problem, it is a rider who is somewhere nobody expects. A single "dropped" counter would
make all three invisible at once.

**A refused fix does not move the baseline.** Speed is measured against the last *accepted* fix, so a rejected
teleport cannot manufacture a second rejection from the good fix that follows it — the failure mode that makes
a rider's trail stop updating for a minute after one bad point under a flyover.

**Order of the checks is the order of the reasoning.** Mock, then accuracy (an inaccurate fix is evidence about
nothing), then the clocks (a time that cannot be trusted makes a speed meaningless), then ordering, then
speed, then the zone — the only check about *where* rather than *when*.

**One thing the table could not answer.** A backfill carries fixes older than the newest stored one: a rider
who came out of a tunnel. For those, the fix that precedes them in time has already been pruned by the ring
buffer, so no speed can be computed; the gate stores them without a speed verdict rather than refusing them
over a division by a negative interval. The alternative — refusing backfills outright — would throw away the
exact fixes a tunnel produces.

Nothing here writes. `teleport_count`, the exception row and the shift suspension are the caller's writes, and
that is deliberate: the gate decides what the platform believes, and the write path decides what to say about
it.

*Open:* the cadence gate above this (`07 §3.2`, `shouldSend`) and the write budget (`07 §4.2`) are not built;
this rung is the plausibility half of the edge contract, and the two halves share a caller that does not exist
yet.

## D96 — The device decides what is worth sending, and the budget is a test rather than a table

`07 §3.2` gave six rules as Kotlin and `§8.1` gave a write budget as a table. D95 built the server's half of the
edge contract; this is the device's half, in `workers/realtime/src/d1/cadence.ts`, with the budget checked by
simulation instead of re-asserted.

**The profile follows the situation, not the speedometer.** A rider carrying food a hundred metres from the door
is judged by `CARRYING_NEAR` (60 m, 6 s, 25 s) even if they are stopped at a light, because the row is about
what the customer is watching. That is why `phaseFor` takes what the *server* told the device — carrying, on
break, distance to drop — and not the rider's own notion of "moving".

**The battery multiplier lives inside `cadenceFor`.** A caller cannot ask for a profile and get the one belonging
to a phone plugged into a charger: `cadenceFor(phase, batteryPct)` is the only way to get a profile, and 15% and
8% widen every threshold by 1.5 and 2.5. A rider on break is `displacementM: null` rather than an enormous
number, because "never on movement" and "somewhere past a hundred kilometres" are different statements and only
one of them survives a multiplier.

**A turn counts at walking pace.** `07 §3.2` sends on a 45° bearing change once the rider has moved 30 m, which
is what stops a corner looking like a teleport at 1 Hz. Bearing deltas are the shortest way round the compass —
350° to 10° is 20°, not 340° — which is the kind of arithmetic that is invisible until a rider turns left at a
roundabout and the marker spins.

**The budget is now a test.** §8.1 claims 54 writes for a 3.8 km delivery; the suite drives a synthetic rider
along those legs at the documented speeds, offering a fix every second, and the gate allows **53** — one opening
fix, 40 by displacement, 12 by ceiling. A five-minute idle street draws **two** (the opening fix and one
heartbeat), and 6% battery draws fewer on the same leg than 80% does. The number in the document is now an
output of code that could contradict it.

*Open:* the profile is not yet pushed from the server — nothing builds `CadenceProfile` into the shift-start
response or the SSE state change, so `cadenceFor` is called with constants today. The Kotlin port does not exist
either; this module is the specification the port must match.

## D97 — The route where the two halves of the edge contract meet, and the four things it refuses

D95 judged batches that nothing sent; D96 chose fixes that nothing carried. `POST /rt/location/batch` is the
caller: `d1/batch.ts` decodes the delta-encoded flush (`07 §4.2`), `d1/ingest.ts` judges it, `d1/store.ts`
writes the survivors into the ring and the current row, and the response carries the next cadence — the push
`§3.3` describes, delivered in the round trip that already happened.

**The device owns `seq`, and the counter advances per position *offered*.** The ring is a modular counter
(`§5`), and only the phone knows how many fixes it produced across a dead network. A refused fix still consumed
a slot on the device, so the server advances the counter for every position in the batch and drops the ones it
cannot store. The alternative — advancing only for accepted fixes — drifts the two counters apart for the rest
of the shift, and a trail that reassembles by `recorded_at` hides the drift until the day it does not.

**Four refusals, each with a different sentence.** A batch past 2 048 bytes or twelve positions is refused
whole rather than truncated, because half a trail is a marker that jumps — worse than a client that learns its
upload failed and retries. A malformed delta names the rule it broke. A rider with no current row is
`SHIFT_NOT_OPEN`, not a 404: the phone has a shift, the server does not have it open. And a batch whose
`shiftId` disagrees with the shift on file is refused, because a queue flushing after an ended shift must not
write into the next one — the failure mode is one rider's breadcrumbs appearing under another rider's shift at
6 a.m.

**The response is where the cadence is pushed.** `phaseFor` + `cadenceFor` run against the rider's state after
the batch, so a rider who has just started carrying food gets `CARRYING_FAR` back immediately. `stale_after` in
`rider_current` is computed from the same profile (`receivedAt + 2 × ceiling`), which is what makes "the marker
goes grey" a property of the current row rather than of a constant somewhere in a dashboard.

**What this route does not do, stated because it matters.** It does not check the zone's bounding box: realtime
can read a rider's zone *id* from D1 but not the zone's shape, so `IngestContext.zone` is now nullable and the
route passes `null`. A position twenty kilometres outside the city is caught by nothing until `undal-core`
puts the box on the shift. It does not audit: a breadcrumb is precisely what `§6` promises not to keep, so a
suspension is answered to the device and recorded nowhere — the operator visibility that needs is a core
exception, and that is the next rung's problem.

*Open:* the zone box (above); the erasure path (`§6`: end shift, go offline, presence-declared offline) deletes
rows nothing writes yet, so it is still unbuilt; `/rt/shift/end` and `/rt/shift/start` do not exist, which is
why the route learns a rider's vehicle and zone from `rider_current` instead of from the shift request.

## D98 — Erasure got a caller, and the doors are different doors

`07 §6` promised immediate deletion and had two SQL statements with nothing to run them. D97 made a rider's
breadcrumbs exist; this makes them disappear.

**Two doors, because there are two kinds of caller.** `POST /rt/location/erase` is authenticated by the rider's
own token and erases that token's `sub` — there is no rider id in the body, so an app cannot erase a colleague
by guessing one. It is deliberately not named `/rt/shift/end`: ending a shift is core's business, and a route
here with that name would imply realtime owns the shift record. It says "my live location, now".
`POST /internal/erase` is core's, naming the rider, for an admin force-end or a sweep that noticed a device
stopped existing.

**Erasure is idempotent, and that is a privacy property rather than a convenience.** A shift end, a presence
timeout and an admin force-end can all fire within a second of each other. The second caller gets `200` with
zeros. A `404` would tell a caller the trail is still there when it is not — and a client that believes that is
a client that retries, or worse, a client that gives up.

**It answers with counts.** `{positions: 37, current: 1}` is a claim an operator can check against the ring's
bound of 120; `{ok: true}` is a claim that cannot be audited. The counts come from D1's own `meta.changes` per
statement, not from a preceding `SELECT`.

**The bug the tests found was mine, and it was the worst kind.** `checkInternalToken` is asynchronous and
answers a result object; I wrote `if (!authorised)` on the promise, which is a permanent `true` — an internal
erasure endpoint open to anybody who could reach it, with a test suite that would have passed had I not written
the "no internal token configured" case. It now awaits and checks `.ok`, and the route carries a comment saying
why the bare form must never come back.

**What it did not do yet** — the presence trigger, closed by D99 below.

*Open:* `/rt/location/batch` still learns a rider's zone and vehicle from `rider_current` because no shift-start
route exists to tell it.

## D99 — The trigger nobody presses, wired to the thing that must happen within five seconds

`§6.1` lists five erasure triggers. D98 built the doors for four of them — a rider pressing end shift or go
offline, an operator forcing one, and the sweep for a device that stopped existing. The fifth is the one the
promise is really about: *the presence engine declares the rider offline*, because a phone that died in a tunnel
cannot ask to be forgotten.

**The hook already existed and had no consequences.** `PresenceHub` publishes an absence at its alarm and calls
`onPublished`, which nothing supplied. It does now: `absenceEraser` (`d1/on-absence.ts`) is passed by
`ZoneHub`, over the room's own `RIDER_DB`. The hub's comment said "the hub reports; whoever owns those effects
decides" — this is the first effect the room owns outright, because the live channel is the room's territory
and reassignment is not.

**Erasure happens at publication, not on a later sweep.** D91 already spends up to two seconds proving the
device is silent; a second scheduled job that erased "shortly after" would add a window with no owner. Deleting
in the same breath makes the five-second promise a property of the alarm's latency, which is the only part of
the path that is measurable.

**A failed erasure does not fail the absence.** The ledger has already been swept and the coordinator told;
throwing would abort the alarm and delay every other absence in the zone. The failure is reported to a callback
that logs it, and the ring is overwritten by the next shift's first flush anyway — a stale trail is a wrong
answer to "where is my rider", not a permanent one. The asymmetry is deliberate: refusing to publish would leave
a rider marked present forever, which is worse than a trail that outlives them by one shift.

**It does not ask what kind of actor was absent.** The id is the key and a customer's id has no rows in D1, so
the deletion is a no-op that costs one batched statement. Branching on the role would make erasure depend on a
field that a future vendor live-tracking feature would have to remember to add to — and the failure mode of
forgetting is a trail that never gets erased.

Tests: the module's six cases (each reason, idempotence, no binding, a failure with and without a reporter) and
four at the room: a silent socket erases at the alarm that publishes it, a deliberate goodbye erases too, a room
that never connected erases nothing, and a deployment without a binding still publishes.

*Open:* `/rt/location/batch` still learns a rider's zone and vehicle from `rider_current` because no
shift-start route exists to tell it; and the 60-second housekeeping sweep (`§6.1`'s last row) still needs a
listener that notices a token is invalid.

## D100 — The replay window cannot say "you missed nothing" about history it does not have

`EventRing` had two holes, both in the one part of the SSE surface a customer can feel: the resumption after a
dropped connection.

**A cursor the ring has never reached was answered `complete: true`.** `since(150)` on a fresh ring returned no
events and "nothing was missed". That happens for three ordinary reasons — a new isolate, an evicted room, a
missing snapshot — and all three mean the frames the client is quoting went somewhere this channel cannot see.
The client then showed a stale order as if it were live, which is exactly the failure the ring's own doc comment
says must never happen. A fresh ring now answers `complete: false` for any cursor above its `highestId`; a
cursor at zero is still complete, because nothing was promised. `EventRing.restore(undefined)` inherits the
same rule, which is the case the `restore` doc comment was already worried about.

**A frame could arrive after a higher-numbered one.** Two requests for the same order can be in flight at once,
and the one carrying the later sequence can reach the room first. `push` appended it, which broke the two
invariants every reader relies on: `since` returns events in id order, and `trim` evicts oldest-id first. A late
frame is now inserted where its id belongs, and `trim` filters by age rather than shifting the front, so a late
event carrying an old timestamp does not linger until the front overtakes it on a quiet channel. The live socket
that already received the higher id cannot be repaired after the fact — that is the broadcaster's ordering
problem, not the ring's — but the replay window can, and the replay window is what a reconnecting client
depends on.

**One existing expectation changed and it was wrong.** `store.test.ts` asserted that a resume at cursor 5 of a
channel that never spoke is `complete: true`. That test encoded the bug. It now asserts `false` for cursor 5 and
`true` for cursor 0, with the reason written beside it.

Tests: `sse-ring-order.test.ts` (11 cases: unseen cursors, restore with and without a snapshot, late ids,
duplicate ids, oldest-id eviction, age trimming of a late event, evicted cursors) plus the amended store cases.

*Open:* the live broadcast path still has no ordering guarantee across isolates — a socket can receive frames
out of sequence even though its reconnect will be exact. Fixing that needs the broadcaster to sequence per
order, which is core's `announce()` and a separate decision.

## D101 — A sequence belongs to the channel that owns it

D100 made the ring robust against ids that arrive out of order. It did not ask where those ids come from, and
the answer was wrong in one place: `broadcast` copied core's per-order `seq` onto **every** channel it fanned
out to, including the zone.

**The bug that produces.** `order_state_events.seq` is per order and starts at 1. A zone channel carries every
order in the zone, so order A's first event and order B's first event both arrive as id 1 — and `EventRing.push`
treats a repeated id as *the same event, revised*, so B's frame silently replaced A's. The admin map lost A's
event with no error anywhere: the ring did what it was told, and the fan-out told it two different events were
one.

**The fix is scoping, not more machinery.** The order channel keeps the order's log sequence, which is exactly
what a resuming client should quote: `Last-Event-ID: 4` is also a row in `order_state_events` for that order.
The zone channel is numbered by its own ring, because a zone's frames have no per-order sequence to inherit and
pretending they do makes the shared id space a collision domain. `channelsFor` still returns both channels;
`broadcast` decides the sequence per channel rather than per broadcast.

**Verified the way a claim has to be.** Reverting the one-line scoping decision fails three of the four new
tests — including the two-order case, which is the bug itself — and restoring it passes all four.

Tests: `fanout-seq.test.ts` (the order channel keeps its sequence; an unnumbered broadcast is ring-assigned; two
orders with seq 1 both survive on the zone; five orders numbering their own frames 1–5).

*Open:* closed by D102 — the append now retries on `DUPLICATE`.

## D102 — A duplicate key is the index telling us to take the next number

The sequence D101 handed to the order channel is allocated with `MAX(seq) + 1` and written by a second statement.
Two transitions on one order can read the same maximum; the `UPDATE … WHERE state = ?` has already won and moved
the order by then; and `uq_order_events_seq (order_id, seq)` then refuses the event row. The failure is the worst
shape a failure can take here: the order changed, the log does not say why, and the caller is told their request
errored.

**`DUPLICATE` is a retry, everything else is not.** `appendEvent` re-reads the maximum and tries again, up to five
times. The classification is the platform's existing one (`classifyError`), so a lock timeout or a dead connection
is rethrown on its first attempt rather than being retried into an event row that never appears. Five is not a
guess at a contention level: losing twice means two other transitions allocated the same number twice in the
microseconds between a `MAX` and an `INSERT`, and by the third attempt the alternative explanation — a genuinely
reused event id — has to be the answer, which deserves an error rather than a sixth silent try.

**The append is now a named function, not four lines inside `moveState`.** That is what makes it testable without a
transition, and it is what let the retry be verified rather than assumed: with the attempt count forced to one, two
of the eight new tests fail; restored, all eight pass.

**What a retry cannot fix.** The `UPDATE` and the `INSERT` are still two statements in autocommit, so an order can
move and its event row can be lost to a crash between them. Closing that needs a transaction the `Db` port does not
expose — the port deliberately prefers single-statement atomicity (`db/client.ts`), and a transition is inherently
two statements. Retrying the duplicate takes the common race off the table; the crash window is recorded here as
the honest remainder rather than quietly claimed.

*Open:* the crash window above; and `nextEventSeq` remains the allocation strategy, which means the retry is what
makes it correct rather than the allocation itself. A `SELECT … FOR UPDATE` on the order row, or a sequence column
on `orders` incremented in the same `UPDATE`, would remove the retry — both change the schema or the lock profile
of every transition, and neither is worth doing without the load numbers to justify it.

## D103 — The stream tails its channels, because a replay and a keepalive are not a live feed

D100–D102 made the ring's ids ordered, scoped and unique. All three only paid off at reconnect, because the
stream had no live half: `streamResponse` wrote the opening replay, then one keepalive every twenty seconds,
forever. A customer who opened the order page during a quiet minute and waited for the vendor to accept learned
nothing until the page was reloaded — the frames were recorded, the ring held them, and nothing asked.

**The fix is a tick, not a push.** Once a second (the keepalive interval is derived from it, so there is still
one timer per connection) the stream asks the same source a resume would: frames after this channel's cursor.
That is why the earlier rungs were the prerequisite — the tail is a resume that happens while connected, and it
is only correct because the ring returns id order (D100) and each channel numbers its own frames (D101).

**One cursor per channel.** A stream can watch an order and its zone at once, and the two number their frames
independently: after D101 the order channel's ids are the order's log sequence while the zone's are ring-assigned.
A single cursor for the connection would skip or repeat a frame on whichever channel moved second.

**A gap is admitted once per episode.** `complete: false` means the client must reconcile; writing that comment
on every tick would be a stream that shouts "reconcile" once a second until the client does what it was already
told. The flag clears the next time the channel answers completely, so a second gap later is admitted again.

**A failed pull is a missed tick, not a dead stream.** The cursor is not advanced, so the next tick asks for the
same range; the alternative — closing the connection because the coordinator hiccuped — is worse than a second of
silence. Overlapping ticks are prevented by a flag rather than by the timer, so a slow source delays the next pull
instead of racing it.

**Verification.** With the once-per-episode guard removed, the gap test fails (three comments in three ticks);
restored, all eight pass. The other seven cover what the tail must not break: cursor advancement, per-channel
cursors, keepalives when nothing is written, the no-tail path, and cancellation releasing the interval.

*Open:* the tail polls, so a frame waits up to a second. A push path — the room waking its own sockets — is the
alternative, and it needs the sockets to live in the room rather than in a request's stream; that is a different
architecture, not a smaller interval. The load this adds is one ring read per channel per second per open stream,
which is why the ring is preferred over the order log where a room is bound.

## D104 — The fan-out reaches the vendor, because a subscription nobody feeds is a lie in a channel's clothes

`fanout.ts` has always said "one broadcast becomes up to four channel records", and `channels.ts` has always let
a vendor subscribe `vendor:self` and a rider subscribe `rider:self`. `channelsFor` returned **two**: the order and
the zone. So a vendor app could hold a healthy 200 stream on its own channel and never receive a frame — the same
class of bug the channels module's own comment warns about ("an ignored channel is a client that believes it is
subscribed and is not"), one layer down where no refusal could catch it.

**The fix needed a contract change, not a loop.** Reaching a vendor means knowing *whose* vendor, and the only
worker that can turn an order into "the user who owns this vendor" is the one that owns the row. So the broadcast
now carries an optional `audience: {vendorUserId?, riderUserId?}` — core's `announce()`, the typed client and the
internal route all pass it through — and `channelsFor` publishes to exactly the channels the audience names.
Without an audience the broadcast reaches the order and the zone, and that is the honest limit of what core said.

**The id is a user id, in hex.** `vendor:self` resolves to the caller's `actorId`, which is the token's `sub`,
which core mints as `userIdHex`. Publishing to the vendor's *row* id would produce a frame in a room nobody can
join, with no error anywhere — the failure mode is silent by construction, so the type comment says it in the one
place a call site will read it. `usableId` refuses anything the stream grammar could not carry, for the same
reason: an id nobody can subscribe to is not an id to publish to.

**The audience channels are numbered by their own rings.** D101's rule holds unchanged: only `order:` channels
take the order's log sequence. A vendor's channel carries many orders, so copying the sequence there would be the
same collision D101 removed from the zone — the new test asserts it does not come back.

**Placement is wired end to end, and the lookup is not paid twice.** Placement resolves the vendor's owner once
and hands the hex id to both the announcement and `ringVendor` (which previously looked it up itself). The lookup
is created before the response but awaited only inside `waitUntil`, so placement latency does not include a query
the notification needs; a test counts the `owner_user_id` statements to prove there is exactly one.

Tests: three realtime fan-out cases (a named vendor gets fed; a vendor and a rider reach four channels; an
unusable id is skipped; an audience channel does not inherit the order's sequence), two internal-route cases (three
recorded with an audience, two without), two announce cases (the field travels; absent means absent), and two
placement cases (the body carries the owner's hex id; one lookup).

*Open:* only placement supplies an audience. Accept, reject and the dispatch transitions still broadcast to the
order and the zone, because those routes have to resolve a rider's *user* id from `orders.rider_id` — the same
mapping problem `vendorOwnerUserId` solved for vendors, and a lookup per transition that deserves its own rung.
Until then a vendor's other devices learn about an acceptance when the customer's page does, which is correct but
not what the four-channel promise implies.

## D105 — Three transitions were broadcasting names the stream refuses, which is the quietest failure available

Comparing `state-machine.ts`'s event names against `EVENT_NAMES` found three that the stream does not carry:
`order.rider_assigned`, `order.rider_search` and `order.auto_cancelled`. The catalogue (`08 §9.1`, from which
the apps are generated) has `order.assigned`, `order.searching` and `order.cancelled`. The internal broadcast
route answers `unknown_event` for a name it does not know, and `announce` treats any failure as a degraded
notification — so in production **every rider search, every assignment and every auto-cancellation moved the
order and reached nobody**. Not a crash, not a log flood: a customer watching "searching for a rider" forever
while a rider was already on the way.

**The machine was wrong, not the catalogue.** The catalogue is the contract the clients are generated from, and
the realtime worker enforces it; the machine had invented its own spellings. Three literals changed in
`state-machine.ts`. The stored `order_state_events.event` column follows the same literals, which is a naming
change in new rows and nothing more — replay maps the *state kind* (`RIDER_ASSIGNED`) through the catalogue, so
history written before today still replays correctly.

**The check that would have caught it is a test, not a review.** `catalogue-coverage.test.ts` imports
`TRANSITIONS` from core and asks `catalogueName` about every distinct event in the table. It fails the moment a
row is added with a name the stream cannot carry — verified by changing `order.assigned` back to
`order.rider_assigned` and watching the test go red. Two modules that must agree now have one place that says so.

**The acceptance also reaches the vendor's own channel**, closing half of D104's open: the vendor answering an
order is the vendor owner, so their user id is `principal.userId` and naming it costs nothing. A vendor's second
device, or their desktop, now learns about the acceptance in the same second as the customer, instead of on the
next poll. Verified by removing the one line and watching the route test fail.

Tests: three in `catalogue-coverage.test.ts` (the exhaustive check, the three corrected names, the stored-kind
mapping) and one in `order-routes.test.ts` (the broadcast body carries `audience.vendorUserId` = the owner).

*Open:* closed by D106 for pickup and auto-cancel; dispatch still has no route to name an audience from.

## D106 — The two transitions with the most at stake name their audiences, and one helper does the naming

D105's open was two free wins and one lookup. Both are done, and the duplication the third case would have
created is the module that carries them.

**`bindings/audience.ts` is the only place a row becomes an identity.** `announce` reaches the order and the
zone with the ids it is given; reaching a vendor's or a rider's own channel needs `vendor:self`'s identity, which
is the vendor owner's *user* id, and `rider:self`'s, which is the rider's. `audienceForOrder(ctx, {vendorId,
riderUserIdHex})` resolves both: the rider for free, because `orders.rider_id` is already a user id; the vendor
through `vendorOwnerUserId`, the same helper D93 added for the ring. Three routes now call one function instead
of each inventing the mapping — and the mapping is the kind of thing that is silently wrong (a vendor *row* id
produces a frame in a room nobody can join).

**A failed lookup is an order with no audience, not a failed transition.** `audienceForOrder` never throws: if
the vendor lookup fails, the announcement still reaches the order channel and the zone, which is the whole of
what D85 promised. Refusing to announce because one more audience could not be named would invert the rule that
a notification never degrades a state machine.

**Pickup and auto-cancel were chosen because they are where a missing frame is felt.** A pickup that only the
customer hears leaves the vendor's screen saying "waiting for pickup" about a meal that left the counter, and
the rider's second device showing nothing it is carrying. An auto-cancel that only the zone hears is the worst
of all: the vendor's silence is what caused it, and their screen is the one that must stop showing the order.
The vendor is therefore named in an auto-cancel announcement even though they are the reason for it.

**Both audience resolutions run behind `waitUntil`.** The lookup is part of the notification, not of the
response, so a pickup's latency is a pickup's; the announcement is deferred by a task that awaits the audience
and then calls `announce`, which defers again. Nesting `waitUntil` is deliberate and cheap: the outer one only
waits for a `SELECT` and a `fetch` that would otherwise be in front of the rider's screen.

**Verified by deletion.** Removing the `audience` argument from either route fails that route's new test — the
pickup case and the auto-cancel case — and restoring them passes both.

Tests: one in `order-pickup.test.ts` (vendor owner plus the rider's hex id both travel, and the announcement
still happens) and one in `auto-cancel.test.ts` (the vendor is named; no rider is named when none was assigned).

*Open:* the dispatch transitions (`RIDER_SEARCH` → `RIDER_ASSIGNED` → `RIDER_ASSIGNED` reassignment) have no
route in this Worker yet, so there is no call site to name an audience from. When one is written, both ids are
already on the row and the helper already accepts them.

## D107 — The fifth erasure trigger is the one nobody can ask for, so the room asks

`§6.1` lists five erasures and four existed. *App uninstalled / token invalid, next zone sweep, under 60 s* had
no implementation, and it is the only row in that table whose caller can never arrive: an uninstalled app sends
no end-shift request, and a revoked token cannot authenticate one. What it leaves behind is a `rider_current`
row nothing refreshes — the largest thing the platform would otherwise keep that no user asked it to keep.

**The sweep reads time, not people.** `rider_current.stale_after` is `updated_at + 2 × ceiling`, recomputed on
every flush, so "expired more than a minute ago" is the platform's own answer to "this marker is not live".
`d1Positions(...).sweepStale(cutoffMs)` is two statements in one batch: positions first, selected through
`rider_id IN (SELECT rider_id FROM rider_current WHERE stale_after < ?)`, then the current rows. The order is
not cosmetic — deleting the current rows first would leave orphaned trail rows for a rider the platform has
already forgotten.

**Presence goes first, and that is what `runZoneAlarm` exists for.** An absence published by this tick erases
its own rider through `onPublished` (D99). A sweep that ran first would report a departure the room was about to
explain — an operator line about a phone that was merely slow. The orchestration is a function over two
callbacks rather than three lines inside the Durable Object, so the ordering is testable without a Workers
runtime: presence, then sweep, then report.

**The grace minute is the design.** A sweep at `stale_after` exactly would race the flush in flight, and a phone
on a bad connection looks stale between retries. One minute is four retries at D91's ceiling, and `§6.1`
promises under 60 s *from the next sweep*, not from the moment the phone died.

**A failed sweep does not fail the alarm.** The same tick publishes absences with a five-second budget; a D1
error here is logged and retried by the next alarm, while this rider has already been gone a minute. The
inverse — a presence failure — does propagate: an absence that cannot be published is a live problem, and
hiding it behind a tolerated deletion would be exactly backwards.

**Three D99 tests had to change, and that is the interesting part.** They counted statements containing
`DELETE FROM rider_positions`, which the sweep's subquery form also matches, so the count went from one to two.
Their intent was "this rider was erased once", so they now count the per-rider form
(`WHERE rider_id = ?`) — the sweep's statement is asserted separately, in the test that is actually about it.

Tests: seven in `sweep.test.ts` (ordering, cutoff, quiet zero, reported removal, swallowed failure, no database,
and a presence failure that propagates), two in `d1-store.test.ts` (statement order and parameters; zero is
success), one in `zone-hub.test.ts` (the alarm reaches the sweep with `now − 60 000`, verified by setting the
sweep to `null` and watching it fail).

*Open:* the sweep only runs in a zone room that is armed, and a room with no sockets clears its alarm (D91). A
zone that empties completely is therefore swept by the next connection, not by a timer. That is the same
trade-off D91 made deliberately — no alarm with no members — and the residual case it leaves (one rider alone
in a zone, socket closed without a presence absence) is the case the presence path already covers.

## D108 — The shift's first row is the only row anybody can write, and core writes it

Every flush is judged against `rider_current`: the zone the rider is in, the vehicle they are on, the state they
are in. A rider without that row is refused with `SHIFT_NOT_OPEN` — correctly, because a position with no shift
cannot be judged — and until now nothing wrote the row. `rider_current` was written only by `write()`, which the
ingest route calls *after* `context()` has already answered. The live-tracking channel could therefore never
start: the first flush of every shift would be refused, and so would every one after it.

**The gap is exactly one row, and only the shift's start knows its contents.** The zone and the vehicle are the
shift's, not the batch's. So core opens the shift in TiDB and calls `POST /internal/shift/open`, which is the
one internal route that writes D1 rather than announcing something. It carries `{riderId, shiftId, zoneId,
vehicle, point, state?}` and answers `{opened, shiftId, staleAfterMs}`.

**Three statements, one batch, in an order that is the decision.** `DELETE FROM rider_positions`,
`DELETE FROM rider_current`, then `INSERT OR REPLACE INTO rider_current` with the seed. The deletions are not
tidy-up: a new shift's trail is that shift's, and leaving the previous shift's last fix in the ring would hand
the first flush of the new shift a `newest` from somewhere else and judge the rider a teleporter on their own
doorstep. A half-opened shift — row deleted, seed not written — is a rider with no marker, so it cannot be two
batches.

**The seed is honest about what it is.** `accuracy_m = 100` because the start point comes from the selfie step,
not from a fix, and a seed that claims five metres would make the map draw a confident dot at a guess. Its
`stale_after` is `now + 2 × the idle-stationary ceiling` (ten minutes), the same rule every flush uses, so a
seed that never receives a flush goes grey rather than staying a permanent "online" claim.

**A deployment without a D1 binding says so.** `positions` is optional in `InternalContext`; without it the
route answers `501 live_positions_not_configured` rather than opening a shift whose first flush will be refused
with a different error. Two errors for one cause is how an operator spends an afternoon.

Tests: three in `internal.test.ts` (the seed's state, point, accuracy and deadline; the 501 without a store; a
body that is not a shift writes nothing) and one in `d1-store.test.ts` (the three statements in order, with the
values bound to them).

*Open:* core's `/v1/rider/shift/start` — the caller — is the next rung; until it exists this route is reached by
tests and by nothing else. The shift's end has the mirror problem: `POST /rt/location/erase` exists (D98) and
`/v1/rider/shift/end` does not.

## D109 — The shift's beginning exists, and it refuses rather than half-opens

D108 closed the mouth of the live-tracking channel from realtime's side. This is the caller: `POST
/v1/rider/shift/start`, the first route in the repo that makes a rider's live row exist because a rider asked
for one. Before it, nothing in the platform could open a shift at all.

**Four questions, four refusals, each naming the screen that fixes it.** The token resolves to a rider by
`user_id` — never by a rider id in the body, which would be a user able to name a rider they are not. The rider
must be `APPROVED`: under review is `SHIFT_KYC_PENDING` (409), suspended is `AUTH_ACCOUNT_SUSPENDED` (451), and
the two are different screens so they are different codes. An existing open shift is `SHIFT_ALREADY_OPEN` with
its id rather than a quiet `200` returning it — a stale shift that answers success is a shift nobody will ever
close. And the zone: the home zone always, any other only through a live `rider_zone_assignments` row.

**The selfie is required and is not verified here.** `19 §3.1` accepts the shift on the on-device checks and
sends 10% plus every first shift to a human afterwards, so the API requires an https URL of at most 512
characters (`selfie_url` is a `VARCHAR(512)`) and records `selfie_verified = 1`, which means *accepted at the
door*. A review that later fails ends the shift; it never blocks the start, because a rider who cannot start
because of a camera heuristic is a rider who cannot earn.

**The seed is synchronous and its failure undoes the shift.** D108 argued that a shift without a live row is
untracked. The consequence is that a shift start which wrote TiDB and skipped D1 would leave a rider visible to
dispatch, invisible on the map, and unable to fix it — every flush refused with `SHIFT_NOT_OPEN` and no error
the rider can see. So the internal call is awaited, and on failure the route deletes the shift row, puts
`shift_state` back to `OFFLINE`, writes no audit row, and answers
`503 SERVICE_DEGRADED { component: "realtime", reason: "live_position_unavailable" }`. A shift that cannot be
tracked does not exist; the rider taps again in a second. The same refusal covers a deployment with no realtime
configured, because there the seed is impossible rather than slow.

**One permission key was added and the register's count moved, deliberately.** `rider.shift.start` did not
exist: the specification's 412 keys include `rider.shift.read`, `force_end`, `approve_selfie` and
`reject_selfie`, and nothing a rider could hold to begin their own shift. The register therefore holds 413 and
asserts it at module load, `21`'s two counts moved with it, and the RIDER actor holds the new key. A route
gated on a key that does not exist fails closed and reads as a UI bug; the count assertion is what caught it.

Tests: ten in `shift-start.test.ts` — the happy path (row, state, audit, and the seed's rider/zone/vehicle/point),
the second tap, under review, suspended, no rider row, a non-https selfie, an unassigned zone writing nothing, an
assigned zone succeeding, the unwind (row deleted, both state writes, no audit), and the unconfigured deployment.
Verified by deletion: removing the unwind block fails two of them.

*Open:* the cash gate. `25 §2` has a `CASH_LOCKED` rider unable to start, and that state is produced by the
shift *end* — which does not exist yet — so the gate is written when there is something that can set it. Also
open: `GET /v1/rider/shift/current`, break toggling, and the sampled admin review that flips `selfie_verified`.

## D110 — The shift's end, and the identity bug the start shipped with

The end of a shift, and with it the correction of a bug D109 put in the start.

**The seed was keyed by the wrong id.** D109 wrote `rider_current` with `riders.id` — the row id — while every
flush is judged under the token's `sub`, which is a *user* id (`D97`). The two are 32 hex characters each and
neither looks wrong in a log. The effect would have been a shift that opened, seeded, answered `200`, and then
answered `SHIFT_NOT_OPEN` to every position for eight hours; the sweep of D107 would have eventually deleted the
unread row, which would have looked like the erasure working. Found by writing the end route, which erases by
identity, and noticing the two routes would have named different keys. `openShift` now carries the user id, the
start route passes `principal.userId`, and the test that previously asserted the row id asserts both the
identity and that it is not the row id. This is the session's recurring bug — a row id where an identity
belongs — and it is now stated at the type in the realtime client's `eraseLiveLocation`.

**Three writes and an erasure, in an order that is the design.** `closeShift` is an `UPDATE … WHERE id = ? AND
ended_at IS NULL`; the zero it can return is the race between two ends, and the loser is told
`SHIFT_ALREADY_CLOSED` rather than allowed to rewrite the moment the shift ended. The rider's state becomes
`OFFLINE`, or `CASH_LOCKED` when a balance row says they still owe cash — the state is written here, by the
route that knows the amount, because otherwise every reader would have to derive it. Then the live channel is
erased through `POST /internal/erase`, synchronously, before the answer, because `§6.1` promises under a second
for the button the rider actually presses.

**An erasure that fails does not fail the end.** Trapping a rider online because realtime is cold is a worse bug
than a trail that outlives its shift by a minute, and D107's sweep is exactly the fuse for that minute. The
failure is logged and reported in the answer (`liveLocationErased: {positions: 0, current: 0}`) rather than
swallowed into a claim that the promise was kept.

**An open order refuses the end, and the registry had no code for it.** `25 §2` blocks the end while deliveries
are live; the error table's twelve shift codes covered cash, zones, vehicles, KYC and a checklist, and nothing
for "you are still carrying someone's dinner". `SHIFT_ORDERS_ACTIVE` (409, `{active_orders}`) is the addition,
the register is now 185 codes, and the two docs that quote the count moved with it. Reassigning the order behind
the rider is dispatch's business, not a side effect of a button.

**The cash gate on the start arrived with the thing that sets it.** `SHIFT_CASH_OVERDUE` is `25 §2`'s block, and
a rider can only be `CASH_LOCKED` because an end put them there, so the gate is two lines in the start route
reading the balance only for a rider who is already locked. The registry's details for that code name
`{outstanding, due_at}`; the schema stores no settlement deadline, so the answer carries `outstanding` and not a
date the platform cannot ground. That is recorded as open rather than invented.

Tests: seven in `shift-end.test.ts` (the no-cash end with its erasure and audit, the cash lock, the active order,
no open shift, the racing end, a failed erasure that still ends the shift, and a malformed point writing nothing)
and one more in `shift-start.test.ts` (the cash gate, and the seed's identity). Verified by reversion: seeding
with the row id fails the start test, and removing the erasure call fails two of the end tests.

*Open:* `due_at` on a cash lock (needs a deadline the schema does not store); `online_seconds` counts the wall
clock between the two taps rather than the time the device was actually online, which is the number the summary
wants and needs the presence ledger of D91 to be exact; and break toggling (`/v1/rider/shift/break`) plus
`/v1/rider/shift/current` remain unwritten.

## D111 — The rider's own screen: a read that refuses to call the normal case an error, and a break that is one flag

The shift's three routes are now the whole loop a rider lives in: start, look, break, end. This is the two that
were missing.

**`GET /v1/rider/shift/current` answers `200` with `shift: null` for an offline rider.** That is the decision in
the route, not an accident of implementation. The app calls it on every launch and every resume, most riders are
offline at any moment, and `SHIFT_NOT_FOUND` would (a) fill the client's error log with the normal case and
(b) teach the client that an error from this endpoint means "go to the shift screen" — which would show the shift
screen to a rider who has not started one. The `404` stays on the *end*, where asking to close a shift that is not
open is a mistake worth naming. A read route's job is to describe the world, including the parts that are absent.

**It answers what the other two routes changed**, so the app never has to derive them: the shift's own totals
(`ordersCompleted`, `distanceM` — columns the schema already had and nothing had read), `onlineSeconds` computed
from the start, and `cashOutstandingPaisa` with `settlementRequired`. The cash figure on the read is what lets the
app warn a rider *before* the end locks them, instead of showing the locking screen as a surprise.

**The break toggle is a route rather than a `PATCH` on the shift.** Two screens have the button, and the audit
trail wants to say which was pressed, so the actions are `rider.shift.break.start` and `rider.shift.break.end`
rather than one `rider.shift.updated` with a payload a reviewer has to read. It writes one column and lets the
device's next flush carry `state: "BREAK"` to realtime: two systems, one flag, no second source of truth about
whether the rider is on a break.

**No shift means no break, and nothing is written.** Tested by asserting the statement list is empty, because a
`shift_state` written for a rider with no shift is a rider who looks online with nothing to be online *in*.

**One more permission key.** `rider.shift.break` — the register is now 415, `21`'s two counts moved, and RIDER
holds it. This is the third key this session has added to a register that claims to match the specification, and
the honest description is that the specification enumerated the *admin* half of the rider's shift surface
(`force_end`, `approve_selfie`, `reject_selfie`, `read`, `list`) and never the rider's own half (start, end,
break). Every addition is recorded here rather than slipped in.

Tests: eight in `shift-current.test.ts` — the open shift with its totals and clock, the offline `200` with `null`,
the cash warning, a token with no rider, break on and break off (state and the two audit actions), no open shift
writing nothing, and a non-boolean body refused before any read.

*Open:* `online_seconds` on the read is wall clock since the tap, which includes time the phone was not sending;
the exact figure needs D91's presence ledger and is the same gap D110 recorded on the end. The break does not
touch the D1 row directly — a rider who takes a break and then stops sending keeps their last `ONLINE` state
until the seed's deadline passes, which is a deliberate consequence of letting the device own the flag.

## D112 — The quadratic lookup that was really an unstated invariant

`routes/location.ts` built its ring writes with `judgement.accepted[judgement.acceptedIndexes.indexOf(index)]`:
a search through up to twelve entries, inside a map over up to twelve entries. Small, and wrong in a way that
matters more than the arithmetic.

**What it actually said.** `indexOf` expresses the relationship between the two arrays as a search, so it reads as
*"find the accepted fix whose index this is"* — as though the arrays were independent and the correspondence had
to be discovered. They are not independent: `judgeBatch` pushes to both inside one loop iteration, so
`accepted[position]` is the fix at `acceptedIndexes[position]` by construction. The lookup was O(n²) for a batch
capped at twelve, which nobody would notice, and the *expression* was the defect: a future change that sorted
`acceptedIndexes` (a reasonable-looking tidy-up) would have written the right slots with the wrong fixes — a trail
where every position is real and every position is in the wrong place.

**The fix is the invariant, written where the invariant is used**: a positional read with a comment that names the
construction it depends on. `d1-ingest.test.ts` now asserts the alignment directly, with a batch whose middle fix
is refused — the case where a reordering shows up — and checks that `accepted[position].recordedAtMs` is the
timestamp of the fix at `acceptedIndexes[position]`. Verified by reversion: replacing `push` with `unshift` in
`judgeBatch` fails the new test and nothing else, which is the point — the array's order is now load-bearing and
the suite knows it.

This closes the wart D97 recorded. There is no behaviour change: every existing location-route test passes
unchanged, because the same elements are read in the same order. The change is to what the code claims.

## D113 — The transition that nothing could fire now has a caller, and the database is the arbiter

`RIDER_SEARCH → RIDER_ASSIGNED` has been legal in `state-machine.ts` since the machine was written, with a
`riderClaimedOffer` guard, a catalogue name (`order.assigned`), error codes for every race and an audience helper
that could reach the rider's own channel. Nothing could fire it. `POST /v1/orders/{code}/offer/{offerId}/accept`
is the caller, and with it the dispatch half of the platform has a first honest step.

**The database decides the race, not a coordinator.** `11 §7.3` puts an atomic `claimOffer` in the coordination
layer, and that remains right for what it is for — delivering a wave to fifty phones and stopping it early. The
*claim* needs exactly one of fifty conditional updates to succeed, and `UPDATE orders … WHERE id = ? AND state =
'RIDER_SEARCH'` already gives that: forty-nine zero-row answers, forty-nine `OFFER_CLAIMED`, which every loser
needs anyway to stop ringing. A coordinator would be a second arbiter with a second answer.

**The order moves first and the offer records it second.** If the order's state had been left to a later
statement, a claim could mark an offer accepted for a rider who then did not get the order — a screen saying
"yours" above food somebody else is collecting. So `moveState` is conditional and first; if it reports zero rows,
the rider is told `OFFER_CLAIMED` and *nothing else is written*, not even the offer's own answer.

**A wave ends the moment it is claimed.** `11 §7.2`'s early termination is one statement: every unanswered offer
on the order becomes `WITHDRAWN` in the same call. Leaving them `NULL` would keep fifty phones ringing for a
delivery that is already assigned, and would let one of them claim an order that is no longer searching. Verified
by deletion: removing that statement fails the winning-claim test.

**Four refusals, in the order a rider can hit them.** Not the offer (`OFFER_NOT_FOUND`, including an offer that
belongs to another order), not this rider's (`OFFER_NOT_TARGETED` — read from the offer's own `rider_id`, never
guessed from a body), already declined (`OFFER_ALREADY_REJECTED`), the TTL passed (`OFFER_EXPIRED`, 410, and the
expiry is *recorded* so the rider's screen and any sweep agree), the order stopped searching or the state change
lost (`OFFER_CLAIMED`), or the machine refused a claim the route had already checked (`OFFER_CLAIM_RACE`, a bug
in this route, named so the rider retries rather than believing the offer was never theirs). A second tap from
the winner is a `200` with `repeated: true`: a flaky network must not look like a lost delivery.

**Two new rows are written and one existing column moves.** `order_assignments` records who had the order and
from when (its `end_reason` is for the reassignment rung), `responded_at` records when the offer was answered,
and `orders.rider_id` is set by the same statement that sets the state, because an order assigned to a rider in
two writes can be observed with one of them.

**No new permission key.** `order.deliver` gates the route: accepting is the first act of delivering, the
register's `order.offer.*` keys are the dispatch-side half (`create`, `expire`, `cancel`,
`view_rider_identity`), and minting a rider-facing key per verb would be a fourth addition to a register that
claims to match the specification.

Tests: ten in `offer-claim.test.ts` — the winning claim (conditional move with `rider_id`, the single answer, the
withdrawals, the assignment row, the audit), another rider's offer, expiry with its recording, an order that
stopped searching, a lost state change writing nothing further, a repeated tap, an already-declined offer, an
offer from another order, an unparseable offer id, and the announcement carrying the rider's identity and the
vendor's owner.

*Open:* the **reject** half (`/v1/orders/{code}/offer/{offerId}/reject`) is documented and unimplemented, and
`reject_reason` is a `CHECK`ed column waiting for it. Also open: nothing creates offers yet — the dispatch engine
that scores riders and writes `order_offers` rows is core's brain, not this route — so the claim path is proven
against rows a test writes until that rung lands.

## D114 — Declining is the claim's opposite: the order does not move, and nothing punishes the rider

`POST /v1/orders/{code}/offer/{offerId}/reject` — the other half of the pair D113 opened, and the one `11 §9`
is really about: a rider must be able to say no in a way that costs them nothing but a statistic.

**The order does not move.** A decline answers one offer; the order is still `RIDER_SEARCH` and the next wave or
the next rider hears about it. That is why the route writes two rows and no state change, and why the answer
says `state: "RIDER_SEARCH"` — the app must not close its screen assuming the delivery is gone from the platform
as well as from the phone. Tested by asserting no `UPDATE orders` statement is issued at all.

**No reason carries a direct penalty, and that is enforced here rather than promised.** `11 §9.1` refuses the
dark pattern of penalising a rider for a genuine inability; this route writes no suspension, no lock and no
score. What it writes is `rider_shifts.orders_rejected = orders_rejected + 1`, which `11 §9`'s acceptance factor
reads — a feedback loop, not a punishment. Verified by deletion: removing the counter fails the first reject test.

**The reason set is the API's, not the app's.** `REJECT_REASONS` holds `11 §9.2`'s nine rider-facing codes in the
order the sheet shows them, and `NO_ALTERNATIVE_FORCED` is deliberately absent — a rider cannot claim the machine
told them not to. An unknown reason, or `OTHER` with blank text, is `422 OFFER_REASON_REQUIRED {allowed}`, so a
client that invents a tenth reason receives the list instead of "invalid": a refusal a UI can act on.

**The refusals are ordered by what the rider can still do.** Already declined (`OFFER_ALREADY_REJECTED`), already
answered by someone or expired (`OFFER_REJECT_NOT_ALLOWED` with the order's state, or `OFFER_EXPIRED` 410 with
the expiry *recorded* so the sweep and the screen agree), another rider's offer (`OFFER_NOT_TARGETED`), the order
claimed while the sheet was open (`OFFER_REJECT_NOT_ALLOWED {state}`), and losing the write race to a second tap
(`OFFER_ALREADY_REJECTED`). Every one of them names what happened; none of them leaves the offer unanswered.

**The interesting reasons' effects are recorded, not invented.** `VENDOR_SLOW` implies a 45-minute cooldown for
that vendor and `AREA_UNSAFE` a permanent per-cell exclusion (`11 §9.2`); both are dispatch state owned by the
engine, and writing them here would put a policy where the data is. The reason and the free-text note are on the
offer row for whoever builds that.

Tests: nine more in `offer-claim.test.ts` — the recorded reason and the moved counter with no order change and no
wave withdrawal, `OTHER` with blank text, an invented reason, `OTHER` with text, a second decline, an offer
another rider won, a decline after the TTL, another rider's offer, and an order claimed while the sheet was open.

*Open:* the same as D113 from the other side — nothing writes `order_offers` rows yet, so both halves are proven
against rows a test writes. The `VENDOR_SLOW` cooldown, the `AREA_UNSAFE` exclusion, the `TAKING_BREAK`
auto-break and the `VEHICLE_ISSUE` auto-offline are four dispatch behaviours this route creates the evidence for
and does not perform.

## D115 — The reconciliation read, and the clock the client must not trust

`GET /v1/rider/offers` — the third and last of the rider's offer routes. `08 §8` calls it *reconciliation* and
says the FCM payload is authoritative; this is what the app asks when a notification was missed, a screen was
backgrounded, or a rider wants to be certain nothing is ringing.

**The predicate is the claim's predicate, not a second one.** Unanswered (`response IS NULL`) and inside its TTL
(`expires_at > now`), in one statement over `order_offers` joined to `orders` for the code. An offer whose TTL
has passed is excluded here *even before the sweep writes `EXPIRED` on it*, because the rider's screen must never
show a delivery they can no longer take — and the claim route would refuse it with `OFFER_EXPIRED` anyway. Two
answers to "is this offer live" would eventually disagree; there is one.

**`secondsRemaining` is computed by the server and travels with `serverTimeMs`.** The obvious client would
subtract `expiresAt` from its own clock, and the phone that most needs this endpoint is the one whose clock is a
minute out — a rider with eighteen seconds left would see zero and let it go. The countdown is therefore the
API's arithmetic, and the client's only job is to tick.

**No history.** Answered and expired offers are not returned at all, and the limit is twenty: a list of dead
deliveries is not a decision surface, and a rider scrolling history while a wave is ringing is a rider losing
the delivery.

**The key is `order.read`, not a new one.** The handler queries by the rider the token resolves to, so this is
the read half of the delivery surface the RIDER actor already holds. That keeps the register at 415 and avoids a
fourth addition for a noun.

Tests: four more in `offer-claim.test.ts` — a live offer with its code, wave, payout and countdown plus the
server clock; the query's own predicate and its rider parameter; an empty list being a `200`; and a token with no
rider row.

*Open:* the same hole as D113/D114, stated once more because it is the one that matters: **nothing writes
`order_offers` rows.** The three rider routes now describe the whole life of an offer — listed, claimed,
declined — and the engine that creates them, scores the candidates (`domain/order/assignment.ts` has the pure
planner and the numbered filters), rings the phones and schedules the waves is still unbuilt. Until it lands,
every one of these routes is proven against rows a test writes.

## D116 — The TTL becomes a row, not three separate opinions

`POST /internal/offers/expire` — the sweep that writes `EXPIRED` on offers nobody answered.

**Three routes already agreed an expired offer is not live, and none of them wrote it down.** The rider's list
excludes it by comparing `expires_at` with now; the claim route refuses it with `OFFER_EXPIRED` and writes the
expiry *on that path*; the reject route does the same. Those are answers about the moment of asking. The row is
the answer about what happened — and `11 §9.3` needs it, because an expiry counts against a rider's acceptance at
**half the weight of a refusal** and the acceptance factor is computed from rows. A sweep that never ran would
leave dispatch statistics quietly optimistic: every abandoned offer invisible, every rider looking more reliable
than they are. That is the kind of wrong that never surfaces as a bug report, only as an order offered to the same
rider who ignored the last four.

**One instant, applied twice.** The sweep reads its `now` once and uses it for both the `SELECT DISTINCT wave`
and the `UPDATE … WHERE response IS NULL AND expires_at <= ?`, so a wave can never be reported as timing out in a
statement that excludes it. Both statements carry the same bound, which the test asserts by comparing the two
parameters.

**It reports the waves.** `{expired: 3, waves: [2]}` is a different signal from "three riders were slow": a whole
wave timing out is a zone with too few riders, one rider timing out is a rider. `11 §7`'s wave model is the whole
reason the distinction exists, and it costs one `SELECT DISTINCT` on the same predicate.

**No audit row.** An expiry is the absence of a decision; the audit chain is about people, and a ledger of things
that did not happen is a ledger nobody reads. The `order_offers` rows are the record, the count is logged, and an
operator can compute the same number from the table.

**Internal, behind the shared token, checked in the handler.** The route is declared anonymous so the pipeline
does not demand a session from a Worker, and its first act is `requireInternalToken` — a route that forgot the
check would otherwise be served to anybody who found the path, and an absent token is a refusal rather than a
wildcard (D82). Tested by calling it with no token and asserting the statement list is empty.

Tests: three more in `offer-claim.test.ts` — the expiry with its single instant and named wave, a quiet zero with
no audit row, and the refusal without the token.

*Open:* **the caller.** The sweep needs a periodic trigger, and the natural one is the zone room's alarm, which is
the only thing in the system that runs while riders are connected (D107 uses it for the erasure of zombies). That
wiring crosses the Worker boundary — realtime calling core, as it already does for the auto-cancel ladder — and it
is the next rung. Also still open, and now the largest hole in the repository: **nothing writes `order_offers`
rows.** `domain/order/assignment.ts` has the numbered filters and the wave planner; what is missing is a
`RiderSnapshot` per candidate, and core cannot build one because four of its fields (`positionAgeS`,
`positionStaleAfterS`, `distanceToZoneEdgeM` from the live fix, `routedDistanceToVendorM`) describe a position
that only realtime holds. That is a design question before it is a coding one: either the wave writer asks
realtime for freshness per candidate, or realtime publishes a candidate feed. D116 leaves it stated rather than
guessed.

## D117 — The one question core cannot answer, asked once per zone

D116 left the dispatch hole stated in structural terms: a `RiderSnapshot` needs four fields that live only in
realtime's D1. This is the answer to *how*, and the choice is between one call per zone and one call per rider.

**Once per zone, and it returns rows rather than a verdict.** `POST /internal/candidates { zoneId }` reads
`rider_current` for that zone — one statement over `idx_current_zone`, state-filtered to the three states a
dispatchable rider can be in, capped at 200 — and returns every field a snapshot needs from this side:
`riderId`, `vehicle`, `state`, the position, accuracy, battery, `updatedAtMs` and `staleAfterMs`. Per-rider calls
were the alternative and they are the wrong shape: a wave of eight out of a zone of sixty would be sixty round
trips to answer one question that one statement answers, and the ranking only needs the top of the list anyway.

**It does not decide who is fresh.** The row carries its own deadline and the route passes it through untouched;
`POSITION_FRESH` (filter 4) is dispatch's rule, evaluated by the module that also numbers the reason a rider was
refused. A store that pre-filtered would be a second opinion about freshness, and this session has already spent
two rungs removing a second opinion about what an offer is.

**The identity, again.** `riderId` here is the same identity every other D1 row is keyed by — the token's `sub` —
which is what the wave writer will need when it joins these rows to TiDB's `riders` by `user_id`, not by `id`.
That is the trap D110 fixed on the write side; naming it here is what stops it recurring on the read side.

**Two smaller things this route got wrong first and now does not.** The body is read once: a `Request`'s body can
be consumed once, and the first draft called `safeJson` twice, which would have validated `undefined` and answered
`422` for every request that carried a zone. And an absent D1 binding answers `501 live_positions_not_configured`
rather than an empty list, because "no candidates in this zone" and "no database" must not look the same to a
dispatcher deciding whether to fall back.

Tests: three in `internal.test.ts` (a zone's row passed through with its deadline, a body with no zone refused
rather than answered for every zone, and the 501) and two in `d1-store.test.ts` (the statement, its state filter
and the mapping including a null battery; an empty zone being an empty list).

*Open:* the wave writer that consumes this feed — TiDB riders joined to these rows by `user_id`, the numbered
filters, `planWaves`, the `order_offers` insert — and the three fields that even this feed cannot supply
(`distanceToZoneEdgeM` needs the zone polygon core holds, `routedDistanceToVendorM` needs routing that is not
built, `notificationsAllowed` needs the device table). Those are core's to fill, and stating which side owns each
is the point of this rung.

## D118 — The numbers the filters compare against, and who owns them

`assignment.ts` reads `rider.vehicleMaxRadiusM` and `rider.cashLimitPaisa` off the snapshot, which is the right
shape: the module that decides *whether* a rule passes should not know *what* the rule's threshold is. But that
only pays off if the thresholds live somewhere with a citation — and two of them (`max_concurrent`, the vehicle
radius) lived nowhere at all. Not wrong: **absent**. No column in `riders`, no constant, no owner. A wave writer
would have had to type `12_000` at the call site, and the next person would have typed it again, and one of the
two would have been for a bicycle.

**So the numbers get a file.** `domain/order/dispatch-policy.ts` holds `VEHICLE_POLICY` (bicycle 4 000 m / 1
order, motorbike 12 000 m / 3), `DEFAULT_CASH_LIMIT_PAISA` (৳3 500) and `FALLBACK_RELAXATION` (×1.2 radius, ×1.2
cash, 3 000 m outside the boundary), each carrying the section it came from. Frozen, because a policy table is
read by everything and written by nobody.

**An unknown vehicle gets no limits.** `vehiclePolicy("TRUCK")` is `null`, not a default. The column's CHECK
constraint makes a third value a bug, and a `default` branch could only ever fire on that bug — silently handing
it a radius. `null` makes filter 8 refuse the rider *by name*, which is the difference between "no riders
available" and "there is a rider here whose vehicle nobody described".

**The relaxation is three factors and no boolean.** The tempting shape is `relax: true` threaded into the filters,
and it would be wrong in a specific way: a boolean relaxes *everything*, so a slow order would also start
admitting stale positions and unverified faces. `FALLBACK_RELAXATION` loosens radius, cash cap and the zone-edge
allowance — the three that a slow order is genuinely a reason to loosen — and leaves freshness, verification,
suspension and the reject cooldown untouched. `Math.ceil` rather than `Math.round`, because `350 000 × 1.2` is
`419 999.99999999994` in binary and the documented promise is `420 000`: the rounding direction is chosen so the
rider is never a paisa short of the figure the document states.

**And the TiDB half of a candidate gets read.** `repositories/dispatch.ts` `ridersInZone` is one statement per
zone — `riders` joined to an **open** `rider_shifts`, `APPROVED` only, `shift_state` in the three dispatchable
values, with the active load as a correlated count over the three states a delivered order is not in, `LIMIT 200`.
Everything it excludes is something no relaxation could ever re-admit: a closed shift, a rider who is not
approved, a `CASH_LOCKED` rider, the selfie check in progress. A bicycle is *not* excluded even though most orders
are too far for it, because "too far for your vehicle" is a sentence the rider's app can only say if the row
arrived.

**Both identities on the row, named.** `riderId` is the `riders` row an offer points at; `userId` is the token's
`sub`, which is what `rider_current.rider_id` holds and therefore what the D117 feed joins on. D110's bug was
exactly this confusion in the other direction; carrying both fields on one type is how the wave writer avoids
repeating it.

Tests: sixteen in `dispatch-candidates.test.ts` — the table's values and its immutability, an unknown vehicle
getting no limits, the relaxation's three loosened limits and its unchanged load ceiling, the float rounding, the
statement's exclusions and its bound, and the mapper's handling of `BREAK`, an unexpected state, an unknown
vehicle and a numeric string from TiDB.

*Open:* the wave writer that consumes this — join to the D117 feed by `userId`, fill the three fields neither side
supplies (`distanceToZoneEdgeM` needs core's zone polygon, `routedDistanceToVendorM` needs routing that is not
built, `notificationsAllowed` needs the device table), run `FILTERS`, `planWaves`, insert the offers, ring.

## D119 — Zone geometry is JSON, so the distance is ours to compute

Filter 7 asks how far outside their own zone a rider is. TiDB has no spatial types — `zones.polygon` is a JSON
ring of `[lon_e7, lat_e7]` — so there is no `ST_Distance` to lean on and no second opinion available. The
alternative was to leave the field at `0` "until we have PostGIS", which is not a placeholder: a `0` means *this
rider is inside their zone*, so a wrong zero makes every rider in the city eligible for every order in every zone,
and no test would fail because nothing would look broken.

**So the shape gets a module, and the plane is local.** `domain/geo/zone-shape.ts` parses the stored ring, answers
inside/outside by even-odd ray casting, and measures to the nearest segment in an equirectangular frame scaled by
`cos(lat)`. At zone scale — a few kilometres — that frame is accurate to centimetres and fits in a page; a proper
geodesic segment distance is an elliptic integral for a precision nobody downstream can use, since the answer is
consumed as a comparison against 3 000 m.

**Boundary counts as inside.** A rider standing on their zone's edge is available, not a metre away from being
available, and the difference would be an order offered to nobody while a rider sat on the line. This is the case
the deletion proof turns red: removing the inside short-circuit makes the boundary test report a distance instead
of zero, which is exactly the bug that a naive "distance to the ring" implementation ships with.

**A ring with no interior is refused at parse time, not answered with zero.** Three collinear vertices, or four
copies of one point, describe no shape; a zero there would make every rider look inside every zone. `parseZoneRing`
returns `null` for it and `distanceOutsideZoneM` throws, because both callers need a different kind of stop: the
writer wants to reject a bad polygon with a field error, and dispatch wants to fail loudly rather than wave.

**Two honest limits, named in the file rather than discovered later.** The projection degrades far from the
equator's cosine and the ring convention breaks across the antimeridian; Sylhet is neither, and `ringExtentM`
against `MAX_PLANAR_RING_M` (50 km) gives the writer a way to refuse a "zone" that is actually a province. The
antimeridian is stated as unsupported, which is true, rather than handled by code that would never run here.

**What this closes.** Three fields were blocking the wave writer. `distanceToZoneEdgeM` is now computed from data
the platform already stores. `routedDistanceToVendorM` still needs routing, and the honest interim is the ring's
own `estimateRoute` — a straight line marked `ESTIMATED`, which is the same provenance `D67` already promises
customers for the fee. `notificationsAllowed` needs the device tables and is a join, not a decision. So the
assembly is one rung away rather than one design question away.

Tests: fourteen in `zone-shape.test.ts` — parsing, an open ring closed on the way in, refusals for degrees and
floats and unreachable latitudes, inside-ness at the origin and on every vertex and edge midpoint, 445 m for four
steps north, a corner measured to the corner, monotonicity, a concave L whose cut corner is outside while its arm
is inside, the degenerate ring throwing, and the extent guard.

## D120 — The seam, and the two identities it must not confuse

A `RiderSnapshot` is written by three parts of the platform that have never met: TiDB knows who the rider is, D1
knows where they are, and the policy table knows what their vehicle may carry. D118, D117 and D119 each built one of
those halves and each stopped at the edge of its own store. This rung is the join — `assembleSnapshots`, a pure
function, so the seam can be tested with no database and no Worker.

**The join key is the user id; the answer carries the row id.** D1's rows are keyed by the token's `sub`, and an
offer's foreign key is `riders.id`. Both statements are true and they are about different columns, which is exactly
the confusion D110 shipped. Here it is made explicit twice: `fixes.get(userId)` finds the position, and the snapshot's
`riderId` is the row id — the identity an offer will point at. The deletion proof is the point of the rung: switching
that lookup to `rowId` turns **six** tests red, because every rider then looks unconnected, every wave is empty, and
nothing anywhere logs an error. A silent empty queue is the failure mode, so the test asserts behaviour, not a
comment.

**A missing position is not a missing rider.** A rider whose live row is absent cannot have an age measured, and the
tempting move is to drop them during assembly. That would put a second, unnamed refusal into dispatch — the exact
shape of problem this session has spent several rungs removing. Instead they carry `positionAgeS: Infinity` and
`positionStaleAfterS: 0`, which routes them through filter 4 like any stale fix, so they are refused **by name** and
the rider's app can say why. One vocabulary, one place to look.

**Two refusals, and only the unjudgeable ones.** A vehicle the policy table does not describe, and a zone with no
polygon: neither can produce a snapshot at all, so they are reported as data errors carrying the rider's code rather
than converted into a filter verdict. A filter refusal means "we judged you and the answer was no", and saying that
about a rider nobody could judge is a lie that hides a database problem. Both are per-candidate: one bad row does not
remove the good ones from the wave.

**The signals that live outside both stores are required parameters.** Rejected waves for *this* order,
`notifications_allowed`, active suspensions, and the per-vendor cooldown. Required, because an optional map defaults
to "nobody", which silently weakens filters 12, 13 and 14 — three filters whose whole job is to stop an order being
offered to someone who will not take it. Empty is allowed and honest; silent is not. The cooldown has no table yet
(`11 §9.2` deferred), so the writer passes an empty set and the seam is where that effect will arrive.

**The routed distance is the straight line, and says so.** `estimateRoute` marks it `ESTIMATED` in the same module
that prices the delivery fee (`D67`), so eligibility and price are judged on the same number — a rider is not
refused a job the platform would happily charge for. When routing lands, one function changes and both move together.

Tests: fifteen in `dispatch-assembly.test.ts` — the identity join and its death (six red under reversion), a rider
with no fix assembled with an infinite age and refused by filter 4, the first fix winning over a duplicate, age and
budget arithmetic and the clock-skew floor, the straight-line distance within 2 m of the geometry, zero inside the
zone against the real edge distance outside it, the policy table driving the limits, `BREAK` becoming `ON_BREAK` and
failing filter 2, all four signals reaching their filters, and the two refusals with a good candidate surviving
beside a bad one.

*Open:* the writer — read the zone's TiDB candidates, call the feed, assemble, run `FILTERS`, `planWaves`, insert
`order_offers` for wave 1, and ring the phones. That is the last rung of dispatch and it is now ordinary plumbing
plus one alarm, because every decision it needs has been made in the nine rungs before it.

## D121 — A wave is one statement, and one refusal is not another

D120 produced the snapshots; this rung gives the writer its two database verbs and the client call that closes the
loop to realtime. Small by comparison, and two of the decisions in it are the kind that get lost in a loop.

**A wave is written in one statement.** Eight offers inserted one at a time would be eight opportunities for a rider
refreshing their list to see a half-written wave, and `GET /v1/rider/offers` (D115) does not read inside a
transaction. Worse, eight `now`s would give wave 1 eight different deadlines — and `11 §7`'s twenty-five seconds is a
promise about the *wave*, which is why the insert takes `offeredAtMs` and `expiresAtMs` from the caller and repeats
them on every row. An empty wave writes nothing and returns zero rather than attempting `INSERT … VALUES` with no
tuples: the fallback ladder reaching its end is a legitimate outcome, not an error.

**Two things are refused before the database sees them.** The same rider twice in one wave — the unique index would
reject it, but a planner bug should surface at the planner, not as a `DatabaseError` a hundred lines downstream. And
an offer whose expiry is not after its offer, because that is a rider who has lost before they were asked, and the
claim route would answer `OFFER_EXPIRED` to an instantaneous tap.

**Filter 12 counts refusals, not silence.** `rejectedWavesForOrder` reads only `response = 'REJECTED'`. An `EXPIRED`
offer is silence and a `WITHDRAWN` one is a change of plan — `11 §9.3` weighs the expiry at half a refusal in the
acceptance statistic, but the *re-offering* rule is a sentence about something the rider said. Treating silence as a
no would quietly shrink the candidate pool every time a phone slept, which is the same class of error as the sweep
in D116 counting nobody: a statistic and a refusal are different objects. Keys are lower-cased hex so the assembly's
lookups match whatever case TiDB returns.

**The candidate call does not degrade quietly.** `broadcast` discards its failure because a notification that fails
is not a reason to fail an order; `candidates` returns it, because dispatch cannot plan without it. Specifically, a
`200` whose envelope has no `candidates` array is `SERVICE_DEGRADED` and **not** an empty list: "nobody is online"
and "the feed answered something else" look identical downstream, and only one of them means the wave should be
abandoned as a zone with no riders. That is the same distinction D117 drew on the other side of the wire,
deliberately made twice.

Tests: three in `realtime-binding.test.ts` (the list unwrapped from the envelope; a listless 200 as degraded; a
non-2xx as the caller's to handle) and seven in `dispatch-candidates.test.ts` (one statement for eight offers with
matching statement text and eighty bindings, one instant across the wave, rank and score keeping their rider, an
empty wave writing nothing, the duplicate rider refused with no statement issued, the already-expired offer refused,
and the rejection read grouping by rider in lower-case hex while ignoring expiry).

*Open:* the route that composes D117–D121 — order by code, its zone polygon, the vendor point, the feed, the
assembly, `FILTERS`, `planWaves`, `insertOfferWave`, and the ring. Everything it needs now exists; what is left is
the order of operations, the `dispatch_locks` guard that stops two coordinators planning the same order, and the
audit row.

## D122 — Answer the question before you act on it

Nine rungs built the pieces of a dispatch decision. Not one of them could tell an operator what the decision *was*:
the planner is pure, the assembly is pure, the query and the feed each answer half a question, and the writer's store
verbs write. So the first composition rung is deliberately **read-only** — `POST /internal/dispatch/eligibility
{orderCode}` — and it answers with the filter verdict for every rider in the order's zone.

**Why not plan the wave here.** Ranking needs `11 §8`'s acceptance model: eleven factors, weights, a probability per
candidate. It is not built. A route that needed it would either invent a probability (waves nobody can explain, and
a ranking that quietly decides who earns) or fall back to distance (a plausible-looking number with no document
behind it). Both are worse than waiting, because both produce output that *looks* like dispatch and is not. The
verdicts need no model at all: `FILTERS` are numbered rules over a snapshot, and they are already written.

**The refusal is the deliverable.** `{filter: 4, reason: "POSITION_FRESH"}` per rider is what turns an empty wave
from a mystery into a diagnosis. It is also the exact shape the rider's app will render — the number is stable, the
name is localised, and neither is a message invented in a handler. `unjudgeable` is kept separate because a vehicle
nobody described and a zone with no polygon are data errors: reporting them as filter refusals would claim a
judgement nobody made (D120's rule, now on the wire).

**Failures that must not look like an empty zone.** No `REALTIME_BASE` is `503 SERVICE_DEGRADED
{reason: "not_configured"}`; a feed that answers no list is `503 SERVICE_DEGRADED
{reason: "candidate_feed_unavailable"}`. Both are the third appearance of the same distinction (D117's 501, D121's
degraded client) and the reason it keeps recurring is that `[]` is the one answer dispatch cannot safely misread. A
zone row that does not exist is `404 ZONE_NOT_FOUND`; one whose outline will not parse is `422 ZONE_TOO_FEW_POINTS`,
because a city-wide wave from a bad polygon is a worse failure than a refused request.

**Existing codes, no new ones.** The order not being in `RIDER_SEARCH` is `409 ORDER_NOT_ACCEPTABLE {state}`, which is
what the code means: this order cannot be acted on now. Adding `DISPATCH_*` codes would have meant a new prefix,
three pinned counts and a regenerated client, for vocabulary that already exists — and a new prefix is a public
promise about a surface that is internal.

**The device translation is the fourth appearance of the two identities.** `devices` is keyed by user id; the
snapshot's `riderId` is the row id; filter 14 compares row ids. The route translates once, through each candidate's
own two ids, and the deletion proof is that switching it to `riderId` turns two tests red — the same class of bug as
D110 and D120, in the third place it could hide.

Tests: seventeen in `dispatch-route.test.ts` — an eligible rider and the count, refusals by filters 4, 6, 11, 12 and
14 each asserted with its number and name, an unknown vehicle as unjudgeable rather than refused, two riders reported
side by side, the five pre-rider refusals (unknown order, wrong state, missing zone, unparseable polygon, empty
body), both degraded-dependency answers, a missing token with **zero** database calls, and a statement-by-statement
assertion that the route never writes.

*Open, and now precisely one thing:* `11 §8`'s acceptance model. With it, this route's verdicts become `planWaves`
input, `insertOfferWave` gets its wave, and the ring follows. Everything else on the dispatch path is built and
tested.

## D123 — The weights do not add up, and saying so is the rung

`11 §5` lists fourteen factors with default weights and closes with **"Sum: 1.000."** They sum to **1.005**. This is
not a rounding artefact: 0.170 + 0.150 + 0.130 + 0.110 + 0.095 + 0.070 + 0.055 + 0.055 + 0.050 + 0.045 + 0.030 + 0.025
+ 0.010 + 0.010 = 1.005 exactly. The code that implements the table found it on the first test run, which is what
code is for.

**The fourteen numbers stay, the sum is corrected.** Three candidates: trim 0.005 from some factor, divide everything
by 1.005, or implement verbatim and say so. The first changes a weight an operator set; the second changes *all*
fourteen, invisibly, and can reorder two candidates in a way no one can attribute afterwards. So the numbers are
verbatim, `weightSum()` returns 1.005 and exists precisely so the admin panel can warn about it, `DEFAULT_WEIGHTS`
is frozen and carries the explanation, and `11 §5` now says 1.005 with the reasoning.

**`score()` does not clamp to 1.** A rider who is perfect on all fourteen scores 1.005. Clamping would make that
indistinguishable from 1.0, and the number is only ever compared against other candidates' numbers — nothing
downstream treats it as a probability except factor 3, which is separate. The consequence is stated in the module
and asserted in a test.

**Every factor is a named function, not a term in one expression.** The document's `score_candidates` is a single
fourteen-line expression; here each factor is exported with its constants (`ETA_EARLY_DECAY_S`, `ETA_LATE_DECAY_S`,
`FAIRNESS_IDLE_SATURATION_S`, `VENDOR_FAMILIARITY_DELIVERIES`) because the anchors are what a benchmark argues
about, and an anchor that can only be reached through a weighted sum cannot be argued with at all. The deletion
proof for `eta_fit`'s asymmetry — making the late decay 900 s, symmetric with the early side — turns two tests red,
starting with the one that says a rider eight minutes early beats a rider six minutes late.

**`acceptanceProbability` is factor 3, and `score` is the ranking.** They are different objects and the wave model
consumes the first: `pNobodyAccepts` multiplies `(1 - acceptance)`, which is a probability, while the *ordering* of
candidates is the weighted sum. Keeping both on the returned type is what lets `planWaves` (which today sorts by
`acceptanceProbability`) be wired correctly in the next rung without either number being quietly repurposed.

**What is still an input, and what that means.** `acceptanceRate` and `ratingLowerBound` arrive already Wilson-
bounded; the logistic propensity model (`09 §7.4`) and the Wilson estimators are not built, so the factors take
their outputs and the caller supplies them. `zoneCoverage` and `vehicleSuitability` arrive as judged values for the
same reason — the demand forecast and the vehicle judgement belong to `09` and `12`. Each is documented at the
field, so the seam is visible rather than implied.

Tests: twenty-eight in `dispatch-scoring.test.ts` — the weight sum and its immutability, `proximity`'s half-at-median
anchor and its divide-by-zero fallback, `eta_fit`'s sweet spot, both decay slopes, the asymmetry and its reversion,
`reliability`'s 0.6/0.4 split and its clamping order, `fairness`'s saturation, median and 3× anchors, `vendor` and
`area` familiarity, `load_balance` at the ceiling and with no capacity, `cash_headroom` at exactly zero, `freshness`
with no budget, the perfect-candidate total of 1.005, weight-shifting changing the ranking, and determinism under
input reordering plus the lexicographic tiebreak.

*Open:* the last line of the dispatch path — `scoreCandidates` fed by the D122 route's snapshots, `planWaves` ranking
on `score` while its confidence multiplies `acceptanceProbability`, `insertOfferWave`, the ring.

## D124 — Two numbers that were one, and the last pure step before the database

`ScoredCandidate` had a single numeric field, `acceptanceProbability`, and `planWaves` used it for two unrelated
jobs: it **sorted** candidates by it, and it **multiplied** `(1 − p)` to get the chance nobody in a wave accepts. With
D123's fourteen-factor scoring in place that field split in two — a rider can be first in the city on proximity,
idleness, reliability and familiarity while being middling on how often they tap *accept* — and the sorting key is no
longer the probability the confidence arithmetic needs. Sorting by acceptance would rank the glib rider first;
multiplying the weighted sum as though it were a probability would report a `pNone` that is not a probability at all.

**So the type carries both, and each has one job.** `score` is the ranking, `acceptanceProbability` is the confidence,
and `score` is *optional* because a caller with no scoring model still deserves a deterministic order — the fallback
is exactly what the old code did, and it is documented as a fallback rather than presented as equivalent. The
deletion proof is the point of the rung: removing the score comparison from the sort turns the test that says *a
wave is ordered by the weighted score, not by who tends to say yes* red, and nothing else, which is precisely the
bug that would otherwise ship silently.

**`pNone` is still computed from the acceptance probability**, and a test pins `0.5 × 0.75` for two riders so a
future "simplification" that multiplies scores fails loudly. That number is what wave sizing turns on: killing a wave
early because the model says it will be accepted is only cheap while the model's unit is a probability.

**The last pure step gets its own module.** `domain/order/dispatch-plan.ts` `planWaveWrite` maps a `Wave` to the rows
the writer inserts: ranks from **the planner's order** (re-sorting here would let two orderings disagree about who
was asked first, and `rank_in_wave` is the planner's answer recorded for audit), one `expiresAtMs` from
`WAVE_SCHEDULE` via `waveExpiryMs` (a wave's twenty-five seconds is a promise about the wave, D121), the order's
payout on every offer, and the score that produced the rank so a trace can be re-derived months later. A wave naming
a rider who was not scored throws `RangeError`: the planner can only have chosen from the scored list, so a mismatch
means two different lists reached this function and the audit row would carry a ranking the decision never made.

Tests: ten in `dispatch-plan.test.ts` — ordering by score against acceptance, `pNone` from acceptance, the no-score
fallback, sequential ranks, the 25 s / 22 s / 20 s budgets across waves one, three and five, the payout repeated on
every offer, ids round-tripping to the bytes an offer points at, the contradictory plan throwing, and `pNone` riding
along with the plan.

*Open:* the writer route that calls all of this — it needs the scoring facts (`idle_s`, `deliveries_today`, the
Wilson rates, vendor and cell familiarity) which no query reads yet, then `scoreCandidates`, `planWaves`,
`planWaveWrite`, `insertOfferWave`, the audit row and the ring. That loader is the one piece of dispatch that is
data rather than decision, and it is next.

## D125 — History, from three statements, with two zeros that are honest

The fourteen factors needed a rider's past, and nothing read it: `rider_stats` had never been queried, `orders`
carried `delivered_at` for nothing, and the scoring module had been taking `acceptanceRate` and `ratingLowerBound` as
inputs since D123. This rung is the loader, and the shape of it is decided by one constraint — the whole thing sits
inside a twenty-five-second wave, so it is **three statements over an `IN` list**, never a query per candidate. That
is the same rule the candidate feed follows (D117) and the same failure it avoids: sixty round trips inside a wave is
a wave that has expired before its offers are written.

**Every rate is a Wilson lower bound, and that is the load-bearing decision.** A rider who has taken one offer and
accepted it has a 100 % rate; on a raw ratio they outrank a rider with 300 out of 400. `wilsonLowerBound(1, 1)` is
under 0.25 and `wilsonLowerBound(300, 400)` is over 0.70, and the test asserts exactly that ordering. It is also why
no history means exactly zero rather than a hopeful default: the bound prices in what is not known, and for a rider
with no trials the honest value is zero.

**A new rider's disadvantage is visible, not padded.** Every rate factor scores zero for a rider on their first
shift. That is a real cost and it is left in place, because the alternative — an optimistic prior — is a number
nobody can defend when a first-shift rider is dispatched a long order and abandons it. The one place the model
already compensates is factor 5: `fairness` gives a rider with nothing delivered today the full load term, and idle
time accrues from the moment they go online. Stated, so the next person does not "fix" the zeros.

**Two factors score zero because the schema has no evidence, and the difference matters.** `orders` has no
delivery-cell column, so `area_familiarity` (factor 8) has no input; there is no ratings table, so `rating` (factor 6)
has none either, and the loader returns `rating: null` rather than a plausible 0.8. A factor fed zero because the
evidence does not exist is a schema gap; a factor fed zero because nobody wrote the query is a bug. Recording which
one each is, at the module and here, is what stops the second kind being mistaken for the first.

**`DELIVERED` and `SETTLED` both count as a delivery.** Settlement is bookkeeping after the food arrived; a rider's
familiarity with a kitchen does not lapse because the money has not reconciled. `MAX(delivered_at)` gives idle time,
capped at a day, and a future timestamp — a clock skew — is zero rather than a negative. A rider who has never
delivered is zero idle, not infinite: the fairness factor already rewards them through the load term.

Tests: eleven in `dispatch-stats.test.ts` — the Wilson bound at zero trials, at one of one, at 300 of 400, the
ordering between the last two, and an inconsistent aggregate staying inside `[0, 1]`; three statements whatever the
candidate count with one placeholder each; the three answers merging into one history; a rider with no rows absent
from the map; an empty list costing no queries; the vendor bound first so the vendor split is right; and idle time
from the last delivery, never-delivered, capped, and clock-skewed.

*Open:* the writer route. With history, scores, the plan and the wave insert all in place, it is order → snapshots →
facts → scores → waves → `planWaveWrite` → `insertOfferWave` → audit → ring, plus a `dispatch_locks` guard so two
coordinators cannot plan the same order twice.

## D126 — The route that finally writes a wave

Nine rungs of pieces and one line that uses them: `POST /internal/dispatch/plan {orderCode}`. It takes the planning
lock, re-reads the order, asks realtime where the riders are, assembles and filters them, reads their history, scores
them, plans the cascade, writes **wave 1**, records an audit row and releases the lock. Nothing rings yet — the alarm
is the FCM binding's rung — but an offer row that a rider can claim now exists, which means D113's claim route has
something real to accept.

**Three guards, each for a race that actually happens.** The **lock** first: two coordinators woken for the same order
(a retried trigger and the original) would otherwise both write wave 1, producing duplicate offers, and
`dispatch_locks` is unique on `order_id`. The claim uses `ON DUPLICATE KEY UPDATE … IF(expires_at <= now, …)` so a
stale lock from a crashed planner is stolen instead of blocking the order until somebody deletes a row by hand, and
the read-back check is what tells *us* we own it rather than assuming the statement succeeded. It is held for ten
seconds and released in a `finally`, including on every refusal path. The **order state** second: if it was assigned
while we were thinking, this is not a wave, it is a race the claim route already won. The **live wave** third:
unanswered offers inside their TTL mean eight phones ringing, and writing wave 2 tells those riders the order is gone.

**Wave 1 only, and the cascade returned.** `planWaves` returns up to five waves; writing all five offers the order to
everybody at once, which is the exact opposite of a cascade. So one is written and the plan is answered, so the caller
knows when to come back — D116's sweep is already the thing that will notice expiry and call this again.

**No eligible candidates is a 200 with a reason.** `{wave: null, offered: [], reason: "NO_ELIGIBLE_CANDIDATES"}`,
because a zone with nobody available is the state the fallback ladder exists for, not a request to fail. The per-rider
verdicts are what an operator reads to find out *why* (D122), and the route answers rather than 404-ing into a retry
loop.

**Two scoring inputs are deliberately constant, and named.** `coverageValue: 1` and `vehicleSuitability: 1` — the
demand forecast (`09`) and the vehicle judgement (`12`) are not built, and a `1` means "no penalty from this factor",
which is the only honest value available: a `0` would suppress every rider. Factor 8 (`deliveriesIntoCell`) stays `0`
because `orders` has no cell column (D125), and factor 6 (`rating`) stays `0` because there is no ratings table. The
difference between "1, because there is no evidence of a problem" and "0, because there is no evidence of quality" is
the difference between the two kinds of missing data, and it is written down at each field.

**The completion rate is Wilson-bounded from what the platform actually records**: deliveries over lifetime accepted
offers. On-time rate has no separate signal, so it takes the same figure rather than a guess — which makes a rider who
accepts and does not deliver look unreliable, exactly what factor 4 is for. When penalties feed scoring, the two rates
separate; until then one number doing two jobs is stated rather than hidden.

**A ten-second lock, not a transaction.** TiDB's HTTP driver has no session to hold a transaction across a Worker's
`fetch` calls (D90's reasoning), and the work between the lock and the insert includes a network call to realtime. So
the lock is a lease with a deadline, and its failure mode — a planner that dies mid-plan leaves the order blocked for
ten seconds — is strictly better than two planners writing the same wave.

Tests: ten in `dispatch-plan-route.test.ts` — the offer written with wave, rank, score and payout; the single insert
with its ten bindings; the plan returned with wave 1's 25 s TTL; a live wave blocking before any write; another
planner's lock reported as `409 ORDER_LOCKED` with no work done; the lock released on the success path; an assigned
order refused before the lock; no candidates answered rather than failed; the audit row carrying the wave and the
unjudgeable candidates; and a missing token with zero database calls.

## D127 — A wave that nobody is told about is a folder of rows

D126 wrote the offers. This rung makes a phone aware of one, and it does it through the path that already exists —
`announce` → realtime's `/internal/broadcast` — rather than by inventing a push client. The consequences of that
choice are worth stating, because they are the reason it is the right first rung and not a shortcut.

**The audience is the user id, the offer is the row id, and both are needed.** `announce`'s `audience.riderUserId` is
the `sub` that a rider's own channel resolves `self` to, while `order_offers.rider_id` is the `riders` row. The route
already has both on each candidate, so it translates **once** through a map built from the candidate list, and the
deletion proof is that emptying the audience turns the ring test red — the fifth appearance of D110's distinction,
and the first where the symptom would be an alarm delivered to nobody rather than a wave written for nobody.

**The message is data only, and that is a rule with a scar.** The payload carries `title` and `body` as *fields*,
alongside the numbers, and never a platform alert object: on several Android builds letting the OS draw the alert means
the full-screen intent never appears, and a rider misses an order worth ৳1 800 (`fcm-payload-purity`, `15 §9`). The
guardrail enforces it; the module's documentation explains why somebody would otherwise be tempted.

**The countdown is computed from the offer's expiry, not passed in.** `secondsRemaining` is derived inside
`offerAlarm` from `expiresAtMs - nowMs`, so the app cannot be handed a number that disagrees with the row it is
counting down — and an offer that is already expired still produces a message, counting from zero, because the app has
to be able to say "too late" rather than show nothing.

**Both languages always travel.** The rider app picks from `{en, bn}` on the device; sending one language and
translating on the device would mean two builds of every string, and `05`'s copy rules apply to an alarm as much as to
a screen.

**The send cannot fail the wave.** `announce` is handed to `waitUntil` and discards its `Result` (D85's rule): the
offers are written and claimable whether or not a socket heard about them, and a ring that fails costs a missed
notification, not a lost order. What is *not* discarded is the decision to ring at all — the loop runs after
`insertOfferWave`, over exactly the offered riders, so nobody unoffered is woken and nobody offered is skipped.

**What this rung does not do, stated.** It rings **connected** riders: the path is realtime's broadcast, so a rider
whose socket is closed gets nothing until they open the app. The FCM path — writing `fcm_dispatches` rows and letting
the sender deliver to a sleeping phone — is the piece that makes the ring work for a rider with the app closed, and it
needs the device-token join plus the sender's retry semantics. Everything the message needs (a data-only payload, both
languages, a truthful countdown) is now built and tested, so that rung is delivery rather than copywriting.

Tests: seven in `offer-alarm.test.ts` — the countdown from the expiry, an expired offer counting from zero, taka from
paisa and one decimal on kilometres, metres below a kilometre, the payload's exact key set, both languages present and
different, and the catalogue's event name — plus three in `dispatch-plan-route.test.ts`: one broadcast per offered
rider audienced to their user id with the copy in the payload, the ring ordered after the feed and the write, and no
broadcast at all when nobody was offered.

## D128 — The ring reaches a pocket, and a failed send is a row

D127 rang phones whose app is open. That is the minority of the day: a rider between orders puts the phone down, and
the alarm that matters is the one that wakes it. So each offered rider's valid tokens now get a message through
`bindings/fcm.ts`, which is deliberately a *client* and not a queue — one HTTP call, one message, no retry inside it.

**Data only, `high` priority, and both are load-bearing.** The message carries `data` and no platform alert object,
because letting the OS draw the alert means the full-screen intent never appears on several Android builds and a rider
misses an order worth ৳1 800 (`fcm-payload-purity`). The priority is `high` for a subtler reason: a *data* message at
normal priority can wait in a dozing device's queue until the offer has expired, which is worse than not sending it at
all — the rider gets an alarm for a delivery that is already gone. Both facts are asserted in the binding's tests
rather than left to review.

**Strings on the wire, numbers in the code.** The push format wants string values, so the payload is stringified at the
one place it leaves: the same `data` object the SSE ring carries, plus both titles, flattened with `String(value)`. A
number sent as a number is a message the runtime rejects, and the failure would look like a dead token.

**Every send is recorded, including the failures.** One `fcm_dispatches` row per token with `SENT` or `FAILED`, the
attempt index, and the message id when there is one; `device_id` is `null` because the token is the identity this path
has and the join back to the device is the log's job, not the dispatcher's. This is what makes the alarm measurable:
`15 §9`'s coaching flow depends on knowing whether a rider's phone actually received the alarm, and a send that is not
recorded is a claim nobody can check.

**Absent credentials mean no push and no row.** `fcmConfigured` guards the whole branch, and a deployment without
`FCM_PROJECT_ID`/`FCM_ACCESS_TOKEN` still rings connected riders through the SSE path and writes nothing that claims a
send. That is the same rule `announce` follows (D85): an unconfigured dependency is a configuration state, not an error
on every order.

**Queued, not awaited.** The sends go on `waitUntil`, one rider's tokens in sequence within it — eight riders are eight
independent chains, so a slow phone cannot delay the ninth rider's alarm, and the wave's response is not held open by
Google.

**The retry story is deliberately not here.** A `FAILED` row is a fact; retrying is the sender's business, and it needs
the offer's remaining life to decide whether a retry is even meaningful. `attempt` exists on the row for that rung,
which will read unclaimed `FAILED` rows inside their wave's TTL — the same shape as D116's sweep.

Tests: six in `fcm-binding.test.ts` — the v1 URL and bearer token, the data-only body at high priority with the token on
the message, a 404 as a typed failure carrying the status, a 200 with no message name as a failure, an aborted request
as `DEPENDENCY_TIMEOUT`, and `fcmConfigured` on every absent-credential combination — plus three in
`dispatch-plan-route.test.ts`: two tokens rung once each with two recorded rows, the payload carrying the offer data and
both titles, and nothing sent or recorded when the deployment has no credentials.

## D129 — The second wave was going to be the first wave again

Writing D126's route exposed a real bug in it: `planWaveWrite(plan[0])` always wrote **wave 1**, because `planWaves`
numbers a fresh cascade from one. A second planning call — the advance driver, or an operator retrying after a crash —
would therefore re-insert wave 1 and be refused by `uq_offers_order_rider_wave`, which is the good outcome: the bad one
is a retry that quietly writes the same eight riders as "wave 2" and rings them twice for an order they already
declined.

**The fix separates numbering from contents.** The **contents** are the planner's first wave — the best remaining
candidates after the rejections this order has already collected, because `rejectedWavesForOrder` feeds filter 12, so a
rider who said no is not in the plan at all. The **number** is the order's `lastWave + 1`, and the TTL is that wave's
own from `WAVE_SCHEDULE`. Taking the plan's wave 2 instead would have looked correct and silently skipped the best
candidates on every re-plan: a rider who had never been asked would sit behind one who had been asked and had not yet
answered.

**Past wave 5 the ladder ends, and the route says so.** `{wave: null, offence: [], reason: "LADDER_EXHAUSTED"}` with a
`200`, not an error: five waves asked and nobody took it is a state `11 §11` answers with escalation and then a refund,
and neither of those is a wave. A sixth wave would be a policy the document does not contain.

**`/internal/dispatch/advance` is the same handler, named for intent.** It exists because the caller's sentence is
"this order's wave expired, ask the next group", not "plan a wave" — and a route named after what the caller means is
the cheapest documentation there is. The guards are identical: the live-wave check already refuses while phones are
ringing, and the lock already refuses while another planner is working, so the advance path needed no new code beyond
the number.

**The line budget caught the route at 622 lines, and the fix is the right one.** The five joins between a rider's
history and the scoring table — acceptance, the two rates, idle, the zone median — moved to
`domain/order/dispatch-facts.ts`, where they are pure and testable at their anchors, and the route keeps the I/O. A
600-line warning that arrives because a file is doing two jobs is worth obeying; the same warning a year later is
usually noise.

Tests: four in `dispatch-plan-route.test.ts` — a second call writing wave 2 with wave 2 on the insert, a fourth writing
wave 4, wave 5 followed by `LADDER_EXHAUSTED` and no write, and the advance route writing wave 3 from `lastWave: 2` —
plus four in `dispatch-stats.test.ts` for the moved joins: the Wilson bound of lifetime acceptance, completion over
accepted offers with on-time borrowing it, the even-count median of the riders in play, and UTC midnight as the day
boundary.

*Open:* the caller. Realtime's zone alarm is the natural home — it already runs while riders are connected and already
calls core for the auto-cancel ladder — and `POST /internal/offers/expire` (D116) is what tells it that a wave has
timed out. Wiring those two together is the last piece of the dispatch loop.

## D130 — The loop closes: something finally asks for the next wave

Every piece of dispatch existed and nothing called it. The caller had to be realtime, because it is the only thing in
the system that runs while riders are connected, and the shape of the call is what decides whether a stale wave costs
an order or a minute.

**Two calls, and the first one had to change.** `POST /internal/offers/expire` used to answer counts and waves; it now
also answers the **order codes** it left without a live offer, read *before* the update that erases the evidence. That
change is D116's route learning the question its caller actually has — *whose wave expired?* — and without it realtime
would have had to scan offers itself, which is core's data. `POST /internal/dispatch/advance` is then one call per
order that needs one, and a tick with nothing expired is a single round trip.

**It runs last in the alarm, and that ordering is not cosmetic.** Presence first (an absence published this tick erases
its own rider), then the D1 sweep, then dispatch. Advancing a wave towards a rider whose `rider_current` row is being
erased is a wave that rings nobody — the candidate is gone by the time core's feed runs, so the order gets a wave of
nobody and the tick after it repeats. After the sweep the board is honest.

**It runs even with no live-position database.** A deployment without D1 can still have offers: `sweep === null` used to
end the tick, and now it skips to the dispatch step. Offers expire on the wall clock, not on a database being present.

**A failed tick leaves the state alone.** Core refusing (500), the transport dying, or a call exceeding its 1 500 ms
budget all produce `{expired: 0, advanced: 0}` and a log line, never a partial advance recorded as success. The next
alarm is seconds away and the offers are still expired and the orders still searching, so the retry is free; claiming
success for a wave nobody wrote is the one outcome that would strand an order until a human noticed.

**A `null` wave is an answer.** `{wave: null, reason: "NO_ELIGIBLE_CANDIDATES"}` or `"LADDER_EXHAUSTED"` means the tick
did the right thing and there is nothing to count. Treating it as a failure would retry five times on an order that
`11 §11` says should now be escalated or refunded.

**Absent configuration is absent behaviour.** No `CORE_BASE_URL` and no `INTERNAL_TOKEN` builds no client, and the
alarm is exactly what it was before this rung — the rule every core client in this Worker already follows.

Tests: six in `core-wave.test.ts` — a quiet tick as one round trip, each emptied order advanced by code, a `null` wave
not counted as an advance, a 500 leaving the state untouched, a dead transport likewise, and the sweep's empty body —
plus five in `sweep.test.ts` for the ordering: presence → sweep → wave, the wave tick with no D1 store, a sweep failure
that does not stop it, a wave failure that is recorded rather than thrown, and no client meaning no tick.

*Open:* the dispatch loop is closed for a single zone's alarm, but the alarm belongs to a Durable Object that exists
only while its zone has traffic — an order in a quiet zone still needs a driver. The honest fix is either a scheduled
sweeper over `RIDER_SEARCH` orders or moving the tick to the vendor room, which already wakes for a placed order; both
are deployment questions rather than dispatch ones, and this rung states them rather than guessing.

## D131 — A push that failed was the end of the story

D128 sent one push per valid token and recorded `SENT` or `FAILED`. It also said, in its own doc comment, that "no
retry logic" belonged there "because the retry story belongs to the caller that knows how long an offer lives" — and
then nothing ever picked that story up. A 503 from Google, a socket that aborted at 1 500 ms, a rate limit: any of
them meant a rider whose phone never rang for an offer that was still theirs, with a row in `fcm_dispatches` as the
only trace.

**The retry is a statement, not a scheduler.** `POST /internal/dispatch/pushes/retry` runs one query whose joins *are*
the policy: `outcome = 'FAILED'`, `attempt < 3`, the failure at least 2 s old, the offer unanswered and with 3 s or
more of life left, the token still `valid`, and `NOT EXISTS` a later row for the same token and order (which covers
both "it has been delivered since" and "we are looking at an older failure than the newest one"). A pass has no
judgement of its own to get wrong, and the caps are the query's: `LIMIT 20` bounds a pass, `attempt < 3` bounds a
token, and the wave's own 25 s bounds the whole thing.

**Why the retry waits, and why it stops early.** A timeout that just happened will fail the same way if repeated
immediately, so a retry is due 2 s after the failure. And an alarm for an expired offer is worse than silence — the
rider taps, and the accept answers `OFFER_EXPIRED` — so a retry is abandoned once the offer has under 3 s left. Both
windows are constants in `domain/order/push-retry.ts` next to the attempt cap, and both are passed into the query as
`DATETIME(6)` bounds so the database does the arithmetic.

**Permanent failures prune, transient ones wait.** `pushFailureIsPermanent` splits the statuses: 404 (unregistered),
400 (a payload that will be refused the same way), 401/403 (credentials), and everything else that is not 408, 425,
429 or 5xx. A permanent failure invalidates the `device_tokens` row — `valid = false`, `invalidated_at`,
`invalid_reason` — and the retry query's `valid = 1` join is what stops the next pass, without a second table or a
nightly sweep. A 404 is also pruned at **first** send now, which is where the token actually died.

**Two D128 defects fell out of building it.** The alarm carried `offerId` as the **rider's** id, so the deep link a
rider tapped asked `/v1/orders/{code}/offer/{riderId}/accept` for an offer that does not exist; it now carries the
offer row's id, which is what the plan already minted. And `attempt` was the token's index in the device list, so a
rider's second phone started life on attempt 2 and the retry arithmetic (`attempt + 1`, `attempt < 3`) would have been
nonsense. Both are the kind of bug that only surfaces when a second caller reads the first one's rows.

**One audit row per pass, at `INFO`,** listing the orders and the four counters — retried, sent, failed, pruned. The
per-device detail stays in `fcm_dispatches`, exactly as `dispatch-log` put it there, and a pass with nothing to do
writes nothing at all: no rows, no audit line, no chain entry. A table that records heartbeats is a table nobody reads.

**The tick gained a third step, and it had to come last.** Expire → advance → retry. The wave the advance just planned
is the one that just pushed, so its failures are precisely what the pass is for; running it first would find the
previous wave's offers, which the expire has already emptied. Realtime's `createCoreWave` gained `retry()` and the
`WaveTick` gained `retried`, and the alarm's log line only prints when something expired or something was re-rung.

Tests: ten in `push-retry.test.ts` — the permanence table, per-token attempts, a failed send retried and recorded as
attempt 2, the query's window asserted clause by clause, the alarm naming the offer, a 503 left alone against a 404
pruned, nothing-to-do writing nothing, absent credentials, the shared token, and one audit row per pass — plus two in
`dispatch-plan-route.test.ts` for the two D128 defects, and three in `core-wave.test.ts` / `sweep.test.ts` for the
three-step tick and its log line.

*Open:* a retried alarm carries `pickupDistanceM: 0`, because the routing snapshots belong to the request that planned
the wave and are gone by the time the retry runs. Payout and countdown — the two numbers a rider decides on — are the
offer's own, and inventing a distance would be worse than omitting one; the honest fix is a paid routing call per retry,
which is not obviously worth it for a figure the rider has already seen once.

## D132 — The announcement nobody received

D130 closed the dispatch loop and recorded its own gap: the tick lives in the zone's Durable Object alarm, and that
object exists while the zone has traffic. An order placed in a quiet zone — every rider in a pocket, no sockets, so no
heartbeats — had nothing to advance its wave. The honest fix is not a cron (the no-cron rule is not an obstacle to be
worked around: a scheduled Worker that silently stops firing is invisible) and not a global sweeper in another Worker
(core would have to guess at cadences realtime already knows). It is in the room.

**The announcement is the wake.** Core already broadcasts each wave to the zone room (`offer.new`), and a broadcast is a
request, so the object exists for at least that moment. What it lacked was a reason to be alive later, and an offer is
one. `POST /internal/wake` takes the instants the room must wake for, `PresenceHub.armDispatch` merges them into a
sorted list, and `rearm()` now sets the room's single alarm to the earliest of the presence deadlines **and** those
instants. Two per wave: `RETRY_WAKE_MS` (3 s — D131's retry needs a tick while the offer is live, not at its expiry) and
`expiresAtMs + EXPIRE_SLACK_MS` (1 s of slack, because the expiry is a comparison against the database's clock and a
wake a millisecond early expires nothing). The loop then sustains itself — alarm, expire, advance, announce, arm — and
when the ladder runs out nothing re-arms and the object becomes a candidate for eviction, which is exactly the argument
`presence/deadline.ts` already made for being allowed at all.

**The invariants are the interesting part.** An instant already at or before the new ones makes arming a no-op, so a
wave every few seconds is not a storage write every few seconds; a later instant never postpones an earlier one, so an
offer's expiry cannot delay a person's heartbeat deadline; an instant in the past is dropped rather than scheduled,
because a deadline that has passed is a tick already missed; and a fired instant is *spent* — `alarm()` removes what it
fired for and re-arms for what is left, so the retry pass hands the alarm to the expiry and the expiry hands it to
nothing. The body is bounded (`MAX_WAKE_INSTANTS`) and validated, because an alarm set to a nonsense instant is a room
that never ticks again. The zone travels on the wake, and a room that has never been connected **learns** it there —
the first wave into a new zone is precisely the wave that arrives at a room with no history.

**A wake that fails is a missed wake.** The frame is recorded before the forward is attempted, the answer carries
`armed`, and a room that cannot be reached costs a late tick rather than a lost broadcast. Absent `ZONE_HUB` there is
no forward at all and the announcement is exactly what it was before this rung.

**And the hole had a second bottom.** Wiring the wake meant watching an offer actually travel, which is how `order.offer`
turned out to be a name realtime's ring does not carry: `08 §9.1`'s catalogue has an **Offer group** — `offer.new`,
`offer.withdrawn`, `offer.expired`, `offer.claimed_by_other` — and D127 had invented an Order-group spelling. The gate
is a map, so the failure was silent by design: the internal route answered `unknown_event`, `announce` treated that as
a degraded notification, and not one offer frame ever reached a socket. The alarm now emits `offer.new`, the map
carries it, and a catalogue test pins both halves — that `offer.new` resolves, and that the invented name does not.

Tests: six in `dispatch-deadline.test.ts` (the two instants, no deadline, a far horizon, an expiry already past, a wave
announced inside its retry window, ordering), five in `zone-wake.test.ts` (addressing, no-op with nothing to arm,
refusal and a dead transport, the body's validation, route/client agreement), six in `hub.test.ts` (earlier wins, later
ignored, fired instants spent, cleared when empty, past dropped, no redundant write), three in `zone-hub.test.ts` (the
wake arms and teaches the zone, an earlier deadline is not postponed, bad wake refused), three in `internal.test.ts`
(the instants derived from the payload, nothing forwarded without a deadline, a failed wake not failing the broadcast),
and one in `catalogue-coverage.test.ts` for the name.

*Open:* the retry wake is one instant per announcement, so a wave whose retries also fail gets no second retry instant
until the next announcement — the expiry tick runs D131's pass anyway, but by then the offer is gone. A second retry
instant would need the announcement to know `RETRY_AFTER_MS × 2`, which is a policy the room should not have to hold;
the honest fix is for the pass to re-arm itself when it retried something, which is a change to `core-wave.tick`'s
answer rather than to the room.

## D133 — Factor 3 stops being blind to the offer

The dispatch engine ended D132 in good order: a wave is planned, announced, pushed, retried, expired, advanced, and a
zone with nobody in it still wakes. The one thing every step of that shared was a number that did not deserve the trust:
factor 3 of the score — *will this rider accept* — was the Wilson lower bound of that rider's whole history. A rate is
honest and it is unconditional. The rider who takes four offers in five will not take a ৳40 order two kilometres the
wrong way at 23:00, and the rate cannot say so; worse, `pNone` and therefore wave size were computed from it, so a bad
estimate sized the wave wrong too.

**`09 §7.4` specifies eight coefficients and the document is right about why.** Not for accuracy — it concedes the
difference to a large model is under two percentage points — but because eight numbers fit on one screen and an operator
who can see payout positive and distance negative knows the model is sane. So `domain/order/propensity.ts` implements
exactly that: eight features, the sigmoid with the document's own logit clamp, `g = p − y` with an L2 term of 0.001, and
the learning rate of 0.01. `learnStep` returns a **new** vector, because a model that mutates itself cannot be replayed
against a trace and `§12`'s benchmark has nothing to re-run.

**The signs live in the weights; the features are magnitudes.** Every feature is normalised into `[0, 1]` — a distance is
*how far*, not how bad — so a coefficient's sign is the only opinion in the table. Time of day is a sine/cosine pair over
the Asia/Dhaka day rather than an hour, because 23:59 and 00:01 are two minutes apart in a rider's life and fifty-nine
hours apart as a number.

**Shrinkage, not a cliff.** The figure factor 3 receives is `(samples / 50) × model + (1 − samples / 50) × rate`. With no
evidence the answer is exactly the rate that was there before this rung; at fifty recorded outcomes the model is trusted
outright. That is the same confidence arithmetic `11 §5` already applies to every other rate in the table, and it means a
zone cannot be made *worse* by a model it has not trained.

**Configuration, not state.** The weights live in `platform_config` under `dispatch.propensity` — per zone, with the
all-zero UUID the schema already uses for a global default — so they are versioned, audited and editable from Brain Lab
like every other number an operator owns. `scoringZone` reads the zone row, falls back to the global one, and treats a
row that does not parse (a typo, an old shape) as *absent*: a bad coefficient vector must degrade to the rider's record,
never fail a dispatch.

**The route had run out of room, so the push moved out.** Wiring the model needed about ten lines in `routes/dispatch.ts`,
which sat at 599 of a 600-line budget. Rather than shave comments, the eighteen lines that turn one offer into one push
per device became `routes/dispatch-push.ts` — the planner decides *to* ring, that file rings — which is the same split by
responsibility D129 used for the history joins.

Tests: nineteen in `propensity.test.ts` (the feature list and order, the prior's readable signs, coefficient validation,
lenient config parsing, sigmoid clamping, prediction ordering, one step's direction both ways, L2 on absent features,
immutability, convergence, the blend's three anchors and its broken inputs, normalisation and clamping, the hour pair,
weather and batch), six in `dispatch-scoring.test.ts` (no model = the old answer, zero evidence = the old answer, a
trained model conditioning on distance, evidence moving in order, the unit interval, and a ranking that flips on distance
alone), and two in `dispatch-plan-route.test.ts` (a trained zone moving `pNone`; a broken row and a missing row both
falling back without changing the plan).

*Open:* nothing computes `learnStep` yet — the loop that reads answered offers and writes the weights back is the next
rung, and until it lands every zone scores with `PROPENSITY_PRIOR`. `weatherSeverity` and `tripDistanceM` are passed as
absent by the planner because the first needs `09 §8`'s weather feed and the second needs a delivery cell the order table
does not record; both features are then zero, which is the honest "not known" rather than a guess.

## D134 — The offer carries the evidence

D133 put `09 §7.4`'s model in the scorer and left the learning loop for later, on the theory that recording the features
was the small part. It is the load-bearing part. Of the eight features, three are facts about a moment that no table
keeps: the rider's idle time when the offer was made, the routing snapshot that measured their distance to the vendor,
and the weather that minute. A training loop that rebuilt the vector from today's rows would be learning from a
different offer than the one the rider answered — and would silently teach the model that idle time is whatever the
rider's idle time happens to be when the sweep runs.

**So the row records its own vector.** `order_offers.propensity_features` is a nullable JSON column
(`017_offer_propensity.sql`) holding the eight normalised numbers in `PROPENSITY_FEATURES`' order — the model's own wire
format, which is why the order is a constant in code rather than a convention in a comment. JSON rather than eight
columns because the model's shape is the model's business: a ninth feature is a code change and a re-train, not a
migration, and nothing indexes into this column.

**The vector is the one factor 3 used.** `propensityVector(facts, zone)` is extracted from `acceptanceFactor` and both
call it, so the number the ranking acted on and the numbers the row keeps cannot drift. It travels `Scored` →
`ScoredCandidate` → `PlannedOffer` → `WaveOffer` without any of those modules interpreting it: the planner decides who is
asked, the writer knows the table, and neither has an opinion about what the eight numbers mean.

**`null` is a value, not a gap.** An offer written by a planner with no acceptance model has no vector, and a row of
zeroes would be worse than nothing — it looks like a perfectly ordinary sample whose offer had nothing to recommend it,
and the first training pass would learn exactly that. The column stays null and the loop skips it. The same reasoning
covers the pre-migration rows: they are evidence of a decision nobody recorded, and inventing it is not a migration's job.

**The outcome was already there.** `order_offers.response` is `ACCEPTED`, `REJECTED` or `EXPIRED`, so one offer row is
one training sample: `y = 1` for accepted, `0` for the other two — a rider who let the alarm expire did not accept the
offer, whatever they intended. `offered_at` is the loop's cursor, and the index on `(rider_id, offered_at)` already
serves it. Nothing else is needed to train; only a caller is, which is the next rung.

Tests: one in `dispatch-candidates.test.ts` (the JSON string in the eleventh binding, and `null` for a vector-less
offer), three in `dispatch-scoring.test.ts` (eight numbers with a model, `null` without one, and a scored candidate whose
vector is the one its factor 3 used), and one in `dispatch-plan-route.test.ts` (a trained zone's written offer carrying
eight normalised numbers). `db/expected.json` was regenerated by `scripts/db/expected.py`; the table count is unchanged
at 115, the column count moves to 678.

*Open:* the column is written and read by nothing yet. The loop that applies `learnStep` to answered offers and writes
the weights back to `platform_config` is next; when it lands, its first run will find every pre-D134 row null and start
from the first offer this rung wrote.

## D135 — The loop closes where outcomes become final

D133 built the model, D134 made each offer record what it saw, and both left the same gap: nothing ever called
`learnStep`. The remaining question was not *how* to train but *when* — and the honest answer is that a training pass
needs a moment when outcomes become final, which in this system is exactly one event: the expiry sweep. It already runs
on every alarm tick in every zone (D130, D132), it is the instant `EXPIRED` stops being a guess, and it costs nothing
extra to hang the loop on it. No cron (the no-cron rule is not decoration), no new endpoint, no operator button.

**The cursor is inside the model.** A pass that learned from everything it could find would re-learn the same offers
every five seconds and drift its weights on evidence it already counted. So the row gains `trainedThroughMs` — the
`responded_at` of the last outcome folded in — and each pass reads only `responded_at > trainedThroughMs`, oldest
first. It rides in the same JSON value as the weights because the two cannot be updated atomically apart: a separate
cursor row would let a crash between the two writes make the model claim it had seen offers it learned nothing from.
`0` means never trained, which is what every D133/D134 row reads as, and the first pass starts from the first vector
D134 wrote.

**A zone inherits weights, not confidence.** A zone with no row of its own starts from the global sentinel's weights with
`samples = 0`. Copying the samples would let one dense zone's evidence vouch for a district that has never delivered,
and factor 3's trust is `min(samples, 50) / 50` — confidence is a claim about *this* zone's evidence or it is nothing.

**One row per pass, or none.** The write is a single `platform_config` INSERT with `version = propensity.<samples>` and
`created_by` the all-zero UUID: a model that attributed its own training to whichever operator last opened Brain Lab
would be a lie in the audit trail. A pass with nothing to read writes no row and no audit line — a config table that
grows one row per sweep is a table whose history nobody can read — and `trainZones` answers with only the zones it
actually trained, so the sweep's response says what happened rather than what was attempted.

**Bounded on purpose.** 200 samples per zone per pass and 3 zones per sweep. Both are bounds on a *sweep*, not on the
model: a busy minute must not turn an expiry tick into a training run, and the zones that wait are retrained within
seconds because the tick is constant. The zone list comes from a `SELECT DISTINCT o.zone_id` taken before the `UPDATE`
— the same reason D130 reads codes first: the update is what erases the evidence.

Rejected: a `POST /internal/dispatch/train` endpoint (an operator would have to schedule it, which is a cron under
another name), training in the planner (it runs per dispatch and has no notion of an outcome), a batch trainer over
`order_offers` (the sweep already knows which zones just produced outcomes), and a separate cursor row (see above).

Tests: 13 in the new `propensity-train.test.ts` (`trainModel` folds in the order given, skips non-vectors, reports the
watermark; `trainZone` inherits weights with zero samples, writes one row with the right version/author/reason, and
writes nothing on an empty read) and 3 in `offer-claim.test.ts` (a sweep that emptied a zone with vectors returns
`trained` and leaves a new version; a zone with nothing recorded returns `[]` and writes nothing; a sweep with no
expiries does not run a training pass at all).

*Open:* the samples are ordered by `responded_at`, which means a burst of expiries from one wave teaches the model the
same eight features 40 times. A dedupe by `(wave, zone)` or a per-offer reweighting is the next thing worth measuring,
and the label itself — `EXPIRED` counting as a hard `y = 0` — contradicts `11 §9.3`'s half-weight for silence.

## D136 — Silence is not a refusal, even to a gradient

`11 §9.3` settles the question in one sentence: an expired offer counts at half the strength of an explicit rejection,
because the rider may have been riding, in a lift, or on a call. The acceptance *rate* obeys that. D135's trainer did
not — it trained on `y = 0` for every row that was not `ACCEPTED`, so the loop contradicted the rule it was built to
serve, and did so in the direction that matters: a zone whose alarm is broken looks exactly like a zone that is saying
no, and the model would have learned to stop offering work there.

**The sample carries its weight.** `PropensitySample` and `TrainingSample` gain `weight`; `learnStep` multiplies the
gradient by it (`g = w · (p − y)`), leaving the L2 term alone — a decay that scaled with evidence would make silence
*shrink* the weights less than a refusal, which is a second, unintended opinion. `sampleFromRow` sets it from the label.

**Zero weight is a no-op, not a decay.** `learnStep` with `weight === 0` returns the weights unchanged and skips the
defensive return-value copy question entirely. A weight above 1 is clamped: it is a caller's arithmetic error, not
twice the evidence.

**The labels are a map, not an `if`.** `labelWeight(response)` returns `1`, `EXPIRY_WEIGHT`, or `null`, and `null` means
the row is not evidence. Written as `response === 'ACCEPTED' ? 1 : 0.5` it would have been wrong for `WITHDRAWN` — the
vendor closed, an admin reassigned, the customer cancelled — and `CANCELLED`, neither of which says anything about the
rider's preference. Both would have taught the model a refusal nobody established. A map makes adding a label a
deliberate act, which is what a label is.

Rejected: subtracting half a step's worth of confidence from `samples` (the count is how much evidence exists, the
weight is how strongly one piece speaks — mixing them makes `samples` mean two things, and factor 3's trust reads it),
and excluding expiries from training entirely (they are the majority of the data in a healthy zone; `§9.3` says weigh
them, not ignore them).

Tests: three in `propensity.test.ts` (a half-weighted sample moves a coefficient exactly half as far as a refusal, a
weight is clamped and a zero weight changes nothing, and the label map answers for all five responses plus a missing
one) and two in `propensity-train.test.ts` (an `EXPIRED` row folded through `trainModel` lands at ~half the distance of
a `REJECTED` one and still counts as applied; a `WITHDRAWN` row is not a sample while an `EXPIRED` one is).

*Open:* a `WITHDRAWN` offer has no half-weight because it is not evidence at all — if dispatch ever wants "the offer was
pulled out from under the rider" to mean something, that is a separate feature and a separate label. The training read
still scans by `responded_at` for a zone, so bursts stay ordered but unweighted by wave; that observation from D135's
open list stands.

## D137 — The rating arrives

`order_ratings` has been in the schema since the first migration and had no writer, which is why `11 §5` factor 6 has
been answered with `rating: null` for the whole build and the dispatch scorer returns a zero it calls plausible. Every
rung that touched scoring has noted it. This one moves the row.

**The route is `POST /v1/orders/{id}/rate`, and the body is the sheet.** `{ target, stars, comment?, tags? }` — `target`
is `VENDOR` or `RIDER` because `17 §8.1` says food and delivery are separate ratings, and conflating them "punishes a
rider for a cold kitchen and a vendor for a slow rider". `tags` is a closed set of six chips from the same sheet; a
`JSON` column nothing parses is a place to lose meaning in.

**The window is seven days from `delivered_at`.** `08` fixes the closing code (`ORDER_RATING_WINDOW_CLOSED`) and not the
length. A week is the shortest interval that still lets a weekly customer rate the order they are thinking about, and
the longest in which the answer is a memory of the meal rather than of the month. The window opens at delivery, so
before it the rating resource does not exist and the answer is `ORDER_NOT_FOUND` — the same sentence the read route
uses for an order that is not yours, because "not created yet" and "not yours" are both "there is nothing here", and
neither is "you may not".

**One rating per order, enforced by the table and answered without a new code.** `27 §4` names the rule; the unique key
`uq_order_rating_target` is the mechanism. A second request inside the window is answered with the stored rating and
`created: false`, writes no row and no audit entry. *Rejected:* a correction window (a rating a vendor can ask to have
changed is not a rating, and `17 §8.1` offers "Skip", not "Edit"), a `SUPERSEDED` second row (every reader would then
have to remember to filter), and inventing `ORDER_ALREADY_RATED` (the registry is pinned at 185 codes and D36 already
refused to add a system code for symmetry).

**The rider a rating is about is not stored.** `order_ratings` has an order and a target and no rider column, so the
join is `order_assignments` where `end_reason = 'DELIVERED'`. `orders.rider_id` is the *current* rider: a rating written
after a reassignment must not follow the order to somebody who never carried it. `riderTally` therefore returns
`{ good, total }` — the Wilson bound's two inputs — and clamps `good` to `total` rather than trusting a driver.

**`orders.delivered_at` joined `OrderRow`.** The column has been there since `006`; the row type had never selected them
because nothing needed them. The window is a function of that instant and nothing else, and a second query for it would
have been a second place to be wrong.

**One more permission key.** `order.rating.create` — the register is 416, and `docs/21`'s two counts moved with it. The
specification enumerates the admin half of the rating surface (`read`, `moderate`) and not the customer's half, exactly
as it did for the rider's shift (`D109`–`D111`). CUSTOMER holds it; no admin role does, because there is no admin flow
that rates an order.

Tests: fourteen in the new `order-rating.test.ts` — the body reader's happy path (trimmed comment, de-duplicated chips)
and its eight refusals each naming a field, the pickup-order rule, the window's open/close boundary, the insert's seven
bindings and its audit row, a second rating answered with the first and writing nothing, an undelivered order's `404`, a
stranger's `404` with no rating read at all, a week-old delivery's `409`, a pickup order's `422` naming `["VENDOR"]`, the
tally's join and clamp, and the writer reading before it writes.

*Open:* `docs/27 §4` also promises "velocity and device-cluster checks" on rating — one rating per order is structural,
the velocity half is not built. And factor 6 still reads `null`: `riderTally` exists, the loader that calls it is the
next rung.

## D138 — Factor 6 reads the tally, and nobody rated is zero

D137 gave `order_ratings` a writer and left factor 6 answering `0` from a hardcoded literal in the planner, which is a
table with a reader-shaped hole. This rung closes it in the same statement pattern the loader already uses: one more
`IN (...)` query in the `Promise.all`, grouped by rider, so a wave of sixty costs four round trips rather than a
hundred and twenty.

**The join is the assignment, and it is the only honest one.** `order_ratings` knows the order and the target;
`order_assignments` knows who carried it (`end_reason = 'DELIVERED'`). `orders.rider_id` is the rider the order has
*now*, and using it would hand a reassigned order's three-star rating to a rider who never touched it. The same join
appears in `repositories/ratings.ts`'s `riderTally`, deliberately duplicated rather than shared: one is a wave-scoped
`IN` list, the other a single rider, and a shared builder parameterised by "one or many" is how a batched query becomes
a sixty-query loop again.

**`RiderHistory.rating` changed shape.** It has been `{ count, starsTimesTen } | null` since D125, a placeholder for a
table nobody wrote. It is now `{ good, total } | null` — the Wilson bound's two inputs, which is what factor 6 actually
consumes. Keeping the sum of stars would have needed an average-then-bound conversion, which is a different statistic
(the bound of a mean is not the bound of a proportion) and would have priced a rider with one 5★ and one 1★ as if they
were a rider with two 3★s.

**No ratings is zero.** `ratingFrom` answers `0` for a rider with no tally, matching `acceptanceFrom` and `ratesFrom`.
*Rejected:* a neutral `0.5`, which would have made a first-shift rider indistinguishable from an average one and given
them a hand up on the riders the customers actually like.

**A `NULL` sum is not a `NaN`.** `SUM(CASE …)` over zero rows is `NULL` in SQL and `Number(null)` is `0` only by
accident of `??`; the merge normalises it explicitly, because a `NaN` reaching the scorer is a `NaN` in the total score
and the ranking silently becomes insertion order.

Tests: six in `dispatch-stats.test.ts` — the fourth statement's `IN` list and its `end_reason`/`target` predicates, the
tally arriving with the other three, a rider with no rows staying out of the map, a `NULL` sum reading as zero good out
of three, factor 6's bound against a longer record with the same rate, and the one-of-one rider priced as inexperience
— plus one in `dispatch-plan-route.test.ts`: the same candidate scores higher with ninety-six good ratings out of a
hundred than without any.

*Open:* `11 §5` factor 8 (`area_familiarity`) still has no evidence — `orders` has no delivery-cell column — and the
VENDOR side of the rating has no reader at all: the vendor's rank still uses `vendor_stats`. Both are recorded; neither
is this rung's business.

## D139 — The order remembers the cell it was delivered into

Factor 8 has been the one factor with a literal zero since D125, and the note attached to it was that `orders` has no
delivery-cell column. That note was wrong in a way worth recording: the order has had `delivery_lat_e7` and
`delivery_lon_e7` since `006` — snapshotted at placement precisely so a later address edit cannot rewrite history — and
the cell is a *function* of them. Nothing was missing but the derivation.

**A generated stored column, not a written one.** `018_order_delivery_cell.sql` adds
`orders.delivery_cell BIGINT AS (FLOOR(delivery_lat_e7 / 44920) * 1000000 + FLOOR(delivery_lon_e7 / 49520)) STORED` plus
an index. Writing it from the app would be a second copy of the grid that a mass update could silently disagree with;
MySQL maintains this one, and `SHOW CREATE TABLE` and `addresses.cell_id` state the same formula in the same place. It is
`NULL` when the coordinates are — a `PICKUP` order has no delivery point, and null is "no evidence", not "zero".

**The query repeats the expression rather than receiving the cell.** `SELECT_CELL_DELIVERIES` computes
`FLOOR(? / 44920) * 1000000 + FLOOR(? / 49520)` from the order's own coordinates, so the divisor 44920 exists in exactly
one language. *Rejected:* a TypeScript `cellOf(latE7, lonE7)` helper — the tempting version, and the one that would have
been wrong the first time the grid moved, silently, for some coordinates and not others.

**The statement is skipped for a pickup order.** Not run-and-return-empty: there is nothing to ask, and a wave of sixty
pickup orders would otherwise pay for a query whose answer is zero by construction. Four statements for a pickup wave,
five otherwise — the module's own docstring says "four or five", which is the sort of number that should be written down
once and be true.

**Factor 8 is `min(1, deliveries_into_cell / 12)` and had no reader.** It reads `RiderHistory.deliveriesIntoCell`, which
the route now passes through instead of the literal `0`. Twelve is the documented saturation; six deliveries is half
familiarity, and a rider who has delivered forty times into a cell is not more familiar than one who has delivered
twelve, because knowing the gate is binary.

Tests: four in `dispatch-stats.test.ts` — the cell query's expression, its three bindings and its
`DELIVERED`/`SETTLED` predicate; a pickup order running four statements and reading zero; the merge carrying the count
beside the other four; and factor 8's anchors (0, half, saturated, over-saturated, negative) — with the existing merge
and statement-count tests moved from four to five statements. `db/expected.json` was regenerated by
`scripts/db/expected.py`: 115 tables, 679 columns, unchanged table count.

*Open:* the column is derived for new rows and for every row that already has coordinates, so there is no backfill —
but an order placed before `006` (there are none outside the seed) or one with null coordinates will always read as no
evidence. And factor 12's `coverageValue` is still the constant `1` in the route, which the next session should not
mistake for a wired factor.

## D140 — The cash gate says when, and the rider can read the number

`08 §6` fixes the `SHIFT_CASH_OVERDUE` refusal's details as `{ outstanding, due_at }`, and the route has been sending
`{ outstanding }` since D109 — a documented shape that was never met. The fix is small and it exposed the question
underneath it: what is `due_at`?

**There is no future deadline, so `due_at` is the past.** `25` sets no settlement deadline at all, because there does
not need to be one: the block is immediate and the rider is `CASH_LOCKED` from the instant they tap End shift. Inventing
a countdown — "settle within 24 hours" — would be inventing policy in a route. What the screen actually needs is when the
obligation began, so `due_at` is `MAX(ended_at)` over the rider's shifts: the moment the cash became theirs to return.
Said out loud, the sentence is "you have carried ৳2 140 since 22:14", which is true and actionable; "settle your cash"
is neither.

**`cashDueAtMs` is a second statement, not a join.** The balance and the last shift-ended instant live in different
tables with different cardinalities, and a join between `rider_cash_balances` and `rider_shifts` multiplies rows for a
rider with a hundred shifts. Two reads on a path that runs once per shift start is cheaper than one clever query nobody
can read. `null` when no shift has ever ended.

**`GET /v1/rider/cash` exists now** (`08 §8` has listed it since the beginning). The blocking screen is the most
coercive surface in the platform, and a number you are blocked on must be readable *without* being blocked on: a rider
who wants to know what they owe before ending their shift had nowhere to ask. The body is the four facts and nothing
derived: `{ cashInHandPaisa, dueAt, locked, settlementRequired, shiftState }`. Owing nothing is a `200` with zeroes, not
an error — that is the ordinary end of a shift that collected no cash.

**The key is `rider.view_finance`.** The RIDER actor already holds it, so the register stays at 416 and no new key was
added for a noun that already has one. The route reads the rider's own rows by the token's user id, exactly as the shift
routes do.

Tests: three in `shift-current.test.ts` — a locked rider's amount, block and instant; nothing owed as a `200` with
`locked: false`; a token with no rider row refused before any balance is read — and the cash-locked start test in
`shift-start.test.ts` now asserts the refusal carries `due_at` at all.

*Open:* `POST /v1/rider/cash/settle` — the bKash TrxID, the screenshot, the admin approval and the auto-lift when review
exceeds the two-hour SLA (`25 §8`) — is not built. Until it is, a `CASH_LOCKED` rider has a readable balance and no way
to clear it, which is the one gap in this flow that a rider would notice first.

## D141 — The rider submits the claim, and a human still decides

D140 gave the blocking screen a readable number. This rung gives the rider the only action that screen offers: send the
money by bKash, then type five things into the app. Everything about the shape of the write follows from one question —
*what may a claim do by itself?* — and the answer is: nothing but stop asking.

**Submission does not unlock the rider.** `25 §5` says `shift_state = CASH_SUBMITTED` on success, and `riders.shift_state`
has six values, none of them that one (a CHECK constraint, five migrations ago). Rather than alter the constraint to
record a state the platform has no refusal for, the submission leaves the state at `CASH_LOCKED`: the block is released
by *approval* (`25 §6.1`), and a gate a rider can pass by typing ten characters is not a gate. The screen still stops
asking — `GET /v1/rider/cash` reports the pending claim — so the rider may close the app, which is the actual promise in
§5 ("You can close the app. We'll notify you.").

**The transaction ID is the payment, so it is normalised and unique.** Trimmed and uppercased before validation, because
`bKash` prints upper case and a phone keyboard does not, and `uq_cash_settlement_trx` is a table-wide unique key: a reused
TrxID is how one transfer would settle two debts, so it is the one refusal in this flow that is unambiguous. It is
checked before the insert so the rider gets `CASH_TRXID_DUPLICATE` — a sentence about their input — rather than a driver
error about a constraint. **Unless it is their own claim arriving twice**, which is the offline outbox: the answer is the
first row, `duplicate: true`, no write and no audit entry. Idempotency here is not politeness, it is the difference
between a retry and a second payment.

**A mismatch is a flag, never a wall.** `25 §6` marks the number and name comparisons "pass / flag" and the selfie
comparison "advisory — never decisive", and the reason is in the document: face comparison is a hint for a human. So
`checkClaim` answers `numberMatches` and `nameMatches`, both nullable, and the route stores them beside the claim
(`number_matches`, `name_matches`) so the reviewer sees the verdict the platform gave at submission time. `null` is *not
checked* — a rider whose `payout_number` was never recorded is not accused of a mismatch — which is why the columns are
nullable rather than defaulted false. The name comparison is a Dice coefficient over character bigrams at 0.75:
"Md Karim Rahman" and "Karim Rahman Md" are the same person and Levenshtein would call them distant, while bigram overlap
calls them close, which is the right mistake to make for a field that only produces a hint.

**The amount is compared, never taken.** `25 §5` makes the field pre-filled and read-only, so the route reads the balance
and refuses `CASH_OVERPAYMENT` or `CASH_UNDERPAYMENT` (+`short_by`) rather than trusting the body. `25 §7`'s partial
settlement — "I'll settle part of it now", with a reason and a reduced cash limit — is a *path*, and a path needs a
screen, a reason vocabulary and a policy about who may use it. It is not built, and a silent partial would look like
settling a debt while leaving one.

**The evidence columns.** `019` adds `bkash_number`, `account_name`, `screenshot_url`, `selfie_url`, `number_matches` and
`name_matches` to `rider_cash_settlements`. The screenshot is a URL rather than a `media` row because the screen must work
while `26`'s pipeline is cold — a rider in the street at 11 pm cannot be told to wait for an upload job — and because the
one document that is both evidence and a secret is easier to keep out of the customer and vendor surfaces when only the
admin side is given its key. `proof_media_id` stays for the day the screenshot is promoted.

**The module moved.** The cash pair now lives in `routes/cash.ts`; `shift.ts` was at 511 lines with the read route in it
and the line budget is 600. Four routes about shifts belong together; two routes about money belong together; the split
is by noun, not by file length, and the length is what made the noun visible.

Tests: eighteen in the new `rider-cash.test.ts` — the draft with a normalised TrxID, thirteen refusals each naming a
field, the two patterns, number matching across the three spellings of one number, the name similarity's four anchors,
`null` vs `false` for missing data on file, the read route's three states plus the refusal, the insert's thirteen
bindings and its audit row, the idempotent retry writing nothing, a foreign TrxID refused, a pending claim blocking a
second, nothing-owed refused, over/under payment with `short_by`, the unrecorded payout number submitted rather than
accused, and a bad claim reaching no database call at all. `db/expected.json` was regenerated:
115 tables, 685 columns.

*Open:* the review half — approve, approve-a-different-amount, reject, escalate (`25 §6.1`), the rejection reason
vocabulary (`§6.2`), and the 2-hour auto-lift (`§8`) whose deadline the submission now promises as `reviewDueBy`. The next
rung should start with the sweep, because a promise in a response that nothing keeps is exactly the kind of thing this
platform is not supposed to do.

## D142 — The two-hour rule is a deadline the door enforces

`25 §8` calls the two-hour auto-lift "the most important rule in this document", and D141 shipped a submission whose
response promised `reviewDueBy` while nothing in the platform would ever act on it. That is the kind of promise this
build has spent twenty rungs removing, so it is the next rung.

**A cron is not available, so the rule moves to the door.** The platform has no scheduler — no Worker owns a schedule,
and `no-cron` fails the build if one appears. A deadline therefore cannot *fire* anything; what it can do is change what a
request decides. `riders.shift_state` keeps saying `CASH_LOCKED`, and the moment the rider presents themselves —
`POST /v1/rider/shift/start` — the route asks whether their pending claim has waited `AUTO_LIFT_MS`, and if it has, lifts
the block and continues into the shift. One `UPDATE riders`, one audit row.

**The audit row is the record of a platform failure.** Actor `SYSTEM`, action `rider.cash.auto_lift`, reason
`REVIEW_SLA_EXCEEDED`, severity `WARNING`, `before: CASH_LOCKED`, `after: OFFLINE` with the settlement id. `25 §10` is
explicit that auto-lifts are "tracked as a platform failure metric, not a rider metric", and the difference between a
metric and an opinion is that one has a row. The `console.error` beside it exists because the Worker's log is what wakes
somebody up at 3 am; the audit row is what explains it a week later.

**The read computes, and does not write.** `GET /v1/rider/cash` applies the same rule to answer `locked: false` with
`autoLiftDue: true` — the screen must not show a rider a wall the platform has already dropped — but a `GET` that mutates
state is a `GET` that can be triggered by a prefetcher, a crawler or an over-eager app. So the split is: reads compute,
doors write. The first request after the deadline is where the lift becomes a fact, and it is the only request that
needs to be correct.

**Neither a missing claim nor an unreadable clock releases anybody.** `autoLiftDue(null, …)` is false — a rider who never
submitted is not being kept waiting by the platform — and a `created_at` that does not parse is treated as *not* due.
The rule exists because the platform was slow, not as a general escape hatch; a block that lifts whenever its timestamp
is garbage is a block that can be defeated by writing garbage.

**`AUTO_LIFT_MS` moved into the domain.** It was `REVIEW_SLA_MS` in `routes/cash.ts`, which is where a constant goes when
it is only quoted in a response body. It is now the same number the door enforces and the read reports, and a deadline
with three readers should not live in one of them.

Tests: eight — five in `rider-cash.test.ts` (the domain's three anchors plus the boundary and the `NaN`; the read
reporting `locked: false` while the stored state still says `CASH_LOCKED`, and a read writing nothing; a fresh claim
keeping the block; a rider with no claim keeping it without a deadline) and three in `shift-start.test.ts` (an
auto-lifted start returns `200`, writes `OFFLINE`, and audits `rider.cash.auto_lift` at `WARNING`; a five-minute-old
claim still gets `SHIFT_CASH_OVERDUE`; a rider who never submitted is never lifted).

*Open:* the review half itself. There is still no approve, reject or escalate route, so every settlement that is not
auto-lifted waits for a human who has no screen. The auto-lift now bounds the wait, which is what `§8` asks for, but
"bounded" and "resolved" are different promises and only one of them is kept.

## D143 — Approving a settlement, and the first live ledger entry

D141 built the rider's side of a cash settlement and D142 bounded how long the platform may ignore one. Neither gave a
reviewer a route, so `25 §6`'s screenshot review had nobody behind it and every claim that was not auto-lifted waited on
a screen that does not exist. `POST /v1/finance/cash/settlements/{id}/approve` is that screen's only button.

**Approval is where money moves, so it moves in the ledger.** A rider holding ৳2 140 of the platform's cash is the asset
`RIDER_CASH:{id}`; the handover is `RIDER_CASH −amount` / `PLATFORM:BANK +amount`, which is `24 §6` and `25 §9` row for
row. This is the first live caller of `postEntry`, which means the closure assertion that has only ever run in tests now
runs inside a request — and if the rows the database wrote do not sum to zero, `postEntry` deletes the entry, throws, and
the route answers `500`.

**The status transition is the lock, and it is the only one.** `UPDATE ... SET status = 'CONFIRMED' ... WHERE status =
'PENDING'` returns one affected row to exactly one caller. Two reviewers who open the same claim a minute apart cannot
both post an entry; the loser gets `CASH_ALREADY_SETTLED` with the instant the other one decided. A plain `UPDATE ...
WHERE id = ?` would have been simpler and would have doubled the books the first time two tabs were open.

**Approval is three statements and no transaction, so it unwinds by hand.** TiDB auto-commits each statement and the HTTP
driver's interactive transactions are documented as not concurrency-safe, so the order is chosen for what a failure
leaves behind: take the claim (a retry can no longer double-post), credit `deposited_paisa`, then post the entry. If the
ledger write fails, the deposit is credited back, the claim is released to `PENDING`, and the reviewer gets `500` with a
settlement they can simply approve again. The alternative ordering would leave a confirmed settlement with no entry —
a rider released against money the books never saw — which is the one failure this route must not produce.

**`outstanding_paisa` is generated, so the release is one query.** Crediting `deposited_paisa` recomputes the balance
because the column is `collected - deposited`; the route then reads that figure and, only if it is zero and the stored
state is `CASH_LOCKED`, writes `OFFLINE`. An approval that leaves cash outstanding — `25 §7`'s partial case — does not
open the door, which is asserted rather than assumed.

**A clean approval has no reason code, and inventing one would be the bug.** The register holds six operational reasons
plus `CASH_NOT_HANDED_OVER` and `CASH_COUNTED_SHORT` for this key, and all of them describe something anomalous. A
reviewer confirming that the money arrived as claimed has nothing to name, so `reason` is optional and `null` is the
honest record; a supplied reason is checked with `reasonAllowed`, so `BKASH_TRANSFER_CONFIRMED` — a payout's vocabulary
— is refused. That keeps `§6.2`'s list honest: it is a vocabulary of complaints, not a dropdown every approval must
clear.

**Two smaller decisions.** A settlement id that names no row answers `MONEY_PAYOUT_NOT_FOUND`: the pinned registry has
no settlement-not-found code and the register is closed, so the route borrows the nearest 404 and says so in `25 §6.1`
rather than adding a thirty-second code for a noun. And the route lives in `routes/cash-review.ts` rather than in
`routes/cash.ts`, because the rider's screen and the reviewer's screen answer to different people and a 500-line file
that serves both is a file where a rider-shaped assumption eventually lands on an admin path.

Tests: eight in `test/cash-review.test.ts` — the ledger postings and the entry's settlement id, the release and the audit
row that names the entry, a partial debt that does not release, an already-decided claim (409, nothing posted), a lost
race between read and write, an entry that fails closure (500 with the deposit given back, the claim released and no
state write), the reason register's four answers, and an id judged before any query.

*Open:* reject, escalate, and approve-a-different-amount. The reviewer can now say yes; every other answer still has no
route, and `§6.2`'s rejection vocabulary remains unused until one does.

## D144 — Refusing a settlement, and the two vocabularies that meet there

D143 gave a reviewer one button. A review with only "yes" is not a review: `25 §6.1` names four decisions and the second
most common is refusal, which until now had no route, no stored reason and no way for the rider to learn what was wrong
with their evidence. `POST /v1/finance/cash/settlements/{id}/reject` is that.

**A refusal is one statement and it is the cheap decision.** No ledger entry, no balance change, no release: `UPDATE ...
SET status = 'REJECTED' ... WHERE status = 'PENDING'` and one audit row. That asymmetry with D143 is the point — money
moves only on approval, so only approval needs a compensation path, and a reviewer who refuses cannot put the books in a
state that needs unwinding.

**The reason is stored on the settlement, because the person it is for cannot read the audit log.** `§6.2` requires the
rider to see the specific reason on the blocking screen, and the audit log is an admin surface. Migration `020` adds
`rejection_reason VARCHAR(32)` and `rejection_note VARCHAR(280)`, both nullable — an approval has neither — and
`GET /v1/rider/cash` returns them under the rejected row. A refusal the rider cannot read is indistinguishable from the
platform ignoring them, which is the exact failure D142 spent a rung removing from the other direction.

**Two vocabularies meet in this route and neither is bent to fit the other.** `§6.2`'s nine codes
(`TRXID_NOT_FOUND` … `OTHER`) are the rider's vocabulary: the blocking screen translates them into Bangla and pairs each
with a correction path. The audit register is the platform's: a closed list shared with every other action, holding two
settlement words that describe the *reviewer's* situation. Storing the register's word on the settlement would give the
rider "settlement disputed" where they need "retake the selfie"; adding nine codes to the register would put
settlement-specific nouns in a list twenty other actions match against. So the settlement carries the precise word and
the audit row carries the nearest register code — `CASH_COUNTED_SHORT` for `AMOUNT_MISMATCH`, `SETTLEMENT_DISPUTED`
otherwise — through one function, `auditReasonFor`, rather than a reviewer's memory.

**`OTHER` without a sentence is refused.** It is the one code that explains nothing, so the route requires a note beside
it; a note longer than 280 characters is refused rather than truncated, because a silently shortened explanation is worse
than a visible one. The code list is closed in the domain (`REJECTION_REASONS`), so the refusal answer can hand the app
the exact list to render.

**No step-up, and that is deliberate rather than an omission.** Refusing a claim neither releases a rider nor moves money;
`finance.cash.reject_settlement` is a HIGH-risk key and the seventeen other HIGH keys behave the same way. Step-up guards
the moment the platform gives something away, and this is the moment it declines to.

Tests: six more in `test/cash-review.test.ts` (thirteen there now) and two in `test/rider-cash.test.ts` — the refusal that
posts nothing and keeps the block, the mandatory reason with the nine-code list in the error details, an outsider word
(`CASH_NOT_HANDED_OVER`) refused, `OTHER` bare and `OTHER` explained, `AMOUNT_MISMATCH` mapping to the register's count,
the already-decided and lost-race conflicts, and the rider's read surfacing both the code and the sentence.

*Open:* escalate, and approve-a-different-amount. `§6.2` also says `PAYMENT_NOT_RECEIVED` should open a support call
rather than sit as a silent refusal; the code is storable today, and the call is not.

## D145 — The reviewer's queue, and why oldest-first is a rule

D143 and D144 gave a reviewer two buttons. A button needs a list, and there was none: a settlement could be decided only
by somebody who already knew its id, which is a lookup rather than a queue. `GET /v1/finance/cash/settlements` is the
list `25 §6` draws, behind `finance.cash.list_outstanding`.

**Oldest first is the fairness rule, not a display preference.** `25 §8`'s two-hour auto-lift means a claim that reaches
the top of the clock is released without review. Newest-first — the ordering a `created_at DESC` gives for free — shows
the reviewer the claims with the most slack and lets the urgent ones age out of sight. The queue is therefore
`ORDER BY created_at ASC`, and the test asserts the direction rather than the contents.

**The decision is made from the list.** Each row carries the two automated flags from `§6`'s table and both evidence URLs,
because a reviewer who has to open each claim to see the screenshot is a reviewer who approves from the number alone. The
flags stay *flags*: `nameMatches: false` is a reason to look, not a verdict the route has already reached.

**`slaBreached` is computed, not stored.** It is `autoLiftDue` — the same two-hour rule D142 enforces at the door — read
here to colour the row. One function in the domain, two readers, so the queue and the gate can never disagree about who is
late.

**The ceiling is 100, and the limit is clamped rather than refused.** `25 §10` sets zero SLA breaches as the target, so a
queue of a hundred is already an operational failure; the number exists to bound the query, not to let a reviewer page
through a backlog. `limit=900` answers with a hundred rows and says so in the summary rather than returning an error for a
request whose intent was clear.

Tests: three in `test/cash-review.test.ts` — the row with its evidence and flags plus the SQL's ordering, a two-row queue
with one breach and the summary arithmetic, and the empty day with the clamp.

*Open:* the queue has no filters (zone, rider, method), no cursor, and no pagination beyond the ceiling — all three are
answered by "there should never be more than a handful", which is a claim the monitoring in `§10` has to keep true.

## D146 — Escalation: releasing the rider without forgiving the debt

`25 §6.1` names four decisions and D143/D144 built two. The fourth — escalate — is the one the other three exist to avoid
needing: a reviewer who cannot tell from the evidence whether the money arrived (a bKash delay, a screenshot that will not
open, a name that changed last month) should not have to choose between approving a payment they are unsure of and
refusing a rider who may be right. `POST /v1/finance/cash/settlements/{id}/escalate` is that fourth answer, and
`§6.1` states its consequence plainly: the rider is released, because the escalation is the platform's problem.

**Released, not forgiven.** The claim stays `PENDING`, `outstanding_paisa` is untouched, no ledger entry is posted and no
deposit is credited. Migration `021` adds `escalated_at`, `escalated_by` and `escalation_note`; the first is what the lift
reads, the last is what the next reviewer inherits. Releasing a rider and forgiving a debt are different acts, and this
build has no route that performs the second.

**The release is computed, like every other lift here.** `liftStateOf` already answered "is this rider actually blocked?"
from the stored state and the pending claim; it now answers it from three facts instead of two. An escalated claim lifts
the block the same way a two-hour-old one does — `locked: false` on the read, a state write at the door — so there is one
rule about the block rather than one per route. The order of the two checks matters: escalation is tested **before** the
clock, so an escalated claim is never also counted as an SLA breach. `§10` counts auto-lifts as a platform failure
metric; an escalation is a human replying in time, and mixing the two would make the metric unreadable.

**It borrows the approver's key, and that is the conservative choice.** There is no `finance.cash.escalate_settlement` in
the register. Inventing a lighter permission for an action whose *consequence* is the same as approval's — a rider on the
road against cash nobody has confirmed — would put a weaker lock on the same door. So the route declares
`finance.cash.approve_settlement` and inherits its TOTP requirement, and `audit/reasons.ts` needs nothing new: the
escalation cites `SETTLEMENT_DISPUTED`, which is exactly what "a human needs to look at this" means.

**The next shift's end does not re-block them.** `endShift` wrote `CASH_LOCKED` whenever cash was outstanding, which would
have made an escalated rider prove the same promise at the end of the next shift. It now checks for a live escalation and
writes `OFFLINE` instead — the debt is real, the review is real, and blocking again would deny the second.

**A second escalation is refused, not merged.** The guarded update is `WHERE status = 'PENDING' AND escalated_at IS NULL`,
so an already-escalated claim answers `CASH_ALREADY_SETTLED` rather than overwriting the first reviewer's note. Notes are
optional (a reviewer who escalates without typing still escalated) and bounded at 280 characters.

**The queue moved to its own module.** `cash-review.ts` had grown to 582 lines carrying the queue, three decisions and
their doc comments; the guardrail's budget exists to stop exactly that. `routes/cash-queue.ts` now owns the read surface
(97 lines) and `cash-review.ts` owns the decisions (505), which is the split a reviewer of either file would have asked
for.

Tests: seven new — two in `shift-start.test.ts`/`shift-end.test.ts` (an escalated claim opens the door with no
`rider.cash.auto_lift` row; the end of the next shift writes `OFFLINE` while cash is outstanding), two in
`rider-cash.test.ts` (the read's `escalated`/`autoLiftDue` pair, and escalation beating the clock), and three in
`cash-review.test.ts` (the release without a posting, the three refusals, the note's bounds and the queue's marking).

*Open:* approve-a-different-amount is now the only `§6.1` decision without a route, and `§7`'s partial paths —
robbed/lost, emergency, "I disagree" — remain screens.

## D147 — Approving a different amount, and the two numbers a rider needs

`25 §6.1`'s second decision is the last of the four to be built: "Approve a different amount — for a partial or
over-payment. Requires a reason. The difference stays in `RIDER_CASH` and the rider is told clearly what remains." Three
claims in that sentence, and each one is a design choice.

**The accepted amount is stored, not inferred.** Approval now takes an optional `amountPaisa`, and migration `022` adds
`approved_paisa BIGINT NULL` with a check that it is between zero and the claim. `amount_paisa` keeps meaning *what the
rider claimed* — the evidence is the claim — and `approved_paisa` means *what the platform accepted*. The ledger entry,
the `deposited_paisa` credit and the audit row are all built from the accepted figure, so there is one number that moves
money and no path where the books and the settlement disagree about how much.

**A differing figure must be explained; the same figure need not.** A reviewer who accepts the full amount states nothing,
because there is nothing to explain (D143). A reviewer who accepts less must cite a register reason — `CASH_COUNTED_SHORT`
in the ordinary case — because the rider is about to see their claim and the credit disagree, and an unexplained
disagreement is exactly the thing the screen exists to avoid. The reason list in the refusal is the register's list for
this key, so the app can render the choice instead of describing it.

**Two bounds, and both are refusals rather than clamps.** More than the claim is `MONEY_REFUND_EXCEEDS_PAID` — the one
existing code whose shape (`{paid, requested}`) fits "you asked to accept more than is there" — because the claim is the
ceiling: a rider who owes ৳2 140 cannot have ৳3 000 accepted. Zero is `VALIDATION_REQUIRED`, because accepting nothing
while marking the claim `CONFIRMED` would close the claim, release nobody and read as an approval. A non-integer is
refused like every other amount in this codebase. Over-payment is deliberately **not** implemented: `POST /rider/cash/settle`
already refuses a claim above the balance, so there is nothing above the claim to accept until `§7`'s disputed paths can
produce one.

**Both numbers reach the rider.** `GET /v1/rider/cash` returns `amountPaisa` and `approvedPaisa` under the settlement, and
the read's `cashInHandPaisa` does the arithmetic. A settlement that says "confirmed" beside an unchanged balance is the
confusion `§6.1` promises to prevent, and the fix is not a sentence in the app — it is the two numbers that let the app
write one.

**`null` is not zero.** A rejected, escalated, or pre-`022` confirmed row has no accepted amount, and the reader treats
`null` as "not stated". A zero would read as "the platform accepted nothing and released the rider", which is the one
interpretation this column must never produce.

Tests: five new — three in `cash-review.test.ts` (the partial credit and its audit row, the four refusals with the reason
list, the full amount stated explicitly needing no reason) and two in `rider-cash.test.ts` (the two numbers on the read,
and a claim nobody accepted still reporting `null`).

*Open:* `§7`'s partial and disputed paths — "I was robbed", "I have an emergency", "I disagree" — are still screens, and
they are the only route by which a claim could legitimately exceed or undercut the balance.

## D148 — The emergency lift: a rider is believed for a day

`25 §7` opens with four buttons and closes with the rule they exist for: *"The block exists to collect money from people
who have it and are about to go home — not to punish people who do not."* Until now none of the four existed, so a rider
robbed at 11 pm had exactly one option: stay blocked. `POST /v1/rider/cash/declare` with `kind: "EMERGENCY"` is the first
of them, and migration `023` adds `rider_cash_declarations` to hold it.

**A table, not a column.** `§7`'s three constraints are the reason: the emergency path is "limited to once per 30 days",
which is a query over history rather than a flag; every path is "logged", and a log kept in a column holds one entry; and
a declaration is evidence a human reads later, so it needs its own id for the audit chain's `resource_id`. The table
carries `kind`, `note`, `lifted_until` and `routed_to_review`, and the inventory in `06 §2` grows by one name (114).

**The lift is computed, like the other two.** `liftStateOf` now answers the block question from four facts instead of
three, and a live `lifted_until` releases the rider exactly the way D142's clock and D146's escalation do: the read says
`locked: false, declared: true`, and the door writes `OFFLINE` on the next request. No cron, and no timer that has to
fire — the window is arithmetic on a datetime, which is the only kind of deadline this platform can keep. `endShift` also
respects it, so a shift that ends inside the window does not write the block back on.

**Twenty-four hours, not a shift boundary.** A day is the point: an emergency that costs an evening should not cost the
morning too, and a window ending at the next shift boundary would expire exactly when the door checks it.

**The second use in thirty days lifts too, and wakes somebody.** `§7`: "A second use in the window routes to a human
instead of being refused." Both halves matter. *Instead of being refused* is a promise about the lift: every path in that
section lifts the block, and a platform that answers a second emergency with a wall has punished the rider for a pattern
rather than noticed it. So the declaration is written either way, `routed_to_review` marks the second, and the audit row
goes from `NOTICE` to `WARNING` so the reviewer's morning list has it at the top. `repeatedEmergency` is one domain
function with a clock it can read: an unparseable previous timestamp counts as no previous emergency, because a cooldown
exists to notice a pattern, not to manufacture one.

**No reason code, and the register is not consulted.** The rider is not an admin, and `audit/reasons.ts` is a closed list
of admin reasons. The audit row's `after` block carries the kind, the note, the window and the routing flag — everything a
reviewer needs — and `reason` is `null` rather than borrowed from a list that would attribute an admin's vocabulary to a
rider's statement.

**Two buttons answer `501`.** `ROBBED` needs a case with a human owner, a police-report upload and a lift with no expiry
(the column already allows `NULL`); `DISPUTE` needs the order-by-order breakdown `§7` describes, which means reading a
shift's deliveries back to the rider. Both are named in the table's check constraint and in the enum refusal, so the app
can render the button and hide it on a `501` rather than guessing.

Tests: six — four in `test/cash-declare.test.ts` (the day-long lift with the debt intact, the second-in-window lift that
also routes to review, a use outside the cooldown counting as the first, and the two `501`s plus the `422` and `409`),
one each in `rider-cash.test.ts` (a live window and an expired one on the read) and `shift-start.test.ts`/`shift-end.test.ts`
(the door opening without an `auto_lift` row, and a shift ending inside the window staying `OFFLINE`).

*Open:* robbed, dispute and partial. The partial path is the odd one out — "I'll settle part of it now" is not a
declaration but a settlement for less than the balance, which `POST /rider/cash/settle` refuses today with
`CASH_UNDERPAYMENT`. It is the next rung.

## D149 — A robbery is a case, an emergency is a window

`25 §7`'s second button — "I was robbed or lost the money" — is the same declaration as the first with two fields
changed, and the changes are the whole design.

**No expiry.** An emergency writes `lifted_until = now + 24 h`, because the money is still owed and the rider expects to
have it tomorrow. A robbery writes `NULL`, which the reader treats as *lifted* rather than *not lifted*: `§7` says the
amount is "handled case by case", and a case that a timer closes at midnight is not a case. `activeLiftUntil` already
distinguished the two — `NULL` becomes `Infinity` — so nothing in the block's arithmetic had to change; only the
declaration's intent did.

**Always routed, always critical.** `routed_to_review` is set for every robbery rather than only for repeats, and the
audit severity is `CRITICAL` rather than `WARNING`. A robbery is not a pattern to be noticed later; it is a rider who
needs a call back today, and the reviewer's list is the only mechanism this build has for that call.

**A sentence is required.** `note` is mandatory for `ROBBED` and optional for `EMERGENCY`. Somebody will ring this rider
back and "robbed" alone tells them nothing about when, where, or which police station took the report — so the one field
that makes the call possible is the one field the route will not accept empty.

**No cooldown.** The thirty-day limit belongs to the emergency button, which is the path a rider could use as a way out of
paying. A robbery is a different claim: repeat it and a human sees two `CRITICAL` rows with two sentences, which is a
conversation rather than a limit.

**What is still missing is the case.** `§7` also offers a police-report upload and a case a human owns. The declaration
row is the case's first entry — its id, its note and its `routed_to_review` flag are what a reviewer works from — but
there is no `cases` table, no upload, and no closing decision. That is written here rather than implied by a route that
says `200`.

Tests: four new — three in `test/cash-declare.test.ts` (the expiry-less lift with its `CRITICAL` audit row, the mandatory
note, and a robbery after a recent emergency still being a robbery) and one in `test/rider-cash.test.ts` (the read
treating a `NULL` expiry as lifted).

*Open:* the dispute path, the police-report upload, and "I'll settle part of it now" — which is not a declaration at all
but a settlement for less than the balance, refused today with `CASH_UNDERPAYMENT`.

## D150 — The deliveries behind the number

`25 §8` names the failure exactly: *"A bug produces a wrong `cash_in_hand` — the 'I disagree' path exists precisely for
this, and the order-by-order list makes the error visible to both sides."* The platform has been telling riders a number
with no way to check it. `GET /v1/rider/cash/breakdown` is the check.

**Attribution is the assignment, not the order.** The natural join is `orders.rider_id`, and it is wrong: that column is
whoever holds the order *now*, so a reassigned order credits one rider with a delivery and takes it away from another.
The line items come from `order_assignments` where `end_reason = 'DELIVERED'` — the record of who actually delivered —
which is also the rule the rating join (D137) and the statistics query already use. A test asserts the
statement does not mention `orders.rider_id` at all.

**Three numbers, and the difference is the point.** `linesPaisa` is the sum over the whole history, `collectedPaisa` is
the balance's `collected_paisa`, and `differencePaisa` is what is left over. A zero difference is the ordinary case; a
non-zero one is a bug, and the route surfaces it to the rider rather than reconciling it silently. The alternative —
showing a list that adds up to something other than the balance and saying nothing — is exactly the experience that turns
a support call into an accusation.

**The page is capped, the total is not.** `limit` defaults to 50 and caps at 200, `truncated` says whether the page was
cut, and `linesPaisa` comes from its own `SUM` so a rider with four hundred deliveries still sees the figure that matters.
A single query returning everything would have made the response size a function of how long somebody has worked.

**No writing, so no audit.** A `GET` that changes nothing does not get a row; the read is the rider's own data and the
guardrail's audit rule is scoped to mutations. The route is in `PRN`'s `PRESENCE` budget with the rest of the cash read.

Tests: five in `test/cash-breakdown.test.ts` — the deliveries that add up, a disagreement surfaced, the attribution rule
asserted against the SQL, a capped page whose total is still whole, and a rider with nothing collected.

*Open:* `kind: "DISPUTE"` still answers `501`. It now has a source to read from, and what it still needs is a dispute
record, a message thread (`order_disputes` exists in the inventory for orders) and a reviewer decision.

## D151 — A part-payment is a choice, and it has to be said out loud

`25 §7`'s fourth button is the only path in that section that does not need a human: "The rider settles what they can; the
remainder stays in `RIDER_CASH`." The platform could already *record* a claim below the balance — `amount_paisa` has no
lower bound — but `POST /rider/cash/settle` refused one, and that refusal was right.

**The refusal stays, and the flag is how a rider overrides it.** A short figure is far more often a mistyped than a
deliberate part-payment, and a route that accepted it would forgive a thousand taka every time somebody dropped a digit —
the same reasoning that made `CASH_UNDERPAYMENT` carry `short_by` in the first place. So `partial: true` is the rider
stating which it is, a non-boolean is refused, and `is_partial` (migration `024`) records the statement. Nothing is
inferred from `amount < outstanding`, because that inequality is true of both cases and the two need different answers.

**A part-payment that is approved releases the rider.** `§7` promises it: "the rider can go online with a reduced cash
limit equal to their remaining headroom." So `released` is now `outstanding === 0 || row.isPartial`, and the remainder
stays on the books where the weekly invoice gate collects it (`24 §6`). Approving is a human decision, so the platform is
not handing out credit on its own — a reviewer looked at the claim, the evidence and the amount.

**What is not built is the reduced ceiling.** Dispatch has one — `DEFAULT_CASH_LIMIT_PAISA`, ৳3 500, with a
`cashHeadroom` factor in scoring — but it is computed from the *shift's* `cash_collected_paisa`, not from the balance.
So a part-paid rider is offered work at the full ceiling instead of the reduced one, which is a real gap between `§7`'s
sentence and this build, and it is written here rather than left for a reviewer to infer from a route that says `200`.

**Three surfaces see the flag.** The settle response and the rider's read carry `partial` so the screen can say "you paid
৳1 000 of ৳2 140"; the reviewer's queue carries it so a short claim is read as a choice rather than a shortfall; and the
audit row carries it beside `remainingPaisa`, because a chain that records what was paid and not what is still owed leaves
a reader doing subtraction eleven characters apart.

Tests: five — two in `test/rider-cash.test.ts` (the part-payment recorded with its remainder, and the flag's two bounds: a
non-boolean and an overpayment) and three in `test/cash-review.test.ts` (the release with the remainder intact, a full
claim that leaves a balance and therefore releases nobody, and the queue's marking).

*Open:* the dispatch ceiling reading the balance (above), and `kind: "DISPUTE"`.

## D152 — The ceiling counts what the rider owes

D151 released a part-paid rider on the strength of `25 §7`'s sentence — "the rider can go online with a reduced cash
limit equal to their remaining headroom" — and then admitted the second half was not built: dispatch's ৳3 500 ceiling
read a shift's `cash_collected_paisa` and nothing else, so a rider who had just declared they could not pay the whole
balance was offered work against the full ceiling on their next shift. A promise with a hole in it is worse than an
unbuilt one, because the rider has already been let through.

**`DispatchCandidate` gained `cashOwedPaisa`, and it comes from the same statement.** The candidate query already joins
`rider_shifts`; it now carries a correlated subquery over `rider_cash_balances` for `outstanding_paisa`. A second query
per candidate would have been a second round trip per rider per wave — the path that runs every time an order needs a
rider — so the balance rides along with the row that was being read anyway. `COALESCE` and `LIMIT 1` keep a rider with no
balance row at zero rather than dropping them out of the candidate list.

**The snapshot's cash in hand is the sum, and the ceiling is untouched.** `cashInHandPaisa = cash_collected_paisa +
outstanding_paisa`. The limit stays ৳3 500 for everybody; a rider who owes ৳1 140 simply has ৳2 360 of headroom, which is
what `§7` describes and what the dispatch filter already enforces (`cashHeadroom` in scoring, filter 8 in `11 §7`). No new
refusal, no new constant, no second rule about who may work — one number changed meaning, from "what this shift collected"
to "what this rider is carrying".

**It is also more honest for a rider who has not declared anything.** A rider who ended a shift owing cash and was
blocked has an outstanding balance by definition; if they are out on an emergency lift or an escalation, the ceiling now
counts the money they are carrying instead of pretending the earlier shift never happened.

Tests: two — the mapping and the statement in `test/dispatch-candidates.test.ts` (a balance read back as a string is still
a number, and the join is in the same query), and the snapshot in `test/dispatch-assembly.test.ts` (a rider carrying
৳12 500 from today and owing ৳114 000 has ৳126 500 in hand and the same ৳350 000 ceiling).

*Open:* `25 §7`'s remaining button is `DISPUTE`, and the delivery breakdown it needs already exists (D150).

## D153 — A dispute freezes the number it disputes

`25 §7`'s third button: "A dispute is opened with the order list shown line by line; the block is lifted while the
dispute is open; the amount stays outstanding." D150 built the list and D149 built the case shape — a declaration with no
expiry that routes to a human — so this rung is the button, and one thing that neither of those had: the arithmetic.

**The declaration is the robbery's shape with a different sentence.** Lifted with no expiry, always routed, `WARNING`
severity, and a note required — "I disagree" with nothing beside it is not a claim a reviewer can answer. No new status,
no new table, one more kind in a check constraint that already listed it.

**The snapshot is the point.** The breakdown is live: a rider who disputes ৳2 140 on Tuesday and delivers four more cash
orders on Wednesday has a list that now adds up to something else. A reviewer opening the dispute on Thursday would be
reading yesterday's objection against today's numbers and concluding, reasonably, that the rider was wrong. So migration
`025` adds `snapshot_lines_paisa` and `snapshot_difference_paisa`, filled from `cashLinesTotal` and the balance at the
moment of the declaration, and the response hands the rider the same figure the reviewer will see. A dispute about a
figure has to be about *a* figure.

**`differencePaisa` is the bug report.** A dispute raised when the deliveries and the balance agree is a rider saying the
deliveries are wrong; one raised when they disagree is the platform's own arithmetic visible on the rider's screen —
`§8`'s "a bug produces a wrong `cash_in_hand`" — and the snapshot records which of the two this was. The audit row carries
the same two numbers, so the chain does not depend on the row surviving a cleanup.

**Approving a dispute is not a decision this build can make.** The reviewer can reject a claim (D144) or approve one
(D143), but neither is "the rider was right and the balance was wrong": that needs an adjustment entry against
`RIDER_CASH`, which is `finance.cash.adjust` and a step-up key, and it is not built. The dispute therefore lifts the block
and opens a case, and the case has no ending yet — written here rather than implied by a `200`.

Tests: three in `test/cash-declare.test.ts` — the expiry-less lift with its stored snapshot and its audit row, the
mandatory sentence, and an emergency recording no arithmetic at all (because it is not a claim about a number).

*Open:* the adjustment that resolves a dispute in the rider's favour, and the police-report upload beside a robbery.
`§7` is now four for four on the rider's side and has no reviewer-side endings.

## D154 — The other half of §7: a list of the cases it opens

Every declaration lifts the block, so `§7` is complete from the rider's side as of D153 and complete from nobody else's:
a robbery writes `routed_to_review = 1` and nothing reads it, which is the same failure D143–D145 spent four rungs
removing from the settlement side. `GET /v1/finance/cash/declarations` is the list.

**Newest first, unlike the settlement queue.** The two queues answer different questions. A pending settlement's age is a
countdown — past two hours the platform releases the rider anyway (D142) — so the oldest is the urgent one. A declaration
has *already* lifted the block: nothing gets worse by waiting an hour, and a robbery reported ten minutes ago is more
urgent than one somebody has been handling since yesterday. The statement reads through
`idx_cash_declaration_review`, the index migration `023` created for exactly this sort.

**Both numbers, side by side.** A dispute row carries `snapshotDifferencePaisa` (what the platform claimed when the rider
objected, D153) and `outstandingPaisa` (what it claims now, joined from `rider_cash_balances`). A queue showing only one
would let a bug that has since been fixed look unfixed, or an unfixed one look fixed — and the decision a reviewer makes
depends on which it is.

**One permission, two lists.** The route declares `finance.cash.list_outstanding`, the same key as the settlement queue:
both are one reviewer at one screen, and inventing a second read key would have split a single workflow across two grants
with no rule to explain the split. The `ADMIN_WRITE` group is the limiter's only admin-facing bucket (`29 §4`) and both
reads share it, which is the honest accounting of one person's requests.

**The summary is three counts, not a dashboard.** Robberies, disputes and repeated emergencies, because those are the
three kinds `§7` names and the number a reviewer needs is "how many, of which". Anything more is a chart nobody asked for
on a list that should usually be empty.

Tests: two in a new `test/cash-declaration-queue.test.ts` — the dispute row with both figures and the statement's
`routed_to_review` predicate and ordering, and the three counts with an empty morning that is still a `200`.

*Open:* nothing on this list can be *closed*. A robbery has no case object and no police-report upload; a dispute cannot
be resolved in the rider's favour without an adjustment entry against `RIDER_CASH` (`finance.cash.adjust`, a step-up
key). The queue is where those endings will be attached.

## D155 — A debt the platform was wrong about, and the one route that ends it

D154 built the list of open cases and admitted the gap in the same breath: nothing on it could be *closed*. A reviewer
reading a robbery report could look at the balance, agree the platform was wrong, and have no way to act — the only
adjustment key was `finance.cash.adjust`, which moves money *between* two ledgers, and `24 §6` had already named a
different row for this: "shortfall written off". `POST /v1/finance/cash/riders/{id}/write-off` is that row as a route.

**The order is the whole design.** Balance first, ledger second, case third, audit last — and each step can fail in a way
the next one repairs. The balance update is guarded (`collected_paisa >= ?`), so two reviewers pressing the button at
once cannot drive a debt negative; the ledger entry is posted through `postEntry` like every other movement, so the
`RIDER_CASH` column of the books still sums to what riders owe; and if the entry fails the balance is refunded, because
this system runs on TiDB autocommit (D95) and there is no rollback to lean on. An adjustment whose two halves disagree
is the one failure nobody could reconstruct from the ledger later, so it is the failure the code spends its lines on.

**`CASH_WRITE_OFF`, not `CASH_REFUND`.** The posting is `RIDER_CASH −amount` against `PLATFORM:EXPENSE_COMPENSATION
+amount`. It is an expense, not a refund: no money arrived and none left, the platform simply stopped claiming it. Naming
it a refund would make the finance reports show cash leaving a bank account that was never touched, and `24 §6` counts
these as a cost of doing business — which is the honest description of a delivery whose arithmetic was wrong.

**Refusals chosen over clamps.** An amount above the outstanding balance is `MONEY_REFUND_EXCEEDS_PAID` rather than being
trimmed to fit. Trimming is the friendly-looking behaviour and the wrong one: the reviewer typed a figure, the platform
did something else, and the entry that posted is now a number nobody chose. A case that is already resolved — or one
that never existed — is `CASH_ALREADY_SETTLED` (`409`), so a double submit is refused by the same rule that refuses a
stale screen. Neither needs a new error code, which is why the register did not grow.

**`finance.cash.write_off`, with step-up.** The key already existed (`rbac/keys/finance.ts`, `STEP_UP_KEYS`), so this
route added no permission and broke no count assertion. It is the right one because a write-off *spends the platform's
money* — the definition the step-up list uses — whereas `finance.cash.adjust` moves an amount from one ledger to another
and nets to zero across the books. A reviewer who can forgive a debt is a different grant from one who can reclassify
it, and the same person may hold only the second.

**The declaration, closed rather than deleted.** `026` adds `resolved_at`, `resolved_by` and `resolution_note`; the route
sets them when the body names a `declarationId`, and the declaration survives. A robbery report is a historical fact
about a night, and a queue that dropped resolved rows would lose the only record of why the money went away — the audit
row holds the actor and the reason, the declaration holds the story. `resolved_at` is also what D154's list will filter
on when it grows a "handled" tab, so the column earns its keep before the screen exists.

**`released` in the response.** When the write-off takes the outstanding balance to zero from `CASH_LOCKED`, the rider's
next request opens the door — the same conditional release an approved settlement triggers (D143). Saying so in the
response is cheaper than making the client re-read `GET /v1/rider/cash` to find out whether the rider can go online, and
`§7`'s "handled case by case" ends with exactly that sentence.

Tests: seven in `test/cash-write-off.test.ts` — the happy path with balance, entry and audit; the declaration stamping;
an over-amount refusal; a closed case; the refund when the ledger fails; a malformed id and a reason outside the
register; and the case where the write-off clears the balance and reports `released`. The declaration repository
(`repositories/declarations.ts`) was split out of `repositories/cash.ts` on the way — two hundred lines of case
lifecycle do not belong in the file that reads settlements, and the split took the line-budget warning with it.

*Open:* nothing reads a resolution back yet — a `GET` for one case is the next rung — and a robbery still has no
police-report upload and no case object beyond the declaration row.

## D156 — Reading one case back, and the first error code since D110

D154 listed the cases and D155 ended them, and neither returned a record: the queue carries the queue's columns, and a
write-off hands back a receipt. A reviewer who opened a case from a link, or support reading one beside a rider on the
phone, had to assemble the story from three responses. `GET /v1/finance/cash/declarations/{id}` is the story in one.

**`open` is `resolved_at`, never the balance.** A case can end with a debt cleared (a write-off, D155) or with no money
moving at all — a robbery where the platform decides to chase it through the police report instead. Both leave
`outstanding_paisa` at whatever it was; only one is closed. Deriving the flag from the money would report the second as
still open forever, and the reviewer who closed it would find it back on their list.

**The phone number travels with the case.** `§7` sends a robbery straight to a human, and D149's copy says somebody
will ring the rider back. A case record without a number is a record that stalls at the first step, so the
read joins `users` for it. It is the only personal datum the queue does not already return, and it is returned to the
same permission that sees the rider's debt and their sentence — an actor who can read one can read the other, and
pretending otherwise would produce a screen with a blank field where the call-back should be.

**No ledger entries inlined.** The write-off's postings are the finance trail (`24 §6`) and are readable through the
ledger. A case record that joined them in would be a second copy of the books with its own correctness problem — the
exact failure the posting code spent its lines preventing.

**A new error code, and the count moves.** An id that names nothing needs a `404`, and reusing another noun's code
(`MONEY_PAYOUT_NOT_FOUND`) would tell a client the wrong thing about what it asked for. `CASH_DECLARATION_NOT_FOUND`
joins the registry at `{ declaration_id }`, taking the total from 185 to **186** and the `CASH_` group from 9 to 10 —
the first addition since `SHIFT_ORDERS_ACTIVE` in D110, and the reason `08 §11`'s sentence now names two exceptions
instead of one. The registry test asserts both numbers, so the contract and the specification cannot drift apart
silently.

**A malformed id never reaches the database.** `VALIDATION_ID_MALFORMED` is returned before any row is read, which keeps
a bad request out of the query log and gives the client a different answer from "that case is gone" — a distinction that
matters when the client is a link somebody pasted.

Tests: three in `test/cash-declaration-case.test.ts` — a dispute read whole with both figures, the phone and the
`LEFT JOIN` that names the decider; a closed robbery whose `open` is `false` while its snapshot is `null`; and the
missing-id `404` beside a malformed id that touches no rows. `packages/contracts` goes to 186 codes, `workers/core` to
775 tests.

*Open:* a robbery still has no police-report upload and no case object beyond the declaration row; the queue still has no
filters or cursor — D154's list is capped, not paginated.

## D157 — The queue learns to ask, and the bug that taught it

D154's list was every routed declaration, forever. D155 then gave a case an ending, and the two together produced the
quiet failure this rung exists for: a reviewer wrote off a dispute, and the dispute stayed on the morning's list, waiting
to be decided a second time. Nothing errored. The list simply stopped meaning "what needs attention" and started meaning
"everything that ever happened". So `GET /v1/finance/cash/declarations` now takes `?state=`, `?kind=`, `?riderId=`,
`?cursor=` and `?limit=`.

**`open` is the default, and `resolved_at IS NULL` is the predicate.** A queue's default must be the small list. The
history is one parameter away (`state=resolved`), and the audit screen that wants both asks for `state=all` and gets it
with no state predicate at all. The filter is the same column D156 reads for its `open` flag and D155 writes when it
closes a case — one column, three routes, one meaning.

**Keyset, not offset.** The sort is `created_at DESC, id DESC`, so an `OFFSET` page is a page that shifts every time
somebody declares something new — and this table is written in bursts at eleven at night, exactly when somebody is
paging. The cursor is the last row's `(created_at, id)` pair, opaque (`btoa("created_at|id")`), and the statement asks
for what sorts strictly after it. `id` is in the key because two declarations can share a microsecond and half this
table's rows are minutes apart from another's.

**`nextCursor` only on a full page.** A client's stop condition should be "no cursor", not "fewer rows than I asked
for": the second is a rule the client has to remember, and the first is a fact the server knows. The cost is one extra
request when the queue's length is an exact multiple of the page size, which is a page of nothing — cheaper than the
alternative's bugs.

**Filters are bound, never interpolated, and validated before the database.** `kind` must be one of the three buttons
(`isDeclarationKind`), `state` one of the three words, `riderId` a UUID — each refusal names the parameter it is about
(`422 VALIDATION_FAILED { field }`, or `VALIDATION_ID_MALFORMED` and its `field`) rather than answering `200` with a
filtered-to-nothing list. A typo that looks like an empty queue is how a reviewer concludes there is no work.

**`kind` is out of the index on purpose.** `027` adds `(resolved_at, routed_to_review, created_at DESC)` — the statement's
own shape — but not four `kind`-prefixed copies. A filter a reviewer applies occasionally should not be paid for by every
write to the table; the scan after the first two columns is over the open cases only, which is a small set by
construction, since a queue that is not small is an incident.

**The summary counts the page.** It always did; D157 makes that visible by returning `state` and `kind` beside the three
kinds' counts. A total the route cannot compute without a second statement is a number a client cannot act on anyway —
it is about to fetch the rest.

Tests: four new in `test/cash-declaration-queue.test.ts` (six in the file) — the open default with its predicate and a
short page's null cursor, the resolved half showing who closed it, `kind` and `riderId` bound as parameters, a full page
handing back a cursor whose next request resumes strictly after that row, and three query strings plus a malformed rider
id each refused before a row is read. `workers/core` goes to 779; migration `027` adds the index and `expected.json`
stays at 116 tables / 704 columns.

*Open:* the declarations queue has no `?sort=` (a reviewer cannot yet ask for "oldest first"); the settlement queue
(D145) still has neither filters nor a cursor, and now has a working pattern to copy.

## D158 — The queue behind the queue, and a comparator that had to be turned round

D145 built the settlement queue and gave it one state: `PENDING`. That was the right default and the wrong only option.
"Did anybody decide the settlement this rider is ringing about?" had no route, so Monday's settled claim was answered by
reading the table, and "what has been waiting too long?" was answered by reading a page and counting. D157 taught the
declarations queue to take a query string; this rung does the same for the settlement queue, with one difference that
matters more than the parameters.

**The keyset comparator flips.** Both queues are `(created_at, id)` keysets, and for months only one direction existed.
The declarations queue sorts newest first, so its next page is *less than* the cursor. This queue sorts **oldest first**
— D145's fairness rule, the top of the list is the claim closest to the door — so the next page is *greater than* the
cursor. Copying the `<` from the file next door would have paged backwards through the most urgent claims: not an error,
not an empty page, just a reviewer working through yesterday while today's deadline passed. The comparisons therefore
live in `lib/cursor.ts` as an encoding only, and each queue writes its own operator with a comment saying which way it
runs — because the operator is the part that encodes the sort, and hiding it behind a shared helper is how this bug
would have been born.

**`breach=true` is pushed into the statement, not applied to the page.** The row flag `slaBreached` is computed from
D142's two-hour rule at read time, and a filter that ran *after* the `LIMIT` would return a page of ten claims of which
some are late — not a page of the late ones. So the route turns the flag into `created_at <= now − 2 h`, using the same
`AUTO_LIFT_MS` constant the gate and the flag use, which keeps the three in agreement by construction rather than by
review.

**The summary stopped pretending.** `pending` counted the length of a list that is now sometimes decided, so it is
computed from the rows' `status`, and `total` sits beside it. A header that says "0 pending" above ten decided claims is
correct now, and was a lie one commit earlier.

**Decided rows carry what decided them.** `status`, `confirmedAt`, `rejectionReason` and `approvedPaisa` join the row —
the last of these because a part-approval (D147) released less than the claim, and a history without it cannot answer
"how much did we actually take?" Support's version of that question is the reason this half exists at all.

**Filters are bound, and validated before the database.** `method` is checked against `005`'s `CHECK` list held as one
constant, `partial` and `breach` accept only `true`/`false`, `state` only its three words, `riderId` only a UUID.
Each refusal names its parameter. A typo that produces an empty queue is how a reviewer concludes there is no work.

**One bug the tests caught, and it is worth naming.** `state=all` with no other filter produced `WHERE  ORDER BY` — an
empty predicate written out. Two of the three states are predicates and the third is the absence of one, and the first
draft assembled the string unconditionally. The statement now omits `WHERE` entirely when the list is empty, and a test
asserts it, because the failure mode is a `500` on the audit screen rather than on the queue everybody uses daily.

**Migration `028`.** `005`'s `idx_cash_settlement_rider` is `(rider_id, status, created_at DESC)` — built for support's
question, unusable for this one, whose first column is `status`. `idx_cash_settlement_queue (status, created_at, id)`
follows the statement; `method`, `is_partial` and `rider_id` stay out, as filters applied occasionally should not be
paid for by every write.

Tests: five in a new `test/cash-settlement-queue.test.ts` — the pending default with its order and a short page's null
cursor, the decided half with reason and released amount, the four filters (with `breach`'s threshold checked against
the two-hour constant), a full page's cursor resuming *upward*, and six refused query strings that touch no rows.
`workers/core` goes to 784.

*Open:* neither queue takes `?sort=`; the three decision routes (`approve`, `reject`, `escalate`) have no read of their
own verdict beyond this list; `POST /v1/orders/{id}/dispute` and the robbery police-report upload are still the two
holes `25 §7` names.


### D159 — Claim a cash review case; do not pretend an external URL is a police-report upload

- An open routed declaration can be claimed by the current reviewer or released by its owner, using conditional updates to prevent concurrent claims and releases by other reviewers. Ownership and claim time are visible on the queue and case read. Claiming does not make a financial decision or restrict who can resolve it.
- Migration `029` adds nullable owner and claim-time fields. Existing cases are unclaimed. These actions use `finance.cash.reject_settlement` and write an audit record; like other writes, the state update and audit append are not transactional. No admin takeover or reassignment is implemented yet.
- The police-report upload is deliberately still open: `26` describes a sensitive media pipeline, but no implementation or media assets table exists. Accepting arbitrary HTTPS URLs would not implement authenticated private upload, ownership checks, audited views or retention, and could expose sensitive evidence. Implement the secure pipeline before promising the upload.

### D160 — Read TiDB write metadata; production rollout requires financial safety review

The pinned `@tidbcloud/serverless` driver returns an array of rows by default even for a write. The adapter previously read `rowsAffected` from that array and always reported zero, even after the database changed data. Conditional operations could consequently report a conflict after succeeding, and compensation or retries could make matters worse. `Db.execute` now explicitly requests the driver's `fullResult` for writes; query/first retain row-array responses. Tests exercise the actual pinned driver against a simulated HTTP gateway, including a case claim, rather than only `stubDb`.

**This is not a declaration of production readiness.** Correcting the count activates previously malfunctioning write paths. Before production rollout, test against a real TiDB staging instance and review and harden cash approval/write-off and other multi-statement financial operations: the current write-off can close a declaration without checking its rider, limits against collected rather than outstanding cash, and can race because case resolution occurs after financial writes. Several ledger and audit operations also rely on compensating writes rather than atomic transactions. In addition, the current DSN `time_zone` parameter is not read by the pinned driver's URL parser; the claimed UTC connection pin is not established by that parameter. Until those issues are resolved and verified, do not enable financial writes in production. Existing data must be reconciled for writes that succeeded but were reported as failures.


### D161 — Establish UTC on each TiDB session, not in the URL

The pinned serverless driver's DSN parser ignores `time_zone`. Core now lazily runs `SET time_zone = '+00:00'` and verifies `@@session.time_zone` on each request-local connection before any repository statement. Setup fails closed on an error or unexpected value. Calls sharing a connection are serialized, including batches, so the mutable `TiDB-Session` token is carried forward in order; this costs two gateway round trips per database-using request and removes parallel SQL on that connection. A business-statement failure does not suppress later compensation; a failed setup remains failed for that request. `Db.batch` executes sequentially, not atomically.

Tests exercise the pinned driver with a simulated stateful gateway, token rotation, concurrent callers, setup failures, and partial batch failure. An opt-in read-only live check is available with `UNDAL_TEST_TIDB_DATABASE_URL` and `node --experimental-strip-types --test test/db-session-timezone.test.ts` in `workers/core`; it was not run without staging configuration. Validate gateway session semantics, UTC defaults, latency, and existing timestamps on real staging before deployment. External clients must establish their own session timezone. D160's other warnings about financial atomicity and reconciliation remain open; this change does not make financial writes production-safe.


### D162 — Bound cash write-offs by the current outstanding balance and rider

`POST /v1/finance/cash/riders/{id}/write-off` checks outstanding cash, not total collected, and its conditional balance update repeats `collected_paisa - deposited_paisa >= amount` against the live row. If the balance drops before the update, it refuses before ledger posting. Restoration after a ledger error is a separate positive-only operation, not a negative write-off. A named case lookup and resolution both include `rider_id`; a missing or other-rider declaration returns `CASH_DECLARATION_NOT_FOUND`, and an already resolved case returns `CASH_ALREADY_SETTLED`.

**Not production-ready:** these changes do not make the write-off atomic with its case, ledger or audit. Two requests for the same case can both adjust money before one loses the later case-close update; compensation cannot resolve ambiguous commit outcomes, and KV idempotency is not an atomic financial deduplication mechanism. Approval can also race with balance changes. Keep financial writes disabled in production, reconcile earlier writes, and build and verify transaction-backed durable idempotency before enabling them. Tests use stubs and validate guards/SQL; they do not prove TiDB concurrency or failure recovery.


### D163 — Fail closed on non-atomic cash financial writes

Cash settlement approval and cash write-off are blocked by default. After authentication and authorization but before idempotency replay or the handler's financial queries, the pipeline returns `503 SERVICE_DEGRADED` with `component: cash_financial_writes`. Both handlers also enforce the gate when invoked directly. The unsafe paths can be exercised only when `ENVIRONMENT` is exactly `test` or `staging` and `ALLOW_UNSAFE_CASH_WRITES` is exactly `true`; production, preview, missing and unknown environments are blocked even with the flag. Use the opt-in only with isolated non-production data. Configuration must accurately label the environment and never point an opted-in instance at a live database.

This intentionally prevents live approval and write-off; it does not close pending claims, reconcile existing data, or prove the safety of rejection, escalation, other financial flows or the audit chain. The restriction is not a substitute for transaction-backed durable idempotency and real TiDB staging tests. Tests cover both paths, unauthorized requests, the fail-closed configuration matrix, and old cached success responses.


### D164 — Transaction adapter and conservative retry semantics

`createTransactionRunner` / `transactionalFromConnection` adapt the pinned serverless driver's experimental interactive transaction API. Each transaction has its own connection, explicitly requests `READ COMMITTED`, sets and verifies UTC, serializes use of its session token, and rejects ordinary DDL, session/transaction control and multi-statement SQL in its trusted work callback. Transaction handles become terminal as commit or rollback starts. `Db.batch` outside a transaction is still sequential, not atomic.

`withTransaction` retries deadlocks and lock timeouts only after a confirmed rollback. It no longer automatically retries network errors, ambiguous commits or failed rollbacks. A failed commit raises `TransactionCommitUnknownError`; a failed rollback raises `TransactionRollbackUnknownError`. Neither result establishes whether a financial operation was applied. Error classification now recognizes the pinned driver's nested `details.code`. Callbacks must await their database work and have no external side effects; the SQL guard is not a security boundary or general SQL parser.

Tests exercise the real pinned driver against a simulated session gateway and cover UTC setup, isolation request, serialization, rollback, closed handles, lock retries and lost commit acknowledgement. An optional non-mutating staging smoke test uses `UNDAL_TEST_TIDB_DATABASE_URL`; it was skipped without a staging URL and does not prove write rollback or isolation. No cash endpoint uses this adapter yet. The D163 gate stays closed in production: durable operation IDs, atomic balance/ledger/case/audit work, commit reconciliation, and live concurrent/failure testing on isolated TiDB remain necessary.


### D165 — Durable cash operation receipt foundation (not route integration)

Migration `030` adds an indefinitely retained operation identity, scoped by actor, action and SHA-256 idempotency-key hash. The versioned request digest also binds the normalized target and validated canonical business payload. The operation service reserves the identity, runs DB-only work and completes a bounded JSON/ledger receipt in the **same** transaction. Reuse of a key with a different request is a conflict. A duplicate reported specifically as MySQL `1062` at reservation triggers lookup only after confirmed rollback; missing or corrupt receipts are unresolved, never authorization to repeat work. A duplicate reported at commit remains an unknown outcome. The durable response is data, not an HTTP envelope or request ID. There is no cleanup or expiry policy; never prune identities without a safe, reviewed retention/reconciliation design.

Commit acknowledgement or rollback failure propagates as an unknown outcome without automatic retry. `lookupCashOperation` can discover a completed receipt, but absence immediately after an uncertain commit **does not prove rollback** or that an in-flight transaction cannot later commit. Operators/callers must reconcile; lookup must use the same authoritative TiDB database, not a stale replica. Database-only work must use the supplied transaction handle, await all statements and have no external side effects; it may be rerun after a confirmed deadlock rollback. Before any route uses this, balance, ledger, case and audit updates must all be made atomic within that transaction; audit-chain concurrency and other financial invariants require their own design and review. Decide how durable replay interacts with the existing 24-hour KV idempotency layer before integration, including old cached responses.

The tests use a simplified in-memory transaction fake; they do not establish TiDB unique-key timing, isolation, rollback or concurrent commit behavior. Migration `030` has not been applied to a live database. Run write/rollback, same-key and distinct-key concurrency, conflict, ambiguous-commit recovery and transaction failure tests against isolated real TiDB before considering route integration and reopening the D163 gate. The existing cash routes remain unchanged and blocked in production; old data still requires reconciliation.


### D166 — Exact ledger closure and a transaction-only posting foundation

Ledger `sumPaisa` now validates each posting as a safe integer, sums with exact BigInt arithmetic and rejects a final total outside the safe-number range. This prevents floating-point cancellation from falsely reporting a nonzero posting set as balanced; it affects legacy `postEntry` as well. It is not an audit of every money sum or aggregate elsewhere in the system.

The new `postEntryInTransaction` is an **unused foundation**, not route integration. It snapshots inputs, checks closure, requires pre-existing accounts, locks them in sorted code order, verifies their owner/kind/currency, inserts the entry and postings, checks affected-row counts and verifies both actual posting count and exact zero sum in SQL. It returns the entry ID, not the old count-derived pseudo-sequence. The supplied `Db` must be the handle from a caller-owned transaction; the type system does not enforce that requirement. The caller must await it, propagate every failure to the transaction runner and include all associated balance, case, durable receipt and audit updates in that same transaction. No compensation or account provisioning is performed by this function. Account setup, permissions, reconciliation and safe audit-chain concurrency require further design.

Tests cover overflow/cancellation, metadata mismatches, malformed/missing aggregate results and failures with a simulated transaction, and exercise the pinned driver and lock statements against a simulated gateway. These do not prove TiDB locking, isolation, rollback or concurrency. Run those cases against an isolated real TiDB database before integrating financial routes. No staging database was configured and no migration or deployment was performed in this step. The D163 gate stays closed; the current legacy posting and audit paths remain non-atomic. The audit append reads the chain tail before inserting; it is not the single-statement atomic append claimed by its former comment. Other risks remain, including report aggregates that use JavaScript numbers and a balance query referring to a `ledger_entries.seq` column absent from migration `008`. Existing data needs reconciliation.


### D167 — Fail closed on imprecise ledger reports and remove imaginary sequence reads

Ledger account totals, account-grouped postings, trial-balance totals and imbalance exception totals now use exact integer accumulation and reject results that cannot be represented safely by their existing number-based interfaces. SQL values accept integer and zero-scale DECIMAL strings from the driver, but reject missing, malformed, fractional or out-of-safe-range values; counts must also be nonnegative. A report error is not a clean report, and a failed balance check is not automatically an alert — callers must surface and monitor the failure. Trial reports reject invalid, empty or reversed UTC time intervals before querying, normalizing valid boundaries without losing microseconds. `exceptionFromImbalance` now presents positive credit totals consistently with trial-balance exceptions. Reversal refuses an unsafe SQL posting amount instead of rounding it.

Migration `008` does not define `ledger_entries.seq`. The current grouped balance query no longer references it, and `asOfSequence` requests explicitly fail rather than pretending a point-in-time snapshot exists. Entry reads no longer select or order by that column: `(created_at, id)` provides deterministic **display** ordering, not transaction commit order. A single-account lookup distinguishes a missing account from an existing account with zero postings and checks its stored kind. Existing code has no wired consumers of these repository reads; no public API or historical snapshot implementation is added.

Unit tests cover exact cancellation, unsafe/malformed values, missing accounts, query shapes and rejected historical requests. An in-memory SQLite schema check exercises the SQL without a sequence column; it is not TiDB verification. Equal total debits and credits are necessary but do not prove complete or correct entries, detect duplicates, or reveal offsetting errors. The existing report joins also do not independently detect orphaned or missing postings. Entry-level, referential and provider reconciliation, error alerting, real isolated TiDB testing, and atomic financial/audit changes remain open. Cash writes remain gated; this does not make other financial flows production-ready.

**Schema-verification gap discovered:** `scripts/db/expected.py` recognizes only backtick-quoted column definitions. It currently records zero columns for `ledger_entries`, `ledger_accounts` and `ledger_postings`, and omits unquoted columns in other tables (25 tables have no recorded columns). Passing schema parity therefore does not establish column-level parity with TiDB. Fix and test the extractor and regenerate expectations before relying on live schema verification; the present work does not fix it.


### D168 — Schema column verification and fail-closed operational safeguards

`expected.py` now parses quoted and unquoted column definitions and ALTER-added columns, handles top-level commas and generated columns, and rejects unsupported schema changes rather than silently omitting them. The derived inventory grows from 716 to 1,158 columns; all three ledger tables and the audit log are covered. `verify_schema.py` detects missing and unexpected columns and normalizes cosmetic integer display widths while retaining signedness and meaningful sizes. The CI schema job runs the new regression tests. This is still not a full SQL parser or full schema verification: indexes, constraints, nullability, defaults, generated expressions and live enforcement remain unchecked. No live TiDB comparison was run.

The schema verifier workflow now uses the actual `db/expected.json`, installs a hash-pinned PyMySQL wheel and uses `TIDB_READONLY_URL` rather than a migration credential. The migration workflow also installs that pinned driver. Its confirmation is passed through an environment variable rather than interpolated into shell source. Configure a least-privilege read-only secret before running verification; both workflows require isolated staging validation before production use. Python database connections now use a system-trust SSL context with certificate and hostname verification; live TiDB trust compatibility is unverified. Migration ledger reads now treat only missing-table error 1146 as a fresh database and reject ignored custom ledger arguments. DDL and ledger recording still cannot be made atomic by this change.

Retention previously issued DELETE even for dry runs, and the workflow's `DRY_RUN` input did not reach the script's CLI flag. Retention deletion is now disabled; both the library and CLI use bounded SELECT candidate counts, with an explicit error if an internal caller asks to apply deletion. The Actions workflow remains report-only, and requires separate driver/setup and end-to-end validation. This does not resolve retention policy or audit-chain correctness. See `PRODUCTION-READINESS.md` for confirmed blockers and evidence needed before launch; it is a working register, not an exhaustive audit or production certification.


### D169 — Legacy audit checks fail closed instead of reporting false integrity

The legacy writer hashes the caller's original UUID strings and IP while storing UUIDs as bytes; its IP conversion stores IPv4 only and loses IPv6 or other unsupported forms. The digest also uses an unversioned delimiter-based encoding. Consequently the original hash input cannot always be reconstructed from a stored row; existing TypeScript and Python verifiers previously guessed and could issue both false clean and false broken results. A unit test using the real writer demonstrates distinct UUID spellings that store identical bytes but hash differently, and an IPv6 value hashed but stored as null. Do not rewrite historical rows or assume a mismatch proves tampering.

Both `verifyChain` and Python housekeeping now perform bounded, read-only **link and sequence diagnostics only**. They validate row ordering, hash lengths and gaps; detect a non-null genesis predecessor and broken stored links; and report `INCOMPLETE` when no structural break is found. They never claim payload verification. Partial ranges have no trusted predecessor; even a full walk has no independent external anchor and cannot detect every deletion, substitution or payload change. Python's audit-chain command always exits nonzero until complete verification exists. Legacy `audit_verifications` rows have no verifier version: the TypeScript reader treats historical results as `ERROR`, `recordOf` does not emit OK for incomplete reports, and `saveVerification` rejects new OK records. Existing records and audit hashes are not modified.

Shared TypeScript/Python vectors cover empty chains, paging, gaps, links and genesis handling, alongside malformed values and legacy writer data-loss tests. They use stubs, not live TiDB; no audit data was inspected. The production cash gate remains closed. A serialized transactional append, canonical **versioned persisted input**, cross-language tests over stored data, checkpoint/anchor design, historical reconciliation and real concurrency/failure testing are still required before audit integrity or financial production readiness can be claimed.


### D170 — Experimental canonical audit v2 byte format

`canonical-v2.ts` and the independent `scripts/db/audit_v2.py` define a bounded typed byte grammar, deterministic UTF-8 key ordering, explicit UUID/IP bytes, validated UTC microsecond timestamps and domain-separated SHA-256 payload/link hashes. Genesis is explicitly distinguished from a 32-byte predecessor. The proposed payload includes all intended stored audit fields, including user agent; floats, unsafe integers, lone surrogates, cycles and other noncanonical values are refused. The exact format, limits and integration caveats are specified in `AUDIT-V2-FORMAT.md`.

Shared fixtures exercise Unicode, IPv4/IPv6, integer limits, genesis, linked rows and an opaque predecessor; TypeScript tests compare 200 generated nested values with the Python implementation and cover malformed inputs and field tampering. This is a pure foundation only: **no schema, database reader/writer, audit route or verifier uses it**. It does not serialize audit writers, authenticate database columns, establish trusted external checkpoints, recover legacy hash inputs or enable cash financial writes. A future implementation must avoid lossily decoded JSON numbers, verify searchable columns against authoritative canonical bytes, preserve legacy history and separately verify cutover and TiDB concurrency/rollback behavior. No live TiDB or production data was touched.
