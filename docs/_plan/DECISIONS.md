# Decision record

[`35 §7`](../35-execution-plan.md) leaves 31 points to the building agent. The TiDB migration closed
two of them outright (the `gen_random_uuid` source, the PostGIS index parameters), leaving **29
open**; this record adds **three** that the corpus leaves implicit but the build cannot avoid
(D31–D33) and **two visible deviations** from the corpus that the operator's brief forces
(D34–D35). Every entry states the decision, what was rejected, and why — so a later reader can tell
a choice from an accident.

Format: **Decision.** *Rejected:* … *Why:* …

---

## Android (D1–D9)

**D1 — Navigation.** Navigation Compose 2.8 with **type-safe serializable routes**; each feature
module owns its `nav/` graph and the app module composes them. *Rejected:* string routes, Voyager,
Decompose, a hand-rolled navigator. *Why:* type-safe arguments make the 14 deep-link paths
compile-checked, the library is first-party, and nav graphs are testable without a UI harness.

**D2 — State model.** Plain `ViewModel` + `StateFlow` + a sealed intent type with a pure reducer;
no Molecule. *Rejected:* Molecule, MVI frameworks. *Why:* every screen's logic must be unit-testable
on the JVM without Compose; a pure reducer gives that for free, and a 283-screen app does not need a
second concurrency model.

**D3 — Room → domain mapping.** Explicit mapper functions in `core/database/mapper/`, one per
entity. *Rejected:* annotation processors, auto-mappers, mapping in the repository. *Why:* money
and nullability mistakes hide inside generated mapping code; an explicit map is greppable, diffable
and 100%-coverable.

**D4 — Icon pipeline.** `design/icons/*.svg` → a committed generator (`scripts/design/vectors.ts`,
run in CI, output diffed) → `core/designsystem/icons/*.kt` as `ImageVector`. *Rejected:* runtime SVG
parsing (a library and a frame-time cost), hand-porting 118 icons. *Why:* compile-time vectors, no
runtime dependency, and a regeneration diff in CI makes drift impossible.

**D5 — Image cache.** Coil 3 with a 250 MB / 60-day LRU on customer and partner, 120 MB on rider,
cache keys including the chosen variant, and map tiles in MapLibre's own cache so they cannot be
evicted by menu photography. *Rejected:* one shared cache, unbounded cache. *Why:* the rider's
14 MB-per-shift budget (`19 §9`) depends on tiles surviving a shift.

**D6 — Rider offline map.** MapLibre Native with pre-cached vector tiles for the rider's zone.
*Rejected:* Leaflet in a WebView (battery, gesture latency, a second rendering engine, no
`no-layout-animation` guarantee). *Why:* one engine, one style, one attribution component shared with
the admin map; turn-by-turn still hands off to Google Maps (`19 §5.1`).

**D7 — Cronet.** `com.vk.knet:okcronet`, pinned in `libs.versions.toml`; vendoring only via a Gradle
source dependency if an API is missing. *Rejected:* building Cronet from source in Actions (minutes
budget), plain OkHttp (loses HTTP/3, criterion A8). *Why:* the brief names Okronet, and a pinned
published artifact is reproducible.

**D8 — Baseline profiles.** Generated by `android-test.yml` on a controlled emulator with
`BaselineProfileRule`, committed as `src/main/baseline-prof.txt`, regenerated on every release tag.
*Rejected:* hand-written rules, generating on every PR (cost, noise). *Why:* cold start ≤ 1 400 ms
is build-failing, and profiles are the cheapest way to hold it.

**D9 — DI in tests.** Hilt in production; `core:testing` exposes hand-written fakes and
`@TestInstallIn` replacements, and unit tests construct objects directly. *Rejected:* running the
Hilt test runtime for 8 000 JVM tests. *Why:* Robolectric + JUnit5 want plain constructors; the Hilt
test graph costs seconds per class for no coverage gain.

## Workers (D10–D16)

**D10 — Middleware order.** `request-id → logging → security-headers → body-limit → auth → rbac →
step-up → idempotency → rate-limit → zone-scope → handler`, with the envelope written last on both
paths. *Rejected:* idempotency before auth, rate-limit before auth. *Why:* the idempotency key is
scoped to an actor, and rate limits must be per-actor where an actor exists, falling back to IP.

**D11 — Database connection.** `@tidbcloud/serverless` over HTTP, no pool, one lazily created client
per isolate. `DATETIME(6)` columns mean no time-zone conversion happens on write, so the invariant is
enforced three ways: every business timestamp is **app-generated UTC**, `CURRENT_TIMESTAMP(6)` is
used only as a default on audit rows, and a boot probe asserts `@@session.time_zone = '+00:00'` and
fails the isolate if it is not. *Rejected:* relying on a connection-string parameter alone,
`TIMESTAMP` columns, a pooled driver. *Why:* the corpus's UTC guarantee must not depend on a
variable a future driver version might silently change.

**D12 — Python runtime.** Pyodide on the Workers Python runtime. *Rejected:* RustPython/WASM
(incomplete stdlib, no numerics), a second JS implementation from day one. *Why:* the engines are
pure arithmetic and statistics; if cold start exceeds 400 ms the fare engine is ported to TypeScript
(R37) with the differential test guaranteeing identical results.

**D13 — Feature-store hot tier.** KV for versioned config, weights and `vendor_stats` snapshots;
Cache API only as an in-isolate memo of a feature payload for a single request. *Rejected:* Cache API
for config, D1 for features. *Why:* KV's 1 000 writes/day fits config that changes rarely, its
100 000 reads/day fits the hot path, and a per-request memo needs no durability.

**D14 — SSE keepalive.** A `: ping` comment frame every 15 s for proxy/idle keepalive, plus a real
`tick` event every 15 s carrying server time **only** on streams that compute staleness (order
tracking, admin map — `22 §4`). *Rejected:* an `event: heartbeat` on every stream. *Why:* comments
never reach an `EventSource` listener, so they cost nothing; ticks are required where staleness is
displayed and would be noise everywhere else.

**D15 — Binding errors.** Service bindings return the same envelope shape rather than throwing;
`undal-core` maps a downstream failure to `502` with `UPSTREAM_{SERVICE}_FAILED`, preserves the
request id, and writes a dead letter. *Rejected:* letting exceptions cross the boundary. *Why:* a
thrown binding error loses the error code and the correlation id, which is exactly what an incident
review needs.

**D16 — Retry budget.** One request budget (2 500 ms) threaded through hops as `budget_remaining_ms`;
each nested call receives `min(remaining / 2, its own budget)`; retries only on idempotent verbs and
`1213`/`1205`/`5xx`; at most 2 retries per hop and 4 across the chain. *Rejected:* per-hop retry
budgets. *Why:* nested retries multiply tail latency; a single budget makes the p99 provable.

## Web (D17–D22)

**D17 — Router.** React Router 7 in **data mode** (`createBrowserRouter` + loaders). *Rejected:*
framework mode, Next.js, client-only rendering. *Why:* loaders give the pre-render pipeline
data-before-render, while Vite stays in control of the build that Pages deploys.

**D18 — Pre-render.** Our own plugin in `web/storefront/prerender/` (route manifest from
`/v1/public/sitemap-data`, HTML emission, JSON-LD, thin-page failure). *Rejected:* `vite-plugin-ssg`,
a Gatsby-style framework. *Why:* `prerender-verify` requires per-route content assertions a generic
plugin cannot express, and Bengali mirrors double every route.

**D19 — Styling.** CSS Modules + custom properties generated from `design/tokens.json`.
*Rejected:* vanilla-extract, Tailwind, CSS-in-JS. *Why:* zero runtime, static CSS that survives
pre-rendering, and a critical-CSS budget of 42 KB that extraction can actually meet.

**D20 — Virtualisation.** `@tanstack/react-virtual` for admin grids and any list over 60 rows.
*Rejected:* react-window (older API), no virtualisation. *Why:* it composes with TanStack Table,
which the 60+ grids already need, and it is headless.

**D21 — Charts.** Recharts in the admin; hand-rolled SVG in the storefront and apps.
*Rejected:* Recharts everywhere. *Why:* the storefront's 160 KB bundle budget cannot carry a charting
library for three visuals; the admin's budget (420 KB) can.

**D22 — Service worker.** Hand-rolled (~150 lines) implementing the five strategies in
`20 §7` explicitly. *Rejected:* Workbox. *Why:* Workbox adds weight and its defaults are broader than
the corpus's narrow scope — "API mutations are never cached" must be a line of code, not a config
option.

## Data (D23–D26)

**D23 — UUIDv7.** One implementation per language — `packages/contracts/src/common/ids.ts`,
`workers/brain/src/lib/ids.py`, `android/core/common/Uuid.kt` — 48-bit millisecond timestamp + a
12-bit intra-millisecond counter + 62 random bits, against one shared test vector and a 10 000-call
monotonicity test per language. SQL never generates an id. *Rejected:* a SQL function (impossible
without stored functions), v4, `AUTO_INCREMENT`. *Why:* ids must sort by creation time for index
locality, and TiDB has no `gen_random_uuid()` at all.

**D24 — Item snapshots.** Full snapshot JSON on `order_items` (names en/bn, unit price, option labels
and deltas, photo URL), not a delta. *Rejected:* delta against the live menu. *Why:* an invoice must
be reproducible years later, and a delta against a mutable menu cannot be; `receipt-reproducibility`
(A76) is the test.

**D25 — Trace retention.** No partitioning for `brain_traces`; TiDB TTL by age (7 days default, 90
for dispatch and money-adjacent engines) plus the request-triggered sweep as a fallback.
*Rejected:* monthly partition tables, unlimited retention. *Why:* Starter has TTL, the 5 GiB ceiling
is the tightest constraint in the platform, and partitioning would split the single replay query.

**D26 — `vendor_stats`.** Maintained by an upsert inside the order-delivered write path, with a
nightly integrity job recomputing a sample and comparing. *Rejected:* a refresh-on-read materialised
view. *Why:* the ranking hot path must not pay an aggregate join; a bounded upsert on the write path
costs one statement.

## Process (D27–D30)

**D27 — Task graph.** Turborepo with `codegen → build → typecheck → lint → test`, explicit `inputs`
and `outputs`; remote cache off. *Rejected:* remote caching (a paid service for a 40-second cache
hit), Nx. *Why:* the free-tier rule outranks a build-speed win.

**D28 — Versioning.** No changeset tool. Versions live in four constants (`versionName` per app, a
Worker version, a contract version) bumped in the release commit, and `lockfile-drift` guards the
lockfiles. *Rejected:* Changesets, semantic-release. *Why:* nothing here is published to a registry;
a second source of truth for versions is pure overhead.

**D29 — Screenshot tolerance.** Pixel diff only for the 1 200 deliberate visual snapshots
(0.1% differing pixels, per-pixel threshold 0.1). The responsive matrix asserts **layout
invariants** — no overflow, no clipping, target sizes — rather than pixel equality.
*Rejected:* pixel-diffing 56 600 renders. *Why:* cross-platform font rasterisation makes pixel
equality of an unrendered state meaningless; the invariant is the real contract (`A151`, `A154`).

**D30 — Flaky tests.** A failing-on-rerun test moves to a `quarantine` suite that **still runs and
must still pass** but does not gate merges, with an auto-created issue and a 7-day expiry that turns
the build red when it lapses. *Rejected:* skipping, deleting, "fix later". *Why:* the corpus's zero
tolerance needs a mechanism that cannot be quietly ignored; an expiring quarantine is that mechanism.

## Implicit, and decided here (D31–D33)

**D31 — Generated Kotlin models.** `scripts/codegen/kotlin-models.ts` generates `@Serializable` data
classes for all 412 endpoints into `core:network/model/generated/`, with money as `Paisa` (a `Long`
value class) and never `Double`. *Rejected:* hand-written DTOs. *Why:* 412 hand-written mirrors of a
Zod contract drift within a week, and a generated `Double` is a money bug waiting for a fare.

**D32 — QR key rotation.** Two HMAC keys are accepted for a 24-hour overlap
(`QR_HMAC_KEY`, `QR_HMAC_KEY_PREVIOUS`), and `rotate-secret.yml` writes both. *Rejected:* a single
key (rotation invalidates in-flight pickups). *Why:* `27 §6.1` requires rotation without invalidating
in-flight orders; two keys is the only way to satisfy it.

**D33 — Error text ownership.** Every error code's English and Bengali copy lives in
`packages/contracts/src/errors/registry.ts` and is extracted into `packages/i18n`; the server returns
a code plus an optional server-rendered sentence, and clients render from the catalogue.
*Rejected:* server-only strings, client-only strings. *Why:* `i18n-completeness` must be able to
prove all 184 codes exist in both locales, and offline clients must still be able to explain a
failure they received earlier.

## Visible deviations from the corpus (D34–D35)

**D34 — One Pages project, not two.** The storefront and the admin SPA deploy as one project: `/`
serves the pre-rendered storefront, `/admin/*` serves the admin SPA with a **path-scoped** CSP in
`public/_headers` (stricter: no `img-src data:`, no inline styles), an `HttpOnly` refresh cookie
scoped to `/admin`, and a Cloudflare Access policy on `/admin/*`. [`21 §13`](../21-admin-panel.md)
specifies a separate project at `admin.{domain}`; the operator's brief specifies **one Pages
project**, and this is the closest thing to both. *Rejected:* two projects (violates the brief),
one project with one shared CSP (loses the admin's stricter policy). *Why recorded here:* the
residual risk is an origin shared by a public storefront and the admin surface — R36 in the build
plan — and it should be a decision someone can find, not a surprise.

**D35 — `minSdk 26`, not 24.** Non-negotiable 39 in [`01`](../01-mission-and-non-negotiables.md)
requires Android 8.0 and names its own test matrix (API 26/30/34/35); [`16 §3.1`](../16-android-foundation.md)
and [`18 §1`](../18-partner-app.md) say 24. The non-negotiable wins because it is explicitly ranked
above the documents and because CI can only promise what it tests. *Rejected:* 24 (untested floor, a
stated rule broken), 23 (below 16's own warning). *Why recorded here:* it excludes Android 7.x
devices — a small, shrinking share of the Bangladeshi base — and that cost should be visible rather
than discovered in a Play Console device report.

## D36 — The five platform-wide error codes keep their bare names

**Decision.** The sixteenth group file is `packages/contracts/src/errors/rows/system.ts`, but its
five codes are exactly `INTERNAL`, `SERVICE_DEGRADED`, `DEPENDENCY_TIMEOUT`, `IDEMPOTENCY_CONFLICT`
and `NOT_IMPLEMENTED` — no `SYSTEM_` prefix — and the three `OAUTH_*` codes are counted inside the
`AUTH_` group.

**Rejected.** Inventing `SYSTEM_INTERNAL` and the rest so that every prefix matches its table row.

**Why.** `08 §11` labels the row `SYSTEM_` but names the codes without it, and clients match on the
code string exactly. The registry is the contract, so the 184 strings are authoritative and the table
label is the typo. The parity test asserts `AUTH_ + OAUTH_ = 21` and `BARE = 5` so the reconciliation
lives in the test rather than in a reader's head.

## D37 — `platform_config.zone_id` uses the all-zero UUID for "global"

**Decision.** `zone_id BINARY(16) NOT NULL DEFAULT 0x00…00`, where the zero UUID means the global
default. The DDL in `29` was rewritten from CockroachDB types to `VARCHAR`/`BINARY(16)`/`JSON`/
`DATETIME(6)`.

**Rejected.** Keeping `zone_id UUID NULL` with a nullable primary-key column.

**Why.** MySQL — and therefore TiDB — will not store `NULL` in a primary-key column: the insert fails
with 1048 rather than creating the global row the design describes. The sentinel keeps the same
semantics, the same key order and the same access path, and it is visible in the type instead of in
a comment that the database ignores. `no-postgres-dialect` caught the original DDL on the first
guardrail run.

## D38 — An unknown route answers `NOT_IMPLEMENTED`, not `404`

**Decision.** `undal-core` and `undal-realtime` return HTTP 501 with code `NOT_IMPLEMENTED` and
`details: { method, path }` for any path they do not serve.

**Rejected.** Adding a `ROUTE_NOT_FOUND` code (which would break the 184-code contract) or borrowing
`CATALOG_VENDOR_NOT_FOUND` (which would lie about what was missing).

**Why.** On a versioned API an unknown path means "this build does not serve this", which is exactly
what 501 says in RFC 9110, and it is the one registered code whose meaning is true. A `404` would tell
the client the resource exists elsewhere and send it looking.

## D39 — Guardrail exemptions are named, not silent

**Decision.** Three exemptions are written into the rules themselves: markdown is exempt from the
700-line cap; test and fixture paths are exempt from the placeholder scan and the money-float scan;
`scripts/guardrails/` is exempt from the placeholder scan.

**Rejected.** Keep-whole rules with a suppression comment, or a `# guardrail-ignore` escape hatch.

**Why.** A rule that can be silenced locally stops being a rule. Each exemption below is a property of
the tree rather than of a file: the spec corpus is one document per subject and splitting
`06-data-model-tidb.md` at line 700 would separate a table from the paragraph that explains it; tests
are not shipped and a test that asserts "no TODO in the registry" must be able to spell the word; the
guardrail tooling is the code that lists the forbidden words.

## D40 — The Kotlin differential runs on its own workflow

**Decision.** `ci.yml` compares TypeScript against Python on every push; `money-math.yml` adds the
Kotlin answers from the JVM-only `:shared:money` module.

**Rejected.** Setting up a JVM in the main gate for one more language.

**Why.** Three minutes on every push for an assertion whose inputs change only when
`packages/money` or `android/shared/money` change is three minutes the maintainer spends waiting on a
tablet. The paths filter on `money-math.yml` runs it exactly when it can fail.

## D41 — Operational workflows ship before the scripts they call

**Decision.** `migrate`, `verify-schema`, `d1-migrate`, `db-query`, `housekeeping` and `brain-replay`
exist from this response as the interface a browser-only maintainer uses, while the scripts they
invoke arrive with the migration pipeline (R6) and the Brain (R17).

**Rejected.** Deferring the workflows until their scripts exist.

**Why.** Each of these is a `workflow_dispatch` button, and a button that exists, is documented and
fails loudly at a named missing script is better than a button discovered missing at 2 a.m. with a
broken deployment — the failure names its own remedy. Nothing here runs on push, so the gate that
guards every commit is unaffected, and no step in any of them pretends to have done work it did not do.

## D42 — The 109 table names are the schema; the document's total of 99 was a slip

**Decision.** `db/migrations` creates the 109 tables `06 §2` names, and the document's total row now
says 109.

**Rejected.** Implementing 99 tables and dropping ten names, or keeping 99 and hiding the gap.

**Why.** The per-group counts in that table were correct from the start — 14, 8, 12, 12, 12, 15, 12,
10, 14 — and they always summed to 109; the total was the only wrong cell. Ten tables cannot be
dropped to satisfy a typo, so the names win and `scripts/db/check_schema_parity.py` now compares the
inventory to the migrations on every push.

## D43 — `CHECK` is declared in SQL and enforced in TypeScript

**Decision.** `scripts/db/extract_constraints.py` parses every `CHECK` out of the migrations, writes
`packages/contracts/src/constraints.json`, and generates `constraints/generated.ts`: 164 validators
across 76 tables, each carrying the SQL it came from.

**Rejected.** Trusting the DDL, and trusting a hand-written validator list beside it.

**Why.** TiDB parses `CHECK` and does not enforce it, so the DDL alone would look guarded and enforce
nothing. The generator is a real parser (tokens, recursive descent, arithmetic and `NOT IN`
precedence), not a regex: every generated expression is proven to parse as JavaScript by `node
--check` at generation time, and `tsc` proves it again in CI. Anything the parser does not understand
is a hard failure, because a validator that skips a rule silently is worse than no validator.

## D44 — Foreign keys stay where the specification put them

**Decision.** Tables defined in the corpus keep their `REFERENCES` clauses; tables authored against
the inventory get them too, except the three the corpus names as deliberately unkeyed (`order_items`,
`order_state_events`, `order_offers`).

**Rejected.** Removing every foreign key to make migration order easier, and adding keys to the three
high-write tables for uniformity.

**Why.** An orphaned ledger row is a reconciliation bug nobody can fix after the fact, while an
orphaned order item is a row that outlives a cancelled order by design. The exception is documented
where it applies — in the migration that creates each of those three tables — rather than in a policy
statement a reader has to find.

## D45 — `platform_config`'s primary key is ascending

**Decision.** `PRIMARY KEY (key, zone_id, effective_at)`, with no `DESC`.

**Rejected.** The `DESC` the specification wrote, which is legal on a secondary index and not on a
primary key.

**Why.** MySQL rejects a descending column in a primary key; TiDB parses it inconsistently across
versions. "Latest value for this key" is a backward index scan on the same key, which TiDB serves
without a second index, so nothing is lost but the parse failure the SQL validator caught.

## D46 — The geospatial layer is checked three ways, every push

**Decision.** `scripts/geo/parity.py` runs 6 000 deterministic cases through the exported
TypeScript functions, an independent Python mirror, and SQL, and writes
`.artifacts/geo/parity.json`. The `geo-parity` rule fails the build on any mismatch, and in CI
(`GEO_PARITY_REQUIRED=1`) also fails when the artifact is missing.

**Rejected.** A shared constants file, a formula copied into three languages, and a check that
silently passes when no artifact exists.

**Why.** It earned its keep on the first run. SQLite's `/` on two integers truncates where MySQL's
divides into a DECIMAL, so the "same" floor expression gave a different cell for every negative
coordinate; the probe also caught that `haversineMeters` returns whole metres, which the Python
mirror was comparing at three decimals. A check that cannot disagree is not a check.

## D47 — The ledger records statements, not files

**Decision.** `scripts/db/migrate.py` writes one `schema_migrations` row per statement, with the
file's SHA-256, and refuses to continue if an applied statement's checksum changed.

**Rejected.** One row per file, and a `--force` escape hatch.

**Why.** TiDB auto-commits DDL: a file that fails at statement 7 leaves six statements applied and no
rollback. A per-file ledger would then either re-run all six (they are idempotent, but the window in
between is wrong) or mark the file applied and skip statement 7 forever. Per-statement resume plus an
immutability check is the only combination that is safe when the platform has no transactions around
DDL.

## D48 — Two session-security tables join the identity group

**Decision.** `refresh_tokens` and `security_events` are created by `013_session_security.sql`, the
inventory's identity group grows from 14 to 16 names, and the total from 109 to 111.

**Rejected.** Storing refresh families in KV, and logging token reuse to `audit_log`.

**Why.** Rotation with family reuse detection needs a row per issued token that survives a KV
eviction — a stolen token is exactly the event where losing state is unacceptable. Reuse is evidence
about an actor, not an action taken on data, so it belongs in a table security reads rather than in
the finance-facing audit chain, which is also append-only with a single writer.

## D49 — Twenty-seven rate limits, not thirty-eight

**Decision.** `ratelimit/limits.ts` implements the 27 limits the `08 §12` table actually lists, and
asserts that count at module load.

**Rejected.** Inventing eleven more buckets to reach the prose figure.

**Why.** Counted cell by cell the table has 27 filled cells; the surrounding sentence doubles the
auth pair (IP and phone) and the five SSE caps. Same failure as D42, caught the same way: the table
is data and the prose is a summary, and a fabricated bucket would be a limit nobody chose.

## D50 — The audit chain is verified by a second implementation, not by itself

**Decision.** `db/fixtures/audit_chain_vectors.json` holds three chained rows with their digests;
`workers/core/src/audit/chain.ts` and `scripts/db/housekeeping.py` must both reproduce them, and both
do in CI.

**Rejected.** Verifying the chain only in the language that wrote it.

**Why.** A chain checked by the code that wrote it proves the code is self-consistent, which is not
the property anyone needs. The fixture is the contract between the two implementations, and it
immediately earned its keep twice: `null` had to hash like an absent field, and the housekeeping job
was reading a `payload_sha256` column that does not exist.

## D51 — The tip and the small-order fee are inside the collected cash, not beside it

**Decision.** In the canonical `ORDER_DELIVERED` set the customer's whole payment — food, delivery,
tax, tip, small-order fee, less the rounding delta — is the single `RIDER_CASH` debit. The tip and
the small-order fee appear only as credits: the rider's payable grows by the tip and by the rider's
share of the fee, the platform's small-order revenue grows by the rest. A tip added *after* delivery
is its own `TIP` entry with the `+tip / −tip` pair that `24 §3` prints.

**Rejected.** Posting `RIDER_CASH +tip` inside the order set, as a literal reading of the §3 table.

**Why.** §2.1's `raw_total` already contains the tip, so a second cash debit counts the customer's
money twice — the generator caught it on case 21 of the closure property test, which is exactly the
kind of double count that leaves a ₹5 000 hole in a rider's float after a week of tips. The §3 table
describes the *pass-through* entry, not the order entry; the difference only shows up when both
exist, and now the test knows which is which.

## D52 — A balance is a sum, never a stored column

**Decision.** `domain/ledger/balance.ts` computes every balance as `SUM(amount_paisa)` over the
postings table, in one grouped query for the whole platform, with an optional `asOfSequence`.

**Rejected.** A `balance_paisa` column on `ledger_accounts`, updated on every posting.

**Why.** Two sources of truth for money is one source of truth and one source of argument. A cached
column drifts the first time a compensating delete runs, and the daily reconciliation compares these
sums against the provider's statement — so the sum has to be the definition, not a cache of it. The
`asOfSequence` variant exists because an auditor asking "what did we hold on the 3rd" needs the sum
as it stood then, which a mutated column cannot answer at all.

## D53 — The golden posting sets are generated by a second implementation, not by the code

**Decision.** `scripts/money/posting_sets.py` implements `24 §2.1` and `§3` again in Python, from the
document, and writes the thirty-four golden sets the TypeScript builders must reproduce. CI runs the
generator with `--check`, so a drifted golden file fails the build instead of quietly agreeing.

**Rejected.** Committing a table of expected numbers produced by the TypeScript builders.

**Why.** A file generated by the code under test asserts that the code still does what it did last
Tuesday, which nobody doubted. The Python side disagreed twice on first contact and both times it was
right: the pickup tax base must include the pickup fee (it is platform revenue, so invariant 2 of
`§2.3` puts it in the base), and a cancellation refund has to address the *customer*, not the order
id — the TypeScript had been crediting the order. Neither would have surfaced from a hand-typed table
without the same disagreement, and a hand-typed table would already have been wrong.

## D54 — `-0` is not zero

**Decision.** `applyRate` normalises a zero result to `+0`; the refusal test asserts it with
`Object.is`.

**Rejected.** Leaving the sign in place because `-0 === 0` is true.

**Why.** `-0` passes every equality check, survives `Object.is`, prints as `-৳0.00` through the
formatter, and keys a `Map` identically to `0` while failing a `deepStrictEqual` — a shape that only
ever appears in a diff at three in the morning. The coverage gate found it: the branch that
multiplies a negative amount by a small rate had never been executed, and the first execution printed
`-0`.

## D55 — `LEDGER_IMBALANCE` is a value the ledger produces, not a webhook it sends

**Decision.** `domain/ledger/imbalance.ts` returns the exception (`trigger`, `severity`, `slaSeconds`,
the drifting accounts largest-first, both language strings) and leaves delivery to the alarm pipeline.

**Rejected.** Posting the alarm directly from `postEntry`, or from the nightly sweep.

**Why.** The alarm pipeline arrives in R13 and owns retries, dead letters and the on-call page; the
ledger owns the arithmetic. Keeping them apart means the exception is testable without a network, the
admin panel's "verify now" button and the nightly sweep call the same function, and a caught
in-memory imbalance produces the *same* exception shape as a drifted trial balance — one alarm with
two detection paths rather than two alarms that can disagree about severity.

## D56 — The small-order fee splits three ways, and the vendor is one of the three

**Decision.** `ORDER_DELIVERED` credits the vendor's share of the order fee through the vendor's
line (`subtotal − commission − bonus + vendor_share`) and books only
`fee − rider_share − vendor_share` as `PLATFORM:REVENUE_SMALL_ORDER`.

**Rejected.** The two-way split the ledger had: platform gets `fee − rider_share`, vendor gets
nothing.

**Why.** `10 §8` and `§12.1` both print ৳25 as ৳5 rider + ৳5 vendor + ৳15 platform, and the fare
engine's vendor payout carries the vendor's ৳5. The ledger disagreed with the engine by exactly
that ৳5 — every posting set still closed, because closure only says the totals agree, not that they
agree with the *right* people. Found by writing the fare engine's constants next to the ledger's
small-order lines, which is the check that no property test performs: the two modules were each
internally consistent and mutually wrong.

## D57 — At SDR 0.50 the bridge lands on 1.475×, not the table's 1.48×

**Decision.** `surge_bps(0.50)` returns 14 750, the value the printed function computes from the
bridge between the severe and moderate bands.

**Rejected.** Forcing 14 800 to match the row the table prints.

**Why.** `10 §4.3`'s table and `10 §4.2`'s code disagree by 50 bps at exactly one point, because
the table's author rounded 1.475 to two decimals while writing it. The code is the specification
here — it is the thing that ships, it is continuous by construction, and a table row is a
human-written summary of it. The test names the point and states which side it took, so the next
reader does not have to re-derive the disagreement.

## D58 — The delivery line closes on its residual, not on `margin − weather`

**Decision.** The closure identity uses `platform_delivery_net = delivery_fee − rider_fare`, with no
separate weather term. `platform_delivery_margin = delivery_fee − ride_core` remains the *gross*
figure and remains the tax base, exactly as `10 §9` requires.

**Rejected.** The literal identity of `10 §10.1`, which subtracts the weather premium and the gross
margin.

**Why.** The printed identity is true only when the rider's fare equals the core plus the weather
premium. It is not true when a bundle moves the fare onto a marginal detour, and it is not true when
the minimum-payout floor binds — and in those cases it does not merely drift, it *fails*, which the
brain found on vector 06 with a 3 867-paisa drift on a perfectly ordinary order. The residual is the
same statement without the assumption: whatever the customer paid for the delivery minus whatever the
rider was paid for it, and every term stays named in the failure message.

## D59 — Thirty of the forty vectors are regression pins, and the file says so

**Decision.** Vector 01 is asserted by hand against `10 §12.1`'s printed table. The other 39 are
generated by `workers/brain/test/generate_fare_vectors.py`, committed, and checked for drift in CI;
each is also asserted to close over its own terms.

**Rejected.** Implying all forty were derived independently of the engine that produces them.

**Why.** The document works ten vectors in full; the other thirty exist to pin boundaries — every
surge band edge, both bridges, four weather conditions on both vehicles, both clamps, bundles,
tips, discounts. Calling a generated pin "hand-computed" would be a lie in a file whose whole
purpose is to be trusted. The distinction is written into the generator's docstring, the test's
docstring and this entry: one vector is the document's, thirty-nine are history's, and the closure
identity is what makes history worth keeping.

## D60 — A pickup reaches DELIVERED, because the document leaves it stranded

**Decision.** `PICKED_UP → DELIVERED` is a `SYSTEM` edge guarded by `pickupOnly`, `cashRecorded` and
`cashReconciles`; a pickup therefore travels `ACCEPTED → PICKED_UP → DELIVERED`.

**Rejected.** Leaving the row out because `06 §7.3` does not print it.

**Why.** For a pickup the table offers `ACCEPTED → PICKED_UP` (customer, QR scanned by the vendor)
and then no edge that fits — `PICKED_UP → ARRIVED` needs a rider who does not exist, and
`ARRIVED → DELIVERED` is unreachable from there. Taken literally, every pickup order stops in
`PICKED_UP` and its cash never settles: the one path where the money is taken *before* the order is
complete would be the one path the ledger cannot close. The added edge is a `SYSTEM` transition, not
a customer one, so it cannot be used to skip a payment, and the coverage sweep now proves that no
non-terminal state is a trap.

## D61 — Guards read an explicit context, never the database

**Decision.** Every guard is a predicate over `TransitionContext`, a sparse object the caller fills;
a missing field fails the guard rather than passing it.

**Rejected.** Guards that load the vendor or the order themselves.

**Why.** The same transition has to be evaluable by an HTTP handler, a DO alarm, a test and a
replay of last month's events. A guard that reads the world can only be run in one of those four
places, and the event log stops being something a reconciliation job can re-derive. "Absent field
means refused" is the direction that fails closed: a context built by a caller who forgot the quote
refuses the placement instead of selling the order at a price nobody computed.

## D62 — A quote is a signed snapshot, not a row

**Decision.** The quote is a canonical-JSON snapshot of the fare inputs and totals, HMAC-signed and
handed to the client; placement verifies the signature, re-prices from scratch and refuses any
difference with `QUOTE_MISMATCH` and the moved lines. No `quotes` table exists, and none is needed.

**Rejected.** Persisting quotes and comparing rows.

**Why.** A row would be written before the customer has agreed to anything, which means a table that
grows with abandoned carts — and it would still not enforce the promise, because the promise is
*re-price and compare*, not *remember*. The signature proves the platform issued the price; the
re-price is what makes it true. It also survives a Worker restart, a zone boundary and a deploy,
none of which a row would.

## D63 — The order code is derived from the order id

**Decision.** `UND-` plus eight characters folded from the id's own bytes.

**Rejected.** A sequence, a counter row, or `Math.random()` — then checking for collisions.

**Why.** A counter needs a lock, and this platform deliberately has no interactive transactions: two
Workers placing in the same millisecond would race for the same number and one would lose an order.
Deriving the code from the id makes collisions impossible by construction (distinct ids, distinct
codes at this bit width), needs no coordination, and keeps a code the customer can read down a
phone line without a homoglyph in it — the alphabet omits `0/O` and `1/I`.
## D64 — Order routes ask the state table; they never branch on state themselves

A route that decides "can this be accepted?" with an `if` chain reimplements the machine and drifts
from it the first time an edge changes. `accept`/`reject` therefore build a `TransitionContext` and
hand it to the lifecycle, which returns either the target state or a refusal code that the route
returns verbatim. The route contributes facts (who owns the order, the prep time, the reason), never
the rule.

Concurrency is the same question asked of the database rather than of memory: the move is
`UPDATE orders SET state = ? WHERE id = ? AND state = ?`, and `affectedRows !== 1` means another
writer got there first — surfaced as `applied: false` and answered with the refusal for the state the
order is actually in, not a 500. Two vendors accepting at once must produce one ACCEPTED row and one
event, and the loser must be told `ORDER_ALREADY_ACCEPTED`.
## D65 — An order line is a photograph, and the history has no gaps

`order_items` copies the name, the unit price and the quantity the customer agreed to. Nothing on a
receipt is joined live to the menu: a rename or a price rise must not edit an invoice that has
already been paid, and the only way to guarantee that is to stop reading the catalogue at render
time. Modifiers are folded into the unit price rather than stored per row, because the receipt shows
one number per line and a second number that disagrees is worse than no breakdown.

Placement refuses a cart that the rows cannot explain: an empty cart, the same menu item twice, a
quantity outside `1..20`, more than `MAX_ORDER_LINES` lines, and — the check that matters most — a
line subtotal that does not equal the quoted `subtotal_paisa`. A total is a claim; the lines are the
proof of it.

`order_state_events.seq` is dense by construction, so `firstGap` treats a hole as an incident rather
than as history. `orders.state` says where an order is; the event table is the only thing that can
say how it got there, and a deleted row is a settlement dispute waiting for a quiet week.
## D66 — Core prices money; the Brain prices the trip, and a disagreement never moves a price

`10 §4` turns rider counts into a surge multiplier, and that curve is the one float in pricing. It
lives in the Brain (`fare/surge.py`) and nowhere else: Core's deterministic engine takes the
multiplier *published for the zone* as an integer input and refuses anything that is not a whole
value in `10 000..22 000` bps. A second float implementation in TypeScript would be a second answer
to "what does this trip cost", which is exactly what a published multiplier exists to prevent.

Everything below the multiplier is integer paisa and is duplicated deliberately in
`workers/core/src/pricing/fallback.ts`, because an order must still be priced when the Brain is cold,
deploying, or merely slow. The duplication is falsifiable rather than hopeful: the same forty fare
vectors the Python engine is tested against are read from the same file and run through the
TypeScript engine in `test/pricing-fallback.test.ts`.

`resolveFare` treats the Brain as a second opinion, never as the price. If it answers within its
400 ms budget with whole paisa and agrees on all four published numbers (delivery fee, ride core,
rider payout, surge), the order is stamped `fare_source = 'BRAIN'`. If it is late, unavailable,
malformed, or disagrees by a single paisa, the deterministic breakdown stands, the order is stamped
`'FALLBACK'`, and the reason plus every disagreeing field is returned so it can be counted. A
Brain bug therefore cannot charge an unexplainable price, and a Brain outage costs nothing but a
metric.
