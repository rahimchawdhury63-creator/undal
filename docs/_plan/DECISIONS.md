# Decision record

[`35 §7`](../35-execution-plan.md) leaves 31 points to the building agent. The TiDB migration closed
two of them outright (the `gen_random_uuid` source, the PostGIS index parameters), leaving **29
open**; this record adds **three** that the corpus leaves implicit but the build cannot avoid
(D31–D33) and **two visible deviations** from the corpus that the operator's brief forces
(D34–D35). Every entry states the decision, what was rejected, and why — so a later reader can tell
a choice from an accident.

Format: **Decision.** *Rejected:* … *Why:* …

---

## Android (D1–D9)

**D1 — Navigation.** Navigation Compose 2.8 with **type-safe serializable routes**; each feature
module owns its `nav/` graph and the app module composes them. *Rejected:* string routes, Voyager,
Decompose, a hand-rolled navigator. *Why:* type-safe arguments make the 14 deep-link paths
compile-checked, the library is first-party, and nav graphs are testable without a UI harness.

**D2 — State model.** Plain `ViewModel` + `StateFlow` + a sealed intent type with a pure reducer;
no Molecule. *Rejected:* Molecule, MVI frameworks. *Why:* every screen's logic must be unit-testable
on the JVM without Compose; a pure reducer gives that for free, and a 283-screen app does not need a
second concurrency model.

**D3 — Room → domain mapping.** Explicit mapper functions in `core/database/mapper/`, one per
entity. *Rejected:* annotation processors, auto-mappers, mapping in the repository. *Why:* money
and nullability mistakes hide inside generated mapping code; an explicit map is greppable, diffable
and 100%-coverable.

**D4 — Icon pipeline.** `design/icons/*.svg` → a committed generator (`scripts/design/vectors.ts`,
run in CI, output diffed) → `core/designsystem/icons/*.kt` as `ImageVector`. *Rejected:* runtime SVG
parsing (a library and a frame-time cost), hand-porting 118 icons. *Why:* compile-time vectors, no
runtime dependency, and a regeneration diff in CI makes drift impossible.

**D5 — Image cache.** Coil 3 with a 250 MB / 60-day LRU on customer and partner, 120 MB on rider,
cache keys including the chosen variant, and map tiles in MapLibre's own cache so they cannot be
evicted by menu photography. *Rejected:* one shared cache, unbounded cache. *Why:* the rider's
14 MB-per-shift budget (`19 §9`) depends on tiles surviving a shift.

**D6 — Rider offline map.** MapLibre Native with pre-cached vector tiles for the rider's zone.
*Rejected:* Leaflet in a WebView (battery, gesture latency, a second rendering engine, no
`no-layout-animation` guarantee). *Why:* one engine, one style, one attribution component shared with
the admin map; turn-by-turn still hands off to Google Maps (`19 §5.1`).

**D7 — Cronet.** `com.vk.knet:okcronet`, pinned in `libs.versions.toml`; vendoring only via a Gradle
source dependency if an API is missing. *Rejected:* building Cronet from source in Actions (minutes
budget), plain OkHttp (loses HTTP/3, criterion A8). *Why:* the brief names Okronet, and a pinned
published artifact is reproducible.

**D8 — Baseline profiles.** Generated by `android-test.yml` on a controlled emulator with
`BaselineProfileRule`, committed as `src/main/baseline-prof.txt`, regenerated on every release tag.
*Rejected:* hand-written rules, generating on every PR (cost, noise). *Why:* cold start ≤ 1 400 ms
is build-failing, and profiles are the cheapest way to hold it.

**D9 — DI in tests.** Hilt in production; `core:testing` exposes hand-written fakes and
`@TestInstallIn` replacements, and unit tests construct objects directly. *Rejected:* running the
Hilt test runtime for 8 000 JVM tests. *Why:* Robolectric + JUnit5 want plain constructors; the Hilt
test graph costs seconds per class for no coverage gain.

## Workers (D10–D16)

**D10 — Middleware order.** `request-id → logging → security-headers → body-limit → auth → rbac →
step-up → idempotency → rate-limit → zone-scope → handler`, with the envelope written last on both
paths. *Rejected:* idempotency before auth, rate-limit before auth. *Why:* the idempotency key is
scoped to an actor, and rate limits must be per-actor where an actor exists, falling back to IP.

**D11 — Database connection.** `@tidbcloud/serverless` over HTTP, no pool, one lazily created client
per isolate. `DATETIME(6)` columns mean no time-zone conversion happens on write, so the invariant is
enforced three ways: every business timestamp is **app-generated UTC**, `CURRENT_TIMESTAMP(6)` is
used only as a default on audit rows, and a boot probe asserts `@@session.time_zone = '+00:00'` and
fails the isolate if it is not. *Rejected:* relying on a connection-string parameter alone,
`TIMESTAMP` columns, a pooled driver. *Why:* the corpus's UTC guarantee must not depend on a
variable a future driver version might silently change.

**D12 — Python runtime.** Pyodide on the Workers Python runtime. *Rejected:* RustPython/WASM
(incomplete stdlib, no numerics), a second JS implementation from day one. *Why:* the engines are
pure arithmetic and statistics; if cold start exceeds 400 ms the fare engine is ported to TypeScript
(R37) with the differential test guaranteeing identical results.

**D13 — Feature-store hot tier.** KV for versioned config, weights and `vendor_stats` snapshots;
Cache API only as an in-isolate memo of a feature payload for a single request. *Rejected:* Cache API
for config, D1 for features. *Why:* KV's 1 000 writes/day fits config that changes rarely, its
100 000 reads/day fits the hot path, and a per-request memo needs no durability.

**D14 — SSE keepalive.** A `: ping` comment frame every 15 s for proxy/idle keepalive, plus a real
`tick` event every 15 s carrying server time **only** on streams that compute staleness (order
tracking, admin map — `22 §4`). *Rejected:* an `event: heartbeat` on every stream. *Why:* comments
never reach an `EventSource` listener, so they cost nothing; ticks are required where staleness is
displayed and would be noise everywhere else.

**D15 — Binding errors.** Service bindings return the same envelope shape rather than throwing;
`undal-core` maps a downstream failure to `502` with `UPSTREAM_{SERVICE}_FAILED`, preserves the
request id, and writes a dead letter. *Rejected:* letting exceptions cross the boundary. *Why:* a
thrown binding error loses the error code and the correlation id, which is exactly what an incident
review needs.

**D16 — Retry budget.** One request budget (2 500 ms) threaded through hops as `budget_remaining_ms`;
each nested call receives `min(remaining / 2, its own budget)`; retries only on idempotent verbs and
`1213`/`1205`/`5xx`; at most 2 retries per hop and 4 across the chain. *Rejected:* per-hop retry
budgets. *Why:* nested retries multiply tail latency; a single budget makes the p99 provable.

## Web (D17–D22)

**D17 — Router.** React Router 7 in **data mode** (`createBrowserRouter` + loaders). *Rejected:*
framework mode, Next.js, client-only rendering. *Why:* loaders give the pre-render pipeline
data-before-render, while Vite stays in control of the build that Pages deploys.

**D18 — Pre-render.** Our own plugin in `web/storefront/prerender/` (route manifest from
`/v1/public/sitemap-data`, HTML emission, JSON-LD, thin-page failure). *Rejected:* `vite-plugin-ssg`,
a Gatsby-style framework. *Why:* `prerender-verify` requires per-route content assertions a generic
plugin cannot express, and Bengali mirrors double every route.

**D19 — Styling.** CSS Modules + custom properties generated from `design/tokens.json`.
*Rejected:* vanilla-extract, Tailwind, CSS-in-JS. *Why:* zero runtime, static CSS that survives
pre-rendering, and a critical-CSS budget of 42 KB that extraction can actually meet.

**D20 — Virtualisation.** `@tanstack/react-virtual` for admin grids and any list over 60 rows.
*Rejected:* react-window (older API), no virtualisation. *Why:* it composes with TanStack Table,
which the 60+ grids already need, and it is headless.

**D21 — Charts.** Recharts in the admin; hand-rolled SVG in the storefront and apps.
*Rejected:* Recharts everywhere. *Why:* the storefront's 160 KB bundle budget cannot carry a charting
library for three visuals; the admin's budget (420 KB) can.

**D22 — Service worker.** Hand-rolled (~150 lines) implementing the five strategies in
`20 §7` explicitly. *Rejected:* Workbox. *Why:* Workbox adds weight and its defaults are broader than
the corpus's narrow scope — "API mutations are never cached" must be a line of code, not a config
option.

## Data (D23–D26)

**D23 — UUIDv7.** One implementation per language — `packages/contracts/src/common/ids.ts`,
`workers/brain/src/lib/ids.py`, `android/core/common/Uuid.kt` — 48-bit millisecond timestamp + a
12-bit intra-millisecond counter + 62 random bits, against one shared test vector and a 10 000-call
monotonicity test per language. SQL never generates an id. *Rejected:* a SQL function (impossible
without stored functions), v4, `AUTO_INCREMENT`. *Why:* ids must sort by creation time for index
locality, and TiDB has no `gen_random_uuid()` at all.

**D24 — Item snapshots.** Full snapshot JSON on `order_items` (names en/bn, unit price, option labels
and deltas, photo URL), not a delta. *Rejected:* delta against the live menu. *Why:* an invoice must
be reproducible years later, and a delta against a mutable menu cannot be; `receipt-reproducibility`
(A76) is the test.

**D25 — Trace retention.** No partitioning for `brain_traces`; TiDB TTL by age (7 days default, 90
for dispatch and money-adjacent engines) plus the request-triggered sweep as a fallback.
*Rejected:* monthly partition tables, unlimited retention. *Why:* Starter has TTL, the 5 GiB ceiling
is the tightest constraint in the platform, and partitioning would split the single replay query.

**D26 — `vendor_stats`.** Maintained by an upsert inside the order-delivered write path, with a
nightly integrity job recomputing a sample and comparing. *Rejected:* a refresh-on-read materialised
view. *Why:* the ranking hot path must not pay an aggregate join; a bounded upsert on the write path
costs one statement.

## Process (D27–D30)

**D27 — Task graph.** Turborepo with `codegen → build → typecheck → lint → test`, explicit `inputs`
and `outputs`; remote cache off. *Rejected:* remote caching (a paid service for a 40-second cache
hit), Nx. *Why:* the free-tier rule outranks a build-speed win.

**D28 — Versioning.** No changeset tool. Versions live in four constants (`versionName` per app, a
Worker version, a contract version) bumped in the release commit, and `lockfile-drift` guards the
lockfiles. *Rejected:* Changesets, semantic-release. *Why:* nothing here is published to a registry;
a second source of truth for versions is pure overhead.

**D29 — Screenshot tolerance.** Pixel diff only for the 1 200 deliberate visual snapshots
(0.1% differing pixels, per-pixel threshold 0.1). The responsive matrix asserts **layout
invariants** — no overflow, no clipping, target sizes — rather than pixel equality.
*Rejected:* pixel-diffing 56 600 renders. *Why:* cross-platform font rasterisation makes pixel
equality of an unrendered state meaningless; the invariant is the real contract (`A151`, `A154`).

**D30 — Flaky tests.** A failing-on-rerun test moves to a `quarantine` suite that **still runs and
must still pass** but does not gate merges, with an auto-created issue and a 7-day expiry that turns
the build red when it lapses. *Rejected:* skipping, deleting, "fix later". *Why:* the corpus's zero
tolerance needs a mechanism that cannot be quietly ignored; an expiring quarantine is that mechanism.

## Implicit, and decided here (D31–D33)

**D31 — Generated Kotlin models.** `scripts/codegen/kotlin-models.ts` generates `@Serializable` data
classes for all 412 endpoints into `core:network/model/generated/`, with money as `Paisa` (a `Long`
value class) and never `Double`. *Rejected:* hand-written DTOs. *Why:* 412 hand-written mirrors of a
Zod contract drift within a week, and a generated `Double` is a money bug waiting for a fare.

**D32 — QR key rotation.** Two HMAC keys are accepted for a 24-hour overlap
(`QR_HMAC_KEY`, `QR_HMAC_KEY_PREVIOUS`), and `rotate-secret.yml` writes both. *Rejected:* a single
key (rotation invalidates in-flight pickups). *Why:* `27 §6.1` requires rotation without invalidating
in-flight orders; two keys is the only way to satisfy it.

**D33 — Error text ownership.** Every error code's English and Bengali copy lives in
`packages/contracts/src/errors/registry.ts` and is extracted into `packages/i18n`; the server returns
a code plus an optional server-rendered sentence, and clients render from the catalogue.
*Rejected:* server-only strings, client-only strings. *Why:* `i18n-completeness` must be able to
prove all 184 codes exist in both locales, and offline clients must still be able to explain a
failure they received earlier.

## Visible deviations from the corpus (D34–D35)

**D34 — One Pages project, not two.** The storefront and the admin SPA deploy as one project: `/`
serves the pre-rendered storefront, `/admin/*` serves the admin SPA with a **path-scoped** CSP in
`public/_headers` (stricter: no `img-src data:`, no inline styles), an `HttpOnly` refresh cookie
scoped to `/admin`, and a Cloudflare Access policy on `/admin/*`. [`21 §13`](../21-admin-panel.md)
specifies a separate project at `admin.{domain}`; the operator's brief specifies **one Pages
project**, and this is the closest thing to both. *Rejected:* two projects (violates the brief),
one project with one shared CSP (loses the admin's stricter policy). *Why recorded here:* the
residual risk is an origin shared by a public storefront and the admin surface — R36 in the build
plan — and it should be a decision someone can find, not a surprise.

**D35 — `minSdk 26`, not 24.** Non-negotiable 39 in [`01`](../01-mission-and-non-negotiables.md)
requires Android 8.0 and names its own test matrix (API 26/30/34/35); [`16 §3.1`](../16-android-foundation.md)
and [`18 §1`](../18-partner-app.md) say 24. The non-negotiable wins because it is explicitly ranked
above the documents and because CI can only promise what it tests. *Rejected:* 24 (untested floor, a
stated rule broken), 23 (below 16's own warning). *Why recorded here:* it excludes Android 7.x
devices — a small, shrinking share of the Bangladeshi base — and that cost should be visible rather
than discovered in a Play Console device report.

## D36 — The five platform-wide error codes keep their bare names

**Decision.** The sixteenth group file is `packages/contracts/src/errors/rows/system.ts`, but its
five codes are exactly `INTERNAL`, `SERVICE_DEGRADED`, `DEPENDENCY_TIMEOUT`, `IDEMPOTENCY_CONFLICT`
and `NOT_IMPLEMENTED` — no `SYSTEM_` prefix — and the three `OAUTH_*` codes are counted inside the
`AUTH_` group.

**Rejected.** Inventing `SYSTEM_INTERNAL` and the rest so that every prefix matches its table row.

**Why.** `08 §11` labels the row `SYSTEM_` but names the codes without it, and clients match on the
code string exactly. The registry is the contract, so the 184 strings are authoritative and the table
label is the typo. The parity test asserts `AUTH_ + OAUTH_ = 21` and `BARE = 5` so the reconciliation
lives in the test rather than in a reader's head.

## D37 — `platform_config.zone_id` uses the all-zero UUID for "global"

**Decision.** `zone_id BINARY(16) NOT NULL DEFAULT 0x00…00`, where the zero UUID means the global
default. The DDL in `29` was rewritten from CockroachDB types to `VARCHAR`/`BINARY(16)`/`JSON`/
`DATETIME(6)`.

**Rejected.** Keeping `zone_id UUID NULL` with a nullable primary-key column.

**Why.** MySQL — and therefore TiDB — will not store `NULL` in a primary-key column: the insert fails
with 1048 rather than creating the global row the design describes. The sentinel keeps the same
semantics, the same key order and the same access path, and it is visible in the type instead of in
a comment that the database ignores. `no-postgres-dialect` caught the original DDL on the first
guardrail run.

## D38 — An unknown route answers `NOT_IMPLEMENTED`, not `404`

**Decision.** `undal-core` and `undal-realtime` return HTTP 501 with code `NOT_IMPLEMENTED` and
`details: { method, path }` for any path they do not serve.

**Rejected.** Adding a `ROUTE_NOT_FOUND` code (which would break the 184-code contract) or borrowing
`CATALOG_VENDOR_NOT_FOUND` (which would lie about what was missing).

**Why.** On a versioned API an unknown path means "this build does not serve this", which is exactly
what 501 says in RFC 9110, and it is the one registered code whose meaning is true. A `404` would tell
the client the resource exists elsewhere and send it looking.

## D39 — Guardrail exemptions are named, not silent

**Decision.** Three exemptions are written into the rules themselves: markdown is exempt from the
700-line cap; test and fixture paths are exempt from the placeholder scan and the money-float scan;
`scripts/guardrails/` is exempt from the placeholder scan.

**Rejected.** Keep-whole rules with a suppression comment, or a `# guardrail-ignore` escape hatch.

**Why.** A rule that can be silenced locally stops being a rule. Each exemption below is a property of
the tree rather than of a file: the spec corpus is one document per subject and splitting
`06-data-model-tidb.md` at line 700 would separate a table from the paragraph that explains it; tests
are not shipped and a test that asserts "no TODO in the registry" must be able to spell the word; the
guardrail tooling is the code that lists the forbidden words.

## D40 — The Kotlin differential runs on its own workflow

**Decision.** `ci.yml` compares TypeScript against Python on every push; `money-math.yml` adds the
Kotlin answers from the JVM-only `:shared:money` module.

**Rejected.** Setting up a JVM in the main gate for one more language.

**Why.** Three minutes on every push for an assertion whose inputs change only when
`packages/money` or `android/shared/money` change is three minutes the maintainer spends waiting on a
tablet. The paths filter on `money-math.yml` runs it exactly when it can fail.

## D41 — Operational workflows ship before the scripts they call

**Decision.** `migrate`, `verify-schema`, `d1-migrate`, `db-query`, `housekeeping` and `brain-replay`
exist from this response as the interface a browser-only maintainer uses, while the scripts they
invoke arrive with the migration pipeline (R6) and the Brain (R17).

**Rejected.** Deferring the workflows until their scripts exist.

**Why.** Each of these is a `workflow_dispatch` button, and a button that exists, is documented and
fails loudly at a named missing script is better than a button discovered missing at 2 a.m. with a
broken deployment — the failure names its own remedy. Nothing here runs on push, so the gate that
guards every commit is unaffected, and no step in any of them pretends to have done work it did not do.

## D42 — The 109 table names are the schema; the document's total of 99 was a slip

**Decision.** `db/migrations` creates the 109 tables `06 §2` names, and the document's total row now
says 109.

**Rejected.** Implementing 99 tables and dropping ten names, or keeping 99 and hiding the gap.

**Why.** The per-group counts in that table were correct from the start — 14, 8, 12, 12, 12, 15, 12,
10, 14 — and they always summed to 109; the total was the only wrong cell. Ten tables cannot be
dropped to satisfy a typo, so the names win and `scripts/db/check_schema_parity.py` now compares the
inventory to the migrations on every push.

## D43 — `CHECK` is declared in SQL and enforced in TypeScript

**Decision.** `scripts/db/extract_constraints.py` parses every `CHECK` out of the migrations, writes
`packages/contracts/src/constraints.json`, and generates `constraints/generated.ts`: 164 validators
across 76 tables, each carrying the SQL it came from.

**Rejected.** Trusting the DDL, and trusting a hand-written validator list beside it.

**Why.** TiDB parses `CHECK` and does not enforce it, so the DDL alone would look guarded and enforce
nothing. The generator is a real parser (tokens, recursive descent, arithmetic and `NOT IN`
precedence), not a regex: every generated expression is proven to parse as JavaScript by `node
--check` at generation time, and `tsc` proves it again in CI. Anything the parser does not understand
is a hard failure, because a validator that skips a rule silently is worse than no validator.

## D44 — Foreign keys stay where the specification put them

**Decision.** Tables defined in the corpus keep their `REFERENCES` clauses; tables authored against
the inventory get them too, except the three the corpus names as deliberately unkeyed (`order_items`,
`order_state_events`, `order_offers`).

**Rejected.** Removing every foreign key to make migration order easier, and adding keys to the three
high-write tables for uniformity.

**Why.** An orphaned ledger row is a reconciliation bug nobody can fix after the fact, while an
orphaned order item is a row that outlives a cancelled order by design. The exception is documented
where it applies — in the migration that creates each of those three tables — rather than in a policy
statement a reader has to find.

## D45 — `platform_config`'s primary key is ascending

**Decision.** `PRIMARY KEY (key, zone_id, effective_at)`, with no `DESC`.

**Rejected.** The `DESC` the specification wrote, which is legal on a secondary index and not on a
primary key.

**Why.** MySQL rejects a descending column in a primary key; TiDB parses it inconsistently across
versions. "Latest value for this key" is a backward index scan on the same key, which TiDB serves
without a second index, so nothing is lost but the parse failure the SQL validator caught.

## D46 — The geospatial layer is checked three ways, every push

**Decision.** `scripts/geo/parity.py` runs 6 000 deterministic cases through the exported
TypeScript functions, an independent Python mirror, and SQL, and writes
`.artifacts/geo/parity.json`. The `geo-parity` rule fails the build on any mismatch, and in CI
(`GEO_PARITY_REQUIRED=1`) also fails when the artifact is missing.

**Rejected.** A shared constants file, a formula copied into three languages, and a check that
silently passes when no artifact exists.

**Why.** It earned its keep on the first run. SQLite's `/` on two integers truncates where MySQL's
divides into a DECIMAL, so the "same" floor expression gave a different cell for every negative
coordinate; the probe also caught that `haversineMeters` returns whole metres, which the Python
mirror was comparing at three decimals. A check that cannot disagree is not a check.

## D47 — The ledger records statements, not files

**Decision.** `scripts/db/migrate.py` writes one `schema_migrations` row per statement, with the
file's SHA-256, and refuses to continue if an applied statement's checksum changed.

**Rejected.** One row per file, and a `--force` escape hatch.

**Why.** TiDB auto-commits DDL: a file that fails at statement 7 leaves six statements applied and no
rollback. A per-file ledger would then either re-run all six (they are idempotent, but the window in
between is wrong) or mark the file applied and skip statement 7 forever. Per-statement resume plus an
immutability check is the only combination that is safe when the platform has no transactions around
DDL.

## D48 — Two session-security tables join the identity group

**Decision.** `refresh_tokens` and `security_events` are created by `013_session_security.sql`, the
inventory's identity group grows from 14 to 16 names, and the total from 109 to 111.

**Rejected.** Storing refresh families in KV, and logging token reuse to `audit_log`.

**Why.** Rotation with family reuse detection needs a row per issued token that survives a KV
eviction — a stolen token is exactly the event where losing state is unacceptable. Reuse is evidence
about an actor, not an action taken on data, so it belongs in a table security reads rather than in
the finance-facing audit chain, which is also append-only with a single writer.

## D49 — Twenty-seven rate limits, not thirty-eight

**Decision.** `ratelimit/limits.ts` implements the 27 limits the `08 §12` table actually lists, and
asserts that count at module load.

**Rejected.** Inventing eleven more buckets to reach the prose figure.

**Why.** Counted cell by cell the table has 27 filled cells; the surrounding sentence doubles the
auth pair (IP and phone) and the five SSE caps. Same failure as D42, caught the same way: the table
is data and the prose is a summary, and a fabricated bucket would be a limit nobody chose.

## D50 — The audit chain is verified by a second implementation, not by itself

**Decision.** `db/fixtures/audit_chain_vectors.json` holds three chained rows with their digests;
`workers/core/src/audit/chain.ts` and `scripts/db/housekeeping.py` must both reproduce them, and both
do in CI.

**Rejected.** Verifying the chain only in the language that wrote it.

**Why.** A chain checked by the code that wrote it proves the code is self-consistent, which is not
the property anyone needs. The fixture is the contract between the two implementations, and it
immediately earned its keep twice: `null` had to hash like an absent field, and the housekeeping job
was reading a `payload_sha256` column that does not exist.

## D51 — The tip and the small-order fee are inside the collected cash, not beside it

**Decision.** In the canonical `ORDER_DELIVERED` set the customer's whole payment — food, delivery,
tax, tip, small-order fee, less the rounding delta — is the single `RIDER_CASH` debit. The tip and
the small-order fee appear only as credits: the rider's payable grows by the tip and by the rider's
share of the fee, the platform's small-order revenue grows by the rest. A tip added *after* delivery
is its own `TIP` entry with the `+tip / −tip` pair that `24 §3` prints.

**Rejected.** Posting `RIDER_CASH +tip` inside the order set, as a literal reading of the §3 table.

**Why.** §2.1's `raw_total` already contains the tip, so a second cash debit counts the customer's
money twice — the generator caught it on case 21 of the closure property test, which is exactly the
kind of double count that leaves a ₹5 000 hole in a rider's float after a week of tips. The §3 table
describes the *pass-through* entry, not the order entry; the difference only shows up when both
exist, and now the test knows which is which.

## D52 — A balance is a sum, never a stored column

**Decision.** `domain/ledger/balance.ts` computes every balance as `SUM(amount_paisa)` over the
postings table, in one grouped query for the whole platform, with an optional `asOfSequence`.

**Rejected.** A `balance_paisa` column on `ledger_accounts`, updated on every posting.

**Why.** Two sources of truth for money is one source of truth and one source of argument. A cached
column drifts the first time a compensating delete runs, and the daily reconciliation compares these
sums against the provider's statement — so the sum has to be the definition, not a cache of it. The
`asOfSequence` variant exists because an auditor asking "what did we hold on the 3rd" needs the sum
as it stood then, which a mutated column cannot answer at all.

## D53 — The golden posting sets are generated by a second implementation, not by the code

**Decision.** `scripts/money/posting_sets.py` implements `24 §2.1` and `§3` again in Python, from the
document, and writes the thirty-four golden sets the TypeScript builders must reproduce. CI runs the
generator with `--check`, so a drifted golden file fails the build instead of quietly agreeing.

**Rejected.** Committing a table of expected numbers produced by the TypeScript builders.

**Why.** A file generated by the code under test asserts that the code still does what it did last
Tuesday, which nobody doubted. The Python side disagreed twice on first contact and both times it was
right: the pickup tax base must include the pickup fee (it is platform revenue, so invariant 2 of
`§2.3` puts it in the base), and a cancellation refund has to address the *customer*, not the order
id — the TypeScript had been crediting the order. Neither would have surfaced from a hand-typed table
without the same disagreement, and a hand-typed table would already have been wrong.

## D54 — `-0` is not zero

**Decision.** `applyRate` normalises a zero result to `+0`; the refusal test asserts it with
`Object.is`.

**Rejected.** Leaving the sign in place because `-0 === 0` is true.

**Why.** `-0` passes every equality check, survives `Object.is`, prints as `-৳0.00` through the
formatter, and keys a `Map` identically to `0` while failing a `deepStrictEqual` — a shape that only
ever appears in a diff at three in the morning. The coverage gate found it: the branch that
multiplies a negative amount by a small rate had never been executed, and the first execution printed
`-0`.

## D55 — `LEDGER_IMBALANCE` is a value the ledger produces, not a webhook it sends

**Decision.** `domain/ledger/imbalance.ts` returns the exception (`trigger`, `severity`, `slaSeconds`,
the drifting accounts largest-first, both language strings) and leaves delivery to the alarm pipeline.

**Rejected.** Posting the alarm directly from `postEntry`, or from the nightly sweep.

**Why.** The alarm pipeline arrives in R13 and owns retries, dead letters and the on-call page; the
ledger owns the arithmetic. Keeping them apart means the exception is testable without a network, the
admin panel's "verify now" button and the nightly sweep call the same function, and a caught
in-memory imbalance produces the *same* exception shape as a drifted trial balance — one alarm with
two detection paths rather than two alarms that can disagree about severity.

## D56 — The small-order fee splits three ways, and the vendor is one of the three

**Decision.** `ORDER_DELIVERED` credits the vendor's share of the order fee through the vendor's
line (`subtotal − commission − bonus + vendor_share`) and books only
`fee − rider_share − vendor_share` as `PLATFORM:REVENUE_SMALL_ORDER`.

**Rejected.** The two-way split the ledger had: platform gets `fee − rider_share`, vendor gets
nothing.

**Why.** `10 §8` and `§12.1` both print ৳25 as ৳5 rider + ৳5 vendor + ৳15 platform, and the fare
engine's vendor payout carries the vendor's ৳5. The ledger disagreed with the engine by exactly
that ৳5 — every posting set still closed, because closure only says the totals agree, not that they
agree with the *right* people. Found by writing the fare engine's constants next to the ledger's
small-order lines, which is the check that no property test performs: the two modules were each
internally consistent and mutually wrong.

## D57 — At SDR 0.50 the bridge lands on 1.475×, not the table's 1.48×

**Decision.** `surge_bps(0.50)` returns 14 750, the value the printed function computes from the
bridge between the severe and moderate bands.

**Rejected.** Forcing 14 800 to match the row the table prints.

**Why.** `10 §4.3`'s table and `10 §4.2`'s code disagree by 50 bps at exactly one point, because
the table's author rounded 1.475 to two decimals while writing it. The code is the specification
here — it is the thing that ships, it is continuous by construction, and a table row is a
human-written summary of it. The test names the point and states which side it took, so the next
reader does not have to re-derive the disagreement.

## D58 — The delivery line closes on its residual, not on `margin − weather`

**Decision.** The closure identity uses `platform_delivery_net = delivery_fee − rider_fare`, with no
separate weather term. `platform_delivery_margin = delivery_fee − ride_core` remains the *gross*
figure and remains the tax base, exactly as `10 §9` requires.

**Rejected.** The literal identity of `10 §10.1`, which subtracts the weather premium and the gross
margin.

**Why.** The printed identity is true only when the rider's fare equals the core plus the weather
premium. It is not true when a bundle moves the fare onto a marginal detour, and it is not true when
the minimum-payout floor binds — and in those cases it does not merely drift, it *fails*, which the
brain found on vector 06 with a 3 867-paisa drift on a perfectly ordinary order. The residual is the
same statement without the assumption: whatever the customer paid for the delivery minus whatever the
rider was paid for it, and every term stays named in the failure message.

## D59 — Thirty of the forty vectors are regression pins, and the file says so

**Decision.** Vector 01 is asserted by hand against `10 §12.1`'s printed table. The other 39 are
generated by `workers/brain/test/generate_fare_vectors.py`, committed, and checked for drift in CI;
each is also asserted to close over its own terms.

**Rejected.** Implying all forty were derived independently of the engine that produces them.

**Why.** The document works ten vectors in full; the other thirty exist to pin boundaries — every
surge band edge, both bridges, four weather conditions on both vehicles, both clamps, bundles,
tips, discounts. Calling a generated pin "hand-computed" would be a lie in a file whose whole
purpose is to be trusted. The distinction is written into the generator's docstring, the test's
docstring and this entry: one vector is the document's, thirty-nine are history's, and the closure
identity is what makes history worth keeping.

## D60 — A pickup reaches DELIVERED, because the document leaves it stranded

**Decision.** `PICKED_UP → DELIVERED` is a `SYSTEM` edge guarded by `pickupOnly`, `cashRecorded` and
`cashReconciles`; a pickup therefore travels `ACCEPTED → PICKED_UP → DELIVERED`.

**Rejected.** Leaving the row out because `06 §7.3` does not print it.

**Why.** For a pickup the table offers `ACCEPTED → PICKED_UP` (customer, QR scanned by the vendor)
and then no edge that fits — `PICKED_UP → ARRIVED` needs a rider who does not exist, and
`ARRIVED → DELIVERED` is unreachable from there. Taken literally, every pickup order stops in
`PICKED_UP` and its cash never settles: the one path where the money is taken *before* the order is
complete would be the one path the ledger cannot close. The added edge is a `SYSTEM` transition, not
a customer one, so it cannot be used to skip a payment, and the coverage sweep now proves that no
non-terminal state is a trap.

## D61 — Guards read an explicit context, never the database

**Decision.** Every guard is a predicate over `TransitionContext`, a sparse object the caller fills;
a missing field fails the guard rather than passing it.

**Rejected.** Guards that load the vendor or the order themselves.

**Why.** The same transition has to be evaluable by an HTTP handler, a DO alarm, a test and a
replay of last month's events. A guard that reads the world can only be run in one of those four
places, and the event log stops being something a reconciliation job can re-derive. "Absent field
means refused" is the direction that fails closed: a context built by a caller who forgot the quote
refuses the placement instead of selling the order at a price nobody computed.

## D62 — A quote is a signed snapshot, not a row

**Decision.** The quote is a canonical-JSON snapshot of the fare inputs and totals, HMAC-signed and
handed to the client; placement verifies the signature, re-prices from scratch and refuses any
difference with `QUOTE_MISMATCH` and the moved lines. No `quotes` table exists, and none is needed.

**Rejected.** Persisting quotes and comparing rows.

**Why.** A row would be written before the customer has agreed to anything, which means a table that
grows with abandoned carts — and it would still not enforce the promise, because the promise is
*re-price and compare*, not *remember*. The signature proves the platform issued the price; the
re-price is what makes it true. It also survives a Worker restart, a zone boundary and a deploy,
none of which a row would.

## D63 — The order code is derived from the order id

**Decision.** `UND-` plus eight characters folded from the id's own bytes.

**Rejected.** A sequence, a counter row, or `Math.random()` — then checking for collisions.

**Why.** A counter needs a lock, and this platform deliberately has no interactive transactions: two
Workers placing in the same millisecond would race for the same number and one would lose an order.
Deriving the code from the id makes collisions impossible by construction (distinct ids, distinct
codes at this bit width), needs no coordination, and keeps a code the customer can read down a
phone line without a homoglyph in it — the alphabet omits `0/O` and `1/I`.
## D64 — Order routes ask the state table; they never branch on state themselves

A route that decides "can this be accepted?" with an `if` chain reimplements the machine and drifts
from it the first time an edge changes. `accept`/`reject` therefore build a `TransitionContext` and
hand it to the lifecycle, which returns either the target state or a refusal code that the route
returns verbatim. The route contributes facts (who owns the order, the prep time, the reason), never
the rule.

Concurrency is the same question asked of the database rather than of memory: the move is
`UPDATE orders SET state = ? WHERE id = ? AND state = ?`, and `affectedRows !== 1` means another
writer got there first — surfaced as `applied: false` and answered with the refusal for the state the
order is actually in, not a 500. Two vendors accepting at once must produce one ACCEPTED row and one
event, and the loser must be told `ORDER_ALREADY_ACCEPTED`.
## D65 — An order line is a photograph, and the history has no gaps

`order_items` copies the name, the unit price and the quantity the customer agreed to. Nothing on a
receipt is joined live to the menu: a rename or a price rise must not edit an invoice that has
already been paid, and the only way to guarantee that is to stop reading the catalogue at render
time. Modifiers are folded into the unit price rather than stored per row, because the receipt shows
one number per line and a second number that disagrees is worse than no breakdown.

Placement refuses a cart that the rows cannot explain: an empty cart, the same menu item twice, a
quantity outside `1..20`, more than `MAX_ORDER_LINES` lines, and — the check that matters most — a
line subtotal that does not equal the quoted `subtotal_paisa`. A total is a claim; the lines are the
proof of it.

`order_state_events.seq` is dense by construction, so `firstGap` treats a hole as an incident rather
than as history. `orders.state` says where an order is; the event table is the only thing that can
say how it got there, and a deleted row is a settlement dispute waiting for a quiet week.
## D66 — Core prices money; the Brain prices the trip, and a disagreement never moves a price

`10 §4` turns rider counts into a surge multiplier, and that curve is the one float in pricing. It
lives in the Brain (`fare/surge.py`) and nowhere else: Core's deterministic engine takes the
multiplier *published for the zone* as an integer input and refuses anything that is not a whole
value in `10 000..22 000` bps. A second float implementation in TypeScript would be a second answer
to "what does this trip cost", which is exactly what a published multiplier exists to prevent.

Everything below the multiplier is integer paisa and is duplicated deliberately in
`workers/core/src/pricing/fallback.ts`, because an order must still be priced when the Brain is cold,
deploying, or merely slow. The duplication is falsifiable rather than hopeful: the same forty fare
vectors the Python engine is tested against are read from the same file and run through the
TypeScript engine in `test/pricing-fallback.test.ts`.

`resolveFare` treats the Brain as a second opinion, never as the price. If it answers within its
400 ms budget with whole paisa and agrees on all four published numbers (delivery fee, ride core,
rider payout, surge), the order is stamped `fare_source = 'BRAIN'`. If it is late, unavailable,
malformed, or disagrees by a single paisa, the deterministic breakdown stands, the order is stamped
`'FALLBACK'`, and the reason plus every disagreeing field is returned so it can be counted. A
Brain bug therefore cannot charge an unexplainable price, and a Brain outage costs nothing but a
metric.
## D67 — A quote is priced in straight lines and says so; a promotion is a warning, never a refusal

Routed distance needs OSRM, which lives behind the dispatch worker and is not bound yet. Rather than
invent a routed number, a quote uses the haversine distance between the vendor and the delivery point
and returns `distanceSource: "ESTIMATED"` beside it. `08 §4.1` already prints `distanceM` in the
explain sheet, so the provenance travels with the figure: a customer can see that the ৳62 delivery
was priced on 3.8 km as the crow flies, and the day the binding lands the field changes to `OSRM`
without a contract change.

A promotion the customer typed is always answered — an unknown or expired code becomes a `warnings`
entry and a zero `DISCOUNT` line, never a 4xx. Refusing the whole quote because a code is stale makes
the customer re-enter a basket to be told nothing about the code, and it turns a marketing typo into a
conversion bug. A code that applies less than its face value (below the minimum, over its cap) is
reported the same way.

The quote endpoint is a `POST` that writes nothing, and declares `readOnly: true` so the
audit-coverage guardrail can stay strict about every other mutating verb without filling `audit_log`
with thirty quotes a minute. Free delivery is applied *after* the fare engine, so the total and its
rounding line are re-derived from the surviving components and floored once — a cash total is always
whole taka.
## D68 — Placement takes its cart from the signed token, and a guest quote is claimable once

`POST /v1/orders` never reads a cart from the request body. The items come from the signed quote and
are re-priced against today's menu and today's rates; the request contributes only what a quote cannot
know — the delivery point and the customer's note. A client that sent its own items beside a stale
token would otherwise order a different basket at the old price, and the re-price would confirm a cart
nobody quoted.

Re-pricing runs the *same* code as quoting (`pricing/cart-service.ts`), because a comparison between
two implementations reports its own bugs. The snapshot now carries the chosen modifier ids
(`QuotedItem.modifierIds`), so the re-price prices the same choices rather than trusting a modifier
total from the token as a number.

A guest quote records no customer, and the customer who signs in to place it claims it. A quote that
already names a customer belongs to that customer alone. This is what makes it safe to issue a quote
before the customer has an account, and it is a one-way claim: nothing re-opens a claimed quote.

Refusals keep their own codes. An item that left the menu is `QUOTE_INGREDIENTS_CHANGED` — the
customer is told the item is gone, not that "the total changed" — while a price that moved is
`QUOTE_MISMATCH` with every differing line attached, and an expired token is `410 QUOTE_EXPIRED` even
when the price is unchanged, because the five-minute promise is about *when* the customer agreed.

## D69 — Distance is geography, not money, and it says which it is

`domain/order/distance.ts` owns the straight-line estimate and the degrees→E7 conversion. Both round,
and neither is money, so keeping them out of `pricing/` is what lets the money rule refuse *every*
float in a pricing path with no exceptions to audit. `RouteEstimate` carries `source`, which travels
into the quote as `distanceSource: "ESTIMATED"` and into the order row as `distance_source`.
## D70 — Dispatch is fourteen numbered filters and five waves, decided as values

The candidate filters of `11 §3` live in one array with the document's own numbers. A rider who is
not asked is told *which* filter refused them, because "you cannot take this order" and "you cannot
take this order because your notifications are off" are different products — the second is fixable by
the rider in ten seconds. The two rejection filters are separate inputs, not one boolean: a rider who
said no to *this* order is never re-offered it (12), and a rider in a vendor cooldown is not asked
about that vendor at all (13). Collapsing them is how a rider gets the same offer twice.

Waves are filled until the chance nobody accepts falls below one in ten, and the candidate that
crosses the target is *included* — stopping one short sends a wave the model has already judged
worse than the threshold. Ranking is by predicted acceptance, so a stable ranking gives a stable wave;
a wave that shuffled between retries would page one rider twice and skip another.

`decideClaim` is the Durable Object's decision written as a pure function, so the race is testable:
three taps, exactly one winner, and the losers distinguish `OFFER_CLAIMED` (a race) from
`OFFER_EXPIRED` (nobody came) and `OFFER_NOT_YOURS` (a stale card). A race must never look like a
malfunction on the losing phone.
## D71 — A snapshot is a copy with a version, and evidence is judged before it is stored

`06 §7.1` says anything on an invoice is frozen into the order at placement. The part that matters a
year later is the version: a snapshot is read by code that has moved on, so every snapshot carries
`version`, and a reader that does not recognise it refuses rather than guessing. Reading it anyway is
how a renderer drops a field it never heard of and prints an address missing its flat number.

A proof is admissible only if it could be evidence of *this* handover: a photograph needs media, a
scan needs its payload, the capture must be inside the same geofence a pickup scan satisfies, and it
must be recent — a capture from an hour ago, or one dated in the future by a device with a wrong
clock, is refused rather than stored and argued about later. The decision is a pure function on a
capture, so it is assertable with no camera, no GPS and no network.

A delivery needs *one* door-side proof — photograph, signature or handover selfie — and a scanned
pickup code does not count as one: it says the food left the kitchen, not that it reached a doorstep.
## D72 — Pre-flight answers a question; pickup answers with the scanner's facts

`POST /v1/orders/validate` returns `200` with four named checks and a `canPlace` flag, and only a
malformed body is a 4xx. A basket that cannot be placed is not an error — it is the answer to the
question the checkout screen asked, and the screen needs *all* the reasons at once so it can grey the
button and highlight the right field. The checks are produced by unpacking the refusal the pricing
service would have returned, so pre-flight and quote cannot disagree about the same cart.

`POST /v1/orders/{id}/pickup` moves an order out of `RIDER_ASSIGNED` on evidence, not on request: the
presented code is verified against the order's own rotating HMAC, the rider's position is checked
against the same 150 m geofence a handover uses, and the guards are given the *scanner's* facts
(`pickupCodeMatches`, `riderDistanceToVendorM`) rather than the request's claims. An order that is not
waiting at the counter answers `QR_ALREADY_SCANNED` whatever the code contains, and a lost race on the
state update writes no event row, so a concurrent scan leaves no phantom in the history.
## D73 — Dispatch ships the formulas, not the worked table, and normalises weights that do not sum to one

`11 §6` prints a worked dispatch for order `UND-7K2M9QX4` with a full factor table and the rank
**B, A, D, C, E**. Four of its columns do not reproduce from the formulas the same document prints in
`§5.1` and `§5.2`: `eta_fit` matches only for rider E, `fairness` only for rider B. The formulas are the
specification and the table is an illustration, so the engine implements the formulas and the test
file records the discrepancy explicitly (`DocumentDiscrepancyTests`) instead of asserting numbers that
would have to be reverse-engineered to look right. What the table does establish — the ordering, and
that nearest-rider is not the winner — is asserted as the ranking.

`11 §5` also prints "Sum: 1.000" above fourteen weights that add to **1.005**. A weighted average is
only an average if the weights sum to one, and every threshold on a score depends on that, so
`DEFAULT_WEIGHTS` is the printed set divided by its sum (tolerance ±1e-9, enforced in `Weights.__post_init__`).
The printed figures stay in the module as `PRINTED_WEIGHTS` so the next reader can see both numbers.

Dispatch also stops pretending filter 10 is implemented: `batch/feasibility.py` does not exist yet, so
a rider already carrying an order is not offered a second one. That is the conservative answer and the
honest one — a cold meal is worse than a second wave.
## D74 — Batching ships the constraints and the cost function; the worked score is 0.5812, not 0.566

`12 §6.1` prints five terms for the Vector 06 bundle — 0.417, 0.579, 0.750, 0.880, 0.393 — and a total
of **0.566**. The document's own weights (0.32, 0.26, 0.18, 0.14, 0.10, which do sum to 1.0) applied to
the document's own five terms give **0.5812**. The implementation follows the weights and the terms,
and the test asserts both numbers — the computed total *and* that it is not the printed one — so the
next reader finds a recorded discrepancy instead of a silent inequality (`D73` set the precedent for
dispatch's table).

The detour model is the document's, term for term, including the part that is easy to forget: the
second order's detour carries the *whole* of the first order's handover. A model that priced the hop
and forgot the doorstep would promise seven minutes and deliver eleven.

`C2` reports `None` when nothing in the bundle is fragile, which is deliberately different from
"passed": a constraint that does not apply must not be recorded as a constraint that was satisfied, or
the trace cannot tell a careful bundle from a lucky one. `C7` charges a fragile item one bag of
capacity, and `C10` refuses a bundle whose rider payout is below the sum of the two solo minimums —
the rider must never earn less for carrying two meals than for carrying one.

A proof is re-validated when the rider accepts (`12 §5`), and it is checked against the proof's *own*
stored detours as well as the fresh world: a stored detour already over budget means the proof was
never honest, which is a different failure from a world that moved.

## D75 — The trace emits one key per real factor, and the cascade's clock is absolute

`09 §6` prints a `DISPATCH` trace whose fourteen factor keys include `cooldown` and `zoneFit`, and
which omits area familiarity. Cooldown is filter 13 — a veto, not a factor — so a trace that listed it
would show an operator a bar that no score ever produced. The engine therefore derives its trace keys
from the factor list itself (`TRACE_FACTOR_KEYS`), keeps the document's camelCase spelling where a
factor matches (`cashRisk`, `zoneFit`, `vehicleFit`), and the test asserts exactly one key per factor
and that `cooldown` is absent. A new factor cannot be added without appearing in the trace, which is
the only version of "no field missing" (`D12`) that survives the next change.

The cascade advances a wave **immediately** when every rider in it has rejected. Waiting out the
25-second TTL for phones that have already answered is pure delay, and the brief's own rejection flow
says "advance the cascade". The rest of the schedule does not move: the ladder's clock is absolute
from T+0, so an early wave 2 leaves a gap before wave 3 rather than pushing the fallback later. Any
claim or rejection stamped at or after T+112 belongs to the ladder, not the cascade, and is not
replayed into it — a decision after the deadline is a different decision.

The pre-warm invalidates on age (60 s), on drift and at its TTL (180 s), and drift is the *symmetric
difference* over the previous rider set, not additions alone: a zone that lost five riders and gained
five different ones is not the same crowd. The threshold is strict — exactly 20% is still warm — and
the weight version is a fourth invalidation, because a cache that outlives a weights deploy would
serve yesterday's ranking with today's version stamped on it. Step 1 of the ladder widens only the
bicycle radius, the cash cap and the zone edge; a motorbike's 12 km limit is a practical bound, not a
tuning knob, and a boost is floored to taka exactly once like every other amount of money.

## D76 — The benchmark gates on the comparison, not on the printed targets, and reports nine metrics

`11 §12.1` prints eight metrics; `30 §4.1` prints nine, adding the on-time rate. The report carries all
nine and the gate checks all nine, because a dispatch that is fast and late is not a good dispatch and
dropping the ninth number would be choosing the flattering table. The baseline is deliberately strong:
it uses the same five-wave cascade, the same 90% confidence target and the same random draws, and
differs only in ranking by distance — plus the expansion ladder and same-vendor batching, which are
Undal's policy and not the baseline's. Beating a straw man would prove nothing; the gap between the two
policies is therefore the value of the fourteen factors, measured.

The absolute targets in the documents are shown in every row and are usually missed, which is recorded
rather than hidden. The synthetic city is 60 orders over eight riders on staggered six-hour shifts,
with longer trips than the calibrated city the printed numbers came from: assignment waits run in
minutes rather than the printed 41 seconds, and the batch rate is ~7% against a 15–30% target because a
bundle needs two consecutive orders at the same vendor inside eight minutes. What the gate enforces is
that Undal is better than the baseline on every metric — which it is, on 15 000 order-days — because a
relative regression is the thing that can be caused by a code change, while the distance to a target
that was calibrated elsewhere cannot.

Three smaller decisions came out of making the benchmark runnable. The world generator lives in
`bench/world.py` so no file crosses the repository's 700-line cap, and because a world that does not
know which policy will run on it cannot be quietly kinder to one. "No rider found" counts the orders
still waiting when the day closes, not orders that waited a while: a late delivery is measured by the
customer-wait and on-time metrics, and counting it twice would double-charge the same failure. And two
of the seven adversarial scenarios — GPS plausibility and promo eligibility — are rules for modules that
land later (R10 and R17); the benchmark asserts the rule now so that it cannot change quietly, and says
so in the file rather than pretending the shipping code exists.

`brain-replay` is now the harness the workflow calls: a fixture carries the whole request and the answer
it produced, three are committed, and a changed ranking fails the build. Until `brain_traces` has live
rows the fixtures are the record; the workflow's `--traces` input is reserved for the loader that lands
with the realtime worker. The old workflow pointed at `replay.py` and `replay_check.py`, neither of
which ever existed — a check that cannot run is worse than no check, because it looks green by being
absent.

## D77 — The `sql` coordinator composes the statement; only `undal-core` executes it

`05 §4.2` says the free-tier claim is one conditional `UPDATE` against `dispatch_locks`, issued by
`undal-realtime`; `05 §2.1` and `34 §3.1` say `undal-realtime` writes no TiDB row, ever, and reaches the
database only through a service binding into Core. Both are load-bearing, so the coordination layer
resolves them the only way that keeps both: `TiDBCoordinator` takes a `SqlExecutor` port and composes the
statement, and the production executor is Core's internal surface over the binding rather than a driver
in this Worker. The atomicity the claim relies on is a property of the SQL, not of the process that
sends it — one `UPDATE` whose `affected_rows` is 1 for exactly one caller — so moving the execution one
hop changes latency, not correctness.

The consequence is honest about the number R10 must not invent. The claim now includes a binding hop
(same colo, no egress, one extra isolate) on top of the statement, so the free-path p50 stays a range
until it is measured, alongside the withdrawn 31 ms figure discussed in `05 §4.2`. What the suite can
prove without a network is the semantics: `MemorySql` implements the same conditional update and the
same unique `(order_id, seq)` index, and the 50-way claim runs against the real coordinator class, so a
regression in the statement fails the build on both backends.

## D78 — Presence is a socket at `/v1/presence`, and the mode has one name

`14 §2` specifies `wss://realtime.{domain}/v1/presence?role=…`, heartbeats as `{"t":"hb","s":n}` frames,
and the close event as the primary absence signal; `05 §4.1`'s diagram lists `/rt/presence` for
heartbeats. The specific document wins: presence is the socket, because the two-second budget depends on
the runtime's close event arriving in under 200 ms, and an HTTP heartbeat route cannot observe a dropped
connection at all. A POST reconciliation path may be added later, and if it is, it will be a second
signal rather than the transport.

The variable that selects the backend is `COORDINATION_MODE` (`05 §4.2`, `14 §3.3`, `39 §4`). The code
previously read `PRESENCE_BACKEND`, a name no document mentions; it now reads the documented name,
defaults to `sql` because that is what the platform launches on, and refuses a value it does not know
instead of silently running the other backend while the operator believes otherwise. The two-second
promise is arithmetic rather than a benchmark: 200 ms of transport plus the 1 500 ms grace is 1 700 ms,
and the grace is clamped to 1 800 ms so no configuration can push detection past 2 000 ms.


## D79 — `undal-realtime` holds the public half of the signing key, and refuses without it

`29 §2.6` gives `JWT_SIGNING_KEY` to `undal-core` alone, and `05 §4.2` has realtime authorizing a socket.
Both are honoured the same way: realtime is given `JWT_PUBLIC_KEY`, a base64url JWK holding only the public
half, and verifies Ed25519 signatures with it. Verification is the only thing the key can do, so a
compromised realtime deployment cannot mint a session for a rider it wants to dispatch to.

The `kid` is derived rather than configured — base64url of the first eight bytes of SHA-256 over the JWK's
`x` — so a rotation is a deploy of two Worker secrets and no coordination between them: core signs with the
new key, realtime accepts a key whose `kid` it can compute, and an unknown `kid` is `UNKNOWN_KEY` rather
than a signature failure, because "we have never heard of this key" and "you signed with the wrong key" are
different answers to an operator.

The route refuses with `501 jwt_public_key_missing` when the secret is absent, and that is a decision rather
than an oversight. The alternative — treating an absent key as "trust the token's claims" — would make a
misconfigured deploy an open door instead of a loud refusal, and the failure mode of a missing secret is
exactly when a deploy is least likely to be inspected. `INTERNAL_TOKEN` is the same shape: absent, the
internal surface answers `403` rather than serving presence to anybody who finds the URL.
## D80 — A ring outlives the isolate, so a broadcast is a fact rather than a coincidence

`08 §9` promises a reconnecting client the events it missed. An in-isolate ring cannot keep that promise:
Cloudflare may evict the isolate between the broadcast and the reconnect, and the client would be told its
replay is complete when the events it wanted never existed in the process it asked. So a ring lives in a
`StreamRoom` Durable Object, one per channel (`stream:order:<id>`, `stream:zone:<id>`), and the fanout
awaits a `record` for every channel before it answers.

Three details are load-bearing. The snapshot carries `evictedThrough` and `highestId` as well as the
events, because restoring only the events would reset the counters and a later replay would look complete
while silently skipping the gap. `StreamRoom` prunes to the same five-minute window the in-memory ring uses,
so a room that is woken after a quiet hour does not replay an hour. And a broadcast whose rooms are not
bound is refused with `501 rings_not_durable` — the honest answer, since a ring in one isolate is
forgotten by the next request, which is worse than an error a client can see.

Order streams are the exception, deliberately: an order's event log is already the whole truth and already
durable in TiDB (`06 §4`), so replay reads the log and the ring holds zone and admin channels. Two copies of
one order's history would eventually disagree, and the log is the one that is authoritative.

## D81 — Presence is one room per zone, and the Worker hands the room an identity it has already proved

The socket route is `/v1/presence?zone=…` and it forwards into a `ZoneHub` Durable Object addressed as
`zone:<zoneId>` (`14 §2`). Two things follow, and both were choices rather than consequences.

The room never sees a token. `undal-realtime` verifies the access token with the public JWK (`29 §2.6`),
and forwards three headers — `X-Undal-Actor`, `X-Undal-Actor-Type`, `X-Undal-Device` — which the room
believes because there is no other path into it. The headers are set on a *copy* of the request, so a
client that sends its own `X-Undal-Actor` is overwritten rather than trusted. The alternative, giving the
room the public key and letting it verify, would put the same verification in two Workers and would let a
room's misconfiguration be a security difference between routes.

A room per zone rather than one room for the platform: presence is a safety signal and the ladder runs per
zone, so one failure domain for every zone's heartbeats would be one cold start from being the reason no
rider is dispatched. The zone travels in the upgrade query and is remembered in the room's storage, because
`getByName` is not on every account tier and `state.id` on an id-addressed room is opaque. A later upgrade
with no `zone` reuses the remembered one; an upgrade with neither is `422`, and a zone the token does not
carry is `403` *before* any socket is opened, so an unauthorized zone never appears in a presence count.

The room's own refusals (`426` for a request that is not an upgrade, `401` for an upgrade with no
identity) stay rather than being duplicated in the Worker: they are reachable only through the Worker, they
describe the room's precondition, and a duplicate check is a second thing that can drift.

## D82 — The order-authorization answer comes from core, and every other channel is decided locally

`08 §9` lets a client subscribe to `order:UND-7K2M9QX4`, and whether it may is a question about three
order rows: who placed the order, which vendor cooks it, and which rider was assigned. Those rows are
`undal-core`'s (`06 §3`), and realtime is not allowed to read them — so the answer arrives through a port,
`OrderViewer`, implemented by a `POST /internal/stream/watches` call to core with the internal bearer token.

*Rejected:* giving realtime a read replica of `orders`. *Why:* a second copy of the order table is a second
answer to "who owns this order", and the copy that lags is the one deciding who sees a delivery address.

The client is fail-closed in the strongest sense the shape allows: a timeout, a non-2xx, an HTML body, an
envelope with `ok:false`, or an `allowed` that is absent all read as "no". That is not defensive
programming, it is the domain — this one answer decides whether a stranger sees an order's note, its rider
and its money, so an unsettled answer has exactly one safe reading. The timeout is 900 ms, shorter than the
client's patience, because a browser held while realtime waits on a slow core reads a silent stream as a
dead connection.

The rest of the channel table is decided locally and needs no hop. `rider:`, `vendor:` and `admin:` are
identity channels: only that actor, only under the kind their actor type owns. `zone:` is the admin map's
channel and carries every order in the zone, so admins only, and only in a zone their token names. Admins
bypass the port for `order:` as well, because `getOrder` already lets an admin read any order — a hop to be
told what the API would already have said is a hop that can only fail. Everything not in the table is
refused, including a channel kind added later by someone who did not update the table.

A deployment with no `INTERNAL_TOKEN` cannot authenticate the question, so it does not ask: `order:`
channels answer `403` and everything else works. That is the same shape as D79's missing public key —
absent configuration is a refusal somebody notices, never a silent allow.

*Rejected:* answering the watch question inside realtime from the token's claims. *Why:* a token says who
you are, not which orders are yours; the second changes with every assignment.

The `sql` coordinator's executor (D77) is the *other* thing this route is the boundary for, and it stays
unbuilt: it needs the same token and a statement-level permission that has not been designed yet. Naming it
here is deliberate so the next reader does not mistake one finished port for two.

## D83 — The push payload is data-only and signed, and its access token is cached in the isolate

`15 §2.1` fixes the payload and `15 §2.2` shows a KV-backed token cache. The payload is built exactly as
specified — `v`, `type`, `severity`, the order and vendor, `issuedAt`/`expiresAt`, `itemCount`,
`totalPaisa`, `customerArea`, `alarm`, `alarmMaxMs`, `sig`, with `android.priority: "high"`, a TTL of at
most 300 s, `collapse_key`, `direct_boot_ok` — with two additions and one deviation, all recorded here.

**The signature is hex, over the sorted map, excluding `sig` itself.** `k=v` pairs joined by a newline,
HMAC-SHA256, lowercase hex — the same construction `11 §3` uses for other signed payloads. Sorting is not
cosmetic: JSON object order is not preserved across every runtime the platform touches, so a signature over
the serialised JSON would verify on the Worker and fail on a device built by a different Kotlin compiler.
Excluding `sig` lets the map be signed once and the signature inserted, which is why `signatureOf` is a
pure function of the map.

**Every data value is a string, and money is integer paisa.** FCM's client map is `Map<String, String>`;
a number that arrives as a number is an integer on one platform and a double on another, and ৳549.00 as a
double is 54900.0000000001 paisa by the time it is formatted. `totalPaisa` crosses as `"54900"` and the
client formats it.

**Attempts are numbered.** The ladder sends a second push at 10 s and a third at 25 s (`14 §4.1`), and they
replace rather than stack via `collapse_key`. Each carries `attempt: "2"` / `"3"` so the device can tell
which one it is ringing for, and the evidence block (`presence/evidence.ts`) records the message ids.

*Deviation:* the access token is cached **in the isolate**, not in KV. A token lives an hour; a KV read per
alarm would be a paid request per push for a value that changes twelve times a day per isolate, and a cold
isolate can mint a new one in a WebCrypto signature plus one HTTPS round trip. Refresh is single-flight, so
the first alarm of a busy minute mints one token rather than twenty, and a failed mint is not inherited by
the next caller. The cache object is per `createTokenSource` call, so two isolates each hold their own —
which is correct, because a token is cheap and a shared one would need a shared store.

The sender is the only module that may POST to FCM, and it addresses `https://fcm.googleapis.com/v1/…`
from a constant rather than a caller-supplied URL. Failures are classified, not retried blindly:
`UNREGISTERED`/`NOT_FOUND` means delete the token (and, if it was the device's last, raise an exception),
`SENDER_ID_MISMATCH` means a build pointing at the wrong project, `QUOTA_EXCEEDED` backs off, and
everything else gets three attempts at 250/750/2 000 ms. A deployment with only one of the two secrets is
refused at construction (`fcmFrom`), because a service account with no signing key would send payloads every
device discards while the platform recorded a successful delivery.

*Open:* the ladder that calls this module (`presence/escalation.ts` decides *what* is due) still has no
scheduler storing ladder state across isolates, and `fcm_dispatches` (`15 §8`) has no table. Both are the
next rung, not omissions of this one.

## D84 — The two-minute ladder is one Durable Object per order, and its last rung is a request

`14 §4.1` is a schedule: a probe at 8 s, unreachable and a second push at 10 s, a third at 25 s, the backup
contact at 45 s, an exception at 60 s, an early-out offer to the customer at 90 s, and cancellation at 120 s.
The schedule was already a table (`presence/escalation.ts`). What it had was nowhere to live.

It lives in `VendorAlarm`, one Durable Object per order (`VENDOR_ALARM`, migration v5), under one storage
key. That answers three questions a `setTimeout` cannot. *Does it survive the process that published it?*
Yes — an order published at 12:00:03 is still being escalated at 12:02:03 if the isolate that published it
was evicted, which is precisely the case a cold start would otherwise forgive. *What wakes it?* One alarm,
armed at the next unfired rung and re-armed after every run, so nine instants cost one alarm rather than
nine timers. *What if the alarm is late?* It fires everything it owes in table order, once, because the rungs
are marked in the record rather than inferred from the wake-up.

`begin` sends the first push and marks `PUBLISH` fired, because the ladder's 8-second probe assumes the alarm
started at publication. Each push rung carries its `attempt` (`2`, `3`), and all of them collapse onto
`order_<id>` so the third replaces the second rather than stacking on a lock screen.

The last rung is a **request, not a write**. `POST /internal/orders/auto-cancel` is answered by core, which
owns `orders.state`: the `PLACED → AUTO_CANCELLED` edge exists as a `SYSTEM` transition with the
`vendorUnreachable` guard, so a ladder that fires early is refused by the same table that refuses an illegal
customer cancel, and the `WHERE state = 'PLACED'` on the update means a vendor who accepts mid-flight wins
(`raced`). The audit row names `SYSTEM`, carries no user, and records the elapsed time — the one cancellation
nobody clicked is the one the trail has to explain. `moveState` now takes `actorUserId: Uint8Array | null`,
because `order_state_events.actor_user_id` is nullable and a `SYSTEM` actor has no user to name.

Two refusals are honest rather than fatal, and the evidence block records both. A room with no push sender
refuses `begin` (`501 push_not_configured`), because a ladder nobody can ring is worse than no ladder. A room
with no canceller still runs to 120 s and records `canceller_not_configured`, raising the operator's
exception instead of claiming a cancellation that never happened.

Two events the ladder publishes were missing from the stream's name map — `vendor.unreachable` and
`admin.exception_raised`. `StreamHub.record` gates on that map, so a component naming its own catalogue event
was having it silently dropped; they are in the map now (`08 §9.1`). The cancellation is published from the
room as `order.cancelled` in this version, because core did not yet broadcast its own transitions — D85
supersedes that line and the room no longer publishes what core writes.

*Open:* `fcm_dispatches` (`15 §8`) still has no table, so a send's message id lives in the ladder's record
rather than in the platform's evidence table.

## D85 — A transition announces itself, and the announcement can never undo the transition

Core wrote every order transition to a row and answered the caller. Nothing told the watchers, so the SSE
stream had nothing in it and the customer's screen learned about an acceptance by polling. `bindings/
announce.ts` is now called from the four places an order moves — placement, accept, reject, pickup, and the
ladder's auto-cancel — and each call is one line plus a payload.

Three rules make it safe to call from inside a transaction's aftermath.

**It never throws.** `createRealtimeClient` returns a `Result`; `announce` discards it. An order that moved is
a fact whether or not a socket heard about it, and a platform that failed a placement because its notification
path was cold would be losing money to its own broadcast. The suite asserts this against a 502, a thrown
transport and an unconfigured deployment.

**It never blocks the response.** The call is handed to `ctx.waitUntil`, which is no longer faked: `index.ts`
now passes the runtime's `ExecutionContext` through, so the promise outlives the response instead of racing
the isolate's teardown. That was a real defect in the pipeline before this change — `waitUntil` was
`() => undefined`, which silently turned "schedule this" into "start this and hope".

**It says nothing when it is not configured.** No `REALTIME_BASE` or no `INTERNAL_TOKEN` is a deployment that
has not wired the stream. That is not an error and not a warning on every order; the client degrades to a poll,
which is exactly what the platform did before.

The payload is the catalogue name, the order code, the new state and the log sequence. The sequence matters:
a stream that reconnects with `Last-Event-ID` and a stream that is live must agree on the order of frames, and
the only number both can agree on is the one the log wrote.

This removes the duplication D84 recorded. The ladder used to publish `order.cancelled` from the room, because
nothing else did; core announces its own auto-cancel now, so the room's line is gone and one transition
produces one frame.

## D86 — The push log exists, and only core writes it

`15 §8` closes the delivery loop: send → `fcm_dispatches(message_id, token, sent_at)` → the device's
`alarm_received` → the gap between them. The table did not exist, so a send's message id lived in the ladder's
Durable Object and the admin panel's "device matrix" had nothing to be built from.

`014_fcm_dispatches.sql` adds it: `order_id` and `device_id` nullable and `ON DELETE SET NULL`, `fcm_token`,
`attempt`, `outcome`, a nullable `message_id` and `received_at`, and three indexes — one order's attempts, one
token's record, and the receipt sweep. The nullable subject is the point: a dispatch outlives the order it
announced, because "was this vendor's phone reachable last week" is a question asked after the order is gone.

*Rejected:* letting realtime write the table. *Why:* `05 §2.1` forbids it TiDB writes, and the reason it does
is that the only way this Worker would write is with a database credential, which would put a second writer on
the order tables' neighbourhood to save one HTTP call.

So the room reports and core records (`POST /internal/fcm/dispatches`, internal token, a batch of at most
twenty). One call per rung rather than one per phone, because a rung rings every device at once. The route is
not in the path of any decision: nothing reads these rows to decide whether an order moves, so a lost row
cannot hold an order hostage — and the recorder on the realtime side returns `false` and is ignored rather
than throwing, because a delivery log that can fail an alarm silences the thing it is auditing.

The batch is audited **once** at `INFO`, naming the order, the attempts and the sent/failed split. Per-device
audit rows would add tens of thousands a day to a hash-linked chain the admin panel reads end to end, and the
per-device detail already exists — in `fcm_dispatches`.

An unknown order code and an unregistered token both still write a row, with `NULL` in the column that would
have named them. A send that happened is a send that happened; a log that dropped it for want of a foreign key
would be a log with a hole exactly where the interesting case is.

The receipt half of the loop is D87 — at the time this was written nothing filled `received_at`.

One finding, recorded rather than fixed. `scripts/db/expected.py` only reads backticked column names, so
twenty-eight tables parse as zero columns — `orders`, `users`, `devices`, `refresh_tokens` and now
`fcm_dispatches` among them. The generated `db/expected.json` is still the file `verify_schema.py` compares a
live database against, which means for those tables it compares nothing. The regeneration is committed here
because CI regenerates and diffs it; the generator is a change of its own, and this note exists so the gap is
a known one rather than a check that appears to pass.

## D87 — The receipt arrives on the socket, and the device is the session's, never the frame's

`15 §8` closes the delivery loop with the device's acknowledgement. There is exactly one place that can
arrive: the presence socket, because the app does not call the API to say its alarm rang — the alarm is
answered on a lock screen with no app in the foreground.

So `ZoneHub` learned a second frame. `{"t":"alarm_received","orderId":…}` is no longer `not_a_heartbeat`;
the room looks up the session that owns the socket and reports `(orderCode, deviceId, receivedAtMs)` to
`POST /internal/fcm/receipts`, which fills `received_at` on the **latest unacknowledged** dispatch for that order
and device. Anything else on the socket is still refused by name, so a client bug stays a message.

**The device comes from the session, not the frame.** A payload that could name its own device could claim a
delivery for a phone that never rang, and a delivery matrix built from self-reported identity would flatter
exactly the broken phones it exists to find. The order does come from the frame: it is a fact about what rang,
not about who is asking.

A receipt is **not presence evidence**, and there is a test for it. A device can hear an alarm a second after
its socket went quiet — that is the entire reason the alarm exists — so acknowledging a push must not move a
heartbeat deadline or cancel an absence. The two frames answer different questions on the same socket.

Two smaller decisions. The match is against the newest unacknowledged row, because an alarm rings three times
and the receipt is for the one the device heard; and `received_at IS NULL` in the update makes a repeated frame
a no-op rather than a second receipt. A receipt that matches nothing — an order deleted since, a device whose
tokens were rotated — answers `recorded: 0` and writes no audit row: the alarm already rang, and a log entry
about a row that was not there is noise.

*Open:* closed by D88, which stores the two fields the client sends beside the receipt.

## D88 — The device's own measurement is stored beside the receipt, never above it

`15 §8` draws the loop with two numbers in it. The platform can see one of them: `sent_at` from the Worker
that rang, `received_at` from the socket's clock when the `alarm_received` frame arrived, and the gap between
them is the send-to-received latency the device matrix ranks OEMs by. The device sees the other: how long its
own radio took to wake, and which path reached it first. D87 validated those two fields and dropped them,
because storing them needed a decision about what they are.

They are evidence about the device, so they are stored under names that say so — `device_latency_ms` and
`device_path` (`015`) — and the platform's own gap keeps the authority. This matters because a slow phone
often reports a *fast* number: an OEM whose push handler runs before the radio's power state settles measures
from the process waking, not from the message arriving, and a matrix built on that self-report would clear the
exact devices the alarm exists to catch. The median the panel charts is `received_at − sent_at`; the device's
number sits beside it so support can show a vendor "your phone says 400 ms and ours says 9 seconds" instead of
arguing.

Filtering happens once, in core (`receiptDetails`), and it drops rather than refuses. A latency that is not a
finite number, is negative, or exceeds ten minutes loses the number and keeps the receipt; a path outside the
closed set `FCM | SOCKET | BOTH` is not stored, so a client that invents a channel cannot enter one into the
matrix. Refusing the frame would punish the delivery record for a bug in the measurement, and the delivery
record is the half that cannot be reconstructed. Realtime forwards both fields as the device made them,
bounded only so a frame cannot carry a paragraph where a measurement belongs: the room is a pipe, and the
closed set lives at the writer.

The two columns land in the same `UPDATE` as `received_at`. A second statement would leave a window in which a
row is stamped by one caller and measured by another, and `received_at IS NULL` is what makes a repeated frame
a no-op — that guarantee only covers writes inside the statement it guards.

Both columns are null for a client that predates this decision, and the matrix treats null as "not reported"
rather than zero, because a device that says nothing and a device that says 0 ms are different facts.

## D89 — A beat is a frame; a stamp is a write

The `sql` coordinator wrote the presence row on every heartbeat. The arithmetic that makes that wrong is
short: `14 §3.1` asks for a beat every 750 ms, an eight-hour shift is 38 400 beats, and the old `heartbeat`
did a `list` to find the row and a `put` to refresh it — 76 800 store operations per device per shift, to
record a fact the process holding the socket already knows. The same arithmetic kills the store D77 named:
Workers KV's free tier is 1 000 writes, 1 000 reads and 1 000 lists a day, so one vendor's morning would
exhaust the allowance before the lunch rush. The free path's presence store is therefore the TiDB the
executor reaches, which is also what `14 §2` and `14 §3.3` have always said; D77's "key-value store behind a
lease" is corrected here.

What replaces the per-beat write is a stamp and a memo. The memo is per isolate, holds the row's key, the
session as last written and the instant it was written, and it means a beat inside the window costs nothing
at all: no read (the memo holds the value), no list (the key is known), no write. The window is 15 s, so a
shift costs one write per 15 s of beating. A *negative* memo — the device is not present — expires on the
same window rather than being remembered forever, because a beat can arrive before the `declarePresence`
that follows the upgrade, and a device must not be invisible because two frames raced.

The cost is paid in freshness, and it is paid openly. A stamped row is up to one window behind the device
it describes, so a reader that compares `lastHeartbeatMs` against the two-second deadline would call a
beating device gone. The width of "online" is therefore a property of the backend, `presenceWindowMs` —
17 s for stamped rows, 2 s for the Durable Object, which does write on every beat — and `/internal/presence`
asks the coordinator instead of hard-coding either. The two-second deadline is untouched: it is enforced by
the process that holds the socket, and the ack still returns `now + 2 000`.

Listings are not filtered. A row disappears when the escalation that watched the socket go quiet calls
`markAbsent`, never by being quietly omitted from a list, because a row that vanishes is indistinguishable
from a device that never connected and the two deserve different answers. So `listPresence` returns what the
store holds and the readers judge: `/internal/presence` answers `online` by the window and still reports
`lastSeenAt` from the row it found.

*Open:* the store itself is still the test's `MemoryStore`. `presence_sessions` as a table, and the executor
that lets core write it, are the next rung — this one fixes the write pattern so that rung has a budget to
fit inside.

## D90 — The free path's statement travels as a name, and core is the only hand on the database

D77 left the `sql` backend unbuildable: `coordinatorFrom` returned `coordinator_not_configured` because the
`SqlExecutor` port needed core's internal surface and there was none. This rung builds it, and the shape it
takes is the decision.

**A name crosses the boundary, never SQL.** `undal-realtime` composes a statement — `CLAIM_SQL`, `state_put`,
whichever a situation calls for — and the executor turns that text into a catalogue name before anything
leaves the Worker; core looks the name up and runs *that* statement. The catalogue lives in
`@undal/contracts`, so there is exactly one spelling of `claim_lock` in the platform, `statementFor` proves
the coordinator's constant is that spelling, and a statement a caller invented cannot be sent at all: it has
no name. The alternative — a route that accepts SQL text from a sibling Worker — would be a database proxy
inside the trust boundary, which is the specific thing `05 §2.1` exists to prevent.

**Thirteen statements, thirteen fixed spellings.** Locks (`open_lock`, `claim_lock`, `release_lock`,
`lock_holder`), the order log (`next_seq`, `insert_event`, `read_events`), a liveness read (`ping`), and the
coordinator's state (`state_get`, `state_put`, `state_delete`, `state_list`). No table, column, ordering or
limit is caller-chosen; parameters are strings, finite numbers and `null`, and a boolean or an object is
refused rather than coerced, because a driver that quietly turned `true` into `1` is how a lock comes back
held by nobody. Reads answer `{rows, truncated}` and writes answer `{affectedRows}` — the kind is the
catalogue's, not a sniff of the SQL.

**The executor throws.** A claim that answered `affectedRows: 0` because core was unreachable is
indistinguishable from a claim another rider won, and the coordinator would tell a rider the offer was taken
when it was never offered. Timeouts abort the request and reject: 900 ms, the same budget the other
authority calls carry.

**The state the coordinator keeps is a table, not a product.** `coordination_state` (`016`) is a key, an
opaque JSON value and an expiry. D77 named Workers KV and D89 retired it: 1 000 writes a day is one vendor's
morning. The store validates its own keys — no `%`, no `_`, at most 191 characters — because the listing is a
`LIKE` prefix and a key carrying a pattern character would turn a zone's presence into every zone's. Expiry is
an absolute instant computed on the caller's clock, so a row stops being read as present at the moment the
coordinator that wrote it said it would.

**The route is exempt from the audit rule, on the record.** It writes lock rows, order events and coordinator
state, and every one of those is the effect of a decision made in the coordinator or in core's order routes,
where the audit row already lives. An audit row per statement would be a trace of SQL rather than of
decisions, and on the claim path it would put fifty racing riders behind one hash-linked chain for a row that
exists to be contended. The exemption is a marker the rule accepts — `audit-exempt:` with a reason of at
least sixteen characters — so it is an argument a reviewer reads, and the rule still rejects a bare one.

With this, `COORDINATION_MODE=sql` builds when `CORE_BASE_URL` and `INTERNAL_TOKEN` are present, and refuses
by name when one is missing. What has *not* been measured is the number R10 gates on: presence p95 on the
`sql` backend. The binding hop is now real, so the next rung can take that measurement instead of estimating
it.

*Open:* closed by D92, which pages the listing by key instead of stopping at the first 500 rows.

## D91 — The two seconds include the database, so the largest grace is smaller than it was

The two-second promise was arithmetic with two terms: 200 ms for the transport to notice a dead socket, and
1 500 ms of reconnect grace. That was true while the absence lived in a Durable Object's memory — the room
knew, immediately, and writing it down was someone else's problem. D90 made it false: on the free path a
publication costs a row written through core and a row read back, each with a service binding in between,
and a promise whose arithmetic does not mention its own database is a promise nobody is keeping.

So the budget has three terms. `PRESENCE_STORE_OP_MS` is 50 — same colo, one indexed statement, one binding
hop — and a publication costs two of them, 100 ms in total: the marking write, and the read that proves the
device is gone from the list. The default grace stays 1 500 ms and the worst case becomes 1 800 ms, inside
the two seconds with 200 ms spare.

The consequence is in `MAX_PRESENCE_GRACE_MS`, which was 1 800 and is now 1 700, derived as
`MAX_DETECTION_MS − TRANSPORT_CLOSE_BUDGET_MS − PRESENCE_STORE_BUDGET_MS`. An operator configuring the top of
the range now gets a worst case of exactly 2 000 ms rather than one that quietly exceeds it by 100 ms. This
is the whole reason the number is a constant and not a configuration default: a range limit that admits a
grace the platform cannot afford is a range limit that documents a promise it does not keep.

Two smaller things. `50 ms` is a *budget*, not a measurement, and it is stated as one — the honest claim is
"two store operations may cost this much", not "we measured 50 ms", because the measurement needs a deployed
`sql` coordinator and a real TiDB, neither of which a test suite has. And the thousand-loss latency test now
adds the store's allowance to every measured loss, so the p95 it asserts is the one the platform promises
rather than the one its two in-memory terms happen to produce.

*Open:* the wall-clock version of this number — p95 across a thousand real losses against a deployed free
path — is a load test, not a unit test, and is still not run. What this rung fixes is that the arithmetic the
load test would be checked against now includes the thing it is measuring.

## D92 — A listing of a zone finishes, or it says it did not

D90 shipped `state_list` with a `LIMIT 500` and called the truncation open. It was worse than untidy: the
listing is how a zone's presence is read, and a zone entering a busy Friday evening would have had its
sessions listed up to five hundred and no further — a dispatch decision made on half the fleet, with nothing
in the answer to say so.

The fix is keyset pagination, and the choice between that and `OFFSET` is the whole decision. Rows are being
written and deleted while the listing runs, so an offset counts rows that may have moved: a rider who
reconnects between two pages shifts every later row by one and the listing either repeats a device or skips
one. A keyset cursor is the last key returned, `state_key > ?` is immune to that, and `ORDER BY state_key` is
already the table's primary key, so the page boundary is an index range rather than a sort.

Paging stops at `MAX_STATE_PAGES = 20`, ten thousand rows. What happens there is the second decision: it
throws. A caller that asked for a zone's sessions and got a partial list would act on half a fleet without
knowing; a caller that gets a `RangeError` knows exactly what it has. Ten thousand sessions in one zone is
far past anything this platform is designed for, so the ceiling is a bug detector rather than a capacity
limit — and if a zone ever legitimately reaches it, the answer is a per-zone count or a role-filtered listing,
not a longer read.

`state_list`'s parameters therefore changed to `(prefix, after, now, limit)`; the `after` term is `''` on the
first page, which sorts before every key this platform writes because no key starts with a control character.
Nothing else about the store changed, which is the point of having kept the port.

## D93 — The ladder was complete and unreachable, so placement now starts it

D84 built the vendor ladder and D87 closed its delivery loop. Nothing called it. `VendorAlarm` could walk
three rungs, ring every device, receive its own receipt and cancel at 120 s, and a placed order never touched
it — so the sequence existed and the first sentence did not. A placement now ends by ringing the vendor.

**Three facts, three tables, one module.** The ring needs the vendor's owner (`vendors.owner_user_id`), the
live tokens that owner's devices registered (`device_tokens` joined `devices`, `valid = 1`, newest first,
capped at five) and the area to show (`addresses.area`, reached through `orders.delivery_address_id`). They
live together in `repositories/recipients.ts` because they answer one question — whose phone should ring, and
what should it say — and a caller assembling a notification from three repositories would eventually assemble
it slightly differently from the next caller. Staff do not exist yet; when they do, this is the one place that
learns about them.

**The order does not wait for the ring, and the ring does not stay quiet.** Placement is a money event: it
writes rows and answers `201`, so the ring is handed to `waitUntil` and a cold room adds nothing to the
customer's receipt. But D85's rule for announcements — a failure is a degraded poll, so say nothing — does not
transfer. A missed broadcast means a screen refetches; a missed ring means the vendor never learns, the ladder
never starts, and the customer waits two minutes for a cancellation nobody chose. So a ring that could not
happen is an audit row at `WARNING`, `ladder.unrung`, with the reason it did not: `no_device` when the vendor
has no registered phone, `begin_refused` when realtime would not start the ladder. Both are the platform
failing to reach somebody, and neither is allowed to be silent.

**What the push says is what the order knows.** `CRITICAL`, `alarm: loop`, twenty seconds per ring so the
second attempt is audible over the first, and an expiry equal to the ladder's own 120 s — a push that outlives
the ladder would ring a phone for an order the platform already cancelled. The total crosses as paisa because
the client formats it, the short code is the part a person reads out (`UND-7K2M9QX4` → `7K2M9QX4`), and
`attempt` is absent because each rung numbers its own. `customerArea` is the address's area, trimmed, or the
empty string when the customer pinned a map point and typed nothing: the field is always present so a client
never has to handle absence, and an empty one is honest in a way a guess is not.

*Open:* closed by D94, which places a real order through the real route with a stream configured and asserts
that the ring happened — and that it fails when the call site is deleted.

## D94 — The call site has a test that fails when it is deleted

D93 wired the ring into placement and recorded the one thing it could not claim honestly: the call was a
single line, everything around it was tested, and no test would fail if someone removed that line. A mitigation
was named — the `ladder.unrung` audit row — but a mitigation is not coverage. This rung is the coverage.

The test places an order the way a client does: it asks the real quote endpoint for a token, places against it
through the real placement route, with `REALTIME_BASE` and `INTERNAL_TOKEN` configured and a fetch stub in
place of the network. The route hands its background work to `waitUntil`; the harness now collects those
promises instead of discarding them, so the test waits for the ring the route actually started rather than for
a sleep that hopes it did. It then asserts the begin went to `/internal/ladder/begin` with the order's code,
the vendor's two registered tokens, `CRITICAL`, the customer's area from `addresses.area`, and an expiry
exactly 120 s after the issue — the ladder's own window.

Two more cases, both about the failure being visible rather than quiet. A vendor whose owner has registered no
device produces **no** begin and an audit row containing `ladder.unrung` and `no_device`. A deployment with no
stream configured places the order, hands nothing to `waitUntil`, and calls no transport at all — the same
"unconfigured is not broken" rule the announcement follows, asserted rather than assumed.

The harness needed one change to make any of this possible: the placement tests now answer the three reads the
ring performs — `vendors.owner_user_id`, the owner's live `device_tokens`, and the order's
`delivery_address_id` — which is what "teach the harness the recipient queries" turned out to mean. They are
matched before the generic vendor handler, so the order's own vendor lookup still sees the vendor row it
expects.

And the claim was checked the only way that makes it a claim: commenting out the `ringVendor` call fails two
of the three tests, re-enabling it passes all ten. A test that would not notice the feature's absence is a test
that documents a hope.

## D95 — A position is a claim by a phone, and the gate says which claims it believes

R11 starts where `07 §4.5` left a table and no code: the rules that decide whether a fix may land in D1 at
all. `workers/realtime/src/d1/ingest.ts` now implements them, and the decisions that are not in the table are
the ones worth recording.

**A mock flag is a batch decision, not a fix decision.** One fix carrying the OS's mock flag rejects the whole
upload and sets `suspendShift`. The tempting alternative — store the nine honest fixes, drop the spoofed one —
produces a device that is *partly* trustworthy, and the platform has no way to say which part. A rider whose
phone is mocking its location is either testing the platform or defeating it, and both deserve a human before
the next order.

**Refusals are named, because the names are different stories.** `poor_accuracy` is a phone under a bridge and
costs nothing. `implausible_speed` is a tower fix, a tunnel exit, a spoof or a teleport; it increments
`teleports` so the caller can add it to the rider's `teleport_count`, which is what puts a rider in front a
reviewer. `outside_zone` sets `raiseException`, because a position twenty kilometres outside its bounding box
is not a data-quality problem, it is a rider who is somewhere nobody expects. A single "dropped" counter would
make all three invisible at once.

**A refused fix does not move the baseline.** Speed is measured against the last *accepted* fix, so a rejected
teleport cannot manufacture a second rejection from the good fix that follows it — the failure mode that makes
a rider's trail stop updating for a minute after one bad point under a flyover.

**Order of the checks is the order of the reasoning.** Mock, then accuracy (an inaccurate fix is evidence about
nothing), then the clocks (a time that cannot be trusted makes a speed meaningless), then ordering, then
speed, then the zone — the only check about *where* rather than *when*.

**One thing the table could not answer.** A backfill carries fixes older than the newest stored one: a rider
who came out of a tunnel. For those, the fix that precedes them in time has already been pruned by the ring
buffer, so no speed can be computed; the gate stores them without a speed verdict rather than refusing them
over a division by a negative interval. The alternative — refusing backfills outright — would throw away the
exact fixes a tunnel produces.

Nothing here writes. `teleport_count`, the exception row and the shift suspension are the caller's writes, and
that is deliberate: the gate decides what the platform believes, and the write path decides what to say about
it.

*Open:* the cadence gate above this (`07 §3.2`, `shouldSend`) and the write budget (`07 §4.2`) are not built;
this rung is the plausibility half of the edge contract, and the two halves share a caller that does not exist
yet.

## D96 — The device decides what is worth sending, and the budget is a test rather than a table

`07 §3.2` gave six rules as Kotlin and `§8.1` gave a write budget as a table. D95 built the server's half of the
edge contract; this is the device's half, in `workers/realtime/src/d1/cadence.ts`, with the budget checked by
simulation instead of re-asserted.

**The profile follows the situation, not the speedometer.** A rider carrying food a hundred metres from the door
is judged by `CARRYING_NEAR` (60 m, 6 s, 25 s) even if they are stopped at a light, because the row is about
what the customer is watching. That is why `phaseFor` takes what the *server* told the device — carrying, on
break, distance to drop — and not the rider's own notion of "moving".

**The battery multiplier lives inside `cadenceFor`.** A caller cannot ask for a profile and get the one belonging
to a phone plugged into a charger: `cadenceFor(phase, batteryPct)` is the only way to get a profile, and 15% and
8% widen every threshold by 1.5 and 2.5. A rider on break is `displacementM: null` rather than an enormous
number, because "never on movement" and "somewhere past a hundred kilometres" are different statements and only
one of them survives a multiplier.

**A turn counts at walking pace.** `07 §3.2` sends on a 45° bearing change once the rider has moved 30 m, which
is what stops a corner looking like a teleport at 1 Hz. Bearing deltas are the shortest way round the compass —
350° to 10° is 20°, not 340° — which is the kind of arithmetic that is invisible until a rider turns left at a
roundabout and the marker spins.

**The budget is now a test.** §8.1 claims 54 writes for a 3.8 km delivery; the suite drives a synthetic rider
along those legs at the documented speeds, offering a fix every second, and the gate allows **53** — one opening
fix, 40 by displacement, 12 by ceiling. A five-minute idle street draws **two** (the opening fix and one
heartbeat), and 6% battery draws fewer on the same leg than 80% does. The number in the document is now an
output of code that could contradict it.

*Open:* the profile is not yet pushed from the server — nothing builds `CadenceProfile` into the shift-start
response or the SSE state change, so `cadenceFor` is called with constants today. The Kotlin port does not exist
either; this module is the specification the port must match.

## D97 — The route where the two halves of the edge contract meet, and the four things it refuses

D95 judged batches that nothing sent; D96 chose fixes that nothing carried. `POST /rt/location/batch` is the
caller: `d1/batch.ts` decodes the delta-encoded flush (`07 §4.2`), `d1/ingest.ts` judges it, `d1/store.ts`
writes the survivors into the ring and the current row, and the response carries the next cadence — the push
`§3.3` describes, delivered in the round trip that already happened.

**The device owns `seq`, and the counter advances per position *offered*.** The ring is a modular counter
(`§5`), and only the phone knows how many fixes it produced across a dead network. A refused fix still consumed
a slot on the device, so the server advances the counter for every position in the batch and drops the ones it
cannot store. The alternative — advancing only for accepted fixes — drifts the two counters apart for the rest
of the shift, and a trail that reassembles by `recorded_at` hides the drift until the day it does not.

**Four refusals, each with a different sentence.** A batch past 2 048 bytes or twelve positions is refused
whole rather than truncated, because half a trail is a marker that jumps — worse than a client that learns its
upload failed and retries. A malformed delta names the rule it broke. A rider with no current row is
`SHIFT_NOT_OPEN`, not a 404: the phone has a shift, the server does not have it open. And a batch whose
`shiftId` disagrees with the shift on file is refused, because a queue flushing after an ended shift must not
write into the next one — the failure mode is one rider's breadcrumbs appearing under another rider's shift at
6 a.m.

**The response is where the cadence is pushed.** `phaseFor` + `cadenceFor` run against the rider's state after
the batch, so a rider who has just started carrying food gets `CARRYING_FAR` back immediately. `stale_after` in
`rider_current` is computed from the same profile (`receivedAt + 2 × ceiling`), which is what makes "the marker
goes grey" a property of the current row rather than of a constant somewhere in a dashboard.

**What this route does not do, stated because it matters.** It does not check the zone's bounding box: realtime
can read a rider's zone *id* from D1 but not the zone's shape, so `IngestContext.zone` is now nullable and the
route passes `null`. A position twenty kilometres outside the city is caught by nothing until `undal-core`
puts the box on the shift. It does not audit: a breadcrumb is precisely what `§6` promises not to keep, so a
suspension is answered to the device and recorded nowhere — the operator visibility that needs is a core
exception, and that is the next rung's problem.

*Open:* the zone box (above); the erasure path (`§6`: end shift, go offline, presence-declared offline) deletes
rows nothing writes yet, so it is still unbuilt; `/rt/shift/end` and `/rt/shift/start` do not exist, which is
why the route learns a rider's vehicle and zone from `rider_current` instead of from the shift request.

## D98 — Erasure got a caller, and the doors are different doors

`07 §6` promised immediate deletion and had two SQL statements with nothing to run them. D97 made a rider's
breadcrumbs exist; this makes them disappear.

**Two doors, because there are two kinds of caller.** `POST /rt/location/erase` is authenticated by the rider's
own token and erases that token's `sub` — there is no rider id in the body, so an app cannot erase a colleague
by guessing one. It is deliberately not named `/rt/shift/end`: ending a shift is core's business, and a route
here with that name would imply realtime owns the shift record. It says "my live location, now".
`POST /internal/erase` is core's, naming the rider, for an admin force-end or a sweep that noticed a device
stopped existing.

**Erasure is idempotent, and that is a privacy property rather than a convenience.** A shift end, a presence
timeout and an admin force-end can all fire within a second of each other. The second caller gets `200` with
zeros. A `404` would tell a caller the trail is still there when it is not — and a client that believes that is
a client that retries, or worse, a client that gives up.

**It answers with counts.** `{positions: 37, current: 1}` is a claim an operator can check against the ring's
bound of 120; `{ok: true}` is a claim that cannot be audited. The counts come from D1's own `meta.changes` per
statement, not from a preceding `SELECT`.

**The bug the tests found was mine, and it was the worst kind.** `checkInternalToken` is asynchronous and
answers a result object; I wrote `if (!authorised)` on the promise, which is a permanent `true` — an internal
erasure endpoint open to anybody who could reach it, with a test suite that would have passed had I not written
the "no internal token configured" case. It now awaits and checks `.ok`, and the route carries a comment saying
why the bare form must never come back.

**What it did not do yet** — the presence trigger, closed by D99 below.

*Open:* `/rt/location/batch` still learns a rider's zone and vehicle from `rider_current` because no shift-start
route exists to tell it.

## D99 — The trigger nobody presses, wired to the thing that must happen within five seconds

`§6.1` lists five erasure triggers. D98 built the doors for four of them — a rider pressing end shift or go
offline, an operator forcing one, and the sweep for a device that stopped existing. The fifth is the one the
promise is really about: *the presence engine declares the rider offline*, because a phone that died in a tunnel
cannot ask to be forgotten.

**The hook already existed and had no consequences.** `PresenceHub` publishes an absence at its alarm and calls
`onPublished`, which nothing supplied. It does now: `absenceEraser` (`d1/on-absence.ts`) is passed by
`ZoneHub`, over the room's own `RIDER_DB`. The hub's comment said "the hub reports; whoever owns those effects
decides" — this is the first effect the room owns outright, because the live channel is the room's territory
and reassignment is not.

**Erasure happens at publication, not on a later sweep.** D91 already spends up to two seconds proving the
device is silent; a second scheduled job that erased "shortly after" would add a window with no owner. Deleting
in the same breath makes the five-second promise a property of the alarm's latency, which is the only part of
the path that is measurable.

**A failed erasure does not fail the absence.** The ledger has already been swept and the coordinator told;
throwing would abort the alarm and delay every other absence in the zone. The failure is reported to a callback
that logs it, and the ring is overwritten by the next shift's first flush anyway — a stale trail is a wrong
answer to "where is my rider", not a permanent one. The asymmetry is deliberate: refusing to publish would leave
a rider marked present forever, which is worse than a trail that outlives them by one shift.

**It does not ask what kind of actor was absent.** The id is the key and a customer's id has no rows in D1, so
the deletion is a no-op that costs one batched statement. Branching on the role would make erasure depend on a
field that a future vendor live-tracking feature would have to remember to add to — and the failure mode of
forgetting is a trail that never gets erased.

Tests: the module's six cases (each reason, idempotence, no binding, a failure with and without a reporter) and
four at the room: a silent socket erases at the alarm that publishes it, a deliberate goodbye erases too, a room
that never connected erases nothing, and a deployment without a binding still publishes.

*Open:* `/rt/location/batch` still learns a rider's zone and vehicle from `rider_current` because no
shift-start route exists to tell it; and the 60-second housekeeping sweep (`§6.1`'s last row) still needs a
listener that notices a token is invalid.

## D100 — The replay window cannot say "you missed nothing" about history it does not have

`EventRing` had two holes, both in the one part of the SSE surface a customer can feel: the resumption after a
dropped connection.

**A cursor the ring has never reached was answered `complete: true`.** `since(150)` on a fresh ring returned no
events and "nothing was missed". That happens for three ordinary reasons — a new isolate, an evicted room, a
missing snapshot — and all three mean the frames the client is quoting went somewhere this channel cannot see.
The client then showed a stale order as if it were live, which is exactly the failure the ring's own doc comment
says must never happen. A fresh ring now answers `complete: false` for any cursor above its `highestId`; a
cursor at zero is still complete, because nothing was promised. `EventRing.restore(undefined)` inherits the
same rule, which is the case the `restore` doc comment was already worried about.

**A frame could arrive after a higher-numbered one.** Two requests for the same order can be in flight at once,
and the one carrying the later sequence can reach the room first. `push` appended it, which broke the two
invariants every reader relies on: `since` returns events in id order, and `trim` evicts oldest-id first. A late
frame is now inserted where its id belongs, and `trim` filters by age rather than shifting the front, so a late
event carrying an old timestamp does not linger until the front overtakes it on a quiet channel. The live socket
that already received the higher id cannot be repaired after the fact — that is the broadcaster's ordering
problem, not the ring's — but the replay window can, and the replay window is what a reconnecting client
depends on.

**One existing expectation changed and it was wrong.** `store.test.ts` asserted that a resume at cursor 5 of a
channel that never spoke is `complete: true`. That test encoded the bug. It now asserts `false` for cursor 5 and
`true` for cursor 0, with the reason written beside it.

Tests: `sse-ring-order.test.ts` (11 cases: unseen cursors, restore with and without a snapshot, late ids,
duplicate ids, oldest-id eviction, age trimming of a late event, evicted cursors) plus the amended store cases.

*Open:* the live broadcast path still has no ordering guarantee across isolates — a socket can receive frames
out of sequence even though its reconnect will be exact. Fixing that needs the broadcaster to sequence per
order, which is core's `announce()` and a separate decision.

## D101 — A sequence belongs to the channel that owns it

D100 made the ring robust against ids that arrive out of order. It did not ask where those ids come from, and
the answer was wrong in one place: `broadcast` copied core's per-order `seq` onto **every** channel it fanned
out to, including the zone.

**The bug that produces.** `order_state_events.seq` is per order and starts at 1. A zone channel carries every
order in the zone, so order A's first event and order B's first event both arrive as id 1 — and `EventRing.push`
treats a repeated id as *the same event, revised*, so B's frame silently replaced A's. The admin map lost A's
event with no error anywhere: the ring did what it was told, and the fan-out told it two different events were
one.

**The fix is scoping, not more machinery.** The order channel keeps the order's log sequence, which is exactly
what a resuming client should quote: `Last-Event-ID: 4` is also a row in `order_state_events` for that order.
The zone channel is numbered by its own ring, because a zone's frames have no per-order sequence to inherit and
pretending they do makes the shared id space a collision domain. `channelsFor` still returns both channels;
`broadcast` decides the sequence per channel rather than per broadcast.

**Verified the way a claim has to be.** Reverting the one-line scoping decision fails three of the four new
tests — including the two-order case, which is the bug itself — and restoring it passes all four.

Tests: `fanout-seq.test.ts` (the order channel keeps its sequence; an unnumbered broadcast is ring-assigned; two
orders with seq 1 both survive on the zone; five orders numbering their own frames 1–5).

*Open:* closed by D102 — the append now retries on `DUPLICATE`.

## D102 — A duplicate key is the index telling us to take the next number

The sequence D101 handed to the order channel is allocated with `MAX(seq) + 1` and written by a second statement.
Two transitions on one order can read the same maximum; the `UPDATE … WHERE state = ?` has already won and moved
the order by then; and `uq_order_events_seq (order_id, seq)` then refuses the event row. The failure is the worst
shape a failure can take here: the order changed, the log does not say why, and the caller is told their request
errored.

**`DUPLICATE` is a retry, everything else is not.** `appendEvent` re-reads the maximum and tries again, up to five
times. The classification is the platform's existing one (`classifyError`), so a lock timeout or a dead connection
is rethrown on its first attempt rather than being retried into an event row that never appears. Five is not a
guess at a contention level: losing twice means two other transitions allocated the same number twice in the
microseconds between a `MAX` and an `INSERT`, and by the third attempt the alternative explanation — a genuinely
reused event id — has to be the answer, which deserves an error rather than a sixth silent try.

**The append is now a named function, not four lines inside `moveState`.** That is what makes it testable without a
transition, and it is what let the retry be verified rather than assumed: with the attempt count forced to one, two
of the eight new tests fail; restored, all eight pass.

**What a retry cannot fix.** The `UPDATE` and the `INSERT` are still two statements in autocommit, so an order can
move and its event row can be lost to a crash between them. Closing that needs a transaction the `Db` port does not
expose — the port deliberately prefers single-statement atomicity (`db/client.ts`), and a transition is inherently
two statements. Retrying the duplicate takes the common race off the table; the crash window is recorded here as
the honest remainder rather than quietly claimed.

*Open:* the crash window above; and `nextEventSeq` remains the allocation strategy, which means the retry is what
makes it correct rather than the allocation itself. A `SELECT … FOR UPDATE` on the order row, or a sequence column
on `orders` incremented in the same `UPDATE`, would remove the retry — both change the schema or the lock profile
of every transition, and neither is worth doing without the load numbers to justify it.

## D103 — The stream tails its channels, because a replay and a keepalive are not a live feed

D100–D102 made the ring's ids ordered, scoped and unique. All three only paid off at reconnect, because the
stream had no live half: `streamResponse` wrote the opening replay, then one keepalive every twenty seconds,
forever. A customer who opened the order page during a quiet minute and waited for the vendor to accept learned
nothing until the page was reloaded — the frames were recorded, the ring held them, and nothing asked.

**The fix is a tick, not a push.** Once a second (the keepalive interval is derived from it, so there is still
one timer per connection) the stream asks the same source a resume would: frames after this channel's cursor.
That is why the earlier rungs were the prerequisite — the tail is a resume that happens while connected, and it
is only correct because the ring returns id order (D100) and each channel numbers its own frames (D101).

**One cursor per channel.** A stream can watch an order and its zone at once, and the two number their frames
independently: after D101 the order channel's ids are the order's log sequence while the zone's are ring-assigned.
A single cursor for the connection would skip or repeat a frame on whichever channel moved second.

**A gap is admitted once per episode.** `complete: false` means the client must reconcile; writing that comment
on every tick would be a stream that shouts "reconcile" once a second until the client does what it was already
told. The flag clears the next time the channel answers completely, so a second gap later is admitted again.

**A failed pull is a missed tick, not a dead stream.** The cursor is not advanced, so the next tick asks for the
same range; the alternative — closing the connection because the coordinator hiccuped — is worse than a second of
silence. Overlapping ticks are prevented by a flag rather than by the timer, so a slow source delays the next pull
instead of racing it.

**Verification.** With the once-per-episode guard removed, the gap test fails (three comments in three ticks);
restored, all eight pass. The other seven cover what the tail must not break: cursor advancement, per-channel
cursors, keepalives when nothing is written, the no-tail path, and cancellation releasing the interval.

*Open:* the tail polls, so a frame waits up to a second. A push path — the room waking its own sockets — is the
alternative, and it needs the sockets to live in the room rather than in a request's stream; that is a different
architecture, not a smaller interval. The load this adds is one ring read per channel per second per open stream,
which is why the ring is preferred over the order log where a room is bound.
